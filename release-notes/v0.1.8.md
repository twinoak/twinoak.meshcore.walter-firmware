## What is new

- A unit that has taken a radio update goes back to sleeping for the interval it was set to: since its first update it had been waking about every five and a half minutes instead, because the slot the update emptied still read as a download half finished. The console's image list says that slot is empty too. Seen on the simulated bench, not yet on a board.
- When a call to the server fails, the unit now writes down what its modem did while it waited — how long each answer took, what it announced, when the other end closed — and keeps it over a sleep and a power cut. `agent calls` and the unit's report say it. It cures nothing; it is how the failures costing most wakes half a minute can be read. Seen in the host tests, not yet on a board.
- When a call's answer fails to come back, the unit now asks its modem once more before giving the call up — if the answer is still in there, the call succeeds and nothing is sent twice. It is still half a minute late, and how often the second ask has helped is on `agent calls` and in the unit's report. Seen in the host tests, not yet on a board.

**Which repeater firmware this goes with.** A unit is two boxes and one key signs both: this
release runs beside
[`twinoak.meshcore.repeater-firmware` v0.1.2](https://github.com/twinoak/twinoak.meshcore.repeater-firmware/releases/tag/v0.1.2),
key `73efdd383a957596`. Nothing in the box link changed with this release, so a radio at that
release needs nothing done to it.

**Taking it from the release before, over LTE.** *Offer a release* on the unit's page on
meshmaster.dk with the Walter's product, then *Apply the candidate*; the unit fetches it on its
next check-in, writes it into its other slot, switches, and is brought back by the bootloader if
the trial fails. A unit that will not come up at all goes by cable, with the factory image and the
`esptool` line below.
