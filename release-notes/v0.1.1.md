**What the first unit showed, fixed.** On 6 November 2026 `v0.1.0` went onto the first unit's
Walter and could not do the thing an LTE box is for: put an image on its radio. Five faults came
out of that evening, every one of them invisible to the host tests because every fake did what the
code expected. Each is fixed here, and each fake was taught the board's behaviour so that the test
fails before the fix:

| What the board did | Fixed by |
|---|---|
| `rak update --first-install`: `watchdog reset` at every boot, twelve in a row, then `STUCK: no image to return to`. Nothing on the debug-port path blocked, so the idle task never ran and the task watchdog ended every attempt — 6 minutes 48 seconds of flashing with no yield, measured | [p8-01](https://github.com/twinoak/twinoak.meshcore.walter-firmware/blob/main/tasks/phase-8/reports/01.md) |
| `walterctl.py push`: `no answer to type 0x03 seq 9`, for ever. The transfer's answers are frames and went out through the console's LF → CR LF conversion for a terminal, so every answer that carried a `0x0A` was corrupted. **The same conversion also made a push take two and a half hours**; it is seconds now | [p8-02](https://github.com/twinoak/twinoak.meshcore.walter-firmware/blob/main/tasks/phase-8/reports/02.md) |
| the second HTTPS request of a wake: `the request did not go out`, or `the connection closed before the body was complete`. Every connection was socket 1, so the *previous* connection's close landed on the next one. Consecutive connections now alternate between two socket ids, and an event for the id not in use changes nothing | [p8-03](https://github.com/twinoak/twinoak.meshcore.walter-firmware/blob/main/tasks/phase-8/reports/03.md) |
| a job for the unit's **own** repeater went out on the air, because `agent wake` had asked no `HELLO` and the unit could not yet tell its own radio from a stranger's. Every wake now reads the radio before it claims; a wake that cannot offers only the unit's own job types, so such a job is never claimed | [p8-04](https://github.com/twinoak/twinoak.meshcore.walter-firmware/blob/main/tasks/phase-8/reports/04.md) |
| meshmaster.dk could not pick an image for a radio with no golden image: it needs role, board **and** band, and `HELLO` said no band | [p8-05](https://github.com/twinoak/twinoak.meshcore.walter-firmware/blob/main/tasks/phase-8/reports/05.md) |

**Link 1.1, and a 1.0 radio still works.** `HELLO`'s answer and `EV_BOOT` now end with the radio's
`band`, which is the last of the three words the server picks an image by. This Walter asks in 1.1;
a radio that knows only 1.0 answers in 1.0 with no band, and the session then says *not said (a 1.0
radio)* rather than guessing. Nothing else compares the link's **minor** anywhere: a 1.1 Walter
accepts, flashes, proves and talks to a 1.0 repeater image exactly as before, which is the pairing
the unit on the bench is running today.

**What has been on a board, and what has not.** One Walter has run a *development* build of this
firmware and checked in with the real meshmaster.dk (23 October 2026, `0.0.0-dev`), and the first
unit ran `v0.1.0` on 6 November — which is where the five faults above come from. **No released
image has yet done a whole radio install, a whole wake or a whole day**: the fixes here are held by
the host tests against simulators and by the measurements in the reports, not by silicon. The walk
that turns that sentence over is
[`docs/bench.md`](https://github.com/twinoak/twinoak.meshcore.walter-firmware/blob/main/docs/bench.md),
and this is the release it is walked with.

**Putting it on a Walter:**
[`docs/flashing.md`](https://github.com/twinoak/twinoak.meshcore.walter-firmware/blob/main/docs/flashing.md).
A unit already running `v0.1.0` has its own section there — *A unit at 0.1.0* — because **its own
update goes by cable**: the one `esptool` line below, which keeps the unit's settings, its journal
and the radio images it has stored, so a stored candidate and a radio slot marked *stuck* both
survive. Then `rak hello`, `rak update --first-install`, and the radio's first install finishes.

**The LoRa box.** This release goes with
[**`twinoak.meshcore.repeater-firmware` v0.1.1**](https://github.com/twinoak/twinoak.meshcore.repeater-firmware/releases/tag/v0.1.1),
which is the radio half of link 1.1 — it says `band 868` in its `HELLO` and nothing else of the
link changed. Its `v0.1.0` is still a radio this Walter talks to, flashes, proves and rolls back;
the band is the one thing such a radio does not say, and the only thing that costs is the server
picking an image for a slot that has never had a golden one.
