**0.1.3 could not start, and this is 0.1.3 that can.** On 9 November a Walter at `v0.1.2` fetched
`v0.1.3` over LTE for the first time ever, switched to it, and was back on `v0.1.2` a moment later
by itself: *the image never reached its main loop*. The core dump it left says why:
`assert failed: esp_startup_start_app app_startup.c:86` — ESP-IDF could not create the main task,
because its 16 kB stack no longer fitted in the heap that the static initialisers leave behind. This
board has no PSRAM, and 1 728 bytes more static data had moved a 20 kB block into the heap the stack
needed. **The same is true by cable**: a Walter flashed with `v0.1.3` restarts in a loop until
another image is flashed. Do not install `v0.1.3`; this release replaces it.

| What was wrong, and what this release does | Task |
|---|---|
| **No room for the main task.** Both releases measured from their builds, with a model of the heap at start that explains both: `v0.1.2` started with 12 796 bytes to spare, `v0.1.3` was short. The release build no longer compiles the modem library's debug lines in, which puts the room back: **11 720 bytes to spare**. The modem trace is a build of its own again (`docs/bench.md` §13), and `trace modem on` in this build says so | [p11-01](https://github.com/twinoak/twinoak.meshcore.walter-firmware/blob/main/tasks/phase-11/reports/01.md) |
| **Nothing checked it.** Every build now runs the model and **fails when the main task would not fit with 8 kB to spare**, before anything is copied or released. The second line of every boot is `heap:` — what the board really got — and `heap` on the console adds the least free since boot and the main task's stack high-water mark | [p11-02](https://github.com/twinoak/twinoak.meshcore.walter-firmware/blob/main/tasks/phase-11/reports/02.md) |
| **A rollback said too little.** A trial that ends in the bootloader's hands is now reported with the reset that ended it and, when the core dump is the trial image's own, its panic line and task — in `self status`, the apply's result on meshmaster.dk and `twinoak.fw.state`. `coredump` on the console reads it; nothing erases it but `coredump erase confirm` | [p11-03](https://github.com/twinoak/twinoak.meshcore.walter-firmware/blob/main/tasks/phase-11/reports/03.md) |

Everything else is `v0.1.3`'s: its notes list the six fixes, and they are all here.

**What has been on a board, and what has not.** This build has started in the QEMU the pinned
ESP-IDF image ships, with its main task where the model put it. It has **not** started on a Walter
yet. The first one is the author's, over LTE from `v0.1.2`; if it fails its trial, the Walter goes
back to `v0.1.2` by itself, as it did on 9 November. (A failed trial *from* `v0.1.2` is reported in
`v0.1.2`'s words; the fuller report above starts with the release after this one.)

**From `v0.1.2`, over LTE:** *Offer a release* on the unit's page with the Walter's product, then
*Apply the candidate* — the walk in
[`docs/flashing.md`](https://github.com/twinoak/twinoak.meshcore.walter-firmware/blob/main/docs/flashing.md),
which still names `0.1.3` and is otherwise the same. **A Walter stuck on `v0.1.3`** goes by cable:
this release's factory image, with the `esptool` line below. Goes with
[`twinoak.meshcore.repeater-firmware` v0.1.2](https://github.com/twinoak/twinoak.meshcore.repeater-firmware/releases/tag/v0.1.2);
the key is unchanged, `73efdd383a957596`.

**Once, on the first boot from `v0.1.2`:** the record kept in RTC memory across a sleep is four
bytes longer than `v0.1.2`'s, so that first wake says *the record did not survive*, its battery band
is `unknown` and the next interval is 60 minutes. The wake after it is normal.
