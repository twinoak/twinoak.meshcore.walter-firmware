# p15-05 — the second ask goes

Task p15-03 gave a receive that failed with the connection's close already handed over one more
ask, on the chance that the modem still held the answer the failed command never brought back.
The unit has had it since the evening of 16 November. On the morning of the 17th its report said

```
  asked again after a failed receive: 35 since this unit was made, 0 of them answered
```

and in both records read so far the second ask came back at once with `+CME ERROR: 4`. The bytes
are gone when the first command gives up. It is gone, and a failing call costs one command
timeout again:

```
  what the modem said in it (observations), on socket 1: 308 bytes sent, 3 receives answered "nothing buffered yet"
    it ended as: the connection closed before the body was complete
    +320 ms: a ring: the modem announced 815 bytes
    +359 ms: the other end closed
    +30310 ms: a receive failed after 30000 ms: nothing answered, the library gave up on the command
```

**That block is a host test's, printed by the firmware's own console code, and no byte of it was
read off a unit** — the review of 01 to 03 asked for that to be said where a block is printed.
The three figures in the sentence above it are the unit's own, from its report of 17 November
(`tasks/phase-15/FOLLOWUPS.md`, *From the first night of 0.1.8*).

## What it is made of

**One `if`, where a rule was.** `components/modem/walter_tls.cpp`'s `receive()` is what it was
before task p15-03: the close seen is `kClosed`, no close and a failed command is `kError`
(`kSocketFailed`), and nothing is sent to the modem that was not going to be sent.
`core/net/read_again.h`, `core/net/read_again.cpp`, `WalterTlsSocket::askOnceMore()`,
`CallRecord::again()`, `CallRecord::readAgain()`, `CallLog::readAgain()` and the hooks in
`CallLog::begin()`, `save()` and `forget()` are gone with it — 329 lines of the rule's own source
and 503 of its tests, and 1 115 lines removed against 475 added over the whole change.

**The record of task p15-02 is untouched, and still prints the ask.** `CallMoment::kReadAgain`
keeps its number, `ReadAgainFound` moved from the deleted header into `core/net/call_record.h`
where the stored nibble is documented, and `describe()`'s four lines for that moment are
character for character what they were. Nothing writes the moment any more; every unit that ran
v0.1.8 has a record in its store that holds one, and that is the only reading anybody has of what
the modem answered the ask. A test reads two such records **out of the stored hex** and checks
the lines.

**The key is erased once.** `CallLog::begin()` erases `agent_reread` (named
`agent::kRetiredReadAgainKey`, where the other keys of the list are) before it reads the list. On
a unit that never ran v0.1.8 there is no such key and the store says so without spending a byte of
flash — `NvsKeyValue::erase` treats `ESP_ERR_NVS_NOT_FOUND` as *already forgotten*. `agent calls`
and the report's `calls` section print no *asked again after a failed receive* line at all.

**The bench's socket keeps what it learned.** `host_test/sim/fake_tls_socket.h`'s hang path still
answers *closed* when the close has been delivered and `kError` when it has not — the decision
task p15-03 found it was getting wrong — but it makes no second ask and has no knob for one. The
`second_ask` and `hang_after_bytes` knobs went with the rule they scripted.

## Deviations from the spec or the task

**`spec/` is untouched** (`specsync.py verify spec`: ok) and says nothing about this: how this
firmware reads bytes off its own modem is this repository's business.

**The `hang_after_bytes` knob of the bench's socket went too, and the task did not ask for that.**
Deliverable 4 asks that the bench socket keep what it learned, which is the *closed*-against-
*failed* decision, and it does. `hang_after_bytes` was added by task p15-03 to script a response
half read when the command fails, so that the second ask had something to complete; with no second
ask nothing in the suite used it, and an unused knob in a simulator is a thing that rots. It is
two lines to put back if task p15-07 wants that shape.

**`ReadAgainFound` kept its name.** It is the vocabulary of a stored nibble now and nothing else,
and a record written by v0.1.8 is read with it; renaming it would have made the one place that
decodes those records harder to find from the firmware that wrote them.

**The erase is at every boot, not once in the unit's life.** There is no flag saying *this unit
has already been cleaned*, because a flag would be another value of the store to keep. `begin()`
asks the store to erase a key that is not there, which on NVS is `nvs_erase_key` answering
`ESP_ERR_NVS_NOT_FOUND` and a commit with nothing dirty: no write, no wear. *Once* in the task's
words is *once there is anything to erase*, and after that boot there never is again.

## Decisions taken without asking

**Where the retired key is named.** `walter_agent/call_log.h`, beside `kCallsKey` — the object
that erases it, and the one that already owns the keys of this feature. It is not in
`core/net/`, which is where it was: nothing of `core/` has a use for it any more, and a constant
in a component that no longer reads it would be the first thing a later task deletes without
noticing what it is for. Its comment says it exists to be erased.

**The two tests are two files and not one.** The socket's half
(`host_test/core/net/test_no_second_ask.cpp`) must run in the build **without** the agent, which
is `tools/verify.sh`'s second host configuration — `host_test/agent/` is excluded there. The
unit's half needs a whole Walter and lives in `host_test/agent/`.

**"No second command" is proved by the answer not arriving, not by a counter.** The scripted
server holds the whole 878-byte response for the length of the stall, so a second ask would be
answered with it and the call would come back `200`. The call comes back *closed* with
`bytes_out == 0`. That is the same proof the task's own acceptance criterion asks for — *whose
next receive would return a whole response* — and it needed no new field in the fake.

**The fixtures are built to the format, and say so.** The two stored records in
`host_test/agent/test_the_second_ask_goes.cpp` are written by hand from the packed layout of
`core/net/call_record.h`. Their *shape* is the unit's — the two rings and the close of wake 254,
which `FOLLOWUPS.md` records, and an ask answered `+CME ERROR: 4` — but the times of the failed
receive and the ask are made up, and the file says in its header that no byte of either was read
off a unit. That is the review's finding about report 02, applied where the next person will read
it.

**`CallLog::save()` went back to returning `true`.** Task p15-03 made it answer for two writes;
with one value again there is one answer, and `counters_.writes` counts the list and the record
as it did before that task.

   - **`agent calls` has no *asked again after a failed receive* line** above its list at all, and
     the key it was kept under is gone from the store;
   - **the record below the list still prints the ask of the firmware before it** while the kept
     record is one v0.1.8 wrote — *asked again after that: it failed too, +CME ERROR: 4*. A record
     written by this firmware has none, so that line disappearing is itself the sign that a call

     which is what the first timer wake of v0.1.8 was. A wake ended by the five-minute bound is
     task p15-06's line, not this one.

What the thirty seconds **are** — which AT command goes unanswered and why — is unchanged by this
task, is `tasks/phase-15/FOLLOWUPS.md`'s first item, and is still not known. This task only stops
the firmware paying twice for it.
