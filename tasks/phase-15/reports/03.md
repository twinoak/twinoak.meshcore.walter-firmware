# p15-03 — read again before giving up

A receive command that fails when the connection's close has already been handed over used to end
the call. The pair read as *the other end hung up*, `receive` answered `TlsRecv::kClosed`, and the
modem — which may still have been holding the answer the failed command never brought back — was
never asked a second time. It is now asked once:

```
  what the modem said in it (observations), on socket 1: 308 bytes sent, 3 receives answered "nothing buffered yet"
    it ended as: ok
    +150 ms: a ring: the modem announced 878 bytes
    +900 ms: the other end closed
    +30150 ms: a receive failed after 30000 ms: nothing answered, the library gave up on the command
    +30150 ms: asked again after that: the modem still held 1019 bytes
```

and `agent calls` carries, above its list, the only figure that says whether that ever does
anything on a unit nobody has a cable to:

```
  asked again after a failed receive: 3 since this unit was made, 3 of them answered
```

Both blocks above are this task's own host tests, printed by the firmware's own console code; no
board has run a line of this. **Whether the modem really does hold those bytes is still not
known** — nobody has looked, which is the task's own second paragraph. This makes the board look,
once per failing call, and write down what it found.

## What it is made of

**One rule, in one expression, with no modem in it.** `core/net/read_again.h` is written the way
`core/net/socket_rotation.h` is and for the same reason — a host test has to be able to drive it:

```c++
constexpr AfterFailure after(bool closed_seen, bool asked_already) {
  if (!closed_seen) return AfterFailure::kFailed;
  return asked_already ? AfterFailure::kClosed : AfterFailure::kAskAgain;
}
```

`kFailed` is `TlsRecv::kError` and `kSocketFailed`, exactly as before; `kClosed` is what the socket
answered before this task; `kAskAgain` is the one new thing. `components/modem/walter_tls.cpp`'s
`receive()` branches on those three and has nothing of its own: `kAskAgain` calls `askOnceMore()`,
which is one `WalterModem::socketReceive` and no loop. `ReadAgain::onFailedReceive()` spends the
call's one ask *before* the ask is made, so a second failure of the same call is `kClosed` whatever
comes of the first, and `CallRecord::begin()` — the one place a call begins — gives the next call
its own.

**The bench's socket now obeys the same object.** `host_test/sim/fake_tls_socket.h` is the board's
peer and not its caller, so this is where the host tests reach the rule: its hang path asks
`record_->again().onFailedReceive(closedNow())` and does what it is told, and one knob —
`second_ask`: `kNothing`, `kHeld`, `kFailed` — is what the modem is scripted to answer. One more
knob, `hang_after_bytes`, makes the command fail after part of the response has been handed over,
which is the *half read* case.

**The record says it.** `CallMoment::kReadAgain` is a sixth kind in the 79-byte record of task
p15-02, in the six bytes every moment already has: the state nibble holds which of the three the
ask found and `value` the bytes when it found some, and a failed ask keeps its `+CME ERROR` number
in the same biased byte a failed receive uses. The record is the same 79 bytes and the same key.

**Two totals, in a value of their own**, `agent_reread`: how often the ask was made and how often
it answered, a version byte and two 32-bit figures, the shape and the reasons of
`core/cycle/wake_counters.h` and `walter_agent/flood_counters.h`. **They need a key of their own
and not a corner of `agent_calls`**, because an ask that recovers an answer makes its call come
back `2xx` — so that wake has no failed call to hang the figure beside, and it would be written
nowhere. `walter_agent/call_log.h` reads them back at its `begin()` and writes them at its
`save()` **on a flag of their own**, so a wake in which the list did not move can still write
these, and the other way about; a unit whose modem behaves never writes this key in its life.

**No byte of `.bss` was added**, which deliverable 5 asks for: the rule is a member of
`core::net::CallRecord`, and that record is taken from the heap in `app_main` (task p15-02). It is
reached by exactly the two objects the record is — the socket layer that makes the ask and the call
log that keeps and prints what came of it — and both already hold a pointer to it, so a pointer of
its own in either would have been four bytes of `.bss` apiece out of a margin counted in tens of
bytes. The class, its file and its tests are its own; *Deviations* says this out loud because it is
a decision about bytes and not about concerns.

## Deviations from the spec or the task

**`spec/` is untouched** (`specsync.py verify spec`: ok) and says nothing about this: how this
firmware reads bytes off its own modem is this repository's business. S-12 is the one line that
bears on it, and the record and the two totals are numbers only — a host test reads the printed
lines and the stored hex for a byte of the body and of the token and finds neither.

**The deadline does not refuse the extra ask, and the task says it should.** Deliverable 1 ends
*"Once, not a loop, and inside the call's deadline"*. The ask is inside the **call** — it is made
before `receive()` returns and before the call ends, not as a retry of anything — but it is not
gated on a deadline, and it cannot be: *the command that failed is the command that overran the
deadline*. `receive()` is given the sooner of the call's total deadline and `now + piece_ms`
(`core/net/http_over_tls.h`: `kDefaultPieceMs` is 15 000 ms), and the failing command takes 30 000
of the library's own; task p15-02's record from the unit has the failed receive returning at
**+30 150 ms**. So the wall is always past the deadline by the time this rule is asked, and an ask
gated on it would never be made at all — the rule would be dead code on the one unit it exists for.
What bounds it instead is that there is exactly one of it: **one AT command, and no third**, so a
failing call can cost at most one command timeout more than it did (60 s instead of 30 s in the
worst case, where the second ask hangs as well), and the wake's own uplink deadline still bounds
the wake — `walter_agent/modem_uplink.h` begins no call with less than `kLeastCallMs` left of it.
That worst case is named in the bench line, which asks for the length of a wake that recovered an
answer. A shorter command timeout for a receive is the library's to offer and is already
`tasks/phase-15/FOLLOWUPS.md`'s third item.

**The bench's socket answered a failed receive without looking at the close, and the board does
look — so two of p15-02's assertions moved.** Before this task
`host_test/sim/fake_tls_socket.h`'s hang path returned `kError` whether the close had been
delivered or not; the board's `receive()` has always answered `kClosed` when `closedSeen()`.
Deliverable 3 puts that decision in the rule, which the fake now asks, so the 30-second stall those
tests script — whose close arrives at +500/+900 ms, inside the hang — ends as **the connection
closed before the body was complete** instead of *the modem stopped answering for this socket*.
That is the sentence `tasks/phase-10/FOLLOWUPS.md`'s first item quotes from 8 November, so the
tests are nearer the board than they were; four assertions in
`host_test/core/net/test_call_record.cpp` and one in `host_test/agent/test_what_the_modem_said.cpp`
say the new sentence, each with a comment saying why it changed. Nothing else of those tests moved
and no figure of the record changed.

**The one shape of the fault this rule leaves alone, said out loud.** The record quoted in
`tasks/phase-15/reports/02.md` — wake 1214, 16 November — ends as *the modem stopped answering for
this socket*, which is a failed receive with **no close seen**, although that same record shows the
close handed over at +514 ms. A close the rotation discounts as an older connection's debt looks
exactly like that from `receive()` (`core/net/socket_rotation.h`, and `lte` prints the discount
count). Deliverable 2 says that shape does not move, and it does not; whether a discounted close
should count as *the close was seen* for this one decision is a change to the rotation's accounting
and is a new item in `tasks/phase-15/FOLLOWUPS.md`, to be read against the `asked again` line from
a unit rather than guessed at. It is also why the bench line's first reading is *N is 0 after wakes
whose calls failed*.

**A build with no record makes no second ask.** The rule is reached through
`CallRecord::again()` and through nothing else, so a socket with no record wired (`recordInto`
unset — `core/update/tls_check.h`'s bare handshake, a test that wants none) gets `after(closed, true)`,
which is this firmware's behaviour before this task. `main/main.cpp` always has a record. That is
the honest fallback for a build that writes nothing down either, and it is said in both headers.

## Decisions taken without asking

**Why the rule is a member of the record.** It is reached by the socket layer below the transport
and by `walter_agent/call_log.h`, and both already hold a pointer to the record, which is on the
heap. A standalone object would have needed a pointer in `modem::WalterTlsSocket` and one in
`agent::CallLog`, both of which are `main/`'s namespace-scope objects: eight bytes of `.bss`, and
on this heap eight bytes move `_heap_start` by eight and the tightest big allocation from main's
996 to 988 — below main's, which the task's own deliverable 5 forbids. p15-02 had to find twelve
bytes in `SocketRotation` to pay for its record; there was no second twelve to find without
shrinking counters `lte` and seven tests read. So the rule lives inside the record, with the
reason beside it, and is otherwise wholly its own: its own header, its own file, its own key, its
own tests, and nothing of the record in it.

**Two totals and not four.** Asks and answers; *found nothing* and *failed too* are the difference
between them and are named moment by moment in the record, which is where a person reading one
failure wants them. A total apiece would have been eight more bytes in the value and two more
figures in a console line that has to stay under 200 bytes.

**Only bytes count as an answer.** `found(kBytes)` moves `answers()`; `kNothing` and `kFailed` move
nothing but the record. The question the pair answers is *did this ever recover an answer*, and a
figure that counted asks which found nothing as answers would answer it wrongly.

**The ask is spent before it is made.** `onFailedReceive()` sets the flag and counts the ask, then
the caller makes it. A second failure of the same call is therefore `kClosed` even if the ask
itself threw the modem into another 30 seconds, which is the one thing that must not happen twice
in a call.

**A failure with no close seen spends nothing.** `after(false, …)` is `kFailed` and leaves the ask
unspent, so a call whose first failure was the socket's own still has its one ask for a later
failure that does have a close behind it. A test holds it.

**One counter for all three values of the store.** `CallLogCounters::writes` counts the list, the
record and now these two totals, because a counter of its own would be two more bytes of static
storage and what a person asks is how much flash this whole thing has spent. Its comment says so
and `agent calls`'s line already read *N written to the store*.

**`forget()` clears the totals whether there is a store to erase or not**, so that a unit after
`agent forget` says what a new unit says — *never yet* — rather than printing figures whose record
and list are gone.

**The fake's `second_ask` defaults to `kNothing`.** It is 8 November's shape from the outside — the
answer was lost — and it is what every test written before this task was written against, so no
test that scripts a stall silently becomes a test about a recovered call. The cases that want the
other two say so in one line.

**`hang_after_bytes` instead of a second hang knob.** The *half read* case needs the command to
fail at a chosen point in the response, and one figure — how many bytes have been handed over —
says it without a second script. 0 is the first receive, which is every test written before this
task.

## Not verified here (and why)

No session opens a port. The line below is `docs/bench.md` §13's, in the order the rig is brought
up, and it is **new in this task**. It needs no cable: the figures reach a person through the
report.

1. **Did the one more ask ever find anything** (§13, the item under *The record on a unit with no
   cable*). On a **release** build after half an hour of the unit's own wakes, read `agent calls`'s
   own line — *asked again after a failed receive: N since this unit was made, M of them answered*
   — from the console or from the report's `calls` section after *Fetch now*. Write N and M down.
   Three readings, three findings: **N is 0 after wakes whose calls failed** means the unit's
   failures are the no-close-seen shape this rule leaves alone, and the follow-up above is next;
   **N > 0 and M is 0** means the modem does not hold the answer when the failed command gives up,
   and the record's own line says which of *the modem held nothing* and *it failed too* it was;
   **N > 0 and M > 0** means the answers are being recovered — then the list of failed calls should
   thin out and meshmaster.dk should stop storing the same batch twice. Also worth one line:
   whether a wake that recovered an answer is about 30 s and not 60 s, which is the one cost this
   rule can add.

Everything else of this task is host tests and a build. What the thirty seconds **are** — which AT
command goes unanswered and why — is `tasks/phase-15/FOLLOWUPS.md`'s first item, is out of this
task's scope by its own last paragraph, and is still not known.
