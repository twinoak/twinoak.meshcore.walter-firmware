# p15-01 — a voided slot is no download

The reading in the task file was right, in every step. A radio update that commits promotes the
candidate; the area that held the old golden image becomes the candidate area and `invalidate`
writes zeros over its record's magic without erasing the sector; the progress markers that
image's **own** download left in that header sector are still there; `read` finds no record,
falls back to `readProgress`, and the newest marker stands below the image's size. So the
candidate slot read as *a transfer interrupted at X of Y* for as long as nothing new was
downloaded into it, and `WakeCycle::stepSleep` shortened every sleep in `plenty`.

The fix is one rule in one function, and the whole of it is which fact in flash the rule stands on.

## The fact in flash

**The record's own magic word**, the first four bytes of the header sector:

| the word | what the header sector is | the markers above it |
|---|---|---|
| all ones (`0xFFFFFFFF`) | erased, and a write may be under way | a transfer, as far as it got |
| anything else | a record has stood here | an old download's; not read |

Nothing else in the sector can tell the two apart, and this can, because of the shape of NOR
flash the store is already built on: **a write only clears bits**, so no sequence of writes can
put the all-ones back. Only an erase can, and the erase that puts it back is the one at the head
of the next write into that area — which takes the old markers with it in the same operation.
The three ways a record stops being a record all leave something that is not all ones: the magic
itself (a record that is there but whose format, CRC or descriptor does not hold), the zeros
`invalidate` writes, and the half word a torn write of either leaves (`sim/sim_flash.h` models a
torn write as half the bytes; the store's own table in `store.h` already turned on the same word).

A transfer that is really under way always reads from an all-ones word: `beginWrite`'s fresh path
invalidates the record and **then erases the header sector**, before its first marker; its resume
path writes no record and touches nothing. So the rule costs the resume nothing, which is what the
unchanged tests show.

`readProgress` therefore reads those four bytes first and answers *no transfer* unless they are
all ones — six lines in `components/core/image/store.cpp`. Everybody who asks about a slot goes
through `Store::read`, so there is exactly one place to change: the sleep rule
(`core/cycle/wake_cycle.cpp` `stepSleep`), the heartbeat's knowledge (`fillStore` →
`interfaces::BackendImage`), `twinoak.fw.state` (`agent/firmware_jobs.cpp` `writeStateResult`,
which already omits a slot that is not present), `image list` (`console.cpp` `imageOneLine`), and
the offer's *bytes already held* (`firmware_jobs.cpp`, which was reporting the old markers'
figure to the server as this wake's starting point) all say *empty* for a voided slot now.

## Decisions taken without asking

- **The markers are never read again; the promotion erases nothing.** The read rule is needed
  either way: the unit in service has the state in its flash **today**, and deliverable 1 asks for
  it cured with nobody at a console, which only a rule in the read can do. Given that rule, an
  erase at the promotion would add an eighth flash operation to a path whose every interruption is
  held by a test, for a unit that has already promoted would do nothing, and would make a second
  place that has to be right about the same thing. So `promote()` is byte for byte the operation it
  was, and the comment there says what is left behind and why it is safe. The next write into the
  area erases it, as it always did.
- **A header sector whose record is there but does not hold** — the magic present, the format, CRC
  or descriptor wrong — also reads as no transfer now, where before it read the markers. It is the
  same case for the same reason: a record stood there, so the markers below it are a finished
  download's. It is not a case any test reached before and none reaches now; it is in the table in
  `readProgress` so that nobody has to work it out again.
- **A commit whose final magic write is torn** (the power going in those four bytes) now reads as
  an empty slot with no transfer, where before it read a transfer and resumed. The next attempt
  sends the whole file again instead of the last 64 KB of it. That is a once-in-a-firmware's-life
  window, it is on the safe side — nothing resumes into bytes a half-written record was about to
  describe — and `test_store_power_loss.cpp` shows the store runs to completion from there either
  way. Said here because it is the one behaviour the rule changes that nobody asked for.
- **The bench items went in as `docs/bench.md` §24**, with no row in the walk's table: §§20–23 are
  in the same position, and the table is the phase-3 walk's order (its own note says so).
