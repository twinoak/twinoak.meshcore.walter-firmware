# p15-04 — a batch keeps its id

The task waited for the agent library at a release holding the exit-node firmware's task
p1.13-55, and that release is here: the sync pile's task 01 brought the copy to
**`b6d4cfb242cee93c2be5adfbdaa54bf8ef42c60b` (`v0.7.3`)** on 20 November, merged as #87. So the
library keeps the pending batch's id and its count in the image a sleep keeps
(`agent/KeptImage.h`, version 2), and **what was left for this board is two things**: the room
the bigger image needs, and the one fact about a waiting batch the library has no notion of —
**since which wake** it has been waiting.

`tools/verify.ps1` is **green** on this machine, 608 s, all eight steps.

## Deviations from the spec or the task

- **The first deliverable was already done, by the sync pile's task 01.** The task asks for
  `kKeptScratchBytes` and the two assertions under it "held to the library's own figures as they
  are now". They are: `kLargestKeptImage` is `mm::kMaxKeptImageLen` and not a sum of this
  repository's own, which is the change sync-01 made when the bump grew the image by the batch's
  40 bytes (its report's item 3). Nothing here moved them, and the report says the figure the
  task asked for: **19 368**.
- **The *tightest big allocation* is 56 bytes below main's**, while the margin the script's
  verdict names and `--min-spare` gates — 15 636 bytes in the heap the main task's stack comes
  from — is exactly main's. The task's words are *the margin is not below main's*, and that is
  the figure `heap_at_start.py` calls the margin and R22 is written against; the second figure is
  the one that says how much `.bss` may still grow before the 19 456-byte scratch lands in
  another heap, and 6 252 bytes of room is left (phase 11's task 01 died of 117). It is said here
  rather than left to be found: this task adds static storage, and phase 13's follow-up asks
  whoever does that to say so.

## Decisions taken without asking

- **The wake is kept in a value of the settings store of its own, `agent_batch`** — a version
  byte, the wake's number and a 32-bit fingerprint of the batch's id, 15 characters of hex. The
  library keeps the batch; a wake is not a notion it has, and its image's layout is the library's
  and is not edited here, so the figure is this board's to keep. A key of its own is what
  `agent_calls` (task p13-02) and `agent_flood` (p14-02) have, for the reasons
  `walter_agent/call_log.h` gives: RTC memory has no slot left and the figure has to survive a
  power cut, which RTC memory does not. **The flash is not spent on it**: the value is written
  only when the answer the object gives changes — a batch that starts waiting, one that stops,
  one replaced by another — which is only ever a wake whose observations call failed or the wake
  after one, and a unit whose posts are answered writes it never. A test holds that.
- **A fingerprint of the id and not the id itself.** What the stored wake needs is *is the batch
  waiting now the batch this wake is about*, and the id is already in the image the library reads
  back, so storing it again would be 36 bytes of a 160-character value for something the loop
  holds. FNV-1a over the id's bytes answers the question in four bytes. Two ids whose
  fingerprints collide would leave the figure one batch too early, in one line of a console
  command and one of a report; it is said in the header beside the hash.
- **56 bytes of `.bss`, and where they went.** `agent::PendingBatch` is about 24 bytes (the store,
  the loop, the fingerprint, two 16-bit numbers, three bools and the two write counters), the
  probe's pointer to it is 4, and the console's observation view grew by 12. The view's two new
  numbers are **16-bit and not the widths their neighbours have** — a batch holds at most twenty
  adverts and the wake is clamped to 0xFFFF where it is kept — for the reason every structure in
  static storage here carries: four bytes of `.bss` move the heap the kept scratch is carved out
  of. Nothing else was given back to pay for them: the two candidates phase 17's follow-ups name
  (the modem library's 3 080-byte debug buffer and the manifest's bytes held twice) are each a
  task of their own, and spending this task on one of them would be scope creep for 56 bytes of
  6 252.
- **`note()` and `save()` are at the end of the wake and not in `beat()`.** The trial's extra
  heartbeat (task p14-05) runs with a body cap of one byte, which stops every observation batch,
  so no trial heartbeat can change what is waiting. Said beside the call.
- **The scripted meshmaster.dk de-duplicates on `clientId` now**, which it did not, and has a
  knob named after upstream's own — `loseTheAnswerToObservations` — so that a case here reads as
  the library's case for the same thing. The batch is stored **before** the answer can be lost,
  because that is precisely the failure the kept id exists for: the rows are on the server and
  the unit does not know it. `batches` is still every body posted, duplicates among them, so no
  existing case reads differently; what is new is `seenBatches()` and `storedAdverts()`, which is
  what *nothing is stored twice* is asserted on.
- **The test puts its adverts in through §7 and the simulated RAK**, which needs a repeater
  behind the radio: `sim::QuietRepeater`, as task p4-04's own observation tests use, because the
  library's real simulated repeater asserts with GoogleTest and belongs in the other binaries.
- **`wakeUntilBatches`**: a failed post leaves a backoff behind it, and how many sleeps that
  takes is the library's arithmetic. The cases wake until the server has been posted what they
  are waiting for, with a cap, rather than pinning a number of sleeps that is not this
  repository's to decide.

## Not verified here (and why)

A session can build and run the host tests; it cannot flash a board, reach a network or talk to
meshmaster.dk. Everything above is tested against simulators only — a simulated RAK with a quiet
repeater behind it, a simulated flash window for the kept image, a simulated NVS, and a scripted
meshmaster.dk whose answer to one post is lost on purpose. The items below are in
`docs/bench.md` **§27**, in the order the rig is brought up; §26's third item is the library's
half of the same thing and stays where it is.

- [ ] **`agent obs` names the batch that is waiting**, on the unit in service. *Fetch now* on the
      Diagnostics tab after a night of hourly wakes, and read the `observations` section: while a
      post's answer is being lost there is one line more, and **the wake it names must be the same
      number as `agent calls`'s `observations` entry for the failure that lost that answer**, or
      earlier. A line whose wake moves forward at every wake would mean the batch is being rebuilt
      rather than kept, which is 16 November coming back.
- [ ] **It goes when the batch goes.** The wake after one whose post the server answers: no such
      line at all, the ring back to `0 of 64 waiting`, and the value behind it erased.
- [ ] **The exit node's page.** Over the same night: the count of distinct neighbours in the
      unit's newest hundred rows against the count of adverts its heartbeats say it heard. They
      must agree — the number that was three times too high before.

**What is not verified anywhere, and is not this task's:** why one modem command goes unanswered
for thirty seconds after an observations post. That is phase 15's first follow-up and the ★ line
of `docs/bench.md` §13. This task does not soften the lost answer, make it less likely or explain
it; it makes the batch cost one resend the server recognises, and says since when it has been
waiting.
