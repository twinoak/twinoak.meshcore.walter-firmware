# p4-02 — The mesh over the link

`IMesh` — what the agent's runner believes a radio is — is a class over the box link now:
`components/agent/link_mesh.h`, `agent::LinkMesh`, each call one request of
`spec/LINK-PROTOCOL.md` §6 and the reply the `EV_MESH_REPLY` that follows, with `REPLY_GET` when
it does not. The proof that nothing was lost in the crossing is the one the task asked for: the
library's own `test_runner` suite — **46 cases, unchanged** — compiled a second time with a header
shim that puts a simulated RAK (`host_test/sim/sim_rak.h`) and `LinkMesh` between the runner and
the library's own simulated stock repeater, and passing with every assertion it had in the same
process, plus one it did not have: at the end of every job, `client_tx` as the mesh read it from
`MESH_COUNTERS` equals the sends the repeater on the far side was asked for, exactly. Beside it,
21 cases of the link's own (the lost event, the lost request, the job timeout, the password read
back as zeros, the local door for each core type, `client_tx` exact, the radio restarting under a
job), the console's `rak mesh status <key>` for the bench, and the link client's receive side
wiped after every packet, because a repeater's reply to a password line echoes the password.

Done in one session. One thing is not as the task and `FOLLOWUPS.md` describe it and is the first
thing a reviewer should read, under *Deviations*: **`trace` is carried over the link.** The
specification this repository holds has `SEND_TRACE` (§6.2) and a trace record (§6.3, state 5), and
the runner's trace scenario passes through the framing; `supports("trace")` is therefore true, and
spec wins over the task file.

**Every send carries `timeout_ms` = 60 000**, a ceiling, because §6.2 takes the timeout at the send
and the library gives it at the await (`docs/library.md` §11 asked for exactly this: "pass a

the test `TheSendCarriesACeilingAndTheWaltersOwnTimerDecides` holds both ends and that the RAK is
never busy afterwards.

| type | over the UART, for the unit's own repeater | outcome |
|---|---|---|
| `telemetry` | `LPP_GET` at `0x07`, the bytes a mesh admin would be told | served |
| `cli`, `config.apply`, `advert.request`, `clock.sync`, `acl.set` | `CLI` lines (§5.7), with console privileges | served |
| `password.set` | `CLI`, the password line sensitive (wiped like a login), the restore after it | served; the value nowhere afterwards |

| `config.read` | `CLI` lines for every key, `region`, `region default`, `ver`, `board`; the access-list request answered with silence, which the library reads as *no ACL in this snapshot, no evidence either way*; the restore | served, without the ACL |
| `discover` | the UART is the direct path: the synthetic login "teaches" zero hops | served: `ok`, `hops: []` |
| `status` | `REQ_TYPE_GET_STATUS` is `RepeaterStats` as bytes; `stats-core`/`stats-radio`/`stats-packets` at d9296435 print text | `failed`, *the packet could not be built* — **link 1.1** |
| `neighbours` | the paged binary list; `neighbors` at d9296435 prints text | `failed` — **link 1.1** |
| `trace` | a round trip from the radio to itself | `failed` |

The two `failed` rows are the input to a link 1.1 request: a `STATS_GET` answering `RepeaterStats`
as the mesh answers it (the Walter already reads `POWER_GET` and `ENV_GET` the same way) and a
`NEIGHBOURS_GET` with `count`, `offset`, `order` and the prefix length, answering the page. Owner
info (`0x07`, the firmware version the status job reads at class `acl`) is the same gap and moot
until status is served. Why `failed` and not `unsupported`: `supports()` is asked per *type* and
not per peer (it is what the heartbeat advertises), so a type the link carries for a neighbour
cannot be declined for one peer without a `SendResult` the library has not got; the library's rule
is that `Failed` is a failed job with *the packet could not be built*, which is what the log line
says.

## Deviations from the spec or the task

### `trace` is carried, and `supports("trace")` is true

`FOLLOWUPS.md`'s `[02]` item says *`trace` is `false` until `LINK-PROTOCOL.md` has a trace request
(it does not)*, and `docs/library.md` §11 says the same of the link. The specification this
repository holds — `spec/LINK-PROTOCOL.md` 1.0 as copied, held to its manifest — has
`SEND_TRACE` (`0x28`, §6.2: a trace along the given round-trip path, always direct, `hash_size`
1, 2, 4 or 8), a trace record (§6.3 state 5: `trace_flags`, `final_snr_q4`, the hashes, one SNR a
hop) and a fixture for each (`trace over a two-byte round trip`, `mesh reply: a trace`). The
runner's `ATraceReportsTheRoundTripAndThisBoardsOwnHopLast` passes through the framing with the
same six hops and this unit's own hop last; `EveryCoreTypeIsCarriedWithASessionAndNoneWithout`
holds the type carried. *Spec wins over the task file*, and the sentence the library and the
follow-up rest on seems to come from an earlier draft of the link — the library's own `IMesh.h`
header lists `SEND_*` and `REPLY_GET` as the link's and never saw §6.2's table. What *is* true is
narrower: the RAK cannot trace a round trip to **itself**, so a trace of the unit's own repeater is
`Failed` at the local door. The two other gaps the follow-up names (`overheard`, the count by type)
stand and are in the table above. The reviewer may want to carry this to the exit-node repository's
`docs/library.md` §11.

### What the library asks `LinkMesh` for, as `v0.3.0` shaped it

`supports(jobType)` is implemented (above); no `viaPath` and no `snr` are assigned (`MeshReply` has
neither since `v0.3.0`; the link's `via_path`, `snr_q4`, `rssi` and `elapsed_ms` go to
`lastRecord()` and the console prints them); the timestamp of a CLI send is **returned**, from the
response's `sender_ts` — this end stamps nothing, ever (§6.2) — and at the local door it is 0,
because no packet was stamped.

### The receive side is wiped too, and the link client gained two calls

The task says the link client's *transmit* buffer is wiped after the frame is on the wire, and
phase 1's client already did that for `SEND_LOGIN` and a sensitive `SEND_CLI` (its `sensitive`
exchange: the request and the frame zeroed after the exchange, `test_link_client_retries.cpp`'s
case reads them back). What phase 1 could not know is what comes *back*: a repeater answers
`password <new>` with `password now: <new>`, and `APasswordSetRecordsNoValueAnywhereThroughTheLink`
found that echo in the client's event queue (a vacated slot keeps its bytes), in the receiver's
decode buffer (the next, shorter frame overwrites only its head) and in the 64-byte read chunk —
none of them logged, all of them RAM nobody reads, and S-12 says *nowhere else*. So the client
wipes its receive side now: the receiver's two buffers once a packet has been copied out
(`FrameReceiver::wipe()`, new), the chunk once it has been fed, the last response at the start of
the next exchange, and a queue slot when it is vacated. About 600 bytes zeroed per frame; nothing
else about the client's behaviour changed, and every test of phase 1 passes as before.

The two calls: `Client::cli(line, sensitive)` — §5.7 has no flag, so the wiping is this end's own,
for the local door's password line — and `Client::takeEvent(type, out)`, which takes the first
event *of that type* and leaves the rest for whoever they are for (the console's `rak events`, the
supervisor's `EV_ATTENTION`). `test_link_client_mesh_hooks.cpp` holds both.

### The timeout's two ends, and `JOB_BEGIN` as the way to end a wait

§6.2 takes `timeout_ms` at the send; the library gives the timeout at the await (and the mesh
cannot know it earlier — it is the claim's `perHopMs` times the hops, which the runner computes).
So the send carries a ceiling of 60 s, the Walter waits the runner's timeout plus 250 ms over the
event, and asks with `REPLY_GET` when it did not come. A record that is already final is the lost
event the specification describes. A record still *pending* is the RAK waiting on toward its
ceiling, and §6 has no request to end a wait but `JOB_END` and `JOB_BEGIN` ("ends any job in
progress first ... forgets ... any awaited or held reply"); `JOB_BEGIN` with the same peer and the
path this end holds is the one that keeps the job, so that is what is sent, once, and the next send
is never `ERR_BUSY`. One sentence in §6.2 would make this the specification's rather than this
firmware's reading — the library asked for it in the same breath; it is for the hardware
repository's `FOLLOWUPS`.

### `rail R14` reworded, `R12` widened

Phase 3's R14 said *no mesh request is sent by this firmware* and grepped `components/` and `main/`
for the twelve request names outside `core/link/`. This task is the agent's mesh client, so the
rail is *no mesh request is sent outside the agent, and none in a wake yet*: `components/agent/`
may name them, nothing else may, and the simulated month's assertion (*no mesh request sent*
over 2 400 wakes) is unchanged — the console's probe is not in a wake. R12 (*core/ includes
nothing of ESP-IDF or the modem library*) walks `components/agent/` as well, and
`tools/cmake/no_idf_include.cmake` took a `NAME` so that the build step can say *agent has no
ESP-IDF include* beside core's.

### `docs/bench.md` §17, not "15. The agent"

`FOLLOWUPS.md`'s `[06]` item renumbers the agent's bench sections to §17 and §18 because §15
*Sleep* and §16 *A day* exist; this task's one bench item is in a new **§17 *The agent*** with its
row in the walk's table, which task 06 fills and orders. Nothing is ticked.

### Two GoogleTest binaries of this repository's own

Task p4-01 kept this repository's tests doctest and GoogleTest for the library's two suites alone.
The simulated stock repeater the task names — the library's `FakeMesh` — is written against
GoogleTest (`support/Fixtures.h` asserts with `EXPECT_*`), and the "runner scenarios again" are
the library's GoogleTest suite re-run. So the two binaries that put `LinkMesh` under that fake are
GoogleTest too (`agent_core_runner_link_tests`, `agent_link_tests`); the simulators they share with
`core_tests` assert with doctest's `REQUIRE` inside their own code, so doctest's runtime without
its main (`host_test/third_party/doctest_runtime.cpp`, one context set as the default for
assertions outside test cases) is linked beside GoogleTest. The console's test and the
no-allocation check are doctest in `core_tests`, as everything of ours is.

## Decisions taken without asking

- **The shim, by `#include_next`.** The scenarios run "unchanged in their assertions" by compiling
  the copied `test_runner.cpp` with a directory first on its include path whose
  `support/FakeMesh.h` and `support/FakePlatform.h` rename the library's classes
  (`FakeMeshRepeater`, `FakePlatformUpstream`) on the way in and define the same names as
  subclasses: the platform carries the link's `FakeClock` and moves both clocks whichever is
  asked; the mesh derives from the repeater, forwards every `IMesh` call to `LinkMesh`, hands the
  repeater to the RAK through an inner `IMesh` that calls the base class by name, and keeps every
  knob and record the scenarios read. Two of the repeater's methods call its own virtuals
  (`await()` → `loop()`, `beginJob()` → `endJob()`); while the RAK is driving the repeater
  (`SimRak::busy()`) those are the repeater's and go no further. The alternative — a copy of the
  suite with `FakeMesh` replaced — would be a second file to drift from the copied one.
- **`SimRak` over the scripted radio, by composition and a hook**, not a second radio:
  `ScriptedRadio` gained `on_request` (consulted after its refusal knobs and §3's remembered
  response, so both still apply; answering with an empty payload is *no response at all*, a
  line that restarts the node) and `sendEventPayload`, and `Seen` keeps the response it gave.
  Everything of task p1-02's radio — HELLO, the clock, attention, the scanner, every knob — is
  the RAK's as before.
- **The repeater behind the RAK is polled a millisecond at a time.** The library's fake delivers a
  reply on its own clock inside a blocking `await`; the RAK asks it `awaitReply(tag, 1)` at every
  access, which is one look at whether the reply is due at the cost of one millisecond of both
  clocks. Faithful enough for every scenario (the gaps and the per-minute cap are measured on the
  repeater's record of sends, unchanged), and it keeps the RAK's answer to a send immediate, as
  §3 wants.
- **The RAK's `tx` is `client_tx` plus a thousand** in the simulator, so that a mesh that reported
  the radio's `tx` as its own transactions is caught by the equality every scenario holds.
- **`PATH_SET` with hops** (mode 2, which the library never sends) re-begins the repeater's job in
  the simulator, because `IMesh` takes a path of hops with `beginJob` alone.
- **The local login is silent without a session that has `CLI`**, so that a dead radio is
  `unreachable` and not a job reported *ok as sent* against nothing.
- **The access list at the local door is silence, not `Failed`**, because `Failed` would end a
  `config.read` of the unit's own repeater with fifteen good keys in hand, and the library's own
  rule for the ACL — the one key whose silence a reachable repeater guarantees — gives the read its
  outcome with *no ACL in this snapshot*. A `discover` of one's own repeater reports `ok` with zero
  hops for the same reason: the UART is the direct path, and the runner reads `hasPath()` after the
  login.
- **`counters()` is refreshed at `endJob()` and on demand**, not at every call: `counters()` is
  `const`, the library reads one field of it for the errors report, and one `MESH_COUNTERS` a job
  is the figure the shim's equality holds. `refreshCounters()` is there for the console (the probe
  reads it before and after).
- **`rak mesh status` sends no login.** The bench item is *one packet, one reply, `client_tx` up by
  one*; a login is a second packet and a password on a console line. The neighbour answers a bare
  status request when its ACL holds this unit's key, which `docs/bench.md` §17 says how to arrange;
  the login is task p4-05's, through the runner.
- **The include directory is `walter_agent/`** (`#include "walter_agent/link_mesh.h"`), not
  `agent/`, which is the copied library's prefix (`<agent/IMesh.h>`); two components exporting one
  prefix would be a thing to explain at every include.
- **`MeshProbe` is a seam in `core/console/`** (`mesh_probe.h`: an interface and a struct of
  numbers), because `core/` cannot name `components/agent/` (which is built on it) and the console
  is `core/`'s. What crosses it is numbers; nothing the mesh said as text does (S-12).
