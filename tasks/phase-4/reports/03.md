# p4-03 — The uplink over the modem

`IUplink` — what the agent's loop and runner believe meshmaster.dk is — is a class over phase 3's
HTTPS client now: `components/agent/modem_uplink.h`, `agent::ModemUplink`, the seven calls of API §3
each **one request** of `core/net/client.h` over the modem's TLS, each leaving behind the `Call`
record the library's `ServerPolicy` reads. The token crosses in a header and nowhere else: read from
`server.token` into one buffer of the object at the start of a call, handed to the client as a
pointer, wiped when the client returns — and the client's transport, which writes the one copy below
the caller's that this firmware can reach, wipes the request head it wrote the moment the head is on
the wire (a *sensitive* request, the way task p4-02 taught the link client the same word). The proof
is the one the task asked for: the library's own `test_loop` suite — **47 cases, unchanged** —
compiled a second time with a header shim that puts `ModemUplink`, the client and the scripted server
behind the firmware's own HTTP/1.1 between the loop and the library's scripted meshmaster.dk, and
passing with every assertion it had; beside it 19 cases of the uplink's own against the contract
fixtures' bytes, 6 of the console's two new lines, and one of the transport's wipe. Done in one
session.

One thing is not as the task wrote it and is the first thing a reviewer should read, under
*Deviations*: **the library has no `Retry-After` parser** — its `docs/library.md` §4 says so in so
many words — so the header is read here, by the rule that document gives (seconds as they stand, 0
for absent, unparseable or a date), which is the reference `AgentClient`'s minute by another road.

## What a status means, against the policy

`mm::actionFor(reachable, httpStatus, retryAfterS)` is what the loop does with a record
(`agent/ServerPolicy.h`); the test runs every row through it.

| the answer | the `Call` | `ServerPolicy` |
|---|---|---|
| 2xx, the body fit and parsed | `reachable`, `ok`, the status | `Ok` |
| 2xx, the body passed the bound | `reachable`, `ok = false`, the status, *http 200 but the reply is longer than 2048 bytes and was cut there* | `Ok` by the status, and the call returned false (as the reference's does) |
| 2xx, the parser refused it | `reachable`, `ok = false`, *http 200 but the reply did not parse: <the parser's reason>* — the reason and never a byte of the body | the same |
| 401 | `reachable`, `ok = false`, 401, *the token was refused* | `Halt` — the loop stops; task p4-04 raises attention |
| 403 | 403, *this unit is refused (paused, or not its route)* | `Discard` |
| 429 | 429, `retryAfterS` the header as seconds (0 for a date), *rate limited; Retry-After N s* | `WaitRetryAfter`, `retryAfterMs(0)` = a minute |
| 502, 503, 504 with `Retry-After` | the status, `retryAfterS` | `WaitRetryAfter` |
| 5xx without, 500 | the status, `retryAfterS` 0, *the server is not well* | `BackOff` |
| 3xx | `reachable`, `ok = false`, the status, *a redirect, which an agent route never answers and this unit never follows*; **one request made** | `BackOff` |
| another 4xx (400, 404, 409, 410, 413, 422) | the status, *http N* | `Discard` |
| no status: DNS, TCP, the handshake, a timeout, no uplink | `reachable = false`, status 0, *no reply: <the transport's sentence>*, with *(the wake's budget)* when the deadline was the wake's | `BackOff` |
| refused before the wire (above) | `reachable = false`, status 0, the sentence | `BackOff` |

`Retry-After` is bounded at an hour (`core::net::kRetryAfterCapS`, where the client bounds its own
reading), `X-RateLimit-Remaining` is read into `rateLimitRemaining` and -1 when absent or not a
number, `via` is `"lte"`, `atMillis` is `interfaces::Clock`, `atEpoch` is `interfaces::WallClock`
(0 while the unit has no time).

## Deviations from the spec or the task

### There is no `Retry-After` parser in the library

The task says *seconds or a date — the library's parser; find it*. `docs/library.md` §4, at the
pinned commit: *"There is no `Retry-After` parser in the library — a thing worth knowing before you
go looking for one. `Call::retryAfterS` is a count of seconds you parse yourself, and the rule is
simple: the integer form as it stands, and 0 when the header is absent, unparseable, or an HTTP
date. `mm::retryAfterMs` turns a 0 into one minute and bounds anything above an hour."* So the
header is asked for as a wanted header and read in `modem_uplink.cpp` by exactly that rule, bounded
where `core/net/client.h` bounds its own reading. The reference `AgentClient` answers **60** for a
date; the library's rule answers 0 and `retryAfterMs` makes it the same minute. The client's own
`Result::retry_after_s` (an HTTP date is the cap, an hour) is not used for the record, because a
429 whose date was read as an hour would hold the unit back sixty times longer than the server
asked; the test holds both forms.

### Where the library's policy and the reference implementation disagree

Three places, none of them a problem for the loop, all worth knowing:

1. **`ok` is 2xx here, `code == 200` in the reference.** `docs/library.md` §4.1 says *2xx and the
   body parsed*, and the task says 2xx; meshmaster.dk answers 200 on every agent route today, so
   nothing moves.
2. **A 200 the parser refuses, or one whose body passed the bound, is `Ok` to the policy and false
   from the call.** `actionFor` reads the status and not `ok`; the reference has the same shape.
   The loop's `noteFailure` resets the backoff on it and the call's false return is what the step
   acts on. Said here so nobody expects a backoff from a reply that was cut.
3. **The reference tries a second root on a verification failure and remembers the choice; this
   firmware does not.** `core/net/trust.h` holds every host to one root per host and the modem's
   profile validates the chain and the name (the TLS rail); a chain that does not end there is a
   refused handshake and `reachable = false`, and `via` is the one word `"lte"` rather than the
   root's name. Which root a host is held to is the trust table's business, not the uplink's.

### The deadline is given, not read from phase 3's budget

The task says *each call takes the wake's remaining uplink budget as its deadline (phase 3's
budget)*. `IUplink`'s seven calls carry no deadline, and the budget is the wake cycle's (step 8's
`deadline_ms` reaches the backend seam as an argument, `interfaces/backend.h`). So `ModemUplink` is
*told*: `setDeadline(deadline_ms)` on `interfaces::Clock`'s milliseconds, and every call from then
on takes what is left as its total deadline (`core::net::Options::total_ms`), with
`kLeastCallMs` (5 s, a bench number) the least a call is begun with — below it the call is
`reachable = false` with *budget* and the modem is not touched (the test holds `opens == 0`); above
it a server that never answers costs exactly what was left, then the socket is closed and the
caller takes the modem down. Task p4-05's `AgentBackend::exchange` is the one that calls
`setDeadline` from its argument and `setLinkUp` from step 6's outcome; today nothing does, and the
console's `agent probe` runs under the transport's own defaults (`core/net/http_over_tls.h`).

### `link()` is what the owner says, not what the modem is asked

`LinkState { up, connects, drops }` is counted from `setLinkUp(bool)` rather than read from
`core::uplink::UplinkPolicy`, because the uplink is brought up by the wake cycle's step 6 before the
agent runs and the agent never brings it up itself (the library gates every call on `link().up`
and reports `connects - 1` as the heartbeat's reconnects). Reading the policy would have put a
modem and a policy under the loop suite's shim for a boolean; the console's `agent probe` is held
to *the uplink is up* by the console itself (`uplinkUp()`, as `http get` is).

### meshmaster.dk's task 120 says nothing about the version header

The task says *read what 4.14's 120 decided a `native` agent reports and follow it* for
`X-Agent-Version`. `tasks/phase-4.14/120-an-exit-node-that-sleeps.md` at today's `master`
(`def65a49`) decides the two optional heartbeat fields, the bounds, health and lateness, and names
no version header and no board; API §3 says only that the header must be present (a missing one is
a 400 that names it) and that `board` is an optional heartbeat field. So `X-Agent-Version` carries
**this firmware's version** (`core::version()`, `0.0.0-dev` here and the release's tag on a
release), as the task's own sentence says, and the heartbeat's `board` and `agentVersion` are the
identity task p4-04 fills (`HeartbeatIdentity`). The library's version is not sent in any header:
the library reports it through the identity, where task p4-04 may put it beside the firmware's.

### The transport wipes, as the link client does; the token's buffer is a member

The task asked for the client's header buffer to be extended with a sensitive path. `core::net::Client`
keeps no copy of any header — `Options::authorization` is the caller's pointer and goes into the
request as a pointer — so the one copy below the caller's is the request head `HttpOverTls` writes
(`head_`, 2560 bytes). `Options::sensitive` → `HttpRequest::sensitive` → the transport zeroes the
head through a volatile the moment the head is on the wire, before the body goes and before the
seconds a response takes, and again on every way out (`finish`). The modem's own copy — the bytes
the library hands `uart_write_bytes` — is the one this firmware cannot reach, as the reference says
of HTTPClient's. The token's buffer in `ModemUplink` is a **member** (`secret_`) and not the stack
buffer the task names, so that the test can read it back after the call — and because the main
task's stack is 3584 bytes. Wiped before the client's return is acted on.

### What the suite's second compile needed of the simulators

Two things, both in `host_test/sim/` and both the kind of knob task p4-02 added to the scripted
radio: `ScriptedServer::on_request`, a hook consulted after the request is recorded and before the
script (a claim's answer depends on what was claimed before, and a 401 on cue is a decision per
request); and `FakeTlsSocket::spend()` now waits through `clock.delayMs()` rather than
`clock.advance()`, so that the clock tie of `host_test/shim/support/FakePlatform.h` sees a connect's
cost — the loop measures a wake's uplink seconds on the platform's clock, and the test
`AnUplinkBudgetSpentAtTheJobStepKeepsTheResultRatherThanPostingPastIt` holds `uplinkMs == 3000` for
three calls at `setCallMs(1000)`, which is now three connects of a second each. No test of phase 3
read the socket's `delayed_ms`, and every one of them passes as before. The tied `FakePlatform.h`
**moved** from `host_test/agent-link/shim/support/` to `host_test/shim/support/`, because the loop's
binary needs it without the mesh shim beside it; the two link binaries get it from there now.

### What failed first, and is now evidence

The heartbeat case found the uplink **wiping its own request buffer at the start of every call**:
`call()` zeroed the reply and the request buffers together, and the heartbeat's body lives in the
request buffer, so 231 zero bytes went out under a `Content-Length: 231` and the fixture's reply
came back all the same (the scripted server does not read a body it is not asked about). The test
holds the body on the wire against `writeHeartbeat`'s bytes, and it was the only one of the 47 +
19 cases that could have seen it. The request buffer is wiped after the call now, with the reply's.

## Decisions taken without asking

- **`kLeastCallMs` is 5 s and marked for the bench**, with its row in `docs/bench.md`'s table: a
  connect and a handshake over LTE-M are seconds each, and a call begun with less ends in a timeout
  that cost the modem for nothing. The first `agent probe` on a real network is where the number
  comes from (§17's first item says to write it down).
- **One reply buffer, 6 kB, wiped after every call**, not one per call as the reference keeps
  them (`static char body[kBodyCap]` three times over): the library makes one call at a time and
  never from inside another (`docs/library.md` §4), and a buffer that is zero between calls is one
  that cannot carry a claim's password into the next call's `lastCall()`. The per-call bound is
  what cuts a long reply (2 kB for six of them, 6 kB for a claim); the object is about 9 kB and is
  a namespace-scope object in `main/`, never a local.
- **The heartbeat's body buffer is 1536 bytes**, the reference's 1024 with room: the contract
  fixture is 544 bytes, a unit with thirteen job types, a board, the two optional fields and a few
  error counters fits, and a body that does not fit is refused before any call with a sentence
  (the test overflows it with two hundred error counters).
- **The library's log, through `mm::logf`**: one line per call — the endpoint, the status, the
  bytes, the milliseconds, or the sentence — never a body and never the token (the test searches
  the capture). Nothing sets the library's log sink until task p4-04's platform does, so on the
  board today those lines are formatted and dropped, which is what `agent/Log.h` says a library
  that owns no port must do.
- **`setClock(mm::IClock*)`**: the server time a config reply and a claim carry is offered to the
  library's clock when the platform gives one (task p4-04), as the reference's `AgentClient` offers
  it; the heartbeat's is the loop's own business (`AgentLoop.cpp` takes it). Without one nothing
  is offered.
- **`agent url` reads and does not call; `agent probe` wants the uplink up**, as `http get` does,
  and both are under `help`'s *the uplink* group: a server is not a radio and the lines take no
  slot. The probe seam (`core/console/uplink_probe.h`) carries the `Call`'s fields and the config's
  numbers and words, copied, and has no field for the token — the console cannot print what it is
  not given — and `agent url` says *set* or *unset* as `get server.token` does.
- **The console's grammar test's list of compared words gained `"agent"`**: no file but the parser
  may compare it, as for the other ten.
- **The shim is not a subclass of the library's `FakeUplink`** (the p4-02 shims subclass): the
  original's script is private and is consumed by its own methods, which parse a reply they built
  and never put on a wire, so there is nothing to forward to. The semantics are copied line by line
  with the original's sentence beside each (the claim's oldest batch and `max` of it, the fault
  before the call, the cost on the clock, what is recorded when), and the original is still
  `#include_next`ed under another name for its `PostedResult` and its fixtures.
- **The contract fixture `ClaimResponse.json` is used as it is**, four-character repeater key and
  all: `parseClaimResponse` takes it (the key's length is the mesh's business, `Jobs.h` says), and
  what this task holds is the uplink's parse and the wipe, not a job.
