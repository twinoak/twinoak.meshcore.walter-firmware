# p4-01 — The library arrives

The MeshMaster agent's job logic is in this repository, compiled for the board and for the host,
linked into the image, and held to its own tests: `twinoak/twinoak.meshmaster.exitnode-firmware`'s
`lib/agent-core/` at **`v0.3.0` = `cc5a34366b316ead6248f651e8263c294bb6feea`**. Its
`CMakeLists.txt` registers as the component `agent-core` **without a single edit**, and at this
release nothing of the library is compiled differently here from the way our own code is — no
dialect of its own, no warning exempted.

**This task was done in three sessions**, and the gap between them is the point of the dates:
session one (15 October) brought the library across at `v0.2.0`, built it for the board and the
host for the first time anywhere, and reported two portability findings upstream; it stopped
because acceptance criterion four needs a GitHub secret. Session two (20 October) stopped at once,
because `tasks/phase-4/FOLLOWUPS.md` had meanwhile told this task to pin **`v0.3.0`** — which the
exit-node firmware had not tagged yet, and pinning an untagged commit mid-way through a wire-dialect
change was the one thing that item forbade. This session (22 October) found `v0.3.0` tagged
(`cc5a3436`, the merge of that repository's pile-1.6 task 24), re-copied at it, dropped both local
measures because upstream had taken both findings, and finished. The commits of session one stand;
nothing of it needed redoing.

One thing is not as the task wrote it, and it is the first thing a reviewer should read: the
library arrives as a **checked copy at one commit**, the way `spec/` does, and not as a
component-manager `git` dependency — because the repository it comes from is private and the clone
the component manager would make happens *inside the build*, where no credential exists.
*Deviations* has the whole of it and `docs/upstream.md` has the page. The reviewer's instruction to
resume on this branch is the decision that settles it ("the checked copy stands"), so the two items
session one raised for a person are not re-raised here.

## Deviations from the spec or the task

### The library is a checked copy, not a component-manager git dependency

The task's first deliverable is `agent-core` from
`git: https://github.com/twinoak/twinoak.meshmaster.exitnode-firmware.git`, `path: lib/agent-core`,
`version:` the commit — which is exactly what the library's own `docs/library.md` §2 tells a
consumer to write. It does not work, and the reason is not a detail:

```
$ git clone https://github.com/twinoak/twinoak.meshmaster.exitnode-firmware.git
remote: Repository not found.
fatal: Authentication failed
```

That repository is **private** (`gh api repos/... --jq .private` → `true`), and the component
manager resolves a `git` source by cloning it *while the build configures* — which happens in two
places that have no credential and should not have one: the ESP-IDF container on this machine
(nothing of ESP-IDF is installed here; the container has no `~/.gitconfig`, no credential helper
and no key — session one ran the clone inside it and got the error above), and the CI runner,
whose `GITHUB_TOKEN` is scoped to *this* repository. So a build pinned that way is a build nobody
can run, **CI included**, and CI is what decides whether a branch may merge.

The smallest decision consistent with the spec was to bring the library across the way this
repository already brings another repository's files: **`spec/` is a checked copy**, written by a
script, held byte for byte against a manifest, never edited here. The task itself asks for the
fakes and the fixtures that way, for the same reason; extending it to the library's own sources
changes *how the bytes arrive* and nothing about what they are:

| | the task's way | what was built |
|---|---|---|
| where the bytes are | `managed_components/twinoak__agent-core/`, fetched at build | `components/agent-core/`, in the repository |
| the pin | `version:` in `idf_component.yml` + the sync manifest | the `# source: … at commit …` line of each tree's `MANIFEST.txt` |
| two places, held equal | a test | the same test, over the two manifests |
| the library edited here | never | never — and now checkable: `-Verify` re-hashes all 187 files |
| who can bump it | anybody with a build | a machine that can read the upstream repository |
| CI | cannot run | runs, and verifies the copy |

**What would restore the dependency**, when somebody wants it: the exit-node repository made
public, or a *Contents: read* token available to both the container and CI. `docs/upstream.md`'s
*How the library gets here, and why it is a copy* says what would change — three lines of
`main/idf_component.yml`, one variable in `host_test/CMakeLists.txt`, and the sync script keeps
the fakes and the fixtures (which the component manager does not carry: they are not part of the
library). **Not one line of tasks 02–05 changes either way** — the include path is `<agent/X.h>`
in both.

### `PROJECT_DIR` is a staged directory in the build volume, new at this release

Three of the loop suite's new cases read the library's **own sources** — `fs::path(PROJECT_DIR) /
"lib/agent-core/src/AgentLoop.cpp"`, the same for `JobRunner.cpp` and `include/agent/IUplink.h` —
to hold what their text may say: no use of the store outside the two functions `wake()` reaches,
every call to the server through the uplink's ledger, no unbounded flush in the runner. Upstream's
`PROJECT_DIR` is its repository root, where the library *is* `lib/agent-core/`; here the library is
`components/agent-core/` and its test support is `host_test/agent-core/`, so those three cases
failed against the real bytes of a tree they could not find (and a fourth read an empty
`IUplink.h` and so looked for calls in nothing).

So upstream's layout is staged in the build directory, out of **symbolic links**:

```
<build>/host/agent-core-project/lib/agent-core -> components/agent-core      (the bytes the board gets)
                               /test           -> host_test/agent-core/test
                               /tests          -> host_test/agent-core/tests
                               /platformio.ini -> host_test/agent-core/platformio.ini
```

Links and not copies on purpose: a case that reads the library's source reads the same bytes the
board compiles and the same bytes `-Verify` hashed, and a copy of a copy is a second thing to
drift. Nothing of it is in the repository — it is one directory of the build volume, made at
configure time, and the host tests are built in the container, where a symbolic link needs no
privilege. It is reported upstream below as the one thing a consumer should not have to invent.

### `v0.3.0` brought an interface no task of this phase owns

`agent/IRetained.h` and `agent/KeptImage.h` are new and **optional**, and they exist for exactly
this unit: a result the server did not take, or an advert a wake could not post, lives in RAM,
which a deep sleep takes with it — so the library's promise *no job left leased and silent* held
only within one boot. `AgentLoop::setRetained(store, scratch, len)` and `restoreKept()` are the
seam: one image a wake, at most about 19.5 kB, written only when it differs from the one the store
holds, refused whole when torn or foreign, and counted when it is. Phase 4's tasks were written
before it existed, so none of them names it. §13 of `docs/ARCHITECTURE.md` now does: it describes
the fourth seam, says the image may hold nothing a result may not (the runner wipes every
credential before a result is written), and says where it belongs — `capacity`/`write`/`read` over
a flash region or an NVS blob beside `WalterPlatform` in **task p4-04**, with task p4-05's
simulated month as what shows it is worth having. Nothing is implemented here (*Out of scope*:
implementing a seam is 02–05); it is named so that it cannot be missed, and the reviewer may want
it tagged in `FOLLOWUPS.md`.

### The copy brings two fixture sets, not one, and upstream's `platformio.ini`

The task names `tests/fixtures/contracts/`. `test/support/Fixtures.h` — which both suites
include — `#error`s without **`COMPANION_DIR`** as well, and `FakeMesh` answers from the
transcribed MeshCore frames of `tests/fixtures/companion/`, so that set had to come too (the
library's `docs/library.md` §12 says both directories come in as defines; the task's list was
short). Each set keeps its own upstream `MANIFEST.txt`, naming the meshmaster.dk commit it is
from — `79b1e9c` for the envelopes, `f518ebd` for the frames — because the two move for different
reasons. Upstream's `platformio.ini` came across as well, for its `[meshcore]` pin, which is the
only way the runner's `Citations` case can check that a fake's citation names a commit. 187 files
in all: 59 under `components/agent-core/`, 128 under `host_test/agent-core/`.

### A `deps` step in `tools/verify.sh`, before the host tests

The task asks `host_test/` to compile the library "from the managed-components checkout (the same
bytes the board gets)". ArduinoJson *is* a managed component and the host-tests step runs before
the build step, so the component manager has to have run first. `verify.sh` has an eighth step,
`deps` (`idf.py reconfigure`, 6–15 s), which resolves `managed_components/` and prints
`dependencies.lock`; the build step reuses that configure, so nothing is done twice. Its
by-product is that `dependencies.lock` is written by a step of its own rather than as a side
effect of the build. (Session one's deviation, unchanged, and the only line of the lock file this
session moved is its `manifest_hash`: the library's `idf_component.yml` says `0.3.0` now.
ArduinoJson is still `7.4.3`.)

### `host_test/core/console/test_console_grammar.cpp` does not walk the copied library

Its *no file but the parser matches a command word of its own* case walked everything under
`components/`, and six lines of the agent core compare the job type `"status"` — which is also a
console command of ours and means something else. The library is not our grammar and is never
edited here, so `firmwareSources()` skips `agent-core`, with the reason written down; the same
exclusion is in `tools/check_rails.py`'s `sources()`, so that the fifteen rails written before it
keep exactly the scope they were written with. The one entry that *is* about the copy is entry
**A**, which names both trees itself. `host_test/core/net/test_trust_rail.cpp` deliberately **does**
walk it: the library makes no socket of its own, so its greps must find nothing there.

### A merge of `main`, not a rebase

`main` moved five merges while this task waited for the tag (phase 5 and the refreshed spec), so
the branch carries a merge of it. Two files conflicted: `tasks/phase-4/FOLLOWUPS.md`, where
`main`'s copy is kept whole because it is the reviewer's and carries this session's instructions,
and one help string of `tools/check_rails.py`, which now names `R3b` and `A` together. Phase 5's
rails and this task's entry A all hold: **17 entries, all green.**

## Decisions taken without asking

- **The copy over a credential**, and **`components/agent-core/`** rather than `managed_components/`
  or a `third_party/` of its own: it is a component of its own, under `components/` where a reader
  looks for one, picked up without an `EXTRA_COMPONENT_DIRS`, and `components/core/`'s no-ESP-IDF
  rule is unaffected because the library is not under it. Everything that scans "our code"
  excludes it by name, in one place each. (Both session one's, and the reviewer's instruction to
  resume is what settles the first.)
- **The staged `PROJECT_DIR`, by symbolic link, at configure time.** The alternatives were a
  second copy of the library inside `host_test/agent-core/` (two copies to drift, and `-Verify`
  would have to hash both), or filtering three cases out (the proof the copy is whole is that
  *nothing* is filtered). A link costs nothing and reads the same bytes. If a link cannot be made,
  CMake stops with the reason rather than silently falling back to a copy.
- **`IRetained` is named in §13 and pointed at task p4-04**, not implemented and not tagged in
  `FOLLOWUPS.md` — a session does not write the reviewer's file, and implementing a seam is out of
  scope. Task p4-04 is where it fits (it is the task that already owns retained storage and the
  platform), but the reviewer may place it in p4-05 with the firmware jobs instead.
- **Still only the two suites the task names.** `v0.3.0` has twenty-four suites, and three more
  would be cheap and are tempting — `test_json_escaping` (the new wire dialect, clause by clause),
  `test_seams` and `test_contract_fixtures` (the fixtures against their own manifest). The task
  names `test_runner` and `test_loop`, which are the two that exercise the library whole, and *no
  scope creep* decided it. Adding one is three lines of `host_test/CMakeLists.txt`'s `foreach`.
- **GoogleTest 1.17.0, by release tarball URL and SHA-256, for those two binaries only** — the
  version upstream's `[env:native]` passes the suites with. `FetchContent` with `URL_HASH` is a
  hard pin: no tag, no branch. This repository's own tests stay doctest; nothing of ours links
  GoogleTest.
- **`main/agent_anchor.cpp` anchors five functions, which keeps all twenty-three objects.**
  `AgentLoop::wake`, `AgentLoop::loop` and `JobRunner::claimAndRun` reach twenty-one of them at
  this release — `KeptImage.cpp` is new and `wake()` reaches it, so it needed no name of its own —
  and `ConfigReply.cpp` and `LogRing.cpp` are reached by nothing *in* the library (they are a
  consumer's to call), so `parseAgentConfig` and `LogRing::copyTo` are anchored by name. The
  volatile read is in that translation unit and `app_main` only keeps what it returns, which is the
  shape `core/image/verdict.h`'s anchor established.
- **The two manifests exclude a root-level `MANIFEST.txt` and `README.md` from themselves**, as
  `specsync.py`'s `LOCAL` does, so that a note this repository writes about a copy is not part of
  the copy. A `README.md` *inside* a copied tree is upstream's and is in the manifest.
- **`-Verify` runs on the host, in `tools/verify.ps1`, before the container starts**, which is what
  the task asked. The *pin*'s two places are held equal twice over — there and by a host test —
  because that is the one thing a checkout which never runs the script must still be held to.
- **No bench lines.** Nothing on a board changes (the task says so), so `docs/bench.md` is
  untouched and *Not verified here* is almost the empty list it ought to be. §12's forward
  reference to the agent's bench sections now says **§§17–18** rather than §§15–16, because
  `FOLLOWUPS.md`'s `[06]` item has renumbered them; `docs/bench.md` itself is task 06's and is not

## Reported upstream (a diff for the exit-node repository)

Session one's two findings — a parameter named `unix`, and ArduinoJson's `-Wmaybe-uninitialized`
at `-O2` — are **fixed in `v0.3.0`** and are not repeated here. One is left, and it is small.

### The suites can only find the library at `PROJECT_DIR/lib/agent-core`

`test/test_loop`'s three source-reading cases hardcode the library's path under `PROJECT_DIR`:

```cpp
const std::string loop = readFile(fs::path(PROJECT_DIR) / "lib/agent-core/src/AgentLoop.cpp");
```

`PROJECT_DIR` is the one knob a consumer has, and it has to point at the directory that holds
`test/support/`, `platformio.ini` and `tests/fixtures/` for the runner's `Citations` case — so a
consumer whose library is **not** at `lib/agent-core` relative to that directory cannot satisfy
both at once. The ESP-IDF consumer this library was written for is exactly that consumer: a
component lives under `components/`. Here it is staged with symbolic links, which works and reads
the right bytes, but it is a thing to invent and it is invisible until three cases fail. A fourth
define, beside the three `[env:native]` already passes, costs upstream one line and spares every
consumer the staging:

```diff
--- a/platformio.ini
+++ b/platformio.ini
 [env:native]
   -D PROJECT_DIR='"$PROJECT_DIR"'
+  -D LIBRARY_DIR='"$PROJECT_DIR/lib/agent-core"'

--- a/test/test_loop/test_loop.cpp
+++ b/test/test_loop/test_loop.cpp
+// Where the library's own sources are. Upstream's own layout by default; a consumer whose
+// component lives elsewhere (an ESP-IDF `components/agent-core/`, say) passes its own.
+#ifndef LIBRARY_DIR
+#define LIBRARY_DIR PROJECT_DIR "/lib/agent-core"
+#endif
-  const std::string loop = readFile(fs::path(PROJECT_DIR) / "lib/agent-core/src/AgentLoop.cpp");
+  const std::string loop = readFile(fs::path(LIBRARY_DIR) / "src/AgentLoop.cpp");
```

(The same three lines serve `include/agent/IUplink.h` and `src/JobRunner.cpp` in the two
`TheWakesLedger` cases.) Nothing is patched here — *Out of scope*: changing the library is
reported upstream — and no patch file exists, so there is nothing to track as temporary.
