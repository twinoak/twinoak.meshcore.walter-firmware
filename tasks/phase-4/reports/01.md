# p4-01 — The library arrives

The MeshMaster agent's job logic is in this repository, compiled for the board and for the host,
linked into the image, and held to its own tests: `twinoak/twinoak.meshmaster.exitnode-firmware`'s
`lib/agent-core/` at **`v0.2.0` = `bbe7ae0515ba7640e4a80f9bc4541386d940f535`**. This is the first
ESP-IDF build of that library anywhere, and its `CMakeLists.txt` registered as the component
`agent-core` **without a single edit**.

One thing is not as the task wrote it, and it is the first thing a reviewer should read: the
library arrives as a **checked copy at one commit**, the way `spec/` does, and not as a
component-manager `git` dependency — because the repository it comes from is private and the
clone the component manager would make happens *inside the build*, where no credential exists.
*Deviations* has the whole of it, `docs/upstream.md` has the page, and
`tasks/phase-4/FOLLOWUPS.md` has the one decision it leaves for a person.

**This task did not merge itself.** Acceptance criterion four — the upstream workflow's rehearsal
opening and closing a pull request — cannot be met without a GitHub secret, which `RUNBOOK.md` §5
makes a stop condition. Everything else is done, verified and on this branch;
`tasks/phase-4/logs/STOPPED-01.md` says what is missing in two sentences.

## Acceptance checklist

- [x] **`tools/verify.ps1` green with the component in the board build and in the host build; the report gives the board image's size delta.** Green, all eight steps, twice: once warm, and once from the condition a CI runner is in (`managed_components/` deleted and the host build directory wiped, so the component manager and GoogleTest's download both ran from scratch) — 280 s. The board image went from **584 496 to 643 808 bytes** (`twinoak-walter.bin`; `Total image size` 584 367 → 643 683), **+59 312 bytes**, 20.5 % of the 3 MB slot. Of the library's own contribution the map accounts 56.5 kB of `.text`, 23.5 kB of `.rodata` and 6.2 kB of literals, and **about 18 kB of RAM** (`.bss` + `.data`) — the scratch buffers its kept functions reach, chiefly an 8 kB observation-batch buffer in `AgentLoop.cpp`. That RAM is spent on code nothing calls until task 05; it is the price of proving the library *links* and not merely that it compiles, and task 05 spends it for real. DIRAM is at 72.3 % with 94 753 bytes remaining.
- [x] **The pinned commit appears in exactly two places (`idf_component.yml`, the sync manifest) and a test holds them equal.** Two places, and they are the two manifests — `components/agent-core/MANIFEST.txt` and `host_test/agent-core/MANIFEST.txt` — rather than an `idf_component.yml` and one manifest, because there is no git pin to put in a manifest (see *Deviations*). `host_test/rails/test_rail_agent_core.cpp`'s first case reads the commit out of both headers and fails if they differ, saying why it matters ("the board would run one release of the agent and the suites would test another"); `tools/sync-agent-core.ps1 -Verify` checks the same thing before the container starts, so a checkout that never runs the script is still held to it. The same file also holds the library's three statements of its own version equal (`agent/Version.h`, `library.json`, `idf_component.yml`) and ArduinoJson's pin against `dependencies.lock`.
- [x] **The library's runner and loop suites pass in this repository's host build.** `agent_core_runner`: **45 cases, all passed** (43 `RunnerTest` + the fake's two `Citations` cases). `agent_core_loop`: **31 cases, all passed**. Both are ctest entries beside `core_tests`, under the same ASan/UBSan options, from the suites copied at the same commit; the counts are upstream's own. `core_tests` went from 800 to 804 doctest cases (574 039 assertions) with the new rail file. Nothing of either suite is filtered out or skipped here — which took laying the copy out at **upstream's own paths** under `host_test/agent-core/`, because the runner's `Citations` case reads `test/support/FakeMesh.h`, `platformio.ini`'s `[meshcore]` pin and `tests/fixtures/companion/` relative to a `PROJECT_DIR` it is handed. (The half of that case which reads a pinned MeshCore checkout is conditional and is skipped here, as it is in upstream's own CI: neither has one.)
- [ ] **The upstream workflow's rehearsal opened and closed a pull request; the report links the run.** **Not met, and it cannot be from here.** `.github/workflows/upstream.yml` is written, and so are the two scripts it is made of, but every path of it that looks at upstream needs a credential for a private repository — `AGENT_CORE_READ_TOKEN`, a fine-grained token with *Contents: read* and nothing else. Without it the workflow stops at its first step, **green**, with the whole explanation in the run summary; it does not fail red every Monday and it does not pretend to have looked. What was rehearsed instead, locally and for real: `tools/upstream-check.ps1` against the clone beside this one (the "nothing newer" path, and the "newer" path with `-Version 0.1.4` → *yes, v0.1.4 → v0.2.0*) and over the network (which works on this machine, where `gh auth` has left a git credential helper); `tools/sync-agent-core.ps1 -Ref v0.2.0` re-run over the same commit, producing both manifests **byte for byte identical** — the workflow's one step that is not `gh`; and `tools/new-sync-task.ps1 -Tag v0.3.0 -Pr 42`, which wrote `tasks/sync/01-agent-core-v0-3-0.md` and a row the driver's regex `^\| (\d\d) \| \[([a-z0-9-]+)\]\(` accepts (`N=01 name=agent-core-v0-3-0`). Both were removed again and copies are in `out/p4-01/`. A rehearsal of the pull-request path to an *older* tag is impossible for a second reason worth knowing: `v0.2.0` is the first tag of that repository that has `lib/agent-core/` at all, so there is no earlier commit to copy — `git archive` refuses with *pathspec 'lib/agent-core' did not match any files* and the script changes nothing.
- [x] **Every edit the library needed to build under ESP-IDF is in the report as a diff for the exit-node repository, and in FOLLOWUPS as temporary if a patch file exists.** **The library needed no edit to build under ESP-IDF** — `tools/patches/` does not exist and nothing applies a patch at build. Two findings came out of building it anyway, one of them a genuine portability bug; both are below as diffs for the exit-node repository and both are in `FOLLOWUPS.md`. Neither is patched here (*Out of scope*: changing the library is reported upstream).

## Deviations from the spec or the task

### The library is a checked copy, not a component-manager git dependency

The task's first deliverable is `agent-core` from
`git: https://github.com/twinoak/twinoak.meshmaster.exitnode-firmware.git`, `path: lib/agent-core`,
`version:` the commit — which is exactly what the library's own `docs/library.md` §2 tells a
consumer to write. It does not work, and the reason is not a detail:

```
$ git clone https://github.com/twinoak/twinoak.meshmaster.exitnode-firmware.git
remote: Repository not found.
fatal: Authentication failed
```

That repository is **private** (`gh api repos/... --jq .private` → `true`), and the component
manager resolves a `git` source by cloning it *while the build configures* — which happens in two
places that have no credential and should not have one:

- **the ESP-IDF container on this machine.** Nothing of ESP-IDF is installed here and the build
  runs in `espressif/idf` with the repository bind-mounted; the container has no `~/.gitconfig`,
  no credential helper and no key. `git clone` of the line above inside it is the error printed
  above — I ran it.
- **the CI runner.** A workflow's `GITHUB_TOKEN` is scoped to *this* repository. The exit-node
  repository has no deploy key and this repository has no secret (`gh api .../actions/secrets` →
  empty), and `actions/permissions/access` is `none` — which governs reusable workflows anyway,
  not `git clone`.

So a build pinned that way is a build nobody can run, **CI included**, and CI is what decides
whether a branch may merge. `RUNBOOK.md` §2's bar — green locally, then green in CI, with the same
script — would have been unreachable for every task from here to the end of the phase.

The smallest decision consistent with the spec was to bring the library across the way this
repository already brings another repository's files: **`spec/` is a checked copy** of the design
repository, written by a script, held byte for byte against `spec/MANIFEST.txt` by
`specsync.py verify`, and never edited here (`spec/README.md`, `tasks/README.md`). The task itself
asks for the fakes and the fixtures that way ("**The fakes and the fixtures, by checked copy**"),
for the same reason. Extending it to the library's own sources changes *how the bytes arrive* and
nothing about what they are:

| | the task's way | what was built |
|---|---|---|
| where the bytes are | `managed_components/twinoak__agent-core/`, fetched at build | `components/agent-core/`, in the repository |
| the pin | `version:` in `idf_component.yml` + the sync manifest | the `# source: … at commit …` line of each tree's `MANIFEST.txt` |
| two places, held equal | a test | the same test, over the two manifests |
| the library edited here | never | never — and now checkable: `-Verify` re-hashes all 159 files |
| who can bump it | anybody with a build | a machine that can read the upstream repository |
| CI | cannot run | runs, and verifies the copy |

What it costs is the last row but one, and that is the honest price: nobody can bump the library
without a clone of a private repository. The weekly watch is meant to be that machine and needs
one secret to be it, which is the open item in `FOLLOWUPS.md`.

**What would restore the dependency**, when somebody wants it: the exit-node repository made
public, or a *Contents: read* token available to both the container and CI. `docs/upstream.md`'s
*How the library gets here, and why it is a copy* says what would change — `main/idf_component.yml`
gains the three-line block, `host_test/CMakeLists.txt` points `AGENT_CORE` at
`managed_components/twinoak__agent-core`, and the sync script keeps the fakes and the fixtures
(which the component manager does not carry: they are not part of the library). **Not one line of
tasks 02–05 changes either way** — the include path is `<agent/X.h>` in both.

### The copy brings two fixture sets, not one, and upstream's `platformio.ini`

The task names `tests/fixtures/contracts/`. `test/support/Fixtures.h` — which both suites include —
`#error`s without **`COMPANION_DIR`** as well, and `FakeMesh` answers from the transcribed MeshCore
frames of `tests/fixtures/companion/`, so that set had to come too (the library's own
`docs/library.md` §12 says both directories come in as defines; the task's list was short). Each
set keeps its own upstream `MANIFEST.txt`, naming the meshmaster.dk commit it is from — `0595dc2`
for the envelopes, `f518ebd` for the frames — because the two move for different reasons.
Upstream's `platformio.ini` came across as well, for its `[meshcore]` pin, which is the only way
the runner's `Citations` case can check that a fake's citation names a commit; it is 5 kB and it is
in the manifest like everything else. 159 files in all: 54 under `components/agent-core/`, 105
under `host_test/agent-core/`.

### A new `deps` step in `tools/verify.sh`, before the host tests

The task asks `host_test/` to compile the library "from the managed-components checkout (the same
bytes the board gets)". ArduinoJson *is* a managed component, and the host-tests step runs before
the build step — so the component manager has to have run first. `verify.sh` gained an eighth step,
`deps` (`idf.py reconfigure`, 10–14 s), which resolves `managed_components/` and prints
`dependencies.lock`; the build step then reuses the very configure it did, so nothing is done
twice. Its by-product is that `dependencies.lock` is now written by a step of its own rather than
as a side effect of the build. `step_build`'s three `idf.py` invocations and the `sdkconfig.defaults`
stamp were factored into one `idf_run()` so that both steps pass the same cache variables.

### `host_test/core/console/test_console_grammar.cpp` no longer walks the copied library

Its *no file but the parser matches a command word of its own* case walked everything under
`components/`, and six lines of the agent core compare the job type `"status"` — which is also a
console command of ours and means something else entirely. The library is not our grammar and is
never edited here, so `firmwareSources()` in that file now skips `agent-core`, with the reason
written down. The same exclusion went into `tools/check_rails.py`'s `sources()`, so that all
fourteen existing rails keep exactly the scope they were written with; the one entry that *is*
about the copy is the new entry **A**, which names both trees itself.

`host_test/core/net/test_trust_rail.cpp` deliberately **does** walk it: the library makes no socket
of its own, so its greps must find nothing there, and a bump that brings a TLS setting into the
library fails that test. Its comment now says so.

## Decisions taken without asking

- **The copy over a credential.** Above. Had a secret been the answer, it would have been a secret
  in CI *and* one inside every session's container, for bytes that are already in this repository
  and verified.
- **`components/agent-core/` rather than `managed_components/` or a `third_party/` of its own.** It
  is a component of its own, under `components/` where a reader looks for one, picked up by the
  ESP-IDF without an `EXTRA_COMPONENT_DIRS`; `components/core/`'s no-ESP-IDF rule is unaffected
  (the library is not under it). Everything that scans "our code" excludes it by name, in one place
  each.
- **`-std=c++17` for the library and its suites, not this repository's `gnu++17`.** Forced: see the
  first upstream finding. `twinoak_ours()` gained an optional dialect argument rather than a second
  copy of the flag list.
- **GoogleTest 1.17.0, by release tarball URL and SHA-256, for those two binaries only.** The
  version upstream's `[env:native]` passes the suites with. `FetchContent` with `URL_HASH` is a hard
  pin — no tag, no branch — and the download lands in the build volume, so only a cold run fetches
  it (a cold run needs the network for the managed components anyway). This repository's own tests
  stay doctest; nothing of ours links GoogleTest.
- **`main/agent_anchor.cpp` anchors five functions, which keeps all twenty-two objects.**
  `AgentLoop::wake`, `AgentLoop::loop` and `JobRunner::claimAndRun` reach twenty of them;
  `ConfigReply.cpp` and `LogRing.cpp` are reached by nothing *in* the library — they are a
  consumer's to call — so `parseAgentConfig` and `LogRing::copyTo` are anchored by name. The
  volatile read is in that translation unit and `app_main` only keeps what it returns, which is the
  shape `core/image/verdict.h`'s anchor established: a volatile pointer-to-member written directly
  in `app_main` is elided and the library goes with it.
- **The two manifests exclude a root-level `MANIFEST.txt` and `README.md` from themselves**, as
  `specsync.py`'s `LOCAL` does, so that a note this repository writes about a copy is not part of
  the copy. A `README.md` *inside* a copied tree — the fixtures each have one — is upstream's and
  is in the manifest.
- **`-Verify` runs on the host, in `tools/verify.ps1`, before the container starts**, which is what
  the task asked ("`-Verify` runs in `tools/verify.ps1` and CI"). It is one reading of the manifest
  format and it needs no network and no clone. The *pin*'s two places are held equal twice over —
  there and by a host test — because that is the one thing a checkout which never runs the script
  must still be held to.
- **No bench lines.** Nothing on a board changes (the task says so), so `docs/bench.md` is
  untouched and *Not verified here* below is the empty list it ought to be.

## Reported upstream (diffs for the exit-node repository)

### 1. A parameter named `unix` makes `ConfigReply.cpp` unbuildable on a Linux host in any GNU dialect

GCC predefines `unix` as `1` in every `gnu++` dialect on a Linux target, so
`uint32_t& unix` becomes `uint32_t& 1` and the file is fifteen errors — `'err' was not declared in
this scope`, `too many arguments to function 'takeTime'`, and so on. The board build never sees it
(the xtensa cross compiler has no such predefine) and upstream's own
`tools/check-library-host.py` is `-std=c++17`, strict, where `unix` is not defined — which is why
nothing there catches it. Any consumer that compiles the library as part of a tree built in a GNU
dialect, as this repository's own code is, hits it immediately.

```diff
--- a/lib/agent-core/src/ConfigReply.cpp
+++ b/lib/agent-core/src/ConfigReply.cpp
-bool takeTime(JsonObjectConst obj, char* text, size_t textCap, uint32_t& unix, char* err, size_t cap) {
+// `unix` is not a name a parameter can have: GCC predefines it as 1 in every gnu++ dialect on a
+// Linux host, so a consumer compiling this file as gnu++17 gets fifteen errors here.
+bool takeTime(JsonObjectConst obj, char* text, size_t textCap, uint32_t& epoch, char* err, size_t cap) {
   const char* s = obj["serverTime"];
   if (s == nullptr) {
     say(err, cap, "missing: serverTime");
     return false;
   }
   std::snprintf(text, textCap, "%s", s);
-  if (!parseUtc(s, unix)) {
+  if (!parseUtc(s, epoch)) {
     say(err, cap, "serverTime is not a UTC timestamp");
     return false;
   }
   return true;
 }
```

Worked around here by giving the library and its suites the strict dialect
(`twinoak_ours(agent_core c++17)`), with the reason in `host_test/CMakeLists.txt`. Worth adding a
`gnu++17` pass to `tools/check-library-host.py`: it is the dialect a consumer is most likely to be
in, and it costs one more compile.

### 2. ArduinoJson 7.4.3 trips `-Wmaybe-uninitialized` on GCC 13 at `-O2`

```
ArduinoJson/Object/ObjectImpl.hpp:36:21: error: '<anonymous>.…CollectionIterator::nextId_'
    may be used uninitialized [-Werror=maybe-uninitialized]
   36 |     return iterator();
```

attributed to `ConfigReply.cpp` and `JobEnvelopes.cpp` — the two sources that include ArduinoJson —
because the diagnostic survives inlining and an `-isystem` include path does not silence it. The
board build does not see it: ESP-IDF exempts the whole of `-Wextra` for a managed component. Turned
off per source file here, the way `core/third_party/tweetnacl/tweetnacl_verify.c`'s two exemptions
are, so every other warning in those two files is still an error. Upstream may want the same
exemption in its host check, or a newer ArduinoJson. This is the dependency's warning and not the
library's.

## Not verified here (and why)

Nothing on a board changes. The library is linked and called by nothing until task 05 puts
`AgentLoop::wake()` behind the backend seam, so there is no bench line to add and `docs/bench.md`
is untouched — `tasks/phase-4/06-the-rails-and-the-bench-again.md` writes §§15–16 for the agent

library's static buffers take is in the build's own figures above and does not need a board to
confirm.

Two things need a person rather than a bench, and they are the open items in
`tasks/phase-4/FOLLOWUPS.md`:

- **the decision about the copy** — leave it as it is, or make the exit-node repository public and
  let the component manager do it;
- **`AGENT_CORE_READ_TOKEN`**, without which the weekly watch cannot look at upstream at all:
  `gh secret set AGENT_CORE_READ_TOKEN --repo twinoak/twinoak.meshcore.walter-firmware`, a
  fine-grained token with *Contents: read* on the exit-node repository and nothing else. Then *Run
  workflow* with `version = 0.1.4` is the rehearsal that acceptance criterion four asks for, and
  the pull request it opens is the thing to close.
