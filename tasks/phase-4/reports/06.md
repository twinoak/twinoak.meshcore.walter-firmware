# p4-06 — The rails and the bench, again

Phase 3's last task made every promise of this firmware a test or a grep in one place. Phase 4
added an agent with promises of its own, inherited from the firmware its library came from — and
the exit-node repository's tests hold those at the library's seams, where this firmware's end of
them is invisible. **This task holds that end**: seven new entries of
[`tools/check_rails.py`](../../../tools/check_rails.py) (R15…R21), two existing ones widened
(R9 and R7), and one test most of them rest on — the month of task p4-05 with everything that
could leak planted in it, and then every place this unit writes anything searched for all of it.
**Twenty-four entries, all holding.**

Three things a reviewer should read first, all under *Deviations*:

1. **R20 did not hold as the task worded it.** "Nothing starts an update but a claimed job or a
   console command" has a third door: the supervisor's golden-image rung. It is the unit looking
   after itself rather than a server reaching in, so the rail names three doors and holds the
   supervisor to `Kind::kRoleRepeater` and to naming no candidate slot. R14's name was stale for
   the same reason and is now *none in a wake without one*.
2. **Nothing in the bench had ever set the library's log sink**, so no test of a wake could see
   what the copied library logged — including task p4-05's checklist line about searching "the log
   capture over the month". `wake_bench.h` now wires it exactly as `main/main.cpp` does, and the
   rails' month searches 1 467 of its lines.
3. **R9 is *never written down*, not never sent.** A job's result and an observation batch carry
   what the mesh said, because that is what the server asked for; so are the bytes of a result
   kept in flash across a sleep. The rail is the console's ring, the library's log, the journal
   and the retained records — and the test says which of the two lists each place is searched
   against.

## Deviations from the spec or the task

### R20: the supervisor is a third door into an update, and the task's table names two

"Nothing starts an update but a claimed job or a console command" is **not** what the firmware
does: `components/core/supervisor/supervisor.cpp`'s golden-image rung calls `RadioUpdate::start`
when it finds that the chip no longer holds the golden image (`docs/supervisor.md`, rung 4). That
is by design and predates phase 4 — it is the unit looking after its radio with no server in the
loop — so the honest rail is **three doors**, and the entry holds what makes the third safe rather
than pretending it is not there:

- the supervisor names `update::Kind::kRoleRepeater` and nothing else it can *start* (it reads
  `kFirstInstall` to recognise one), so the rung can put back what the store already calls golden
  and can never flash a candidate;
- it names no `Which::kCandidate`, so no image a server offered is reachable from the ladder;
- and it is inside the daily caps and the battery rule, which rail R11 holds.

Four call sites of `RadioUpdate::start` (the wake cycle's ask, the console, the agent's apply job,
the supervisor's rung) and three of `SelfUpdate::switchNow` (no supervisor: the ladder never
switches the Walter's own image). The entry prints all seven.

### The library's log was captured by nothing, and task p4-05's report overstates one line

Task p4-05's checklist says *"the month runs with the agent's log sink into the console's ring and
searches it"*. The month asserts a great deal and searches nothing, and — the part worth fixing —
**`host_test/.../agent_half.h` never called `WalterPlatform::beginLog`**, so in every test of a
wake the library's `mm::log*` lines went to a null sink. A rail about what is written down cannot
be held against a log nobody collected, so `wake_bench.h` now wires the sink exactly as
`main/main.cpp` does — into the life's console (and so into the four kilobytes `dump` prints) and
into a string that outlives every life of the Walter — at the `log.level` setting, which the rails'
month turns up to `debug`. It collected **1 467 lines** over 200 wakes, and they are searched. No
test changed its expectations because of it; the one risk (library lines appearing in `dump` where
a test counts its contents) did not materialise.

### R9 is "never written down", not "never sent"

The task's table says *the log capture and the journal searched for every payload `FakeMesh`
produced and every observation's name*. Searching **everything** for them would be wrong, and the
test says so where it could be read as a weakness: a `config.read` job's result **is** what the
neighbour said, and it goes to the server that asked for it over TLS; an observation batch **is**
the stranger's name; and a result the server would not take is kept **in flash** across the sleep,
so those bytes are in the kept-image window on purpose. The password and the token are searched
for everywhere including both of those; what the mesh said is searched for in the console's ring,
the library's log, the summaries, the journal and the retained records. This is the same shape as
phase 3's R9 (`rak text` shows a person a line and `dump` does not carry it afterwards) and the
file's header carries the table.

### The rails' month is 200 wakes, not 300, and it is a second month

Task p4-05's month (300 wakes) is unchanged and still runs. The rails' month is a **second** one
with the same bench and different content — the jobs that carry a password, the adverts with
names, an offer for the wrong slot — and 200 wakes is what covers all of it with the week away
still in it. The two together cost 4.6 s of the suite's 228 s. Making one month serve both would
have meant task p4-05's assertions and this task's needles in one case, and a failure that could
not say which rail it was.

### `test_rail_agent_month.cpp` lives in `host_test/rails/` and is compiled elsewhere

The task says the rails table is `host_test/rails/` and `tools/check_rails.py`. The agent's month
needs the library's own simulated stock repeater, which asserts with GoogleTest, so the file is in
`rails/` with its brothers but `host_test/CMakeLists.txt` removes it from `core_tests`' glob and
adds it to `agent_backend_tests` — two lines, with the reason in a comment. The alternative (a
sixth GoogleTest directory, or GoogleTest linked into `core_tests`) would have put the rail
somewhere a reader of `rails/` would not find it.

### The specification was not found wrong, and nothing in `spec/` was touched

`python spec/tools/specsync.py verify spec` passes (rail R13). The gaps the five reports raised are
collected in [`tasks/phase-4/FOLLOWUPS.md`](../FOLLOWUPS.md) under *After the run*, each with the
**repository it belongs to** — the hardware repository (link 1.1: `overheard` and a count by type,
§6.2's ceiling sentence or a `REPLY_CANCEL`, and `STATS_GET`/`NEIGHBOURS_GET` so that a `status` or
`neighbours` job for the unit's *own* repeater is served over the UART instead of `failed`), the
exit-node repository (the library's two missing advert fields, and `docs/library.md` §11's sentence
that the link has no trace), and meshmaster.dk (what a budget-stopped download reports, the
self-apply's late result, and what `X-Agent-Version` should carry). The bench pile's own agent
items are in the same place.

## What will be wrong first with the real server

The honest list the task asks for: what in the agent is most likely to be wrong when the first unit
talks to the real meshmaster.dk, hardest first, with why. Every item is a thing no simulator in
this repository can reach, because every simulator here was written from the same documents the
firmware was.

1. **The heartbeat's shape against the real serialiser.** Every body this firmware posts is the
   library's own, held byte for byte against meshmaster.dk's contract fixtures at `79b1e9c` — and
   a fixture is what the server's tests *said* it accepts, not the server. A field the real
   `Envelopes.cs` requires and the fixture made optional is a 400 at the first wake of the first
   unit, and the unit will report it as *the body did not fit* or *http 400* and keep trying on its
   interval. First thing to look at, and the cheapest to fix.
2. **The clock, and `at` on a unit that has never attached.** The heartbeat's `at`, the lease
   arithmetic and the journal's timestamps all come from the network's time, and a unit whose modem
   has not yet answered `AT+CCLK?` has none. The library stamps what it can and the server has its
   own `serverTime`; which of the two wins where is exactly the kind of thing two implementations
   disagree about silently, and the symptom is a job reported `late` or a lease that looks expired
   the moment it arrives.
3. **The lease, the budget and a wake that is minutes long.** `maxTransactionsThisWake` and
   `nextCheckInS` are this firmware's promises; `minGapSeconds` and `maxTransactionsPerMinute` are
   the server's. A real cell's attach time (two minutes, guessed) plus a real job's round trips may
   not fit inside a wake that also has to sleep, and the first symptom is a lease that expires
   mid-job — which this firmware handles by posting nothing, and which the server sees as a unit
   that claims and never answers. §18's day is the measurement.
4. **The firmware routes.** `{base}/manifest.json`, its signature and `{base}/files/{name}` are
   `unit-protocol.md` §4 as read; the server's own range handling, its ETags and whether it serves
   the signature at all are not things a scripted server can be wrong about in the same way the
   real one can. A download that resumes against a server which ignores `Range` would silently
   fetch the whole file every wake, and the only sign is the bytes on the SIM.
5. **The keyless heartbeat, and the moment a key appears.** A unit registered before its repeater
   sends a body with no `companionPublicKey` and an empty `jobTypes` (`FOLLOWUPS` `[04]`), and the
   server is supposed to keep the key it had and show *radio not identified*. Both halves are
   written against a fixture that **does not exist yet** (`AgentHeartbeatNoKey.json` is pile 4.16's
   task 132), so this is the one body in the whole phase that was built from a sentence rather than
   from bytes.
6. **`transport: native` and what the server routes by.** This unit advertises thirteen mesh job
   types plus four `twinoak.*` ones, and advertises the four even before the radio has a key
   (p4-05's deviation). If the server routes a job type it did not expect from a `native` agent, or
   refuses to route one this unit offers, nothing on the unit's side will look wrong at all — the
   page simply never hands it a job.
7. **A 401 halting the loop.** The library stops on a refused token and this firmware raises an
   attention for it; a server that answers 401 for *anything* other than a bad token — an expired
   registration, a unit moved between accounts — would stop a healthy unit until somebody types a
   new token at the cable. The blast radius is one unit and the cure is a cable, but the first
   person to see it will think the token was mistyped.
8. **The observation batch.** The adverts this unit hears go up in a batch whose fields were mapped
   from MeshCore's `app_data` by reading `AdvertDataHelpers.h`. A name that is not UTF-8 after all,
   a position scaled differently, or a batch the server refuses whole for one bad record: the ring
   fills, the drops are counted, and the symptom is a unit whose observations never appear.
9. **The kept image across a sleep.** A result the server would not take is written into a flash
   window and read back by the next wake — the one piece of phase 4 with no second net under it. A
   torn record is refused whole (the library's own rule) and the result is lost, which is correct
   but silent; if the window's addressing is wrong on a real partition, every refused result is
   lost and nothing says so.
10. **The energy of a wake that actually works.** Every budget in `core/cycle/wake_cycle.h` was set
    against a wake that heartbeats and sleeps. A wake that attaches, claims two jobs, puts four
    packets on the air and downloads a megabyte is the first wake nobody has measured, and the
    interval table is written in watt-hours that assume the quiet one. §18's last item is the
    number that settles it.
