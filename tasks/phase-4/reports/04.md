# p4-04 — The platform and the identity

The third seam is filled and the unit has a name for itself. `components/agent/walter_platform.h`
is `mm::IPlatform` and the `mm::IClock` behind it; `identity.h` is who this exit node says it is,
read from the radio over the box link and from this firmware's own tables and **from nothing a
person types**; `observations.h` drains §7's `OBS_PULL` into the library's advert ring with
MeshCore's own `app_data` decoded; and `core/cycle/agent_attention.h` is the Walter's own
attention — a 401, and a restart the library asked for and did not get — as a byte of the duty
cycle's retained record, a letter in the wake record and a line in `status`. Three console
commands read all of it (`agent id`, `agent heartbeat`, `agent obs`), and the proof the task asked
for is that **the heartbeat body equals meshmaster.dk's own contract fixture** for the scripted
identity, with six named substitutions and no other difference — and equals, byte for byte, the
body the copied library's own `AgentLoop::wake()` posts when it is driven over the same identity.

Done in one session. Two things are not as the task wrote them and are the first things a reviewer
should read, both under *Deviations*: **the radio block is `get radio` and not `get freq`** —
there is no `get bw`, `get sf` or `get cr` on a MeshCore console at all, and the specification's
own fixture is the `get radio` exchange — and **`rebootForHealth` is `[[noreturn]]`**, so "does
not reboot" had to be resolved rather than asserted.

## Every field of the identity, and where it comes from

Nothing in this table is typed by a person, and nothing of it is a setting.

| field | source | cost |
|---|---|---|
| `companionPublicKey` | §5.6 `IDENTITY`'s 32-byte key, as 64 lowercase hex. This exit node **is** its repeater (S-1), so the repeater's MeshCore key is the key the server knows the unit by | one request, once a boot |
| — the name beside it | §5.6's `name`, the repeater's advert name. Printed by `agent id` and **sent nowhere**: it is not a heartbeat field | the same request |
| `companionFirmware` | §5.1 `HELLO`'s `fw_version`: the **repeater firmware's own release version** (`0.1.0+abc1234` in the fixtures) | free - the session copied it |
| `agentVersion` | `core::version()` - this firmware's | free |
| `board` | `walter`, a constant of ours | free |
| `transport` | `native`, meshmaster.dk's word for an exit node that is its repeater (EXIT-NODES §2, `AgentTransports`) | free |
| the radio block (freq, bw, SF, CR) | §5.7 `CLI get radio` → `> 869.618,62.5,8,8`, parsed | one request, once a boot and again when stale |
| `jobTypes` | **the library's own**, from `IMesh::supports()` over its thirteen and then the extension's | no request: `MESH_CLIENT` in the session |
| `budget` | the server's, kept by the library between calls | — |
| `at` | the clock below | — |
| `queueDepth`, the six `errors` | the loop's and the runner's; this task fills the three it can and task p4-05 the rest (`HeartbeatExtras`) | — |
| `nextCheckInS` | the interval policy's decision for the band, in seconds (phase 3, task 04) | — |
| `maxTransactionsThisWake` | the per-band table below | — |

**When each is read again.** The key once a boot, and again whenever `boot_id` changes - §5.1: a
restart means every per-boot thing we hold about the radio is gone. The radio block after the key,
and again when `radioSettingsStale()` has been called: a `set` line that crossed the local door
for the unit's own repeater may have moved exactly those four numbers. The three `HELLO` strings
at every refresh, because they cost nothing. **A refresh with nothing to do makes no request at
all**, and a refresh with no session makes none either - opening one is `HELLO` and that belongs
to whoever runs the wake (the supervisor's check at step 2, or `rak hello`).

**A radio with no identity is not a failure.** A RAK with no application answers §5.6 with a key
of all zeros, which is not a key; `rak role scanner` leaves no session at all. Either way
`known()` is false, the heartbeat carries no `companionPublicKey`, no `companionFirmware`, no
`radio` block and an **empty** `jobTypes`, and the unit still checks in - alive, with its repeater
*not identified* (`FOLLOWUPS.md`'s `[04]`, meshmaster.dk's p4.16-132). The key is asked for again
at every wake while there is none, which is one §5.6 request a wake and is what makes *the
identity appearing between two wakes* work; both bodies are held against fixtures (below).

### The per-band intent

`mm::WakeIntent`, EXIT-NODES §6's two optional fields. The interval is the duty cycle's own
decision; the cap is a table written in the library's **own arithmetic**, so a release that
reprices a job moves it:

| band | `nextCheckInS` | `maxTransactionsThisWake` | why |
|---|---:|---:|---|
| `plenty` | 900 | 74 | `kClaimMax` (2) × the dearest job there is (37: a `config.read` of `kMaxConfigKeys` keys, the two extras, `regions`, the login and the ACL restore) |
| `normal` | 3600 | 37 | half of it: one worst-case job, or several ordinary ones |
| `saving` | 21600 | 21 | one *real* job's worth - the daily `config.read` of the server's own default key list, which is what `configReadTransactions(nullptr, 0)` prices |
| `critical` | 86400 | **0** | the modem is not brought up at all in this band, so the intent is moot - and 0 is the library's own *proposes nothing*, which leaves the field out of the body rather than promising a wake that will not happen |
| `no-reading` | 3600 | 37 | the medium one, as `kUnknownMinutes` is `kNormalMinutes` |

Five placeholders, every one with a row in `docs/bench.md`'s *What to bring back* (114 constants
now, in 20 files). The dearest-job figure is **not** a bench number and has no row: it is the
library's arithmetic, and a `static_assert` holds that a `config.apply` of the most commands one
may carry is cheaper than it, so the next bump of the library fails here rather than drifting.

## The observation mapping, record for record

§7's record → `mm::HeardAdvert` (`agent/Observations.h`). The two records every test uses are the
specification's own fixture (`observations: two adverts`), whose `app_data` is a real MeshCore
advert payload.

| §7 | `mm::HeardAdvert` | |
|---|---|---|
| `pubkey` (32 B) | `publicKey` | |
| `age_s` | `heardAtMillis` = this clock's now **less** `age_s` | §7 measures it, so it is right whatever either clock said. `heardAtEpoch` is left 0 on purpose: the library stamps a pushed advert from `heardAtMillis` and its own clock, and "the mesh never sets it" |
| `snr_q4` | `snrQ4` | quarter-decibels, as the air carries them |
| `rssi` | `rssi`, with §7's `0x7FFF` mapped to the library's `kNoRssi` | absent is not zero on either side |
| `path_len` bits 5–0 | `hops` | |
| `path_len` bits 7–6 + 1 | `pathHashSize` | |
| `path` | `pathBytes` / `pathByteLen`, bounded at `kMaxObservationPathBytes` (24) | eight hops at three bytes: further than an advert worth reporting has travelled |
| `app_data` byte 0, low nibble | `advType` → the library's `roleName()` | `ADV_TYPE_*` of MeshCore's `AdvertDataHelpers.h` at `d9296435` |
| `app_data` `0x10` + 8 B | `hasPosition`, `latE6`, `lonE6` | two little-endian `int32` of degrees × 1e6 |
| `app_data` `0x80` + the rest | `name`, bounded by the field (32) and then by the library's own `validUtf8PrefixLength` | a JSON string has to be UTF-8 and this is whatever a stranger typed |

**The gaps**, all three small and none of them a specification request:

1. **`adv_ts` has nowhere to go.** §7 carries the timestamp *inside* the advert; the library's
   struct has only when *we* heard it, which is what the server's `Observation.At` means
   (`Envelopes.cs`). Nothing is lost that the server has a field for.
2. **`ADV_FEAT1`/`ADV_FEAT2` have nowhere to go.** MeshCore reserves two `uint16` for the future
   and `HeardAdvert` has no field for them, so `ObservationFields.Flags` - which meshmaster.dk
   *does* have - is never sent. Their bytes are stepped over so that the name begins where the
   builder put it, and a test holds that. A library finding, not a link one, and worth nothing
   until MeshCore uses the bits.
3. **`rxByType` cannot be filled** (task p4-02's gap, repeated here because the ring is the other
   half of the same heartbeat): §6.4 has no count by payload type.

**Records of this unit's own repeater are dropped before they are kept.** The RAK hears its own
repeater advertise, and that repeater *is* this exit node; meshmaster.dk's 119 ignores such an
observation anyway, and the bytes are not worth an attach. **The drops are counted once**: §6.4's
`obs_dropped` is cumulative since the radio booted, so the first reading of a boot is a *baseline*
(nobody could have collected what was lost while this unit slept) and only the increase after it
is added to the library's `observationsDropped` - which is the name the reference agent uses for
its own ring's drops and the one the heartbeat carries. §7's per-pull `dropped` is recorded for the
console and **not** added, because adding both would count one loss twice; a test holds that.

A drain is bounded three ways and the report should say which bites: §7 answers as many records as
fit one 240-byte payload (four of a record with a path and application data, five of the smallest),
`max` is asked as `kMaxObservations`, and `kMaxPullsPerWake` is **16** - eighty of the smallest
records, more than the library's 64-entry ring holds, so the bound is never what ends a healthy
radio's drain. It is there so that a radio answering `remaining` for ever cannot hold a wake open,
and a test holds that too.

## Deviations from the spec or the task

### The radio block is `get radio`, one line and one request

The task says *the radio block … over the link's `CLI` (`get freq`, … — the exact lines from the
repeater's `docs/console.md`)*. The exact lines are not four lines, because three of them do not
exist. MeshCore's `CommonCLI::handleGetCmd` at `d9296435` has a `radio` branch -

```cpp
} else if (memcmp(config, "radio", 5) == 0) {
  sprintf(reply, "> %s,%s,%d,%d", freq, bw, (uint32_t)_prefs->sf, (uint32_t)_prefs->cr);
```

— and a `freq` branch that answers the frequency alone; there is **no `get bw`, no `get sf` and no
`get cr`**. So `get radio` is not a shortcut, it is the only line that carries all four, and the
specification's own fixtures say the same thing: `spec/fixtures/link/link-v1.json`'s *cli request*
**is** `get radio` and its *cli response* **is** `> 869.618,62.5,8,8` - the same four numbers
meshmaster.dk's `tests/fixtures/contracts/RadioParameters.json` carries. The task's `docs/console.md`
is also not in the repeater firmware (it has none); `CommonCLI.cpp` at the pin is what was read.

The parse is a hand-written decimal reader and not `strtod`: locale-free, and `869.618` is built as
`869618 / 1000.0`, which is the nearest `double` to that decimal and so the same `double` the
server's own `869.618` is. The four are bounded by what the repeater's own `set radio` accepts
(150–2500 MHz, 7–500 kHz, SF 5–12, CR 5–8) as a sanity check and not as a policy of ours: a reply
this end half understood is **no radio block**, which the heartbeat leaves out, and never four
numbers guessed at. Nine refused forms have a case each.

### `rebootForHealth` is `[[noreturn]]`, and this firmware does not restart

The task says it *journals and does not reboot*. The method's type says it **may not return**
(`agent/IPlatform.h`: `[[noreturn]]`), so three things cannot all be true, and the resolution
matters enough to spell out:

- it journals (kind `kAgentAttention`, with the library's own sentence) and raises the Walter's own
  attention for the wake record and `status`;
- it does **not** restart this board: `WalterPlatform` is given no `interfaces::Restart` at all, so
  it cannot, and a test says so;
- and then it yields for ever - one second at a time through the hal's delay, never a spin - and
  leaves the board to **the one thing that does own restarts**, the bound on the wake
  (`core/cycle/wake_guard.h`, armed by `main/` at every boot). The supervisor and the wake cycle
  own restarts, which is exactly what the task asked for; what the platform refuses is to take
  that decision itself.

**The path is unreachable in this firmware**, and that is the point: in one-wake mode the library
never calls it (`AgentLoop.cpp`: *in one-wake mode the guard is told and not taken*; the report
says `rebootWanted` and the reason, and task p4-05 reads it). It is a guard on a door the Walter
keeps shut. `selfReboots()` is 0 for the same reason: the heartbeat's `reboots` counts restarts
made *that way*, and this firmware makes none. A build with a USB host on the port would sit there
until a person pressed reset - said here because it is the one unattractive corner of the choice,
and it costs nothing because nothing reaches it.

### `companionFirmware` is the repeater firmware's version, not the MeshCore tag

The task says *`HELLO`'s `fw_version` … read what the repeater firmware's `ver` reports and what
meshmaster.dk's `FirmwareVersion.Parse` accepts*. Three readings, and they do not all agree, so
here is what was read:

| | |
|---|---|
| `HELLO`'s `fw_version` | `TWINOAK_FW_VERSION` - the **twinoak repeater firmware's release version** (`src/common/version/Version.h` of the repeater firmware: "`fw_version` is the release's version alone and `upstream` is what it is built on") |
| `HELLO`'s `upstream` | `<meshcore tag>+<pin8>`, e.g. `repeater-v1.17.1+d9296435` |
| the repeater's `ver` | `twinoak-repeater 0.1.0 on MeshCore repeater-v1.17.1 (d9296435) (Build: …)` - all three in one line |
| meshmaster.dk has **two** `FirmwareVersion` types | `Register/FirmwareVersion.Parse` splits a reading into a token and a detail and **accepts any string**; `Configuration/FirmwareVersion.TryParse` reads three numbers for *does this firmware know this key?* |

`companionFirmware` is fed to the first of those (`Register`), and to
`FirmwarePageRules.ReleaseOf(flat, FirmwareProducts.Repeater, …)`, whose `SameVersion` forgives a
leading `v` - so the field is looked up against the **Repeater product's** releases, which for a
unit of this design are twinoak's and not MeshCore's. `HELLO`'s `fw_version` is therefore right and
the task is right; the Heltec sends its MeshCore tag here only because on that board the companion
firmware *is* MeshCore. The MeshCore tag is not lost: `agent id` prints it from `upstream`, and the
version the key-range question uses comes from a `config.read`'s own `ver` reply and not from the
heartbeat. Checked, and no finding for meshmaster.dk.

### The job type list is not reduced by the local door — and `failed`, not `unsupported`, is why that works

The task asked for this to be said in the report and in §13, and to be checked against
meshmaster.dk's `EligibleAsync`. Both are done, and the check turned up something worth reading.

The list the heartbeat carries is **every type the mesh can carry** and is not reduced by task
p4-02's local-door table: `supports()` is asked per *type* and not per peer (it is what the
heartbeat advertises), and a unit that stopped advertising `status` would stop answering `status`
for a *neighbour*, which it does perfectly well. So a `status` or `neighbours` job for the unit's
**own** repeater is routed here and comes back as a failure.

What kind of failure matters, and task p4-02 chose the right one. `EligibleAsync` in
`src/MeshMaster.Core/Transport/AgentProtocol.cs` does hand a job on - *"§9 step 4: the retry goes
to the next candidate. Who has tried is what the result rows say"* - but only for a job that was
**requeued**, and `Settle()` decides that:

```csharp
var retryable = outcome is Outcome.Unreachable or Outcome.Timeout or Outcome.Failed
    || (outcome == Outcome.Unauthorized && job.CredentialCandidate == CredentialCandidates.New);
return retryable && job.Attempts < job.MaxAttempts ? (JobSettlement.Requeued, reason) : (JobSettlement.Failed, reason);
```

`Outcome.Unsupported` is **not** retryable - *"a refused login and a firmware without the feature
do not get better on the next exit node"* - so a job answered `unsupported` is over, and no other
candidate sees it. The local door answers `Failed` (*the packet could not be built*), which **is**
retryable and whose `MaxAttempts` default is 2, so the job is requeued, the result row this unit
left excludes it from the next claim, and the next candidate gets it. **The routing does try the
next candidate, and it does so because the door says `failed` and not `unsupported`** - the task's
own wording expected `unsupported`, which would have failed the job outright. Nothing for
meshmaster.dk's pile; one sentence for `docs/ARCHITECTURE.md` §13, which now has it.

### The wake's drain has no caller in a wake yet

The task's deliverable is *`OBS_PULL` drained at each wake*. `Observations::drain()` is written and
tested, and **nothing calls it from a wake**: the wake's eighth step is the backend seam and
`core::cycle::WakeCycle` is `core/`, which cannot name `components/agent/` (agent/ is built on
core/, not the other way round). The one place a drain belongs is behind the seam, and the seam is
task p4-05's `AgentBackend`. What exists today is the caller a person has: `agent obs pull`, which
is the §7 drain by hand and is what `docs/bench.md` §17 walks. The same is true of the identity's
`refresh()` at a wake - `main/` calls it once at boot and the console calls it per command.

### The library's observation ring is `main/`'s for one task

`AgentLoop::begin()` hands the loop's **own** ring to the mesh (`mesh.setRing(&ring_)`), so from
task p4-05 the ring is the loop's. Until then `main/` owns one, because a drain with nowhere to put
a record is a drain nothing can be shown with. It is 7 440 bytes of DIRAM that p4-05 reclaims, and
the comment in `main/main.cpp` says so where somebody will read it.

### `NetworkClock` learnt where its time came from

`takeServerTime()` had to tell "the Walter's clock keeper … so that the radio's `TIME_SET` of the
next wake has the better source" (the task). §5.4's `TIME_SET` carries a source byte, and phase 3's
`NetworkClock` reported source 1 (the cellular network) for whatever it held - so a server time
given to it would have been announced to the radio as the network's. It has `giveFromServer()` now
and remembers which it was: source 2 for the server, 1 for the network, and a time that came off
the network **wins** over the server's (the library's own rule, and the right way round - the
network's is the modem's own clock and the server's has a round trip in it). The window
`core/uplink/clock_window.h` judges by applies to both, so a server that answers 1970 is refused
exactly as a modem that does.

### A contract fixture this repository does not have a copy of

`FOLLOWUPS.md`'s `[04]` asks for the keyless heartbeat to be held against
`AgentHeartbeatNoKey.json`, *"if it is not on meshmaster.dk's `master` when this task runs, build
the expected body from `AgentHeartbeat.json` minus the field and say so"*. It **is** on `master`
(added by `d8f12ca`, p4.16-132) - but it is not in this repository: the contract fixtures here come
across with the agent library, and that set is the exit-node firmware's copy of meshmaster.dk's at
`79b1e9c`, which is before the fixture existed. Re-pinning the library to bring the newer set
across is task p4-01's and not this task's, and editing a copied tree is forbidden. So the 220
bytes are in `host_test/fixtures/heartbeat_no_key.h` with their source commit named and a note
saying that the file goes when p4-01 next bumps the library and the fixture arrives properly. The
keyless body is held against them with three substitutions; `transport: native` and `jobTypes: []`
- the two the follow-up is about - are **not** substituted and match the server's example exactly.

### The console gained two things of its own

`Console::pump()` and `Console::agentLine()`, both public and both small. The first is what
`delayMs` runs: the radio's port read and one turn of this console, and **not the line editor** -
no byte is read and no command is started, so a pump cannot run a command inside a command; while
a command of this console is itself what is waiting, `tick()` is left alone too, because the
console is already on the stack (a `running_line_` flag, set by `runLine`). The second is where the
library's formatted lines go, so an agent line is on the port and in the ring `dump` prints like
every other line. There is still no third way out of the console.

### `agent obs pull`

The task names `agent obs` ("the ring: count, dropped, the last five"). `agent obs pull` is one
word more on the same command and is in the table, the document and the grammar test as one row.
Without it nothing could put a record in the ring before task p4-05 runs a wake, and the bench
item would be unwalkable. `agent obs` alone asks the radio nothing.

## Decisions taken without asking

- **The token's letter in the wake record is `u`, not `t`.** `t` is already *no time* in the same
  line (`steps …`), and a letter that meant two things in one line would be a letter nobody could
  read; a test holds every agent letter against every outcome letter.
- **The attention's byte lives in the duty cycle's retained record**, in one of the two bytes it
  kept spare. `interfaces/retained.h` has no slot left and says so (`kDutyCycle`: "the next task
  that wants a slot does not have one"), and what the byte has to do - survive a sleep, be read by
  the wake that follows - is what that record is for.
- **It is read at step 10 and cleared by the record that carried it.** Step 1 would be too early: a
  401 happens at step 8, and it belongs in *this* wake's record. Clearing it there means one raise
  is reported once and a condition that is still there raises it again at the next wake - which a
  401 does not, because the library halts, so it is reported once and `status` says it until a
  person fixes the token and the next wake's record is clean.
- **A 401 is not journalled; a refused restart is.** The journal exists so that an *update* is
  never guessed at and is 1024 entries; a token a person has to retype is a state, not news about
  work, and the letter and `status` are where it belongs. A restart the loop asked for and did not
  get is news precisely because nothing happened.
- **The journal entry's reason field is 44 bytes and truncates the library's sentence.** A journal
  payload is 48 bytes (`core/update/journal.h`) and the library's own `why` is up to 64, so its
  45-character sentence loses its last word there. `AgentAttention::lastWhy()` keeps the whole of
  it in RAM for `status`; the header says so and a test holds both.
- **`sourceName()` answers `network`, which is not one of the library's four words**
  ("sntp", "server", "rtc", "none"): the Walter's time comes off the LTE-M network's clock and not
  from SNTP, and saying `sntp` would be a lie in a log line. The library compares this against
  nothing - it is one argument of one `LOG` line in `JobRunner.cpp`, checked by grep - and
  `fromNetwork()`, which the library *does* decide on, is true for both the network's time and the
  server's, because both prove a packet of ours left this board and something answered.
- **`delayMs` pumps before it waits**, so a one-millisecond idle still pumps once: the library
  calls it with 1 in the loop where all of a job's time is.
- **The log sink is a free function through one static owner.** `mm::logSetSink` takes a plain
  function pointer; there is one platform on a board and one in a test, a later construction takes
  the pointer over, and the destructor gives it back - so a test's second rig cannot leave a
  dangling pointer for the next test's first log line.
- **The library's log level is the console's `log.level`**, mapped by a cast with a
  `static_assert` that the two enums are the same four words in the same order: a person who turned
  this port down meant the whole port.
- **Two new interfaces rather than one.** `interfaces/entropy.h` and `interfaces/heap.h`, because
  the table in that directory's README is one concern a row and a `Machine` of two unrelated
  methods would be two concerns in one. Both exist only because the library asks for them, and the
  headers say so.
- **The identity does not open a session.** A refresh with no session reads nothing and asks
  nothing: `HELLO` is the supervisor's check at step 2, or a person's `rak hello`, and an identity
  that opened one would be a second thing deciding when the radio is spoken to.
- **An all-zero key is not a key**, and the radio block is not read without one: a struct that
  said something about a radio we have not identified is a struct a later release could start
  sending.
- **The advert name reaches no console line.** It is in the ring (the batch the agent posts needs
  it) and nowhere else: `agent obs` prints the key, the age, the hops, the signal, the role and
  *whether* there was a position. §7 says it in so many words and the rail greps `dump` for it.
