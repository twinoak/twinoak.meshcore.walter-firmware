## The LTE update, as the code does it

`docs/flashing.md`'s new section is the walk; two things in it are worth having in the report
because they are findings and not transcription.

**1. It works, and nothing goes near github.com.** The only path to the Walter's own image over the
air is a `twinoak.fw.offer` whose `product` is `twinoak-walter-firmware`
(`firmware_jobs.h:90`), and for that product `runOffer` calls `Fetch::runInto` with the
`SelfUpdate` as the transfer target. The base URL is `{server.url}{base}` — meshmaster.dk — the
manifest at `{base}/manifest.json`, its signature beside it and the file at `{base}/files/{name}`.
Checks 1, 2, 3 and the manifest's half of 6 run before a byte of the image is asked for; 4, 5 and
the rest of 6 over the bytes as they lie in the other slot. The console's `fetch <base-url>` is the
only thing in the firmware that reaches github.com, and it writes a **radio** image and never this
one. So the phase-6 item about the modem refusing USERTrust ECC is not a blocker here, as `p8-06`
had already read.

**2. A radio image's download resumes and the Walter's own does not — and two messages say it
does.** `Fetch::fetchInto` resumes from `target.written()`, which the store's target answers from
its progress record; `SelfUpdate::beginWrite` sets `written_ = 0` and the platform's `beginWrite`
erases the slot, and every non-complete verdict calls `abandonWrite()`, which zeroes it again.
`describe(FetchVerdict::kBudget)` nevertheless says *the download resumes next wake*, and
`runOffer`'s budget branch logs and posts the same promise — true of a radio image, false of the
Walter's own, in a branch that already knows which it is in. **No code was changed for it** (this
task is documents and a tag, and the fix is two sentences in two files that a code task should own
with a test); it is written up in `tasks/phase-9/FOLLOWUPS.md` with the arithmetic that says
whether it bites: 763 616 bytes in twelve ranges against a megabyte and twenty minutes, which the
new bench item measures for real.

## Deviations from the spec or the task

- **README said the radio came back *with its identity*, and it did not.** The sentence — *the
  radio came back over its own USB-C from the repeater firmware's `.uf2` with its identity, which
  is the one promise that region boundary exists for* — was written on 7 November and is wrong:
  the radio's next `HELLO` carried a **new key**, meshmaster.dk logged `agent.companion_changed`,
  and its repeater had to be registered again as 41 where it had been 12. The cause is the
  repeater firmware's (the Adafruit core's `InternalFS.begin()` formatting a volume a torn page had
  made unmountable) and its own `v0.1.2` notes correct the same sentence in their own release.
  `docs/flashing.md` already has the whole reading (*A radio recovered by hand may come back with a
  new key*, task p9-04); README now says *came back as a **new node**, so its repeater had to be
  registered again*. The region boundary still holds — neither the flasher nor the `.uf2` writes
  `0xED000`–`0xF4000` — which is why the correction is about what the radio did and not about the
  promise.
- **`docs/field.md` said *a release key does not exist yet*.** *Until a release key exists, a unit
  accepts nothing … `trust` on the console says which keys this build accepts — today, none.* The
  key has existed since 20 October and three releases are signed with it. The paragraph now says
  what is true and keeps the reason the refusal is correct.
- **`docs/field.md`'s sentence about the Walter's own apply was half right.** It said the result is
  posted by the **next** wake. The trial's third condition *is* the heartbeat of the boot after the
  switch, and `AgentBackend::exchange` steps the trial to its end and calls `postOwedResult()` in
  that same exchange (`agent_backend.cpp`, *so that the result the Walter's own apply owes can go
  in this same wake rather than the next*). So it is the next **boot**, in that boot's own wake, and
  not an interval later. `docs/bench.md` §18's own item had it right already.
- **Four files were touched that the task names only in its *Spec* list.** `docs/bench.md` carries
  its own copy of README's state-of-things sentence and named `v0.1.1` as the release the walk is
  walked with, and its §1 named the `v0.1.1` file and banner; `docs/field.md`'s banner did the same.
  Both now say `v0.1.2`. `release-notes/v0.1.0.md` and `v0.1.1.md` were **not** touched: they are
  the bodies of releases that are published, and the corrections go in the new notes where a reader
  of the new release will meet them.
- **Nothing in `spec/` disagrees with this task.** `spec/FIRMWARE-MANIFEST.md` §§2–5 and the
  release tooling are untouched; the manifest this release publishes says `link 1.2`, which is
  p9-06's change and is held against the built image's descriptor by `build_release.py`
  (`ok  twinoak-walter-v0.1.2-factory.bin holds one descriptor … link 1.2`).
