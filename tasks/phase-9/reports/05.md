# p9-05 — agent-core with a local door

The library knew nothing about the local door, so it paced a job for the unit's own repeater like
a job on the air and asked it for a password that nothing at the other end of the UART reads. Both
of those were the exit-node firmware's to fix, and its pile 1.10 fixed them: `mm::IMesh` gained
`answersLocally()` (task p1.10-40) and `loginMaterialFor` asks that question **first** (p1.10-41).
This task brings the copy to the commit that has them and overrides the virtual.

The 34-line `config.read` of the unit's own repeater — job 22032 of 7 November, which reset the
Walter — now walks **3 420 ms** of simulated time at **0 transactions** where it walked **983 829
ms** at 35. An `admin` job of that repeater with no password in the claim **runs**, where it was
`unauthorized` unsent. A job for a repeater that is *not* the unit's own is unchanged to the
millisecond: still paced, still refused without its password.

**The pin jumped three releases**, from `v0.3.0` (`cc5a3436`, 22 October — the pin p4-01 landed and
the only one this repository has ever had) to `8c24da5b`, four commits past `v0.6.0`. Every release
in between is additive and **not one line of this repository changed to compile against them**. Two
faults of `tools/sync-agent-core.ps1` did have to be fixed, both found by this being the first sync
at a commit rather than at a tag; the second of them is the interesting one and is under
*Deviations*.

## What meshmaster.dk can rely on

Read at `twinoak/meshmaster.dk` **`0eba4c6`** (`origin/master` on 8 November; the clone was read
with `git show` and is clean), `src/MeshMaster.Core/Transport/LocalDoor.cs`,
`AgentProtocol.cs` (`DecideAsync`) and `Configuration/FirmwareVersion.cs`.

**Its pile 4.27 has already landed its side** — the sentence the task quotes, *Not at `admin`,
yet*, is gone from `AgentProtocol.cs`. So there is nothing here for it to wait for, and what it can
rely on is this:

1. **The field is the heartbeat's `agentVersion`**, and nothing else. `LocalDoor.AnswersWithoutMaterial(unit)`
   is `unit.Transport == AgentTransports.Native && AtLeast(unit.AgentVersion, NoMaterialFrom)`,
   with `NoMaterialFrom` = **0.1.2** and `UnitVersions.AgentVersion` documented as *the heartbeat's
   `agentVersion`*. There is no new field, no capability bit and nothing for this firmware to add:
   the heartbeat it already sends carries the answer.
2. **That string is this firmware's own version.** `agent::Identity`'s constructor is handed
   `core::version()` (`main/main.cpp:531`) and puts it in `HeartbeatIdentity::agentVersion`;
   `core::version()` is `TWINOAK_VERSION`, which the build sets from `PROJECT_VER`
   (`CMakeLists.txt`), and the release workflow passes `X.Y.Z+<sha7>`. `transport` is the literal
   `kTransport` = `"native"` (`identity.h:72`). So the release task 07 of this phase publishing
   `v0.1.2` is what turns the server's rule on, and nothing else does.
3. **The build suffix does not matter.** `FirmwareVersion.TryParse` drops a leading `v`, then takes
   everything up to the first character that is neither a digit nor a dot. `0.1.2+1a2b3c4` reads as
   `0.1.2`; `0.1.2+TESTKEY` likewise. A string it cannot parse is `null` and **counts as older**,
   which is the right way round — a development build (`0.0.0-dev` → `0.0.0`) is below 0.1.2 and
   keeps the old behaviour.
4. **What it hands, exactly.** At `guest`, `acl` and `none` for a unit's own repeater the claim has
   carried no material since its task 173. From a Walter at 0.1.2 `HandsNothing` is true at `admin`
   too, and `DecideAsync` returns a claim with **no credential** — except that a value typed for
   that one job under prompt custody still rides (`oneShot.Has(job.Id)`), and a `password.set`'s
   **new** value still rides as `NewPassword` with no login material beside it. All three are what
   this firmware wants: the door answers the login itself, and the one thing it does send is the
   `CLI` line that sets a password.
5. **What it may *not* rely on.** The `transactions` of a local job is now **0**, so the server's
   planned load over-estimates a unit that serves its own repeater locally (it prices every
   scheduled probe as air). That is upstream's decision, with its reasons, in report p1.10-40, and
   an over-estimate against a budget is the safe direction. A job page that reads *ok after 0
   transaction(s)* as *a job that did nothing* rather than *a job that used no channel* is a
   follow-up **in that repository**; nothing here reads the figure for a decision.
6. **A unit below 0.1.2 is unaffected**, by construction: `answersLocally()`'s default is `false`,
   and the server keeps the stored admin password and the refusal for one. There is no flag day.

## Deviations from the spec or the task

**The pin was three releases behind, not one.** The task says *whatever else came with the sync
(38, 39) is listed with one line each*, which reads as a pin at `v0.6.0`. It was at **`v0.3.0`**,
22 October — `docs/upstream.md`'s history table has only ever had two rows, and
`git log -- components/agent-core/MANIFEST.txt` has only p4-01's two commits. So the sync carried
`v0.3.1`, `v0.4.0`, `v0.5.0` and `v0.6.0` as well, and the table above lists all six rather than
two. Nothing of it needed code: every change is additive and the whole suite and both builds are
green without one line of `components/agent/` moving. The two facts worth keeping are that
`failedAt` now appears in our results and that a trace to a direct neighbour is two bytes wide
instead of one.

**`tools/sync-agent-core.ps1` was broken for a `-Ref <commit>`, twice.** Its own help documents
`-Ref <tag or commit>`, but every sync until today was at a tag, so neither fault had been met.

1. **`git describe --exact-match` ended the script before it copied anything.** It *fails* on a
   commit that is not tagged, and PowerShell 5.1 turns a native command's stderr into an
   ErrorRecord, which under the script's `$ErrorActionPreference = 'Stop'` is terminating; `2>$null`
   does not help, because the record is made before the redirection. The preference is now lowered
   for that one call and the exit code is what is read. One line of output depended on it.
2. **The copy carried `git archive`'s commit timestamps, and ninja kept stale objects.** This is
   the one worth reading. `git archive` writes the *commit's* mtime into the tar and `tar -x` keeps
   it, so today's copy of yesterday's commit landed **older than the object files of a build that
   ran in between**. Ninja compares mtimes, so the first build of this sync recompiled the test
   sources and *not* the library — and C++ answers a half-recompiled tree with a silent ODR
   violation rather than an error. `mm::Heartbeat` was 152 bytes in `test_modem_uplink.cpp` and 168
   in `Envelopes.cpp`, so `writeHeartbeat` read `hb.observer` eight bytes past the end of the
   caller's object: *stack-buffer-overflow* in one suite and a SEGV on a garbage
   `observerProvider_` in another, both inside the library, both looking like a bad bump.
   **CI would never have seen it** (a fresh checkout stamps every file at checkout), which is
   exactly why the local machine has to be right: a session that trusted the first red run would
   have reported a broken release of agent-core. Every copied file is now stamped at the moment of
   the sync, with that paragraph beside the call.

**The `[05]` follow-up item needed no code**, and is ticked with the reading under it in
`tasks/phase-9/FOLLOWUPS.md`: `readAccessList` does still ask twice and the door does still swallow
both, but at 0 transactions and no wait both tries are two UART round trips. `local_silent` is held
at **2** by a test, so a door that learns to answer the access list — task 06, `LOCAL_REQUEST` — is
a visible change rather than a quiet one. The three items of `tasks/phase-8/FOLLOWUPS.md` this
closes are ticked the same way: *A local job is paced like the air*, *An admin job for the unit's
own repeater needs a password nobody reads*, and **fix 2** of *A busy wait below one tick still

On ticking at all: `tasks/RUNBOOK.md` §0 says *do not tick anything — the reviewer does*, while

all ticked their own. The runbook's sentence reads as being about items tagged for *other* tasks,

## Decisions taken without asking

- **`answersLocally()` holds the expression and `local()` returns it**, rather than the other way
  round. The override is the contract — the library reads it at every `spend` and every login — so
  it is where the sentence belongs; `local()` stays because the console and a test read it under
  that name, and one of the two had to be a one-liner so that they cannot drift apart.
- **p9-01's measurement was moved, not deleted.** The whole point of
  `test_agent_watchdog.cpp` was that a 34-line local `config.read` never holds CPU 0 for more than
  2 s of simulated time, and it measured that by walking a thousand seconds of `delayMs(1)`. This
  task takes that waiting away, so the case would still pass — **vacuously**, at 15 blocking delays
  instead of 1 020 015. Quietly leaving it that way would have retired p9-01's regression test
  without saying so. So the local case keeps the stretch assertion and gains the new figures
  (`transmissions` 0, `totalWaitMs` 0), and a second case,
  *TheSame34LineReadForANeighbourStillPacesAndStillYields*, walks the identical thirty keys over
  the air at the same budget: **34** transactions, **966 503 ms** of waiting, **970 020** blocking
  delays and a longest stretch of **0 ms**. That is p9-01's measurement, on the path that still
  does the waiting. With `kOneTickMs` back at 10 — the code of 7 November — it is the case that
  reports 1 020 000 ms and fails. This is beyond what the task asked for; a test that passes for
  the wrong reason seemed worse than the extra case.
- **The neighbour's console is seeded with thirteen config keys** (`seedNeighbourConfig` in
  `agent_mesh_bench.h`). The library's `FakeMesh` carries the sixteen keys of CONFIGURATION §2's
  default list; the server's read asks for thirty. Without the seed the over-the-air read is
  fourteen `??:` lines, overflows `kMaxConfigRawLines` and becomes a test about the overflow note
  instead of about pacing. The values are the ones `ownConsole` already answers, so the two reads
  are the same read.
- **No change to how a local job is *priced* by the wake.** `AgentLoop::wakeJobs` still prices a
  34-line local read at `34 x (20 s + 8 s)` = **952 s** before it runs it, because `spend`'s gate
  and the wake's are different gates. It does not bite: the exchange is given `kBackendBoundMs`,
  **1 200 s**, and the transaction cap is sized to the dearest job at every band but `critical`.
  But the margin is 248 s, and `AgentLoop` is in the hash-checked copy, so the fix is upstream's —
  report p1.10-40 named it for this task and this report names it back, with the arithmetic, as an
  open follow-up rather than something to be shimmed from this side.
- **`docs/bench.md`'s p9-01 item was rewritten rather than added to.** It told Thomas to expect
  `waiting 20 s for the airtime budget` lines and about seventeen minutes, for *the release build of
  v0.1.2 or later* — which is the build that also has this change, so the item had become wrong.
  It now expects **seconds** and names what a read that still takes minutes would mean.
- **The upstream watch is left comparing versions.** `tools/upstream-check.ps1` reads `v*` tags and
  compares the newest with the version in the copy, so a pin four commits past `v0.6.0` reads as
  *up to date* until the next tag is cut. That is the right answer for a watch whose job is to
  notice releases, and teaching it to compare commits would make every Monday a pull request
  against a moving `master`. `docs/upstream.md` says so where it describes the watch, and the
  history row carries the commit beside the version.
- **The `v0.3.1` and `v0.6.0` rows say what they change here, which is nothing**, rather than being
  left out. A reader asking *what did we just take on* is better served by six rows two of which
  say *nothing* than by four rows and a gap.

below is on the unit at Thomas's bench, and the same lines are in `docs/bench.md` §18 in the order
the rig is brought up. **Both halves of this change need the server's side too, which is already
live**, so an item that refuses with *its Walter is older* is the version gate and not this work.

1. ★ **The read that reset it, now in seconds.** `docs/bench.md` §18, the rewritten `config.read`
   item: turn the repeater's scheduled config read back on (or *Read config*), `lte up`,
   `agent wake`. Expected — the 34 lines with **no** `waiting … for the airtime budget` anywhere,
   no reboot, the result `ok` with the values on the Configuration tab, and `agent jobs` showing
   the job at **0 transactions**. The simulated figure is **3.4 s**. Write down what it really

5. **Nothing is restored on the unit's own repeater.** No `setperm <own key> …` on the console of a

9. **The wake does not refuse it.** The follow-up this report opens: if the backend bound or the

10. **Nothing of three releases moved on the wire that was not meant to.** `agent heartbeat` must
    print a body with **no** `observer` and **no** `flood` member, and a failed job's result must
