# p9-01 — A delay that yields

One session. `tools/verify.ps1` **green in 506 s** (spec 0 s, spec-tools 1 s, deps 5 s, host-tests
467 s, release-tests 2 s, build 28 s, partitions 0 s, release 1 s); `core_tests` **1,049 test cases,
725,030 assertions, 0 failed**. The firmware build is 754,363 bytes with 38,821 bytes of DIRAM left
— within a couple of hundred bytes of v0.1.1's 754,544, which is as close as the two can be compared
(the version string baked into the image is a different length). The tick rate costs no RAM: it is a
timer's reload value.

The fault was one line and the fix is one line:

```
-  const TickType_t ticks = pdMS_TO_TICKS(ms);
-  if (ticks == 0) { esp_rom_delay_us(ms * 1000u); return; }
-  vTaskDelay(ticks + 1);
+  if (ms == 0) return;
+  vTaskDelay(pdMS_TO_TICKS(ms) + 1);
```

…which is only honest because `sdkconfig.defaults` now says `CONFIG_FREERTOS_HZ=1000`, so a
millisecond is a tick and `pdMS_TO_TICKS(1)` is 1 rather than 0. A `static_assert` in the same file
holds the two together: lower the tick rate and the build stops rather than start spinning again.

## The choice, and what it costs

The task offered two ways and asked for one with its reasons.

**Taken: `CONFIG_FREERTOS_HZ=1000`.** A millisecond is a tick, `pdMS_TO_TICKS(n)` is never zero for
n ≥ 1, and `delayMs` can be a plain `vTaskDelay` with no branch. Three reasons:

1. **The floor would have multiplied four timeouts by ten.** A `vTaskDelay(1)` floor at 100 Hz turns
   `delayMs(1)` into 10–20 ms. Four poll loops in this firmware count their timeout in *iterations*
   of `delayMs(1)` — `Nrf52::waitReady` (`kErasePageTimeoutMs` 300, `kWriteTimeoutMs` 50),
   `Nrf52::pollDhcsr` (`kHaltTimeoutMs` 10, `kResetTimeoutMs` 100) and `Dp::powerUp`
   (`kPowerUpPolls` 100) — so a floor makes a page-erase timeout 3–6 s, a halt timeout 100–200 ms
   and the debug port's power-up 1–2 s. That is a change to four timeout semantics, and p8-01's
   decision 4 declined to make it for exactly this reason. At 1000 Hz the same loops stretch by at
   most **2×** (`vTaskDelay(2)` is 1–2 ms), which is a timeout that waits a little longer and never
   one that gives up early, and the number of SWD reads each makes is unchanged.
2. **The floor would have slowed the modem's receive loop and the link's polls** — `delayMs(5)` in
   `WalterTlsSocket::receive` becomes 10–20 ms, and `kPollMs` 10 stays 10–20 ms. At 1000 Hz the
   receive wait is 5–6 ms and the link's poll **10–11 ms rather than 10–20**: the uplink and the
   link both get tighter, not looser.
3. **Espressif recommends 1000 for a board like this one.** `CONFIG_FREERTOS_HZ`'s range is 1 to
   1000 (`$IDF_PATH/components/freertos/Kconfig`, `config FREERTOS_HZ`, read in the pinned image),
   and **every** recommended configuration table in ESP-IDF v5.5's
   `docs/en/api-guides/low-power-mode/low-power-mode-soc.rst` — DFS, auto light sleep, and each of
   the chip's low-power modes — sets it to 1000, because "higher values lead to a higher frequency of
   task scheduling, then the system can also more quickly re-adjust the clock frequencies according
   to the system requirements". So the option the task worried about for power is the one the
   low-power guide asks for.

**What it costs.** 900 more timer interrupts a second **while the Walter is awake**, which on a
240 MHz ESP32-S3 is a fraction of a percent of one core. Deep sleep has no FreeRTOS tick at all
(the chip is off), and this unit is asleep for all but a minute or two of each wake interval, so the
daily energy cost is that fraction of a percent of the awake time and nothing else. `CONFIG_PM_ENABLE`
is off and no tickless idle is configured, so nothing else of the power path changes.

**Everything that counts ticks, audited.** The rule that made this safe is that every tick count in
this firmware and in the modem library is written `pdMS_TO_TICKS(...)`, so all of them mean the same
number of milliseconds at either rate:

| Where | What | At 1000 Hz |
|---|---|---|
| `platform/boot.cpp:53` | `vTaskDelay(pdMS_TO_TICKS(100))`, the port drains "rebooting" | 100 ms, as before |
| `platform/sleeper.cpp:82` | `xTaskGetTickCount() * portTICK_PERIOD_MS`, how long since boot | right at either rate (`portTICK_PERIOD_MS` is derived); read once at boot, for `kUsbSettleMs` |
| `platform/sleeper.cpp:83` | `vTaskDelay(pdMS_TO_TICKS(kUsbSettleMs - since_boot))` | the same milliseconds |
| `platform/uart.cpp:84,120` | `uart_wait_tx_done(pdMS_TO_TICKS(200))`, `(timeout_ms)` | the same |
| `platform/usb_console.cpp:15,22` | `kWriteTimeout` 20 ms, `kBytesTimeout` 1000 ms | the same |
| `platform/usb_console.cpp:60-68` | `writeBytes` keeps its remaining budget **in ticks**, as an unsigned difference | transparent to the rate |
| `platform/usb_console.cpp:74` | `readByte(timeout_ms)`, called once, with 100 | 100 ms either way. A caller with 1–9 would now block a tick where it used to poll; there is no such caller (`main/main.cpp:659` is the only one) |
| walter-modem 1.5.0 | `WALTER_MODEM_CMD_TIMEOUT_TICKS` = `pdMS_TO_TICKS(WALTER_MODEM_CMD_TIMEOUT_MS)`, and every `vTaskDelay`, `uart_read_bytes` and `xQueueReceive` block time derived from it (`WalterModem.cpp`:145, 920, 1527–1546, 1710–1773) | the same 30 s; the library has no raw tick literal in `src/` |

`xTaskGetTickCount()` wraps after 49.7 days at 1 kHz rather than 497 at 100 Hz. Nothing here keeps a
tick count across a long uptime — the two readers above are a boot-time figure and an unsigned
difference — and a Walter's FreeRTOS uptime is one wake, minutes long, because a deep sleep restarts
the chip.

**p8-01's `letIdleTaskRun` against it.** `kIdlePauseMs` stays 10. At 100 Hz that was
`vTaskDelay(1 + 1)` = 10–20 ms; at 1000 Hz it is `vTaskDelay(10 + 1)` = **10–11 ms**, still far more
than the one tick the idle task needs. So the pause is unchanged in intent and its worst case halves:
the measured 548 pauses of a full repeater image cost 5.5–6.0 s of the flash's 413 s (1.3–1.5 %)
rather than the 5.1–10.2 s p8-01 predicted. `docs/bench.md` §9 and `docs/ARCHITECTURE.md` §5 are
corrected.

The same test binaries, the same tests, the same fixtures; the only difference between the two runs
is `fakes::FakeClock`'s `kOneTickMs` — 10, the tick of 100 Hz and the code of 7 November, against 1,
the tick of 1000 Hz. That constant *is* the fix as a host test can see it: the fake's rule for
whether a delay blocks is the board's rule, and the board's rule is the tick rate. Output in
`out/p9-01/before.txt` and `after.txt` (git-ignored).

**1,020,000 ms is seventeen minutes of simulated time with the idle task never running** —
thirty-four times the watchdog's thirty seconds — and the fifteen blocking delays in it are all
outside the job. That is larger than the board's own failure because the board died inside the
*first* 40 s wait and the simulation runs on past the point the Walter rebooted; the shape is the
same fault. After, the longest stretch is **zero**: every millisecond of the thousand seconds of
budget waiting is a `vTaskDelay`, 1,020,015 of them, and there is nothing left in a local job that
holds the CPU at all.

The flasher's three cases moved too, and in the right direction: the full flash's longest stretch
fell from 1,005 ms to 913 ms and its pauses rose from 511 to 548. The 37 extra are the NVMC READY
and DHCSR polls, which were `delayMs(1)` busy waits and are now blocking — so an erase's 85 ms of
polling cuts the page-read stretch that used to be the longest thing in a flash. p8-01's decision 4
("the poll loops were left alone… worth a later look") is settled by the tick rate rather than by a
restructuring.

**The cost in the suite.** `agent_backend_tests` goes from 4.95 s to 5.35 s: the new case is
**0.6 s**, for 1.02 million iterations of the runner's idle loop over the simulated RAK. `core_tests`
is unchanged at 263 s. The whole host-tests step was 467 s on this run against 428 s on the run
before the test existed, which is mostly variance — the two measured binaries account for 0.6 s of
it.

## Deviations from the spec or the task

1. **The task says "a 34-line local `config.read`"; the gate counts 35 transactions.** Both are
   right, and the report says which is which. The job's shape is 34 lines — the login, `region` and
   `region default`, twenty-eight `get`s, `ver`, `board` and the access-list request — and the
   thirty-fifth is a *second* access-list request, because `JobRunner::readAccessList` asks with
   `retry` and `LinkMesh::localRequest` answers `kReqTypeGetAccessList` with silence on purpose
   (link 1.1 has no request that yields the ACL's bytes, and the library's own rule is that the
   ACL's silence is *no evidence either way*). The board spent the same thirty-five on 7 November.
   The test asserts 35 and names the arithmetic; the retry is written up in
   `tasks/phase-9/FOLLOWUPS.md`, tagged `[05]`, because task 40 of the exit-node firmware may make
   its cost nil without anyone touching it.
2. **The 34 lines are the server's real list, read out of meshmaster.dk rather than invented.**
   `ConfigKeys.ReadListFor(null)` at commit `c9732682` (`src/MeshMaster.Core/Configuration/
   ConfigKeys.cs`, read without touching that repository's tree) is thirty keys — every row of the
   key table with a `ReadOrder`, with one of `dutycycle` / `af` and not both. `mm::kDefaultConfigKeys`
   is the *sixteen* an older claim falls back to and would have made a 19-line read, which is not
   the job that failed. The thirty are in `host_test/agent-backend/agent_mesh_bench.h` with that
   citation, and `ownConsole` grew answers for all of them so the read is thirty answers rather than
   fourteen `??:` lines (fourteen would overflow `kMaxConfigRawLines` and make the test about the
   overflow note).
3. **The "before" figure is 1,020,000 ms, not the ~40,000 ms the fault report implies.** The board's
   watchdog fired inside the first 40 s wait; the simulation has no watchdog and runs the whole read,
   and nothing *inside* a local job blocks, so the whole read is one stretch. The test's header
   comment says this, so nobody reads 1,020,000 as "the wait was seventeen minutes".
4. **`delayMs(0)` returns at once and does not yield.** The interface says "blocks for at least this
   long", and zero is nothing asked for. Nothing in this firmware or in agent-core calls it with
   zero (`JobRunner::idle` uses 1; the one mapping of 0 → 1 is a test bench's,
   `bench::WorldPlatform`), and `fakes::FakeClock` models the same rule, so the host suite cannot
   hide a spin on it. If a caller ever appears, `kOneTickMs` makes it visible in the measurement.

## Decisions taken without asking

1. **A `static_assert`, not a new rail in `tools/check_rails.py`.** The invariant is "a millisecond
   is at least one tick", which the compiler can check exactly; a grep rail would have to allow
   `esp_rom_delay_us` in `delayUs` and forbid it in `delayMs` in the same file, which is weaker and
   more fragile. `static_assert(configTICK_RATE_HZ >= 1000, …)` in `platform/clock.cpp` fails the
   build the moment somebody lowers `CONFIG_FREERTOS_HZ`, and the message names the file to look in.
2. **`kIdlePauseMs` stays 10 ms.** It is now ten ticks rather than one, so the arithmetic behind it
   changed; the figure did not, because what it buys is unchanged (the idle task needs one slot) and
   lowering it to 1 ms would make the pause a tenth of a scheduling margin for no measured gain.
   `core/swd/idle_pause.h` says so beside the constant.
3. **The four poll-counted timeouts were left counting polls.** They now run 1–2 ms a poll instead of
   exactly 1, so `kErasePageTimeoutMs` 300 is 300–600 ms of wall time. A timeout that waits up to
   twice as long never gives up early, the SWD read count is unchanged, and restructuring four loops
   into elapsed-time arithmetic is the change p8-01 declined and this task has no reason to make.
   Named in the audit above so that a bench figure can be read against it.
4. **The new test went into `agent_backend_tests`, not a new binary.** That binary already has the
   wake bench with the agent's half of a Walter, the real `JobRunner`, the real `LinkMesh`, the
   simulated RAK and the library's simulated stock repeater over `fakes::FakeClock` — which is
   exactly what the task asked the test to run through — and the scripted meshmaster.dk's default
   budget already *is* 2 a minute, gap 20 s. Nothing had to be built; the measurement had to be
   taken.
5. **`ownConsole`'s key table was extended rather than copied.** It is shared with
   `test_agent_mesh.cpp`, whose read asks three of the keys and asserts one value; adding twenty-two
   answers is additive and leaves that test's meaning alone.

## Not verified here (and why)

No session opens the unit's ports this pile (`tasks/phase-9/README.md`), and a watchdog is a property
of a running Walter: the host suite can only show that no stretch of simulated time passes without a
blocking delay in it, and that the tick rate the whole argument rests on is in the built
`sdkconfig`. The lines are in `docs/bench.md` §18, with the **release** build of v0.1.2 or later:

- **§18, a `config.read` of the unit's own repeater at the budget as it is, timed.** Turn the
  repeater's scheduled config read back on (or *Read config* on its page), `lte up`, `agent wake`.
  Expected: the read walks a line at a time with `waiting 20 s for the airtime budget` /
  `waiting 40 s …` between them, **no reboot**, and the result posted `ok`. **Write down how long the
  whole job took**: the simulated figure is about 17 minutes of budget waiting for 35 transactions,
  so the thing to confirm is that it is slow and not fatal. Task 05 takes the waiting away.
- **§18, `boot` afterwards says `power-on` or `software`, never `watchdog`.** One `watchdog` there,
  even with the job posted `ok`, means some stretch of the wake still holds CPU 0 for 30 s and is a
  finding against this task. `journal` must show no `faults_in_a_row` from the wake either.
- **§9's flash time, measured again.** The pauses are now 548 at 10–11 ms rather than 511 at
  10–20 ms, so the prediction is 5.5–6.0 s of pause on a 413 s flash instead of 5.1–10.2 s. The
  figure only matters once a real flash has been timed (that item is already in §9, uncollected:
  the 7 November first install took about a quarter of an hour where `docs/flashing.md` says seven
  minutes, which task 04 of this phase is to time properly).
- **The 1 kHz tick's real cost, on the battery.** Everything above about power is ESP-IDF's
  recommendation and arithmetic. The number that settles it is §16's day and §18's day as an exit
  node, run again on v0.1.2 and held against the figures they brought back from v0.1.1: a tick
  that costs a fraction of a percent of the awake time should be invisible in a day's energy, and
  if it is not, it will show there and nowhere else.
- **The erase that got faster.** A 3 MB self-slot erase now yields 1 ms every 20 ms instead of
  10 ms every 20 ms (`CONFIG_SPI_FLASH_ERASE_YIELD_TICKS=1`). §10's self-update item is where a
  person would notice: a `twinoak.fw.apply` of a Walter release should spend visibly less time in
  `esp_ota_begin`. Not predicted here with a number, because ESP-IDF's erase accounting is per
  block and this firmware does not time it.
