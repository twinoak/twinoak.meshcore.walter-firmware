# p9-02 — the sixth connection

The review of phase 8 named two ways a socket id can go wrong — **S2**, a close that never comes
leaving that id one close behind for the modem's life, and **S3**, a check-then-set race between
`end()` on the main task and `onClose()` on the library's event task — and neither was fixed. Both
are gone now, and by the same change: an id's whole close accounting is **one value**, and each of
`begin()`, `end()`, `cancel()` and `onClose()` applies **one transition** of it with a
compare-exchange. There is nothing between a read and a write to interleave, "both set" is not a
state the value has, and the debt is bounded by a rule that is one sentence long.

The stall itself is **read but not settled**, on purpose. What the code can prove is here (it is one
AT command that went unanswered for the library's whole 30 s timeout, and that command is
`AT+SQNSRECV`), what it cannot is in `docs/bench.md` §13 as a trace build and four things the trace
must show, and the counters that will say *which id* are now on `http get` and `lte` — which is the
thing the two stalls of 7 November did not have and the reason they could not be read.

## Acceptance checklist

- [x] **S3 under a lock, with the interleaving test; S2's debt bounded by one written rule, tested
      against a modem that never answers a close.**
      **S3** is not under a lock: it is one atomic transition, which is the other half of what the
      task allows and the better half. `CloseState` (`core/net/socket_rotation.h`) is the whole
      accounting of an id — `kClear`, `kSeen`, `kOwed`, `kLastChance`, `kQuiet` — `after(step,
      state)` is a `constexpr` function holding every transition, and `apply()` is a
      compare-exchange loop that takes the transition again from whatever the other task left
      there. A `static_assert` holds `std::atomic<CloseState>` to `is_always_lock_free`, so a
      toolchain that would put a lock inside it fails the build and not a bench.
      The interleaving test is `test_socket_rotation.cpp`, *every transition of the rule, and both
      orders of the two tasks' steps*: the table read in full, and then the review's own
      interleaving both ways round — the close first (`kEnd ∘ kCloseEvent (kClear) = kClear`) and
      the end first (`kCloseEvent ∘ kEnd (kClear) = kClear`). Neither leaves anything owed, which
      is exactly what v0.1.1's two flags could not promise. *The interleaving the review
      describes, through the rotation itself* runs the same thing through `SocketRotation`.
      **S2's rule, written down** (the header, *A debt lives for one connection*): a debt that is
      still unpaid when the connection that waited for it has finished its exchange is **written
      off**, and that id is then marked as one whose closes do not come — nothing owed, nothing
      waited for, nothing discounted — until a close actually arrives, whereupon the rule comes
      back. The modem that never answers a close is the fake's new `close_event_lost`:
      `test_late_close.cpp`, *a modem that never answers a close*, is eight connections through a

## The stall, read against the code

**What is certain.** The console line of 7 November —
`/agent/v1/observations -> no reply: the connection closed before the body was complete after
30935 ms`, with `WalterModem: Command time-out (TX) Attempt 1 of 1` above it — decomposes exactly:

- *no reply* is `modem_uplink.cpp`'s `r.status == 0` branch: **not one byte of the response had
  arrived**, not even a status line.
- The request **did go out**: a `send` that had failed would have said *the request did not go out*
  (`kSendFailed`), which is the 6 November sentence and a different one.
- So the 30 935 ms was spent inside `receive`, and inside it in **one** library call: the receive
  loop's own bound is the piece deadline (15 s by default, `kDefaultPieceMs`) and would have
  answered *the deadline passed*. A library call has no timeout of its own; the command task gives
  up after `CONFIG_WALTER_MODEM_CMD_TIMEOUT_MS` = 30 s, and
  `CONFIG_WALTER_MODEM_DEFAULT_CMD_ATTEMPTS` is 1, so there is no retransmission. 30 935 ms is that
  30 s plus the connect.
- The only library call `receive` makes is `socketReceive`, so **the AT command that timed out is
  `AT+SQNSRECV`**. `Command time-out (TX)` is `_processModemCMD`'s message for a `TX_WAIT` or
  `DATA_TX_WAIT` command whose expected response never came; `AT+SQNSRECV` is `DATA_TX_WAIT`.
- `socketReceive` then returned false with `rsp.result` = timeout and no `+CME ERROR: 4`, so
  `receive` answered `TlsRecv::kError` — which `HttpOutcome` mapped to `kClosed`. **That is why it
  read as a server hanging up.** It is `kSocketFailed` now.

**What the code allows, as mechanisms for a 30-second unanswered `AT+SQNSRECV`** — in the order I
would bet on them, each with what the trace settles it by:

1. **The library's parser was left counting a payload.** `_expectingPayload()` takes
   `+SQNSRECV: <id>,<n>` and puts the parser into `_receivingPayload` with `_receivedPayloadSize =
   n`; `_parseRxData` then consumes exactly `n` bytes as payload. If anything makes the byte count
   disagree — fewer bytes than declared, or a URC landing inside the payload region — the parser
   goes on eating the UART, **the next command's `OK` among it**, and the only thing that clears it
   is the command timeout (`_processModemCMD` sets `_receivingPayload = false` on the way out).
   That fits the observation exactly: one 30 s gap, and the very next connection through in 3.7 s.
   The trace shows it as a `+SQNSRECV: <id>,<n>` before the gap with fewer than `n` bytes after it.
   The URC-inside-the-payload variant is not invented: QuickSpot/walter-arduino#109's own trace is
   `AT+SQNSRECV=1,318`, then `+SQNSH: 1`, then `+SQNSRECV: 1,318` — the close URC arriving between
   the command and its answer, in this very place.
2. **The modem did not answer.** The GM02SP busy in its own TLS teardown, or flow control held
   (`uart_write_bytes` blocks while CTS is deasserted, so the command would not even go out). The
   trace shows it as a `TX:` line with no `RX:` for 30 s — or as **no** `TX:` line at all, which
   distinguishes the two halves.
3. **The modem answered something nobody matched.** The response to `AT+SQNSRECV` is matched by
   text and not by id, so a reply carrying another socket's id would still complete the command;
   an `ERROR` would complete it too (with `maxAttempts` 1 there is no retry). So this is the
   weakest of the three, and the trace rules it out by showing an `RX:` line inside the gap.

**The four questions the task asks:**

- **Is the sixth connection the third on one id?** With two ids alternating, connection 6 of a boot
  is the third on the id of connection 2 — but the rotation is **per boot, not per wake**, and the
  first of the two stalls had four `http get` connections ahead of the wake. So "the sixth
  connection of a wake" is not a fixed id, and the absolute count cannot be recovered from the
  lines there were. That is precisely what the counters now answer: `the last few: 1 6 1 6 …` and
  the connection total, read off `lte` after the stall. The hypothesis is worth testing and the
  bench line tests it.
- **Does the GM02SP keep a TLS session per id that a reused id inherits?** Unanswered, and now a
  follow-up. What could be read of the manual (below) says TLS is **per socket**:
  `+SQNSSCFG:(1-6),(0-1),(1-6)`, and the query lists an enable flag and a profile for each of the
  six ids, so six secure sockets are possible and both of ours are bound to the same profile. A
  *profile* is configuration and is shared; whether a *session* or a session cache is kept against
  the id is in the prose, which could not be extracted.
- **Is it the second POST in a row?** It is consistent with both stalls (the second observations
  batch in one, observations after a result in the other) and with neither exclusively: the third
  shape of the same evening failed at the **dial** of a result, the first POST after a claim. The
  only reading the code supports is that a larger body is more `AT+SQNSSENDEXT` commands — our
  `send` splits at 1500 bytes — and so more chances for mechanism 1 above to be set up by the
  command before the receive. The bench line writes the body sizes down.
- **Which AT command timed out?** `AT+SQNSRECV`, by the elimination above. The trace is what
  confirms it, and it is the first of the four things §13 asks of the trace.
- **Was the refused dial `AT+SQNSD` on an id the modem still held open or closing?** Not settled.
  The library puts no state gate on `socketDial` — `_socketGet` matches on the id alone — so
  nothing of ours stops a dial on an id whose `+SQNSH` has not come, and 12 532 ms for a refusal is
  too long for a local rejection and about right for a name lookup or a handshake that failed. If
  the trace shows `AT+SQNSD` answered `ERROR` on an id with a close outstanding, then the dial
  wants that close first and the rotation's wait is where it belongs — a change this task will not
  make from a reading. There is a bench line for it.

**A lost close is not hypothetical, which is why bounding the debt matters.** The library queues
socket events into a queue of `WALTER_MODEM_EVENT_QUEUE_MAX_ITEMS` = **8** with
`xQueueSend(..., 0)` — a full queue **drops the event and says nothing** — and its event task takes
**one event per loop**, each loop a `vTaskDelay(10)` plus another 10 ms before the dispatch. So a
response that rings more than eight times inside ~160 ms loses events, and one of them can be the
`+SQNSH`. Those same figures are where `kOwedCloseWaitMs` comes from (below).

## Deviations from the spec or the task

**S3 is one atomic transition and not a critical section.** The task allows either ("is under a
critical section, or made a single atomic transition"); the review asked for a critical section.
The transition was chosen because core/ has no lock to take — it would have meant a new interface
and a platform implementation for a two-byte update — and because it removes the race rather than
serialising it: with one value per id there is no pair of flags that can disagree, and the
transition table is a thing a test can read in full. The cost is `<atomic>` in core/net/ (added to
the no-allocation check's allowed includes, with the reason) and the `static_assert` on
`is_always_lock_free`, which the firmware build passes on the ESP32-S3.

**The debt's bound is "one connection", decided as the deterministic rule, and it changes one test
of p8-03.** The task offered two shapes: *the debt expires at the id's next successful exchange, or
after N connections*. Read carefully, the first does not bound the **cost** — every connection on a
silent id still ends owing a close, so every next one still waits — and the plain "after N
connections" does not either, because a discounted close leaves the connection that discounted it
owing one in its turn, which is what made the debt self-sustaining in v0.1.1. The rule that does
bound it is the one written down: the debt is written off **at the end of the connection that
waited for it**, and the id is then known to be one whose closes do not come, so nothing is owed on
it until one arrives. The write-off at the *end* rather than at the *begin* is what keeps p8-03's
"two connections late" case working unchanged — a close delivered after the wait has timed out is
still discounted, because the debt is only written off once the whole connection has gone by
without it.
`test_socket_rotation.cpp`'s *a debt nobody pays stays: the cost of owing a close that never comes*
was the test that **measured** the old behaviour (three waits in a row, three discounts). It is now
*a debt nobody pays is written off, and then that id expects no close at all*, and three cases were
added beside it. Nothing else of p8-03's tests changed.

**A new `HttpOutcome`.** `kSocketFailed = 13`, so that `TlsRecv::kError` is not reported with
`kClosed`'s sentence. The task does not ask for it; it is the difference between a diagnosable and
an undiagnosable next stall, and the two stalls of 7 November are the evidence. Nothing else
changes: the one place that treats `kClosed` as "the headers were there, the body was not" —
`client.cpp`'s redirect condition — takes `kSocketFailed` the same way, so the only difference is
the words.

**`kOwedCloseWaitMs` stays 250 ms, with the reason rewritten, and is still a bench constant.** The
task asks for it to be set "from what the library and the AT manual say". The library says: a
`+SQNSH` is queued by the URC parser the moment the modem reports it, and the event task dispatches
it a `vTaskDelay(10)` and a further 10 ms later — **~20 ms per event, one event per loop**. The
closes we are waiting for are behind whatever rings a response produced, so a handful of events is
tens of milliseconds; 250 ms is a dozen dispatches. The AT manual's prose could not be read (below),
so nothing in it moved the figure. `kOwedCloseStepMs` stays 10 ms and its comment is corrected: one
tick was 10 ms at `CONFIG_FREERTOS_HZ` 100 and is 1 ms since p9-01, so the step is ten ticks now —
and a finer step would only poll harder for something the library cannot deliver in under 20 ms.

**The `DEPRECATION` line is silenced, not removed.** There is no way to remove it: the only public
path to a second socket id at `walter-modem` 1.5.0 is the deprecated `socketConfig` overload with
no id, and the line is that overload's own `ESP_LOGW`. The firmware makes **no other** deprecated
call of the library, so `esp_log_level_set("DEPRECATION", ESP_LOG_NONE)` beside that one call
silences exactly the line it is about and nothing else. The alternative — leaving a line on the
bench console that reads as a mistake and is not one — was the thing the follow-up complained about.

## Decisions taken without asking

- **One value per id instead of a lock** (above, *Deviations*), and the counters the event task
  writes — `discountedCloses`, `otherIdEvents` — made `std::atomic<std::uint32_t>` with relaxed
  ordering, because they were plain `std::uint32_t` incremented from that task and read from this
  one. The three the main task alone counts stayed plain.
- **A debt is written off at `end()` and not at `cancel()`.** A connection the other end never
  answered — a dial the modem refused, which is the third shape of 7 November and cost 12.5 s —
  proves nothing about whether closes arrive on that id, so it gives the debt back rather than
  writing it off (`after(kCancel, kLastChance) = kOwed`). It also keeps p8-03's rule intact: what
  changes accounting is a connection that exchanged.
- **A quiet id is lifted by the first close that arrives**, rather than staying quiet for the
  modem's life. The sticky state is a conclusion drawn from one 250 ms wait; a close arriving
  afterwards is evidence against it, and the cost of being wrong in the other direction (an id that
  never again believes a close) is a dropped body read as a stall, which is the fault being fixed.
- **Eight connections' ids are kept** (`kRecentConnections`), oldest first: a wake's four requests
  and the pair of `http get`s before them, which is the shape of 7 November's evidence. Not a bench
  constant — nothing measures it.
- **`http get` prints the block after a failure as well as after a success**, before the early
  `return` for *no response*. That is the case the counters exist for.
- **The console takes `const net::SocketRotation*` directly**, not a probe interface like
  `uplink_probe.h`. The rule is core/'s own (`core/net/socket_rotation.h`) and the console is core/;
  a seam would have been a copy of a struct for no boundary.
- **`kSocketFailed` is carried through `client.cpp`'s redirect condition** beside `kClosed`, so the
  new outcome changes the words and nothing else about what a request does.
- **The GM02SP's AT manual was read as far as a session could read it** (`Not verified here`): its
  examples and syntax lines, not its prose.

## New libraries (with the one-line justification)

None. `<atomic>` is the standard library, added to the allowed includes of core/net/'s
no-allocation check because the close accounting is written by one task and read by another.

## Not verified here (and why)

No session opens the unit's ports in this phase (the phase README), and nothing of the modem's
socket layer runs without a SIM and a tower. The bench lines are in `docs/bench.md` §13, after the
three task p8-03 left there:

1. **The rotation's own lines, read once.** `lte` after the twenty pairs of `http get`: the whole
   socket block written down. It settles three things no host test can — whether the second socket
   id was granted at all (`ids 1 and 6` against `id 1 alone`), whether the modem answers `+SQNSH`
   for a close this end asked for (`discounted` near the connection count means every close is one
   connection late, `written off` other than 0 means closes are being lost), and whether anything
   rings on an id this firmware never dialled.
2. **The sixth connection.** Two `http get`s, then `agent wake` twice, with `lte` read between each
   step. Which of the two sentences the stall gives (*the connection closed…* or *the modem stopped
   answering…*), which id the stalled connection was on, whether that id owed a close, whether
   anything had been written off.
3. **The trace build, if it stalls again**: `CONFIG_LOG_DEFAULT_LEVEL_DEBUG` and
   `CONFIG_LOG_MAXIMUM_LEVEL_DEBUG`, flashed by cable, never on a unit in service — the same build
   as 23 October. Four things, in order: the last `TX:` before the gap (the command that was not
   answered); whether any `RX:` came in those 30 s and what it was; whether a `+SQNSRECV: <id>,<n>`
   before the gap declared more bytes than followed it; and the `+SQNSH:` lines with their ids and
   their timing against our own `AT+SQNSH`.
4. **A dial refused on an id the modem may still hold**: the third shape of 7 November, with the
   seconds and the id written down.

And four things only the board or a document can answer:

- **Whether the modem reports `+SQNSH` for a socket this end closed.** Search results quoting the
  manual say the URC comes when "the socket is closed by the **network**", which would mean our own
  `AT+SQNSH` produces none — and then the owed-close rule is paying for every connection, which is
  what line 1 shows. I will not write that into the code from a search result; the manual's own page
  or the trace settles it.
- **Whether a TLS session is tied to a socket id and inherited when the id is reused.** The
  manual's prose could not be read in this session: the document is QuickSpot's copy of the
  Monarch 2 LR 8.2 AT Commands Reference (20 MB, over the fetch tool's limit; downloaded and read
  by hand, but its pages use subset fonts with no extractable encoding — only the monospaced
  examples came out). What those examples do say, verbatim: `+SQNSH: (1-6)`,
  `+SQNSRECV: (1-6),(1-1500)`, `+SQNSSCFG:(1-6),(0-1),(1-6)` with the query listing an enable flag
  and a profile for each of the six ids, and
  `+SQNSCFG: (1-6),(0-5),(0-1500),(0-65535),(0,10-1200),(0-255)` — **every parameter
  `walter_tls.h` sets is inside that range**, including the connect timeout we send as 300 (30 s)
  against `(0,10-1200)`. A machine with a PDF reader settles the rest in ten minutes; it is a
  follow-up.
- **Whether `kOwedCloseWaitMs` = 250 ms is right.** Reasoned from the library (above) and still
  *TO BE SET ON THE BENCH*, with its row in *What to bring back*. Since this task it is spent at
  most once per id until a close arrives, so being wrong by a factor of two costs half a second a
  boot instead of half a second a connection.
- **Whether the event queue really loses a `+SQNSH`.** The mechanism is in the library's source
