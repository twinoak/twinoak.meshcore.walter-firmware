# p2-01 — Manifests and signatures

The Walter can now decide whether a file may be flashed. `components/core/image/` holds the six
checks of `spec/FIRMWARE-MANIFEST.md` §5 in the specification's order — the signature, the
manifest, the image for this slot, the file's hash, the descriptor inside it, the region — as
`ImageVerdict::judge()`, which answers with the number of the check that failed and a sentence, or
with an `AcceptedImage`: the token the image store (task 02) will demand, and a type nothing but a
verdict can construct. Underneath: Ed25519 (RFC 8032) over a **verbatim, verification-only extract
of TweetNaCl 20140427** with `S < L` checked before the arithmetic (TweetNaCl does not); a
streaming SHA-512 over TweetNaCl's own block function; the signature line parsed strictly; the
manifest tokenized by a vendored **jsmn v1.1.0** into fixed-size structures with named bounds and
validated rule for rule as `manifestref.validate` does; the image chosen by the slot's three
words and this unit's version and link majors; the file's size, SHA-256 and the one descriptor in
it checked in a single pass over bytes that arrive in pieces; and the manifest's `app_region` held
inside the flasher's board profile. **The trust table is generated at build time from
`keys/release-keys.txt`** through the release gate's own loader, so the firmware and the tooling
cannot disagree about which keys exist — and since that file names no key, this build refuses
every manifest at check 1, which `trust` on the console says in so many words. A build made with
`-DTWINOAK_TRUST_TEST_KEY=1` (`tools/verify.ps1 -TestKey`) trusts the specification's public test
key, is stamped `+TESTKEY`, warns at every boot, and is refused by `build_release.py` twice over.

`tools/verify.ps1` is green: **354 host test cases, 161 229 assertions** (44 new cases, under
ASan and UBSan), 40 release-tooling tests and 8 of the trust generator's, the firmware built with
the six checks linked in — **380 576 bytes, 12.1 % of its slot** (369 536 before the verdict was
anchored, 359 712 after task p1-06) — and the dry-run release signed and verified. One session.

## The choice of Ed25519 implementation

What the task asked: small, well-known, verification only, vendored at a version, compiled for
the board and the host alike. The alternatives read for it, and why TweetNaCl:

| | Size | Audit history | Signing code comes along? | Rejects non-canonical S? |
|---|---|---|---|---|
| **TweetNaCl 20140427** (chosen) | 809 lines for all of NaCl; the verification path is 45 definitions, ≈300 lines | the paper's own review, a decade in the open, the basis of TweetNaCl.js (audited by Cure53, 2017) | only if the whole file is taken — here it is not | **no** (added in the wrapper) |
| libsodium / SUPERCOP ref10 | ~30 KB of precomputed tables plus the code | the most reviewed, libsodium's | yes, inseparably | libsodium yes, ref10 only the top bits |
| Monocypher 4 | one 2 500-line file with ChaCha, Poly1305, BLAKE2b, Argon2, X25519; Ed25519-with-SHA-512 needs a second file | one audit (Cure53), the EdDSA default is BLAKE2b not SHA-512 | yes | yes |
| orlp/ed25519 | ref10-derived, the same tables | little | yes | top three bits only |
| c25519 (D. Beer) | small, written for microcontrollers | little | yes, in the same file | no |
| ESP-IDF's mbedtls | — | — | — | no EdDSA in mbedtls 3.6, and the host could not use it |

TweetNaCl is the smallest thing that is also widely read, and it is the one whose verification
path can be lifted whole and verbatim without touching a line: the field arithmetic, the point
arithmetic, `modL`, SHA-512 and `crypto_sign_open` are self-contained. What it lacks, the range
check on `S`, is ten lines in `ed25519.cpp` and a test that shows the extract accepting `S + L`
and the wrapper refusing it. What it costs: it is slow (no precomputation; the bench will time
`trust`'s self-test), it wants the signed message in one buffer (the hash is streamed instead, so
only the tail of `crypto_sign_open` is called), and two compiler flags for the one file.

**SHA-256 and SHA-512, and which source.** SHA-256 is task p1-05's own 120 lines (FIPS 180-4,
held to the FIPS vectors), used for the file's hash and the key id on the board and the host
alike. SHA-512 is TweetNaCl's `crypto_hashblocks` and initial state, verbatim; the buffering and
the padding are `core/image/crypto/sha512.cpp`'s, held against TweetNaCl's own one-shot
`crypto_hash` for every length from 0 to 300 fed in odd pieces, and against FIPS 180-4's three
examples and NIST's million-'a' vector. One source for both builds in both cases; no ESP-IDF
mbedtls anywhere in `core/`.

## Deviations from the spec or the task

- **The vendored implementation does not reject a non-canonical `S`; the wrapper does.** The
  task: "check that the vendored implementation does, and say so". It does not — TweetNaCl's
  `crypto_sign_open` makes no range check, and `S + L` verifies as `S` does (RFC 8032 §5.1.7
  step 1 says it must not). `core/image/crypto/ed25519.cpp` checks `S < L` before any arithmetic,
  and `test_ed25519.cpp` holds both facts on every RFC vector: the extract accepting `S + L`, the
  wrapper refusing it — so that if a future extract ever refused it itself, the test says so.
  Two other things TweetNaCl does not check and this firmware does not need to: a non-canonical
  encoding of `R` fails anyway because `R` is compared against a canonical packing, and the
  public key `A` comes from our own table.
- **`validate()` is `manifestref.validate` rule for rule, with four places where the reference
  would not reach a verdict.** (1) `sha256` that is 64 characters but not hex: the reference's
  `validate` accepts it and check 4 then never matches; here it is "bad sha256" at check 2 (the
  bytes are decoded at parse time). (2) `load_address` or `app_region` that begins `0x` but is
  not 1–8 hex digits: the reference's `int(x, 16)` raises instead of returning a reason; here
  "load_address is not hex" / "app_region is not hex". (3) A `size` above 2^32: the reference
  takes any Python int; here "bad size" — no image is that large. (4) `commit` is held to length
  40 only, as the reference does (§2's table says "hex"); its content is not used. `requires` is
  not validate()'s in either (the reference ignores it); here a malformed one is refused at
  check 3.
- **The signature line is stricter than `manifestref.verify`.** The reference strips whitespace
  and splits on spaces; the task says "parsed strictly … anything else is no signature", and §3
  says one line. So: the word, one space, 16 *lowercase* hex, one space, 88 characters of
  canonical base64, then nothing or one LF or CR LF. Upper-case hex, a tab, a second space, a
  trailing space or a second line are "no signature".
- **The descriptor's `link_minor` is not held against the manifest.** The task lists "role,
  board, band, version, link major"; `verify_release.py` holds the minor too. §5.1 of the link
  protocol says a minor adds things, so a minor is data and not a refusal here; said in
  `file_check.cpp`.
- **The token is handed out, not filled in.** `judge()` takes no out-parameter: a caller cannot
  declare an `AcceptedImage` (no public constructor), so the verdict keeps one and `accepted()`
  returns a pointer to it after an accepting `judge()`, `nullptr` otherwise; the store copies it.
  "A type, not a convention" — `static_assert(!is_default_constructible)` in the test.
- **The test-key build is a CMake option, and `tools/verify.ps1 -TestKey` is the way to make
  it.** The task says "a build made with an explicit `-D` flag": it is `-DTWINOAK_TRUST_TEST_KEY=1`
  to `idf.py`, and `verify.sh` passes `0` or `1` every time because a cache variable sticks (the
  `PROJECT_VER` lesson of task p0-02). In that mode the release step's whole result is
  `build_release.py` refusing the build, twice.
- **The verdict is anchored from `main`, the way the modem library is.** Nothing calls `judge()`
  until task 02 has a store, and `--gc-sections` drops what nothing references — the first build
  showed the six checks discarded and only the crypto kept (through `trust`'s self-test). A
  volatile read of a pointer to member in `main` was not enough (the compiler elided it);
  `core::image::verdictAnchor()` reads it inside `verdict.cpp` and `main` keeps the result, after
  `modem_anchor.cpp`'s pattern. The cost is 11 KB of flash that task 02 would have paid anyway.
- **`trust` runs an Ed25519 self-test first** (RFC 8032 TEST 1 verified, one bit changed
  refused, the time printed). Not asked for; it is the only way a bench can see the vendored
  arithmetic is right on the Xtensa compiler, where no host test runs, and it is what keeps the
  crypto in the image independently of the anchor.
- **One existing release test changed.** `test_a_trust_table_line_is_held_to_its_key_id` used
  the test key as its example of a *good* line; the loader now refuses that key by name (§3:
  "the Walter's build refuses to include it outside test builds"), so the test uses a key made
  for the test. `verify.sh`'s "banner in image" log line reads the banner with `grep -o` now: the
  literal before it in `.rodata` is no longer one `strings` starts a new line at. Neither changes
  what is checked.
- **jsmn is pinned at `v1.1.0`**, the last tag (2019); its master has moved on without a
  release. `JSMN_STRICT` refuses a bare number as a whole document (a primitive must be followed
  by something), which the parser reports as "not well-formed JSON" rather than "not one object".
- **CI rounds:** filled in below under *CI*.

## Decisions taken without asking

- **An extract, not the whole file, and the exported names kept.** `tweetnacl.c` whole would
  have brought `crypto_sign`, `crypto_sign_keypair` and an `extern randombytes` into every
  build; the extract has 45 verbatim definitions and five small functions of ours below a marked
  line, and keeps `tweetnacl.h`'s names so that the map check means what it says. The one edit —
  `_121665` left out of the constants block — is named in the file, the README and the script.
- **Two compiler flags for that one file:** `-Wno-sign-compare` (its loops compare an `int` index
  with a `u64` count) in both builds, and `-fno-sanitize=shift-base` on the host (`car25519` and
  `modL` left-shift negative values: defined on every compiler here, undefined to UBSan). The
  rest of `-Wall -Wextra -Werror` and of ASan/UBSan apply to it. It compiled on the Xtensa with
  no other warning. jsmn is a system include, as doctest is.
- **The bounds** as listed under the checklist. `kMaxImages` 8 rather than the task's hint of
  "a bounded number" being small: the family is roles × boards × bands.
- **Choosing is strict.** Two images with the same role, board and band (ids differ) are
  *ambiguous* and refused, not the first taken. The manifest's own `link.major` is held as well
  as `requires.link_major` (S-7: an image speaking a major this Walter does not speak is not for
  it yet), and `ThisUnit` carries a list of majors so that a Walter in the middle of a major
  change can say it speaks both. A `requires.walter` this firmware cannot read as `X.Y.Z` is not
  met; `0.0.0-dev` meets nothing (`0.3.0 > 0.0.0-dev`), so the repeater fixture is refused on a
  development build — right, and shown.
- **Base64 is canonical:** the alphabet only, `=` only where the encoding needs it, the unused
  bits zero (RFC 4648 §3.5). A signature `manifestref.py` wrote always is.
- **Key ids are lowercase hex only** (§3 says lowercase).
- **The generator goes through `verify_release.load_keys`**, which now refuses the test key in a
  release table; one loader, one set of rules for the gate and the unit.
- **The signed test variants are made at build time by the reference** (`gen_manifest_fixtures.py`,
  with `cryptography` from the image) rather than by a signer in the tests: the tests then hold
  the firmware against `manifestref.sign`, and no signing code of ours exists anywhere.
- **The no-allocation check moved to `host_test/checks/no_allocation.h`** so that two tests
  share it; the codec and client tests are unchanged in meaning (it gained an extension filter so
  that a README beside a vendored file is not read as source).
- **`kMaxJsonTokens` is held by a `static_assert`** against the two other bounds, so the three
  cannot drift apart.
- **The descriptor scanner is a window of twice a descriptor**, every 4-aligned offset tried
  once; it is held against `find()` rather than trusted.
- **Check 4 refuses a wrong size before reading a byte** (`ImageSource::size()`), and the pass
  over the file is 256 bytes at a time through the member buffer.

## New libraries (with the one-line justification)

- **TweetNaCl 20140427, verification-only extract** (public domain; `core/third_party/tweetnacl/`):
  the smallest widely-read Ed25519, liftable verbatim, no signing code taken.
- **jsmn v1.1.0** (MIT; `core/third_party/jsmn/`): a JSON tokenizer into a caller-provided array,
  which is what "no heap" needs; one header, used from one file.

Nothing else: `cryptography` 44.0.3 was already pinned for the reference code, and the host tests
use it only through `manifestref.py` at fixture-generation time.

1. **`trust` says no update will be accepted, and the self-test passes on the board.** On a
   normal build: `ed25519 self-test (RFC 8032 test 1, and one bit changed): passed, <n> ms` —
   **write `<n>` down**, the first measurement of TweetNaCl's Ed25519 on the ESP32-S3 (TweetNaCl
   has no precomputed tables; hundreds of milliseconds would be no surprise, and it bounds what
   phase 3's download can afford per manifest) — then `trust: none: no update will be accepted
   (keys/release-keys.txt names no key; ...)`, and no `WARNING` among the boot lines. A `FAILED`
   from the self-test means the vendored arithmetic is wrong on the board's compiler, which only
   a board can show.
2. **A build with the real key.** When Thomas has made it (`spec/SYSTEM.md` §10 item 1,
   `keys/README.md`) and its line is in `keys/release-keys.txt`, a build's `trust` prints `1 key
   this build accepts a release signed with: <key id>` — the id `manifestref.py keygen` printed
   — and `verify_release.py` accepts a tag. Until then every manifest is refused at check 1,
   which is the state the specification wants.
3. **A test-key build on a board, if one is ever flashed for the bench:** the banner says
   `+TESTKEY`, the fourth boot line is the `WARNING`, `trust` lists `c17969deb0026955` — and it
   must never leave the bench.

Everything from here to a radio is later tasks': storing a file (02), flashing it (03), fetching
it (phase 3). This task's bench item is one console command.
