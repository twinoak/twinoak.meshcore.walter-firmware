# p12-02 — A release from the button

On 13 November Thomas pressed *Run workflow* on a firmware repository's `release` and nothing was
published, because here a run by hand was a rehearsal and a release was a pushed tag with its
notes written by hand first. It is now the other way round, the way meshmaster.dk does it:

| | |
|---|---|
| **the button publishes** | `workflow_dispatch` with **dry run** left unticked, from `main`, is the release. Nothing is typed. The tag trigger is gone — a tag pushed by hand starts nothing — and the tag is made by the publish step, on the commit it published |
| **the version is in the repository** | [`VERSION`](../../../VERSION), one line, `0.1.5` today: the release that comes *next*. The workflow reads it from there and from nowhere else, adds the commit (`X.Y.Z+<sha7>`) and moves the file on to the next patch afterwards |
| **the notes write themselves** | `release-notes/unreleased/<task>.md`, one line per task that changed something a person with a unit will notice, compiled in the order the tasks merged, with `release-notes/standing.md` under them. `tasks/RUNBOOK.md` carries the rule in meshmaster.dk's words |
| **it refuses when there is nothing to say** | three refusals before a byte is built: nothing waiting; the tag of `VERSION` already exists; the run was not started from `main` |
| **what a release still is** | CI green for the commit, the boot gate in QEMU **before** anything is signed, `RELEASE_SIGNING_KEY`, `verify_release.py` over §5 — unchanged, and in that order |

`tools/release/release_notes.py` is all of the new logic (the version, the lines, the order, the
refusals, the move, and whose CI run speaks for a commit); `tools/release/test_release_notes.py`
is its 38 tests, most of them against scratch git repositories with real commits and tags in them.
**This task published nothing and pushed no tag.**

## Deviations from the spec or the task

- **The task says the merged pull request's commit is what the next release's *ci is green* gate
  must read; this repository will usually leave that pull request open instead.** `main` here
  requires the `verify` status check as well as a pull request (`branches/main/protection`:
  `contexts: ["verify"]`), and no check ever runs on a pull request opened with the job's own
  token — GitHub raises no workflow run from events made with it. So the merge is attempted three
  times and then left open, with the run green and the summary saying so, which is the fallback
  the task's deliverable 6 names; it is simply the normal path here rather than the exception. The
  gate's walk-back is implemented and tested anyway, because the moment Thomas merges that pull
  request by hand the commit it makes is exactly the one with no CI run of its own.
- Nothing else. The task and `spec/` do not disagree anywhere this touched: `spec/SYSTEM.md` S-8
  (the key is a secret of the workflow) and S-10 (local first) are both still true of the new
  path, and `spec/FIRMWARE-MANIFEST.md` §2/§4's one version string is untouched — only where that
  string comes from has changed.

## Decisions taken without asking

- **A line is one paragraph, at most 400 characters**, no heading and no front matter, and a file
  that breaks it stops the release with a sentence naming the file. meshmaster.dk's bound is 120
  characters for one line; here a line must also say *what has and has not been on a board*, which
  is a second sentence, so the bound is wider. It lives in `release_notes.MAX_CHARS` and the tests
  read it from there.
- **The merge order is the committer date of the commit that added the file**
  (`git log --diff-filter=A -1`), with the name as a tie-break, and a file not committed yet sorts
  last. meshmaster.dk asks GitHub for the pull request of that commit to put a link beside each
  bullet; nothing here links the task, because `release-notes/README.md` says a line names no
  task — so no GitHub lookup is needed and the order comes out of git alone.
- **`VERSION` moves by one patch.** A minor or a major release is a person editing the file before
  pressing the button, which is the smallest thing that works and keeps the decision with a
  person.
- **A dry run compiles the waiting lines too.** It needs none and is refused for none, but a
  rehearsal of the body is worth as much as a rehearsal of the files, so a dry run's `NOTES.md`
  shows exactly what would be published. The same is true of the local `release` step.
- **The refused merge leaves the run green** rather than red (meshmaster.dk throws). Here the
  refusal is expected on every release, and a release that goes red after publishing successfully
  would teach the opposite of what red means. It is a `::warning::` and a paragraph in the
  summary, and the next release's second refusal is the backstop.
- **The generated part links `docs/flashing.md` at the commit being released**, not at `main` or
  at the tag: a release body is read a year later and must link the guide as it was.

so no bench line is added to `docs/bench.md`. What is left is one thing, and it is a release:

  `branches/main/protection` and off GitHub's own rule about the job token, not measured. If it
  merges, the summary says so instead and nothing needs doing.
