# p16-05 — The room is in the PSRAM

**The firmware is left as it was, and this report is merged alone** (deliverable 6, and the phase's
own README: *if the PSRAM costs memory the start does not have, task 05 leaves the firmware as it
was and merges its report alone, and the run goes on to 06*).

The work was done and it works. `CONFIG_SPIRAM=y` with the memory brought up by the room of a
session and at no other moment, the room 64 kB of PSRAM where there is PSRAM that answers its
pattern and task p16-03's 8 192 bytes where there is not, `heap room`, the rail, the tests: green
host tests, all 27 rails, and the image **boots in the QEMU of the pinned ESP-IDF where there is no
PSRAM at all**. What it does not do is start on a Walter: switching the PSRAM on costs **5 904
bytes of static DRAM**, and what the start had to spare was **644**. The main task's stack then has
no block in any heap and every boot would end in `assert failed: esp_startup_start_app
app_startup.c:86 (res == pdTRUE)` — which is the thing rail R22 exists to refuse, and it refused it.

So the branch carries the whole implementation in its first commit and **reverts it in the second**.
The merged tree is `main` plus this file. The figures below say exactly what would pay for it; the
number to beat is **5 256 bytes**.

## What it costs, in figures

Both built in the same container, in the same tree, minutes apart (`tools/verify.ps1 -Only build`).

| | `main` | with the PSRAM on | delta |
|---|---|---|---|
| `_heap_start` | `0x3fcd27a8` | `0x3fcd3eb8` | **+5 904 bytes of static DRAM** |
| DIRAM `.bss` | 217 136 | 219 120 | +1 984 |
| DIRAM `.data` | 44 148 | 44 996 | +848 |
| DIRAM `.text` (IRAM) | 43 675 | 46 599 | +2 924 |
| DIRAM used of 341 760 | 304 959 | 310 715 | +5 756 |
| the big heap (`_heap_start`…`0x3fce9710`) | 94 056 | 88 152 | −5 904 |
| the tightest big allocation | **644** | 12 568 (it moved heap) | — |
| the main task's stack | 0x3fcf0f68, **FITS with 12 076 to spare** | **no block anywhere** | — |
| image | 827 747 | 835 831 | +8 084 |

**Why 5 904 bytes of static DRAM stop the image starting, when 31 045 bytes of DIRAM are still
free.** It is the packing, not the total (`docs/ARCHITECTURE.md` §14). Three blocks have to be found
before `app_main`: the library's `JobRunner` (69 632), the agent's kept-image scratch (19 456) and
the main task's stack (16 384), out of two usable heaps — the big one after `.bss` and a 32 768-byte
one at `0x3fcf0000`. On `main` the big heap is 94 056: ESP-IDF's own start-up takes 4 320 of it, the
runner 69 632, and the kept scratch fits the 20 100 left **with 644 bytes to spare**; the stack then
goes to the 32 kB heap and has 12 076 to spare. Task p16-04's report named that 644 as "the number
the next task of this phase has to watch". With the PSRAM on the big heap is 88 152, the runner
leaves 14 200, and **19 456 does not fit in 14 200**: the kept scratch goes to the 32 kB heap
instead, and the stack is then left with 10 348 in one heap and 12 572 in the other and needs
16 384.

**The number to beat is 5 256 bytes.** The big heap needs 4 320 + 69 632 + 19 456 = 93 408 and has
88 152. Anything that frees 5 256 bytes of DIRAM `.bss`, `.data` or IRAM `.text` — or shrinks one of
the three blocks by that much — puts the arrangement back to `main`'s, with the stack in the 32 kB
heap and 12 076 bytes to spare. Nothing short of that helps at all: the cliff is a block fitting or
not fitting, so 5 255 bytes buys nothing and 5 256 buys the whole thing.

**What would pay for it.** Four candidates, none of them this task's:

1. **`agent::kKeptScratchBytes`, 19 456 → 14 192 or less** (`components/agent/`). The scratch then
   fits the big heap again and everything else falls into place. It is the biggest image a wake may
   keep for a later wake to apply (task p4-05), so the cost is a bound on that, and it is the
   cheapest of the four to try.
2. **5 256 bytes out of our own static storage.** DIRAM `.bss` is 219 120 bytes and most of it is
   the copied library's; ours is the console, the update verdict, the link client and the wake
   cycle. No single object of ours is that big, so this is a campaign and not a change.
3. **The PSRAM's own cost, cut.** It cannot be: see below, the leanest configuration ESP-IDF offers
   is 64 bytes cheaper.
4. **The main task's stack, 16 384 → smaller.** It does *not* pay: what is left in the two heaps is
   10 348 and 12 572, so the stack would have to come down to 4 kB or less to keep R22's 8 192-byte
   margin, and p0-01 raised it to 16 kB because 3 584 overflowed on a board at the first `lte up`.
   Measured, not guessed: at 8 192 the model says *FITS, with 1 796 bytes to spare*, which is below
   R22's floor and is not an image this repository builds.

**The PSRAM's cost is ESP-IDF's, not this task's configuration.** The 5 904 bytes were measured
again with the leanest arrangement the pinned ESP-IDF allows — `CONFIG_SPIRAM_BOOT_HW_INIT=n`,
`CONFIG_SPIRAM_BOOT_INIT=n`, `CONFIG_SPIRAM_PRE_CONFIGURE_MEMORY_PROTECTION=n`, no
`IGNORE_NOTFOUND`, nothing of the memory touched at boot at all — and `_heap_start` came out at
`0x3fcd3e78`: **5 840 bytes, 64 fewer.** What costs the memory is `CONFIG_SPIRAM` itself: the quad
PSRAM driver, the MSPI timing tuning the S3 always compiles in with it (`SOC_SPI_MEM_SUPPORT_TIMING_TUNING`
is a chip capability and not an option), and their IRAM-resident code. There is no cheaper door.

**And the configuration itself is sound, which is the one thing worth keeping from this.** Built with
the main task's stack at 8 192 bytes so that the model would pass it, the factory image was booted in
the QEMU of the pinned image by `tools/release/boot_gate.py` — the same gate rail R23 is — on a
machine with **no PSRAM at all**:

```
boot gate: twinoak-walter-factory.bin, 901504 bytes into a 16 MB flash, version 0.0.0-dev
    | twinoak-walter 0.0.0-dev
    | heap: 36960 bytes free, largest free block 18432 (internal, 8-bit), the main task's
    |       8192-byte stack already taken ('heap')
    ok    the image reached app_main
    ok    the banner names the version being released
    ok    the heap: line was printed, with the main task's 8192-byte stack taken
boot gate: PASSED: this image starts
```

A board whose PSRAM is not there, is of the other kind, or has stopped answering boots and runs:
`CONFIG_SPIRAM_IGNORE_NOTFOUND=y` makes the chip's own init at boot a log line and not a panic, and
nothing of the *memory* is brought up until a session asks for a room. That is deliverable 2's
second bullet and deliverable 9's gate, shown — for a build that is not the one a unit would get.

## Deviations from the spec or the task

- **The chip's hardware is brought up at boot; the memory is not.** Deliverable 2 asks for the PSRAM
  to be brought up "when a session takes its room and at no other moment", with a second way — at
  boot, with a PSRAM that is not found ignored — if the pinned ESP-IDF has no supported way to do it
  later. It has one, and it is what was taken, but it splits in two:
  `CONFIG_SPIRAM_BOOT_HW_INIT=y` brings up the **chip and its MSPI timing** at boot, and
  `CONFIG_SPIRAM_BOOT_INIT=n` leaves the **memory** — the mapping, the memory test and the heap pool
  — to `esp_psram_init()` in the application. That pair is ESP-IDF's own supported arrangement, not
  a trick: the help of `CONFIG_SPIRAM_PRE_CONFIGURE_MEMORY_PROTECTION` describes exactly it ("In
  case you wish to disable SPIRAM_BOOT_INIT just for delaying the PSRAM initialization and plan to
  use ... esp_psram_init() in the application code"), and
  `components/esp_psram/test_apps/psram/sdkconfig.ci.psram_no_boot_init` is those three lines run on
  the esp32s3 in ESP-IDF's own CI. **Why the hardware half could not also be deferred**: the chip
  init reconfigures the MSPI timing registers, which are shared with the flash this code is running
  from, through ESP-IDF's `mspi_timing_enter_low_speed_early()` and
  `..._enter_high_speed_early()` — functions written for the boot and named for it. It was measured
  both ways (above): deferring it too saves 64 bytes and gives up the arrangement ESP-IDF tests. So
  an ordinary wake maps no page of PSRAM, has no external pool in its heap and asks the allocator for
  nothing — which is what the test holds and what the deliverable is about — but the boot does read
  the chip's ID, and on a board with none it logs one line and goes on.
- **A fifth state of the seam, and three printed lines.** Deliverable 7 gives `heap` three things to
  say. The seam has four — `none` (this build asks for none), `asleep`, `up`, `failed` — because
  `heap` has to tell "nothing has asked yet" from "it was asked and none answered", and a board
  cannot be asked twice in one boot for a chip that did not answer. `none` and `failed` both print
  *none found*, with a clause each saying which.
- **The room line's fourth shape.** The task gives
  `65536 psram of 2097152; internal 27472, block 12288; least 25300`, which is what is printed. A
  board with PSRAM and a build that was handed no heap seam prints
  `65536 psram of 2097152; this build reports no heap figures`, as task p16-03's own line does for
  the small room.
- **The pattern is written over the big room only.** Deliverable 3 asks for a pattern over "the whole
  room"; it is written over the 64 kB of external memory and not over the 8 192 bytes of the internal
  heap. A room that fails is "given back, and the session takes the 8 192 bytes instead", so the
  fall-back is what the test is for — and the internal heap has nothing to fall back to and nothing
  to prove: it is the memory every other block of this firmware already comes out of, and 8 kB of
  pattern at every session would cost a board time for no answer it could act on.
- **`stop` now silences the scripted scanner.** `host_test/sim/scripted_scanner.h` calls
  `forgetPending()` when it is told `stop`. Not a convenience: a step that ends `full` or on its
  clock with half a minute of frames still queued had those frames arrive **while the golden image
  was going back**, which left the radio in text mode and the session `stuck` with *no HELLO inside
  the boot window*. A real NoiseScope's §5 `stop` ends the activity, which is exactly why a session
  says it; the simulator did not, and the first big-room test found it. Task p16-03's and p16-04's
  own cases are unchanged and green.
- **The `room` journal body is 24 bytes and not 20.** The sixth figure is the PSRAM's size. An entry
  a firmware before this task wrote has a 20-byte body and is read with that figure nought, which is
  what its line meant anyway; a test holds that.
- **The heap model learned a new refusal instead of one.** `tools/heap_at_start.py` stopped at
  `CONFIG_SPIRAM` with *"this build has PSRAM; the model was written for the board, which has none"*.
  With the memory left to the application, the heap at the moment the main task is created is the
  internal regions and nothing else, so the model is exactly as true as it was — and it proved it by
  refusing this build for the right reason. It now stops at `CONFIG_SPIRAM_BOOT_INIT` and at `.bss`
  or `.noinit` in external memory, which are the two arrangements it really cannot model.
- No disagreement was found between `spec/` and the task. `spec/SYSTEM.md` §9 still lists *NoiseScope
  as a job* under *later*; the phase's `FOLLOWUPS.md` carries that item for Thomas.

## Decisions taken without asking

- **The firmware is reverted and the report merged alone**, which is deliverable 6 read literally and
  the phase README's own instruction. The alternative — merging it and letting R22 refuse every build
  — would stop the pile at this task and leave `main` unbuildable, which is the one outcome the
  README asks to avoid.
- **The implementation stays in the branch's history rather than being thrown away.** 5 256 bytes is
  a number a later task may well find, and a reverted commit makes that task an afternoon instead of
  a week. The merged tree is byte for byte `main` plus this file, so nothing of it reaches a unit.
- **One `give()` for both memories** rather than a `giveExternal()`. `heap_caps_free` and the host
  fake both know which heap a block came out of; a caller that had to remember would be one `if`
  away from freeing a 64 kB block as an 8 kB one.
- **The external room's size is carried as a figure and not a flag** (`RoomFigures::external`, the
  PSRAM's own size, nought for the internal heap). It is what the line prints, and an external room
  whose chip is nought bytes is not an external room.
- **The pattern is a value of each word's own index** — the FNV-1a prime times the index, exclusive-
  ored with `0xA5A5A5A5`, written a byte at a time because what the seam hands over is bytes and
  nothing in `core/` may assume its alignment. A constant pattern catches a stuck bit and a dead bus
  but *not* the commonest fault, an address line that answers for another one; an index-derived one
  catches all three. The whole room is written before any of it is read back, which is what makes the
  address case visible at all.
- **`heap room` and not `psram test`.** It is the room of a session that is being proved and not the
  chip: on a board with no PSRAM the same command takes the same room out of the internal heap and
  prints the same line, which is the honest thing for a person at a cable to type.
- **The room is taken by one function both doors go through** (`takeStepRoom`), so that what a person
  proves with `heap room` on a cable is byte for byte what a session gets — the bring-up, the 64 kB,
  the pattern, the fall-back and the figures.
- **40 MHz for the PSRAM**, ESP-IDF's default, where 80 and 120 are offered. The one thing in it is a
  64 kB buffer written a line at a time by a 115 200-baud UART; the slowest setting is the one with
  the least to go wrong on a board that has never had its PSRAM up.

## Not verified here (and why)

**Nothing of this has been on a board, and nothing of it is merged**, so there is no bench item to
walk and `docs/bench.md` is unchanged. The ⚠ items the task asks for — `heap`, then `heap room`,
then `heap` on a Walter alone; `rak session 60 scope 863 870 250 0 1000` on a board with a radio; the
boot's `heap:` line against `main`'s; a wake with no session as long as it was — belong with the
firmware that has the commands, and would be written by whatever task brings this back.

Two things no test here could reach, and one that this report settles:

- **Whether a real PSRAM answers.** No test can bring one up: QEMU's esp32s3 has none, which is what
  the boot gate above proves and all it proves. `tasks/phase-16/FOLLOWUPS.md` already carries the
  item, and it stands: *the PSRAM has never been brought up on a board by this firmware.*
- **Whether 64 kB is the right room**, and what a real NoiseScope sends in a minute. Every figure
  about the room still comes from the scripted scanner, as task p16-04's report says; the `room` line
  is in every session's journal so that the next figure comes from units.
- **Whether the 5 256 bytes can be found** — which is not a bench question but a memory one, and the
  four candidates above are where to look. The first of them, the agent's 19 456-byte kept-image
  scratch, is the only one that is a single number.
