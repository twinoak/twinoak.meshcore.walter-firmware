# p16-02 — an offer into the scanner slot

`twinoak.fw.offer`'s payload gains one member at its end, `into`. Left out, or `candidate`, the
offer is byte for byte the offer of today and every test of it passes untouched; `scanner` sends
the same fetch into the scanner slot. Everything else about an offer is unchanged, because
nothing else had to change: `core::update::Fetch::run` has taken a `Which` since phase 3 and
`core/image/receive.cpp` already derives the role from the slot — *golden and candidate are the
radio's working firmware, the scanner slot holds NoiseScope*. So the work was in three places:
reading the member and refusing the words that are not an offer's (`runOffer`), reading the
progress of the slot the offer names rather than always the candidate's (`runOffer`,
`WakeCycle::stepSleep`), and a release fixture with **both** images in one signed manifest, which
is what a choice between them needs to be shown at all.

Two things were done that the task names but the firmware did not have. They are under
*Decisions* and *Deviations* below: the **stored-already** answer (deliverable 3 says *as a
candidate's does*, and a candidate's did not), and rail R18, which had to be told that
`Store::verify` is a read.

## Deviations from the spec or the task

- **Deliverable 3's *as a candidate's does* was not true.** The task says an offer for an image
  the slot already holds *answers `stored` and fetches nothing, as a candidate's does*. A
  candidate's did not: `Store::beginWrite` resumes only a slot that is `!present && transfer`, so
  a **present** record sends it down the fresh-write path — the record voided, the header sector
  erased, and the whole file downloaded again to be committed a second time. Nothing above it
  short-circuited either (`Fetch::fetchInto` has no such step, and the download's *the sink
  already holds the whole file* path is unreachable because `written()` is 0 after a fresh
  `beginWrite`). The acceptance criterion is explicit and testable, so it was built rather than
  reported as unmet: see *Decisions*. The candidate's offer is the same code and gains the same.
- **Rail R18 now takes `verify` as a read.** `tools/check_rails.py`'s `STORE_READS` listed
  `read`, `isBad`, `begin`, `records`, `badCount`; anything else the agent asks of the store
  breaks the rail, on the ground that *everything that writes takes a token of the verdict*.
  `Store::verify` is a `const` method that reads an area back and compares its SHA-256 with the
  record's — it cannot erase, write or commit, and it cannot make an image out of bytes; it can
  only say that bytes which already passed the six checks still hash to what the record promised.
  It is on the list now, with that reasoning in the file beside it. The rail's rule is kept, not
  widened: the agent still reaches the store's write door through nothing but
  `core::update::Fetch`, which `must_contain` still holds.
- **`spec/` says nothing about `into`.** It is meshmaster.dk's `docs/dev/unit-protocol.md` §4–§5
  and that repository's task 235 that the contract belongs to, as the task file says; nothing under
  `spec/` disagrees with anything built here. `spec/FIRMWARE-MANIFEST.md` §4 was read for one
  thing: the rule that an image's `id` is `<role>.<board>.<band>`, which is how the stored-already
  answer composes an `imageId` the store's record does not keep.

## Decisions taken without asking

- **The stored-already answer is keyed on `expectedSha256` and the record, and it verifies.** The
  payload's hash is the one thing in it that names a *file* rather than a release, so it is what
  the record is compared against; a payload with no hash skips nothing and is fetched as it always
  was. A record exists only because `commit()` took the token of all six checks, so a present
  record whose hash is the server's **is** that file, stored and judged. `verify()` is then called
  before the promise is made, so a slot whose bytes have rotted since is downloaded again rather
  than promised to the server and failed later by the apply's own precondition. The answer is
  `stored` with the image id, the hash and the slot's byte count, and the wake records the
  `kFetchRelease` ask as carried with no time spent outside — which is the whole point of it.
  Cost: one pass over the area in flash, against a few hundred kilobytes over a metered link.
- **`into` is read as *the member is there* and only then *the word*.** `json::text` answers false
  both for a member that is not a string and for a word longer than the buffer, so asking for the
  text alone would read `"into":"<something very long>"` as *absent* and quietly fill the
  candidate. The member's presence is asked first (`json::member(...).found()`), and only a word
  that is exactly `candidate` or `scanner` is an offer's: `whichFromName` knows all four names, and
  `golden` and `base` are refused in words, because the golden image is reached by a promotion and
  the base by `rak provision`.
- **The shortened sleep asks about both downloadable slots.** `stepSleep` read
  `Which::kCandidate` only. A scanner image is fetched by the same ranges into the same kind of
  progress record, so a half-done one is a download the next wake continues too and is worth the
  same few extra wakes of a pack that can pay for them. The golden image is never downloaded into
  and the base is `rak provision`'s, so neither is asked about.
- **One fixture release with both images, rather than two releases.** `store-both` is one manifest,
  signed once, naming `repeater.rak4630-single.868` and `scanner.rak4630-single.868` with a file
  and a descriptor each, surfaced as the two existing-shaped rows `store-both-repeater` and
  `store-both-scanner` that share the manifest and the signature. A release with one image cannot
  show a choice being made, and a manifest merged inside a test cannot be signed by the test key.
  Both files are 150 000 bytes so that two of the store's 64 KB resume points fall inside one and
  the budget case has somewhere to stop; `bench::swdNameFor(manifest, role)` serves the second
  file, since `swdName` takes the manifest's first swd entry.
- **The scanner slot was already covered by pile 15's task 01** (the task asks this explicitly).
  Yes, and by construction rather than by luck: p15-01's rule lives in `Store::readProgress`,
  which is given the header offset of whichever area was asked for and reads *that* record's magic
  word, and `Store::read` is the only way anybody reaches a slot. So a scanner slot whose record
  was voided reads as empty for the same reason a candidate's does. The two ways a scanner slot can
  be void are also narrower than the candidate's: `promote()` swaps the golden and candidate areas
  and never touches the scanner's, so only `erase` (the console's `image erase scanner`) voids it —
  and `erase` takes the header sector in the same call, so the markers go with the record. The new
  wake-cycle case reads both halves of that.
