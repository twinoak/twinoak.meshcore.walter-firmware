# p8-05 — Link 1.1: the band

6 November, job 20990, *read the unit's state*: `{"slot": 0}` and nothing else. The Walter had no
golden image, so it fell back on `HELLO`, and `HELLO` had no band — and meshmaster.dk picks a
release's image by role, board **and** band (`FirmwareRollout.PickImage`), so the canary page said
*Read the unit's state first* for ever and a radio that had never had a first install through its
Walter could not be offered one over LTE.

The reviewer changed the specification that evening: link **1.1** ends `HELLO`'s answer and
`EV_BOOT` with `band`. This firmware now asks in 1.1, keeps the band, prints it and reports it.

**One version, said once.** `codec/wire.h`'s `kProtoMinor` is 1, and `image/this_image.h`'s
`kLinkMinor` is now *defined as* `link::kProtoMinor` rather than being a second copy of it — so the
descriptor in the image cannot claim a minor its `HELLO` does not ask for. The release tooling's
`LINK` is the third place the number appears and the release holds it against the descriptor it
finds in the built image (`hold_against_entry`), which is what makes that copy safe.

**The band is read off the body's own `proto_minor` and off nothing else.** A 1.0 radio answers a
1.1 request with a 1.0 body and no band; the session then says none, and — because `sessionFromBody`
copies the decoded (empty) band every time — a radio flashed back to a 1.0 image does not leave the
1.1 image's band behind. Nothing compares the *minor* anywhere else: `image/choose.cpp`,
`image/file_check.cpp` and the update's health check compare the **major**, so a 1.1 Walter still
accepts, flashes, proves and talks to a 1.0 repeater image. That had to stay true: the unit on the
bench runs repeater v0.1.0.

**And the fakes were taught the board's behaviour**, which is what hid the gap from the host tests:

- `sim::ScriptedRadio` gains a `band`. Empty — the default — and it is a **1.0 radio**: the
  fixtures' 1.0 body, minor 0, no band, which is what v0.1.0 does. Set, and it answers a 1.1 body:
  minor 1 and the band at the end, byte for byte the fixtures' *hello response, 1.1: the band at the
  end*, which a test holds it to.
- `radioBoots()` (both copies, `chip_radio.h` and `update_bench.h`) now takes the band from the
  descriptor of the image on the simulated chip, **and only if that descriptor says link 1.1** —
  `f.link_minor >= kBandMinor`. So the fake radio says a band for the same reason a real one does,
  and `update-golden-link-1-1` is the one generated fixture image built against 1.1.

## Deviations from the spec or the task

- **`status` shows the band on the radio's line, not beside a board it never showed.** The task says
  *"`status` shows it where it shows the board"*. `status` shows two boards: this firmware's own, on
  the `unit:` line, which has had `band lte-m` beside it since p0-02 — and the radio's, which it
  does not show at all (the radio's line is role, version, slot, link; `rak hello` is the command
  that prints its board). So the band went where the radio's other three words are, between the slot
  and the link version, which is the same reading order the `unit:` line has.
- **`rak hello` prints the band on a line of its own** rather than appending it to the firmware /
  board / upstream line. The two sentences the task asks for verbatim are `band 868` and `band: not
  said (a 1.0 radio)`, and the second on the end of that line makes it 112 characters; `status` and
  `rak hello` are read in a terminal window (`docs/bench.md` §14) and the file already splits lines
  for that reason.
- **Nothing of the item's second option was needed.** `phase-6/FOLLOWUPS.md` offered *either* the
  state brings `HELLO`'s band *or* meshmaster.dk says on the canary page that a first install comes
  over the cable. The link carries a band now, so the first is done and the second is not needed —
  except as the truth about a 1.0 radio, which `docs/field.md` now states.

## Decisions taken without asking

- **`kLinkMinor` is the codec's constant, not a copy of it.** `image/this_image.h` now includes
  `core/link/codec/wire.h` and defines `kLinkMajor`/`kLinkMinor` as `link::kProtoMajor`/
  `kProtoMinor`. The alternative was a `static_assert` holding two copies together, which is the
  same coupling with a way to get it wrong in between. The descriptor's link version *is* the box
  link this firmware speaks; deriving it removes the whole class of divergence, and the one
  remaining copy (the release tooling's `LINK`, which is Python) is already held against the built
  image's descriptor before anything is published.
- **`Session::band` is 16 bytes, and a longer band is truncated and counted with the versions.**
  `FIRMWARE-MANIFEST.md` §4 gives the descriptor's band field 8 bytes including its terminator;
  16 leaves room for a word the manifest does not have yet. A band too long is not a protocol error,
  so it is kept truncated and `counters().long_versions` goes up — the same rule the three version
  strings have had since p1-02, and the counter's comment now says *strings* rather than *versions*.
- **The band is told apart from "not said" by `band[0] != 0`, and the *reason* by `proto_minor`.**
  So `rak hello` says `band: not said (a 1.0 radio)` where the radio is one, and
  `band: not said (a 1.1 radio)` if a 1.1 radio ever answers with an empty band string — a lie
  avoided for the price of two format arguments.
- **An empty band is not written to `twinoak.fw.state`; the key is left out.** The server reads a
  present-but-empty band as unknown, so the two are equivalent to it today — but a slot that has
  never been told its band and one whose band is the empty string are different things, and the
  journal of what a unit reported should not blur them.
- **The scripted radio's default stays a 1.0 radio.** The fake could have been made a 1.1 one and
  every existing expectation adjusted. It is not: the radio on the bench runs repeater v0.1.0, every
  generated fixture image but one is built against link 1.0, and the pairing this phase must keep
  working is a 1.1 Walter talking to a 1.0 radio. A 1.1 radio is a knob a test turns on.
- **`linkFixture()` stays 1.0's file; `linkFixture11()` is the new one.** The scripted radio answers
  from `linkFixture()` and the client's and the sim's tests read it, so making it the 1.1 file would
  have changed what every one of them meant. The codec's own test walks both files, which is where
  the obligation to pass every case of both lives. `linkCaseIn(fixture, name)` is how the two tests
  that want particular bytes name them by the specification's own words.
- **The 1.0 Walter's `HELLO` request bytes are no longer compared byte for byte.**
  `test_link_client_requests.cpp` walks 1.0's request cases and calls each; §5.1 says a Walter asks
  for the highest minor **it** knows, so the minor this firmware sends is `kProtoMinor` whatever the
  case was written by. That test now holds bytes 0, 2 and 3 to the case's own fields and byte 1 to
  `kProtoMinor`, and the byte-for-byte comparison moved to one new test in
  `test_link_client_session.cpp` against the fixtures' *hello request, 1.1* — the case of the minor
  this firmware speaks.
- **A new generated fixture image, `update-golden-link-1-1`.** One page, a repeater, descriptor and
  manifest both saying link 1.1: the only image in `host_test/fixtures/` that makes the simulated
  chip's radio answer with a band, which is what the state report's first subcase needs. Every other
  one stays a 1.0 image on purpose. `store_image()` gained a `link_minor` argument for it, which it
  writes into both the descriptor and the manifest's `link.minor`.

## Not verified here (and why)

A session cannot open the Walter's port or the radio's, and this pile runs at a desk
(`tasks/phase-8/README.md`: *Not on the board*). Both lines are at the end of `docs/bench.md` §18:

1. **The band a 1.0 radio does not say.** With repeater v0.1.0 on the radio — the unit's state this
   morning — `rak hello` says `band: not said (a 1.0 radio)` on the line after the firmware and the
   board, and `status`'s radio line says `band not said`. Everything else about the session is as
   before: this is the 1.1 Walter talking to a 1.0 radio, the pairing the whole phase must keep
   working.
2. ★ **The band a 1.1 radio does say, and the state read without a golden image.** With repeater
   v0.1.1 (the repeater firmware's pile 3.8) `rak hello` says `band 868` and `status` says `band
   868, link 1.1`. Then, **before** `rak update --first-install` has made anything golden, *Read the
   unit's state* on meshmaster.dk must report `role repeater`, `board rak4630-single` **and** `band
   868`, and *Mark canary* must offer the release instead of saying *Read the unit's state first*.
   That is the item job 20990 failed on, and the band was the only one of the three words missing.
   If the slot still reports no band while `rak hello` says one, the state report is not reading the
   session.

Also not verified here, and not this task's: the radio's side (the repeater firmware's pile 3.8 is
what makes a radio answer in 1.1 at all — until it lands, line 2 cannot be walked), and
meshmaster.dk, which already reads `band`.
