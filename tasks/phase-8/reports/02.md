# p8-02 — The transfer in bytes

One session. `tools/verify.ps1` **green in 398 s** on the commit this PR is (spec 0 s,
spec-tools 1 s, deps 10 s, host-tests 351 s, release-tests 1 s, build 33 s, partitions 0 s,
release 1 s); `core_tests` **1,016 test cases, 717,083 assertions, 0 failed**, and the `walterctl`
ctest **40 checks, 0 failed, 3.40 s** (the 86-chunk push included). The image is 751,959 bytes.

The fault is one sentence long: the transfer's answers are frames and they went out through
`TextOut::write`, which turns every `0x0A` into CR LF for a terminal — so the answer naming chunk
10 was corrupted every time and the laptop sent chunk 9 for ever. The fix is a second way out of
`TextOut`: `writeBytes`, verbatim and whole, which `Receiver::respond` uses; and the conversion
moved into `core/console/crlf.h`, which the console host of `host_test/` now calls too, so the host
tests see the bytes a board sends.

## The failure, reproduced before the fix

Commit `dd29ca4` is the first half alone: the conversion in `core/console/crlf.h`, the console
host's `TextOut` calling it, and the 86-chunk push in `tools/test_walterctl.py` — **and none of the
fix**. The walterctl test then failed exactly as the unit did on 6 November
(`out/experiments/p8-02-before.log`, git-ignored):

```

  no answer to type 0x03 seq 9; sending it again

  no answer to type 0x03 seq 9; sending it again
```

`again` among the bytes is the console's answer to a chunk it had already taken, printed as text
because walterctl could not read it as a frame — the same thing the 6 November transcript shows.
With the second commit in, the same test is **40 checks, 0 failed**.

Two notes on the chunk count. The push that already existed was 17 chunks of image (4,096 bytes),
so *length* was never what the host tests lacked — the conversion was; the 86-chunk push is added
because the task asks for it and because it is the first one whose byte counts pass 2,640
(`0x0A50`), the second place a `0x0A` appears in an answer. And the failure is at chunk 9 either
way: that answer carries `expect_seq` 10.

## Acceptance checklist

- [x] **Frames are written verbatim and never cut short; the conversion lives in one helper that
  the console host uses too.** `interfaces::TextOut::writeBytes(bytes, count) -> bool` beside
  `write`, **pure virtual** (all three implementations give it: `platform::UsbConsole`,
  `host_test/console_host/`'s `StdOut`, `fakes::CaptureOut`). On the platform it loops until the
  driver has taken every byte or `kBytesTimeout` (1,000 ms) has passed, keeping the remaining ticks
  as an unsigned difference so a tick-count wrap is still right, and returns `at == count`.
  `Receiver::respond` writes §2's leading `0x00` and the frame in **one** call (the `0x00` goes
  into `frame_[0]`, which is what `kMaxWrite` = 247 is for) and counts a short write in
  `cutShort()`; `transferEnded` prints *`N` answers the port would not take whole* when it is not
  zero. `respond` was the only binary path through a `TextOut` in this firmware (`grep` for a
  `reinterpret_cast<const char*>` into `write`: one hit, that one; the LTE fetch writes the store
  directly and the link client writes a `ByteStream`). The conversion is
  `core::console::toCrlf(text, length, out, capacity)` — into a buffer the caller gives, which is
  what lets `UsbConsole::write` keep its own 20 ms-and-drop bound for text while a frame gets a
  second of patience. Tests: `host_test/core/console/test_crlf.cpp` (three cases) and
  *a port that will not take a whole answer: the Walter counts it*.
- [x] **With the helper in and the fix not, the >10-chunk push fails as on the board (in the
  report); with the fix, it passes, and so does the `respond` test.** *The failure, reproduced
  before the fix* above. The `respond` test is *an answer that holds a 0x0A comes out byte for byte
  through a converting console*: ten chunks of a manifest, then the answer to chunk 9 compared
  **byte for byte** against the frame the laptop builds itself with the link's own codec, through a
  `fakes::TerminalOut` that converts text exactly as a board does. `fakes::TerminalOut` is now what
  the whole of `test_receive.cpp` reads its answers out of, so every one of that file's 16 cases
  runs against a board's output rather than a verbatim pipe.
- [x] **walterctl chooses the undo by the Walter's own word; the reviewer's changes are reviewed
  and kept or fixed; `SerialPort.read` has a test.** The word is the console's **ready line**, in
  text, before a frame goes either way: `… framed binary transfer (protocol 2)`, and a line with no
  such word is a Walter at 0.1.0 (version 1). Then `undo_crlf_needed(version, on_a_port)`: the undo
  goes on for version 1 over a serial port and in no other case. The hello's own version word is
  held against that choice and a disagreement stops the push. Tests, in
  `tools/test_walterctl.py`: the ready line of a 0.1.0 Walter, of a 0.1.1 one, of a 0.1.1 one whose
  read stops in the middle of the line (the one bug this had while being written), a console that
  did not open a transfer at all, and the four rows of the undo's truth table; and
  `SerialPort.read` against a fake port — the whole answer in one call with reads of 1 then 6 bytes
  and nothing waited for, one byte alone with no second read, and a silent port returning `b""`
  having waited its timeout once.
- [x] **Docs updated; the `../phase-6/FOLLOWUPS.md` item ticked.** `docs/console.md` (*image

## Deviations from the spec or the task

- **The version does not come from `status`'s first line.** The task offered that as the fallback
  if version 1's hello can itself be corrupted — it can, so a fallback was needed — but `status`'s
  first line is `core::banner()`, the *firmware* version, and reading the protocol off it means
  comparing versions: a developer's own build of this branch says `0.0.0-dev`, which is older than
  `0.1.1` by any comparison and newer than it in fact. The console's ready line is printed by the
  very command that opens the transfer, costs no extra round trip, and says the protocol's own
  number; absence of the word is version 1, which is deterministic for every Walter that ever
  shipped. `walterctl` refuses to send a frame at all if no ready line comes back, which is a
  better message than the old *no answer to 4 attempts* for the case where `image receive` was
  refused.
- **`--undo-crlf` stays, and changed meaning.** It is no longer "take the conversion out" (which is
  now automatic) but "take this to be a protocol-1 Walter without asking its console", for one whose
  ready line cannot be read. It is the only thing left that can reach `UndoCrlf` over a pipe, and
  the hello's version word refuses it against a Walter at 0.1.1 or newer — so the warning the flag
  used to carry in prose is now enforced.
- **`tools/test_walterctl.py --generated` is required.** It was optional and `host_test/
  CMakeLists.txt` always passed it; the 86-chunk push needs it (the image comes from host_test's
  generated fixtures, made from the spec's test key through `spec/tools/manifestref.py`, as the
  task asks), and an acceptance criterion should not be behind an `if`.
- Nothing in `spec/` disagrees with this task. §2's framing is unchanged — the same bytes, written
  the same way; what changed is the firmware's path to the port.

## Decisions taken without asking

- **`writeBytes` on `TextOut`, not a second interface for the receiver.** The task left the choice.
  One interface, because the port is one thing and the two ways out are a property of *it*: the
  platform's console is the object that knows the terminal wants CR LF, and a receiver handed a
  separate `ByteOut` would still have to be given the same object by `main`, with nothing holding
  the two to the same port. It is **pure virtual** rather than a default that forwards to `write`:
  a default would have made exactly this fault compile silently in the next implementation.
- **The raw write's bound is 1,000 ms**, against 20 ms for text. A frame is at most 247 bytes into
  a 1 KB transmit buffer, so a host that is reading at all never comes near it; a host that is not
  gets a second and a `false`. walterctl waits 5 s for an answer and the transfer gives up after
  20 s of silence, so a second of blocking costs a retry at worst. The 20 ms for text is kept
  deliberately: *drop what does not fit* is right for a line on a mast, and that is why the helper
  converts into the caller's buffer instead of writing through `writeBytes` itself.
- **A short write is counted, not retried and not escalated.** To the laptop an answer that went out
  in part is an answer that was lost, and the laptop's timeout is the recovery — the same rule §2
  gives for a dropped frame. What the Walter owes a person at the bench is to say that it happened,
  which is `transferEnded`'s extra line, printed only when the count is not zero.
- **The protocol's version is spelled out in the hello's text** (`"walter image receive 2"`) with a
  `static_assert(transfer::kVersion == 2)` beside it, because `core/image/` holds no formatting (the
  no-allocation test). The console's ready line formats it from `kVersion`.
- **`fakes::TerminalOut` replaces `CaptureOut` in `test_receive.cpp` only.** Every other test reads
  the console's *words*, and converting there would have meant editing expected strings all over
  the suite for no gain. `CaptureOut` keeps writing everything verbatim and says so.

## Not verified here (and why)

No session opens the unit's ports in this pile (`tasks/phase-8/README.md`). The host tests run the
transfer against the conversion a board does, which is the whole point of this task, but nothing
here has had a USB Serial/JTAG peripheral under it. Added to `docs/bench.md`:

- **§8, a whole repeater release pushed in, timed** — `walterctl.py push --as candidate` of a real
  release (400 kB and more, about 1,740 chunks) into a v0.1.1 Walter: `the console: protocol 2`, a
  progress line every tenth, `stored as the candidate image`, then `image verify candidate`.
  **Seconds, not hours** is what the item is for, and the wall-clock figure is the one to bring
  back — the laptop's end waited out its 5 s reply timeout for every chunk until 6 November, which
  was two and a half hours for one image.
- **§8, the same push into a Walter still at 0.1.0, with nothing typed** — only if such a unit is at
  hand: walterctl must say *a Walter at 0.1.0 or older: taking its console's CR LF back out of its
  answers* and the push must finish. And `--undo-crlf` against a v0.1.1 Walter must be **refused**:
  *this push was set up for protocol 1 and the hello says 2*.
- **§10** — the `self receive` push already has an item; it gains the protocol line and the note
  that this transfer was broken in the same way until v0.1.1.

Two things no bench item can cover and which are worth knowing: the 1,000 ms bound on a frame's
write has never met a USB host that stopped reading mid-frame (the *answers the port would not take
whole* line is what would show it), and nothing here has seen `usb_serial_jtag_write_bytes` return
a short count at all — the loop is written for it because the driver's contract allows it.
