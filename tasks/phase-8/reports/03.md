# p8-03 — one connection, one socket

The second HTTPS request of a wake failed on the first unit three wakes in a row on 6 November,
and with one of them a job meshmaster.dk had already leased (21026) died with its one attempt. The
cause was read from the code and is in `../phase-6/FOLLOWUPS.md`: every connection was socket 1
and `WalterTlsSocket::open` cleared the one close flag before it dialled, so the close of the
*previous* connection — a `+SQNSH: 1` the library queues and dispatches a moment later — landed on
the next one. `send` stopped (*the request did not go out*) or `receive` ended early (*the
connection closed before the body was complete*).

The rule is now `core/net/socket_rotation.h`, with no modem in it, and the modem layer is a thin
caller. The fake socket of the host tests has become the modem's socket layer: a connection is on
an id, the server's close is an **event** on that id, and `close_event_lateness` is how late the
library is with it, counted in connections. `as_v0_1_0` puts the released rule back, so the test
that shows the fault keeps showing it.

## The rule, in one place

- **Two ids, turn and turn about.** A close belonging to the connection before this one names an
  id this one is not using. The flags are per id, so a ring or a `DISCONNECTED` for the other id
  changes nothing here.
- **A close can be owed.** A connection that ends without its close having been seen leaves that
  id owing one — the server's `+SQNSH` is still on its way. At most one per id: a socket's life
  produces at most one close.
- **A connection on an id that owes a close waits for it, briefly, and then discounts the first
  close it gets.** The wait is `kOwedCloseWaitMs` = 250 ms in steps of `kOwedCloseStepMs` = 10 ms,
  one FreeRTOS tick, so every step is a `vTaskDelay` and the task that delivers the event can run
  (task p8-01's lesson). If the close has still not come, the connection goes ahead and the first
  close seen on that id pays the debt instead of ending the connection. **That is the answer to
  "two connections late"** — with two ids, a close two connections late arrives on the id coming
  round again — and it is deterministic: the debt is paid by exactly one close event, whenever it
  turns up.
- **A debt nobody pays.** A close that is owed and never delivered cannot be told, from inside the
  rule, from one that is merely very late, so that id's accounting would stay one close behind for
  the rest of the modem's life: every connection on it waits 250 ms in vain and then has its own
  close discounted (`test_socket_rotation.cpp`, *a debt nobody pays stays*, makes it happen and
  measures it). No byte of a response is lost by that — the parser, not the close, is what ends
  one, and every response this firmware asks for carries a Content-Length or is chunked — but the
  wait is real. So **a close is owed only for a connection the other end answered**: a response
  arrives under `Connection: close` with the server's FIN behind it, while a handshake with no
  request behind it (`core/update/tls_check.h`) or a dial that failed has no close coming.
  `WalterTlsSocket` tracks whether `receive` ever returned a byte and calls `end()` or `cancel()`
  accordingly.

## Deviations from the spec or the task

**The two ids are 1 and 6, not 1 and 2, and the second one has to be asked for through a
deprecated call.** The task and the phase-6 item both say "1 and 2". Read at the pinned
`walter-modem` 1.5.0 (`managed_components/dptechnics__walter-modem/`), that is not reachable:

- `WalterModemSocket` (`src/WalterModem.h`) default-initialises `id = 1` for **all six** entries
  of `_socketSet`, and `_socketGet(id)` (`src/proto/WalterSocket.cpp`) returns the first entry
  whose id matches. So `socketConfig(1)` finds entry 0 and `socketConfig(2..6)` find nothing —
  `NO_FREE_SOCKET`, returned locally with no AT command going out. Every socket call goes through
  `_socketGet`, so an id no entry carries is unusable.
- The only thing that renumbers an entry is `_socketReserve()`, which takes the topmost `FREE`
  entry and gives it `id = i + 1` (so a fresh set yields `WALTER_MODEM_MAX_SOCKETS` = 6). It is
  private, and the only public way to it is the **deprecated** `socketConfig(rsp, cb, args, …)`
  overload with no id — `[[deprecated]]`, and this project compiles its own components with
  `-Werror=deprecated-declarations`.
- Which id it handed out cannot be read back: the wrapper writes it into `rsp->data.profileId`
  and `_queueModemCMD` then does `*(cmd->rsp) = {}` before the command is queued
  (`src/WalterModem.cpp`).

So `WalterTlsSocket::askForASecondSocket` calls the deprecated overload once per modem start,
inside a two-line `#pragma GCC diagnostic` for that one call, and then finds the id by asking for
6 down to 2 with the supported overload — each id no entry carries is a local `false` and costs
nothing, and the first one accepted is the entry just reserved. **When the library gives none the
rotation runs on one id and the owed-close rule alone**, which `test_late_close.cpp`'s *one socket
id and nothing else* shows carrying a wake (at the cost of one 250 ms wait per connection); and a
`socketConfig` that fails on the second id — a modem whose socket set has been reset under us, its
ids all 1 again — drops it, falls back to id 1 for that connection and asks again at the next
modem start.

Two things about this that are worth a second pair of eyes and are in *Not verified here*: the
`+SQNSH: ` URC handler does `_socketGet(sockId)->state = …` **with no null check**, so a
`+SQNSH` for an id no entry carries would dereference null — which cannot be reached from here
(an id with no entry cannot be dialled either), but is a reason not to invent ids; and
`_socketReserve()->id` is dereferenced without a null check too, which needs one `FREE` entry of
six and is guaranteed right after a modem start, where this call is made.

## Decisions taken without asking

- **250 ms for the wait, in 10 ms blocking steps.** The close is queued by the URC parser the
  moment the server's FIN arrives and dispatched some milliseconds later (the library's event task
  takes an event off the queue, `vTaskDelay(10)`, then dispatches), and by the time the next
  connection is being opened it has long arrived — so this is spent only when something has gone
  wrong, and a quarter of a second is ten times the slack the dispatch needs. Marked *TO BE SET ON
  THE BENCH* with a row in *What to bring back*. The 10 ms step is one tick at
  `CONFIG_FREERTOS_HZ` = 100, so each step is a `vTaskDelay` and not a busy wait: the event being
  waited for comes from another task.
- **Two ids and no more.** A third would only move "two connections late" to "three connections
  late"; the debt covers both the same way, and every extra id is another deprecated reserve.
- **A close is owed only for a connection the other end answered** (above). The alternative —
  owing one for every connection — leaves a permanent debt behind every handshake-only connection
  and every failed dial.
- **The fake's close is queued when the server answers, not when the firmware stops reading.** The
  scripted server answers and closes (`Connection: close`), so its close is on its way the moment
  the response is. With the default lateness of 0 that is the behaviour every test written before
  this task already had, which is why none of them changed.
- **The bounded wait is tested in the rotation's own tests, not through the fake.** The fake
  delivers its late events *after* `begin()` has cleared the flags — the board's race and the
  harsher case. A close arriving *during* the wait needs something to act in the middle of a
  delay, which is `FakeClock::on_delay`, so that case is `test_socket_rotation.cpp`, *the wait
  ends the moment the owed close arrives*.

## Not verified here (and why)

No session opens the unit's ports in this pile (phase 8's README), and nothing of the modem's
socket layer can be run without a SIM and a tower. The three lines are in `docs/bench.md` §13:

1. **`http get https://meshmaster.dk/` twice in a row, twenty times — forty answers of 200.**
   This is the item v0.1.0 failed. Pairs are the point: a single request always worked. Write down
   the two times of each pair; if the second is reliably about 250 ms slower, the owed-close wait
   is being spent every time and the second socket id was not granted — the firmware is running on
   one id, which works but is the degraded case.
2. **`agent wake` with config, heartbeat, claim and observations all `done`** — four requests, four
   connections, two ids alternating. On 6 November the second step failed every time.
3. **A job claimed, run and its result posted in one wake** — the expensive half of the fault: the
   claim's answer was lost after the server had leased job 21026.

And three things only the board can answer, which no host test here claims to:

- **Whether the second socket id is granted at all.** The reserve is read from the library's
  source and cannot be tried without a modem. If `AT+SQNSCFG=6` is refused by the GM02SP, or the
  reserve hands out an id outside 2–6, the firmware falls back to one id and the owed-close rule,
  which the host tests show carrying a wake. Line 1 above is where that shows.
- **Whether the modem emits `+SQNSH: <id>` for a socket this end closed with `AT+SQNSH`.** The
  rule copes either way (the debt absorbs one, and a connection that was not answered owes none),
  but it decides whether the debt is normally paid at once or waited for, and the GM02SP's AT
  manual — which this session could not read — is where it is written down.
- **That a second socket costs nothing in the modem's own bookkeeping.** `+SQNSS: <id>,<status>`
  for an id of 5 or 6 is dropped by the library (`sockId < (WALTER_MODEM_MAX_SOCKETS - 1)`, which
  looks like an off-by-one of its own), so the library's idea of socket 6's state is only ever
  what our own commands put there. Nothing here reads that state, but `AT+SQNSS?` by hand after
  line 1 would show whether the modem and the library agree.
