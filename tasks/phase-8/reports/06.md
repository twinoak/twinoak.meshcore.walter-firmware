## The question the task asked: can a unit at 0.1.0 reach 0.1.1 over LTE?

The task says *a self-update fetches from github.com, whose root the modem refused on 23 October*.
Read at this commit, and at `v0.1.0`'s, that is not what the code does.

- **The only path to the Walter's own image over the air is a `twinoak.fw.offer` whose product is
  the Walter's**, and its base URL is built in `components/agent/firmware_jobs.cpp`
  (`snprintf(base_url_, …, "%s%s", server_.url(), base)`) — `{server.url}{base}`, the manifest at
  `{base}/manifest.json` and the files at `{base}/files/{name}`. That is **meshmaster.dk**, not
  github.com. `Fetch::runInto`, the entry that takes a transfer target rather than a store slot, has
  exactly one caller in the firmware, and it is that line.
- **meshmaster.dk is held to ISRG Root X1, root 0** — the root that loaded into slot 12 and matched
  at the first request on the first board on 23 October. `components/core/net/trust.cpp`'s host
  table has **one** row, `{"github.com", kRootUserTrustEcc}`, and every host in no row falls to
  `kRootIsrgX1` — including the `githubusercontent` host a GitHub release download redirects to.
  So USERTrust ECC, the root that modem refused, is asked for by one thing only: a person typing
  `fetch https://github.com/…` at the console, which writes a **radio** image into the store and
  never this firmware's own slot (`docs/console.md`, the `fetch` row: `candidate` or `scanner`,
  never the Walter).
- **So a 0.1.0 unit could in principle be offered `v0.1.1` over LTE**, and from `v0.1.1` onwards
  that is the way: *Offer a release*, then an apply, whose result the next wake posts.

What does hold is the *conclusion* — the cable, for this one unit — for a different reason, which
`docs/flashing.md` now gives:

- **0.1.0 cannot be relied on to carry its own download.** An offer is many HTTPS connections in
  one wake: the config, the heartbeat, the claim, then the manifest, its signature and a range per
  wake budget. On 0.1.0 the *second* connection of a wake was the one that failed (`the request did
  not go out`, three wakes in a row on 6 November), which is the fault p8-03 fixes. The firmware
  that would have to fetch the fix is the firmware with the fault.
- And the radio needs a cable in that session anyway, so the Walter's own flash costs nothing
  extra, against 752 kB over LTE-M on a metered SIM across several wakes.

The phase-6 item (`[02]`, *the modem refuses root 1*) is therefore **not a blocker for a
self-update**; it is a blocker for the console's `fetch` of a repeater release straight from
GitHub, which is what that item itself says. It is left open and untouched.

## Deviations from the spec or the task

- **The candidate the unit is holding is on the bad list, so the morning's step 2 is not optional.**
  This phase's README says `rak update --first-install` *flashes the stored repeater v0.1.0 (or push
  the repeater's v0.1.1 first…)*. Read at `components/core/update/radio_update.cpp`,
  `RadioUpdate::fail` calls `store_.markBad(status_.sha256)` — *"the image that failed is never
  tried again (S-5): first thing, before any flash"* — and only **then** takes the first-install
  branch that enters *stuck* with *no image to return to*. The 6 November run reached `fail` from
  `stepFlashing` (`tasks/phase-8/reports/01.md`), so that candidate's hash is on the list, and
  `radio_update.cpp:436` refuses it before a sector is erased: *this image failed a health check
  once and is never tried again*. It cannot be pushed back in either —
  `components/core/image/store.cpp:484` refuses a transfer whose expected hash is bad. So the
  repeater's `v0.1.1` is what has to go in, and `docs/flashing.md` says so with `image bad` as the
  thing to look at first. The one thing a desk cannot settle is whether that `markBad` write reached
  flash: for `Kind::kFirstInstall` the printed reason is `kNoImageToReturnTo` **whether or not it
  did**, because the `bad != kNone` test comes after the first-install return. Hence the bench item,
  which says what to do in either case. `docs/update.md` already stated the rule (*"If it fails, the
  unit is *stuck* with *no image to return to*, and the candidate is on the bad list"*); nothing in it
  needed changing.
- **Four documents were touched that the task names only in its *Spec* list.** `docs/bench.md` and

## Decisions taken without asking

- **`release-notes/v0.1.1.md` leads with a table**, one row per fault, rather than prose. Five
  faults is the whole of this release and a person reading the release wants to know whether *their*
  symptom is in it; the row carries the board's own words (`no answer to type 0x03 seq 9`,

- **The notes link to each task's report**, not to the commits. The report is what says how the
  fault was found, what was measured and what is still the bench's; a reader who wants the diff has
  the commit in the generated part.
- **The notes name `v0.1.1` of the repeater firmware as the release this one goes with**, read
  read-only through `gh api` (published 6 November 22:18 UTC; its body says `HELLO` and `EV_BOOT`
  now end with the band and that a 1.0 Walter is unaffected). `p7-01`'s notes had to say *there is
  no release of it yet*; there are two now, so the pairing is named and the *The RAK* bullet of the
  guide was corrected with it.
- **Links in the notes point at `blob/main`**, as `release-notes/v0.1.0.md`'s do, rather than at the
  tag. One convention in one directory; the generated part names the commit for anybody who needs
  the files as they were.
- **README's *still unverified* paragraph is `docs/bench.md`'s ★ list and not a new list.** The six
  that file already marks as the ones that matter most are the honest summary, and one list that can
  go stale is better than two.
- **The new §1 bench item is not marked ★.** It deserves to be, but *How to read a step* enumerates

## Not verified here (and why)

No session opens a port this pile, and this task flashes nothing. **The whole of it is Thomas's in
the morning**, and the order is `docs/flashing.md`'s *A unit at 0.1.0*. The two new items are in
`docs/bench.md`:

1. **§1, a release taken over an older one by cable, on a unit that is already a unit.** Read four
   things first — `get`, `image list`, `rak update status`, `image bad` — then the `esptool` line
   of the release's `-factory.bin`, and read the same four again. The banner must say
   `0.1.1+<sha7>` with the tagged commit's characters, `self status` `ota_0` and `valid`, and **all
   four readings must be unchanged**: the same keys set, the same images with the same hashes, the
   same journal with the same last state, the same bad list. One key lost or one image gone is a
   finding against the partition table and against `tools/check_partitions.py`, which is the check
   that allows the file to be published. The log above proves where the file *ends*; only the board
   proves what the flash tool wrote.
2. **§9, the first install the 6 November failure left behind.** `image bad` names that candidate's
   hash; `rak update --first-install` on it is refused with nothing on the SWD lines; the
   repeater's `v0.1.1` pushed in is accepted; and the run then reaches *done*, which makes it
   golden and is the last word on a slot the journal left *stuck*. **If `image bad` is empty**, the
   mark never reached flash — write that down, because then the stored `v0.1.0` candidate is usable
   and the refusal will not appear.

And the three things this release is for, each already an item of an earlier task: §9's whole image
flashed with no watchdog reset, timed (p8-01); §8's whole release pushed in, timed (p8-02); §13's
twenty pairs of `http get` and a wake with all four steps `done` (p8-03); §18's two p8-04 lines and
two p8-05 lines. Every one of them needs **this release**, by cable, first — which is why this task
exists and why the bench list of the five before it begins with the same flash.

Two things that are not the bench's and not a session's:

- **the repeater firmware's `v0.1.1` on the radio**, which is what makes the band half of §18
  walkable (its own release exists; putting it on the unit's radio is the morning's step 2 either
  way, since the stored candidate is refused);
- **meshmaster.dk picking an image from `HELLO`'s band**, which is that repository's and is already
  deployed-or-not independently of this tag.
