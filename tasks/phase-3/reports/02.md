# p3-02 — The HTTPS client

The Walter can ask a server a small question and fetch a large file over TLS whose chain **was
checked** - and this firmware cannot be told to do otherwise. The modem does the TLS; the decision
this task rests on is that it does **not** do the HTTP: read at `walter-modem` 1.5.0, the modem's
own HTTP client hands back a response's status, content type and length and nothing else, so a
redirect cannot be followed, a range cannot be checked and a changed file cannot be noticed. The
download is therefore over the modem's TLS **sockets**, with a 600-line HTTP/1.1 writer and
parser in `core/net/` that every one of the tests below runs through - the same bytes the modem
will hand over, in the same pieces. The roots (`keys/tls/`: ISRG Root X1 and USERTrust ECC, the two
the chains of `meshmaster.dk` and of a GitHub release download end at, read this day) are held to
their PEMs at build time and written into the modem's certificate slots **once**; there is **one**
call in this firmware that configures a TLS profile, it asks for the chain and the host name every
time, and a host test and `tools/verify.sh` hold that the library's other validation levels are
named nowhere. Above the socket: a client with the rules (https only, three redirects to https
only, no `Authorization` across hosts, denied/later/failed), a download in 64 KB ranges that
resumes from the image store and restarts rather than splices, and the fetch of a release - checks
1-3 before a byte of the image, 4-6 over the bytes in flash. `tools/verify.ps1` is green: **612
host test cases, 286 566 assertions** (65 cases and 36 266 assertions of this task's own files,
under ASan and UBSan; ten thousand random inputs to the parser among them), the firmware built with
all of it linked (514 727 bytes, 16.4 % of its slot), the dry-run release signed and verified. One
session.

## The decision: sockets, not the modem's HTTP

Read in `managed_components/dptechnics__walter-modem` at 1.5.0 (`src/WalterModem.h`,
`src/WalterModem.cpp`, `src/proto/WalterHTTP.cpp`, `examples/https/main/https.cpp`), and in the
AT commands they wrap:

| Question the task asks | What the library and the modem do | Where |
|---|---|---|
| How does the modem's HTTP work | three HTTP profiles (`AT+SQNHTTPCFG`), six TLS profiles (`AT+SQNSPCFG`, 1-6), certificate slots 0-19 in the modem's NVM (`AT+SQNSNVW`); `httpQuery` sends `AT+SQNHTTPQRY=<prof>,<cmd>,"<uri>"[,"<extra header line>"]`, the answer arrives later as the unsolicited `+SQNHTTPRING: <prof>,<status>,<content type>,<length>`, and `httpReceive` fetches the body with `AT+SQNHTTPRCV` | `WalterHTTP.cpp:60-170`; `WalterModem.cpp:2862-2905` |
| Are a response's headers available | **No.** The ring carries the status, the content type and the length; the library's own comment at the body's parse is *"there is no other header information available"* | `WalterModem.cpp:2842` |
| Can a `Range` header be sent | yes - `extra_header_line` is one header line, and `Range: bytes=a-b` fits it | `WalterHTTP.cpp:125-128` |
| Does `Content-Range` or the status come back | the **status** does (`+SQNHTTPRING`'s second field, so 206 and 200 can be told apart); **`Content-Range` does not**, nor `ETag`, `Last-Modified` or `Location` | the same |
| Size limits | a body is read in pieces of at most 1500 bytes (`httpReceive` clamps `buf_size` to 1500; `WMHTTPEventData::data_len` and `WalterModemHttpResponse::contentLength` are `uint16_t`); a `httpSend` body is `uint16_t` | `WalterModem.h:2062-2114, 2420-2426`; `WalterHTTP.cpp:160` |
| What the header calls buggy | `httpConnect` ("this modem command is buggy", "will also return OK while establishing the connection in the background"); `httpReceive` omits the size from `AT+SQNHTTPRCV` because of a *"Known bug: CME ERROR 4 when attempting to receive a HTTP payload with a fixed size"*; `httpDidRing` and `httpGetContextStatus` are deprecated (task p3-01 said these two would matter) | `WalterModem.h:4596-4636`; `WalterHTTP.cpp:158-162` |
| Is the HTTP body path binary-safe | **No.** With the size omitted, the parser's `_expectingPayload()` finds no length in the command (`WalterModem.cpp:1296-1316`), leaves `_receivedPayloadSize` at `SIZE_MAX`, and `_parseRxData` then reads the payload *as text until it finds `\r\nOK\r\n`* (`_checkPayloadComplete`, `:1150-1193`). A firmware image can contain those six bytes |
| Are the sockets binary-safe | **Yes.** `+SQNSRECV: <id>,<len>` carries the length; `_expectingPayload` reads it (`:1216-1235`) and `_parseRxData` then takes exactly `len` raw bytes by count (*"Receiving binary payload with a known total size"*, `:1365-1375`) | `WalterModem.cpp` |

So: the modem's HTTP could carry a `Range` and would show a 206, but **nothing of the design the
task asks for can be built on it** - not the check that a 206's `Content-Range` is the range
asked for, not `If-Range` (no `ETag` to send back), not a redirect (no `Location`; and the GitHub
release download followed below *is* a 302), not the headers the caller names in
`interfaces/http.h`, and not a binary body one can trust to arrive whole. The sockets carry bytes
by count, so HTTP/1.1 is written and read in `core/net/http1.h` - a request writer and a
response parser with status line, headers (streamed, never buffered; the caller's wanted ones
copied into the caller's buffers), `Content-Length`, **chunked transfer encoding handled**, a body
read until close, and 204/304/HEAD without a body - and `core/net/http_over_tls.h` drives them
over `interfaces/tls_socket.h`, whose one implementation is `components/modem/walter_tls.cpp`:
`socketConfig` → `socketConfigExtended` (rings with the byte count, bytes as bytes) →
`socketConfigSecure(1, true, profile)` → `socketDial(1, TCP, port, host)` (command mode) →
`socketSend` in pieces ≤ 1500 → `socketReceive` ≤ 1500 a call → `socketClose`.

**Chunked is handled, not refused**, because a dynamic page from a Node or Go server is usually
chunked and refusing it would refuse the server this unit exists to talk to; the parser's chunk
rules (hex size, extensions skipped, trailers skipped, a size over 32 bits refused) each have a
test, and the fuzz loop runs over chunked seeds as well.

### What is wrong with the library at 1.5.0, as read for this task

1. **Only socket 1 is reachable through the current API.** `WalterModemSocket` default-initialises
   `id = 1` for all six entries of `_socketSet` (`WalterModem.h:2213`), `_socketGet(id)` returns
   the first entry whose id matches, and only the *deprecated* `socketConfig(rsp, ...)` overload
   renumbers them through `_socketReserve()`. So `socketConfig(1)` finds entry 0 and
   `socketConfig(2..6)` find nothing (`NO_SUCH_SOCKET`). One socket is all this firmware needs
   (one request is one connection), so `kSocketId` is 1 and the fact is written beside it.
2. **A failed dial does not say why.** `AT+SQNSD` answers one `ERROR` whether the name did not
   resolve, the TCP connection was refused or the TLS handshake failed; the library declares
   `WMURCSocketConnRC` (`TLS_ERROR = -5` and friends) and never sets it. The interface therefore
   has an honest value for it, `TlsOpen::kDialRefused`, the console says *the modem refused the
   connection: the host was unreachable or the TLS handshake failed (the library does not say
   which)*, and the bench tells the two apart by choosing hosts (`docs/bench.md` §12).
3. **The HTTP receive path is not binary-safe**, as above; a reason the download is over sockets.
4. **`httpReceive`'s size is omitted because of a modem bug** the library names and works around
   by reading "until OK"; the sockets' `AT+SQNSRECV=<id>,<n>` has no such bug.

Nothing this task calls is deprecated; the deprecated `socketSend`/`socketReceive`/`socketConfig*`
overloads (the ones without a `socket_id` first) are not used - our components compile with
`-Werror=deprecated-declarations`, which is what would have said so.

## Deviations from the spec or the task

- **`components/hal/` is `components/interfaces/`** (task p0-01's deviation, as every task since).
  `hal/Http` is `interfaces/http.h`; the TLS socket beside it is `interfaces/tls_socket.h`.
- **The download is over the modem's TLS sockets, not its HTTP**, for the reasons in *The
  decision*. The task foresaw this ("if the modem's HTTP cannot do ranges, say so, and build the
  download on the library's TLS sockets instead with a minimal HTTP/1.1 request writer and
  response parser in `core/` - that parser then gets the tests below and a fuzz loop"). The
  modem's HTTP *can* carry a `Range`, but shows neither `Content-Range` nor any other header, so
  the design the task specifies could not be held to it; the parser has the split-header, folded,
  oversized and chunked tests and the ten-thousand-input loop. **`components/modem/` therefore
  implements `TlsSocket` and `TlsStore`, not `Http`**: `Http` is `core/net/http_over_tls.h`, one
  implementation for the board and the host - which is what lets every client, download and fetch
  test run through the parser the board runs.
- **The modem's HTTP-only knobs are not used at all**: no HTTP profile is configured, `httpQuery`,
  `httpSend` and `httpReceive` are not called. The task's "using only that profile function"
  holds for the socket: `socketConfigSecure` names a profile that `configureProfile` made.
- **`Range` goes with every range request, and a 200 to it restarts the sink from zero rather than
  being appended** - as the task says - including when the sink holds nothing (then the 200's body
  is simply the file). A 200 with a `Content-Length` other than the expected size is *the wrong
  file* and not retried.
- **A changed file is noticed within one wake, not across wakes.** `If-Range` carries the `ETag`
  (or `Last-Modified`) of the first range *of this download*; the next wake begins a new download
  and learns a new validator from its first range, so a file replaced between wakes is spliced at
  the resume point and caught by the store's check 4 at the end - which is the check the task says
  judges the file. Keeping the validator in the store's progress record would close the gap and is
  task p2-02's record format to change; noted, not done.
- **The bench section is `docs/bench.md` §12, not §11** - §11 is the modem's, from task p3-01
  (which had the same shift from §10).
- **The trust record is in retained storage (RTC memory), not in settings.** The task says
  "compare a hash kept in settings"; the settings store is task p3-03's and does not exist. The
  record survives a reset and a deep sleep and not a power cut, so a power cut costs one rewrite
  of two slots; p3-03's NVS is where it moves to make that zero. `host_test/core/net/test_trust.cpp`
  walks the power cut so that the behaviour is a decision and not a surprise, and
  `interfaces/retained.h` gained slot `kTlsTrust`.
- **The self-update trial's third condition is now a TLS handshake** (`core/update/tls_check.h`),
  which task p2-04's `uplink_check.h` said this task would implement; `main/` constructs it with
  the empty host, so it still answers *not configured* and the condition does not apply - nothing
  about the trial changes until task p3-03 gives the unit a server. Not in this task's deliverable
  list; thirty lines, a test, and a seam closed rather than left described as closed.
- **`trust me` on the console now says *trust takes no argument, or 'tls': me***, and task
  p2-01's test of the old wording was updated to match. The console's random-sequence test
  (task p0-03) gained the three new lines in its bag and its seeded floor on kills went from 70 to
  60, with the reason beside it (three more tokens in the bag, 65 kills with this seed).
- **CI rounds: none** (below).

## Decisions taken without asking

- **One root per TLS profile, and a host held to one root.** `AT+SQNSPCFG` takes one
  `caCertificateID`, so root *i* goes to certificate slot 12 + *i* and TLS profile 2 + *i* (the
  library's example says slots 0-10 and profile 1 are Sequans's and BlueCherry's), and
  `rootForHost()` holds `github.com` and its subdomains to USERTrust and every other host to ISRG
  Root X1. The alternative - trying every root in turn until a handshake passes - is trusting the
  union at the cost of a handshake per miss and of hiding a misconfiguration; a fixed table is a
  release to change, which is also what a CA change at a host would need. The table is in
  `trust.cpp` with the observed chains beside it.
- **USERTrust ECC, not Sectigo's own Root E46, is the anchor for github.com.** The served chain's
  top is E46 *cross-signed by* USERTrust ECC, so USERTrust verifies the chain as served in any
  TLS stack; anchoring at E46 relies on the modem's stack stopping at an intermediate it finds in
  its store, which cannot be checked without the hardware. If Sectigo drops the cross-sign, or if
  the modem will not take a P-384 root, E46 (`crt.sectigo.com`) is the alternative and
  `docs/bench.md` §12 says where that would show.
- **TLS 1.2, pinned.** The profile takes one version; 1.2 is what the library's example sets and
  what all three hosts speak. 1.3 exists in the enum and is the bench's to try; the rail refuses
  anything older than 1.2 by name.
- **Socket 1, with `AT+SQNSCFG` parameters of our own**: packet size 1500, no exchange timeout
  (the deadlines are this firmware's), a 30 s connect timeout, no send delay - each named in
  `walter_tls.h` with a sentence. A received byte count is polled every 50 ms when the modem has
  not rung, so that a missed `+SQNSRING` costs a poll and not the deadline.
- **The response's status and headers are promised before the first body piece**
  (`interfaces/http.h`). That is what lets the download's sink refuse to append a 200 where a 206
  was asked for, and refuse a 206 whose `Content-Range` is wrong, *before* a byte reaches the
  store - a property the tests check. The client's `Options::response` exposes the live response
  for that; the download reads a wanted header's *value*, filled in place, rather than its
  `present` flag, which the client copies back only when the request returns (said in
  `download.cpp`).
- **The client never retries.** 401/403 are *denied* and 429/5xx *later* with `Retry-After`
  capped at an hour (an HTTP-date, which this firmware does not parse, is the cap; absent is 0,
  "the server did not say"); the download retries a range's transport failures three times with a
  two-second pause and stops at once on denied, later, a wrong file or a refused URL. 301/302 after
  a POST become a GET, 303 always does, 307/308 keep the method and the body - the way every
  browser does it.
- **A redirect's body is dropped and cut at 4 KB**, so a 302 cannot cost a megabyte; a response
  over the caller's bound is cut at the bound and reported as *too large*, with the bytes up to
  the bound delivered (the console's `http get` reads a kilobyte).
- **A refusal at check 4, 5 or 6 empties the slot** (`Store::erase`), so that the junk is never
  resumed into; a download that stops on its budget or fails a range leaves the bytes and the
  store's progress record for the next wake. A restart from zero is `abandonWrite`, `erase`,
  `beginWrite` again - which is why `fetch` never targets the golden image (`erase` refuses it, S-5).
- **`http get` and `fetch` refuse to run while the uplink is down** (*'lte up' first*) rather than
  bringing it up: the budget for a bring-up is the wake cycle's (task p3-05) and a console line
  should not spend four minutes of modem by surprise.
- **The trace line a request leaves names the method, the host, forty characters of the path, the
  status, the bytes and the time, and no header.** `test_client.cpp` carries a bearer token through
  a redirect and a 401 and greps the trace for it. The token is `Options::authorization`, set by
  whoever calls (task p3-03's setting through the backend later); the console sets none.
- **The User-Agent is `twinoak-walter <version>`** (`core::banner()`): the product and its
  version, nothing that identifies a unit.
- **`kMaxUrlLength` is 1536**, from the thousand-character signed URL GitHub's release host
  redirects to; `kRequestHeadBytes` 2560 holds that path, a host, five fixed headers and four of
  the caller's; `kMaxHeaderValue` 8192 (github.com's `Content-Security-Policy` is ~3 KB) and
  `kMaxHeaderBytes` 32768 bound what a server may stream as headers.
- **The parser accepts a bare LF as a line end** (RFC 7230 §3.5 allows a recipient to) and refuses
  a bare CR, an obsolete line fold, a header without a colon, conflicting `Content-Length`s, any
  transfer coding but `chunked`, and `chunked` beside a `Content-Length`.
- **The TLS roots table is generated at build time** (as the release-key table is), by a script
  that holds each header to the certificate's own bytes; the roots' order is the file names',
  and `trust.cpp` holds each named index to its file with a `static_assert`.

## The numbers, to be set on the bench

Each is a named constant with a sentence beside it; `docs/bench.md` §12 is how they are measured.
Change a number and its sentence together.

| Constant | Today | What sets it |
|---|---|---|
| **`kRangeBytes`** (`core/net/download.h`) | **64 KB** | the store's resume step; every range is a handshake (seconds), a drop costs the range - **the fetch of a real release decides** |

| `kRangeTries`, `kRetryPauseMs` | 3, 2 s | attempts at one range before the wake gives up |

| `kMaxValidatorLength` | 128 | an `ETag` or `Last-Modified` for `If-Range` |

## Not verified here (and why)

No session can put a SIM in a Walter. `docs/bench.md` §12, *HTTPS*, is the walk, in the order the
rig is brought up; these are its items.

- **`trust tls` after the first boot**: both roots *not written yet*; after the first request,
  *written, matches*; **after a reset, still written and `0 root(s) written in this boot`** - the
  record held in RTC memory; after a power cut, written once more.
- **`http get https://meshmaster.dk/` → 200**, with the time written down.
- **A host whose chain ends at a root this firmware does not carry → refused** (`example.com`
  behind DigiCert, or any host behind DigiCert, GlobalSign or GoDaddy - check the chain first):
  *the modem refused the connection ...*, while the same host answers `curl` on the laptop. **This
  is the test that the rail is real on the modem and not only in the source.** A 200 here means
  the profile is not validating.
- **`http get https://expired.badssl.com/` and `https://wrong.host.badssl.com/` → both refused** -
  for the root, before the expiry or the name is reached, since badssl.com is behind DigiCert; the
  name check on its own needs a Let's Encrypt host reached by another of its names.
- **`http get https://github.com/`** → 200: the other root's profile working, and the modem taking
  an ECC root.
- **`fetch` of the repeater's dry-run release from GitHub on a test-key build**: the 302 followed,
  the six checks, the ranges, *stored*; **the bytes and the seconds written down** - they set
  `kRangeBytes`, the range deadlines and both budgets, and they are the number task p3-05's wake
  budget is built from. Pull power half-way and fetch again: *resuming at N of M bytes*.
- **A normal build refuses the same fetch at check 1** before a byte of the image.
