# p3-01 — The modem

The Walter can get onto the LTE-M network and say what happened when it could not. Everything above
this task sees `core::uplink::UplinkPolicy`: bring it up, what time is it, how good is the signal,
who am I, what power saving did the network grant, take it down — and one of five named failures,
each with its own idea of when to try again. `walter-modem` is behind `interfaces::Uplink` and
nowhere else.

**This task was done in two sessions.** The first was cut off by a usage limit and left a work-in-
progress commit on this branch (`b9e0cb8`, which also carries a one-line change to
`tasks/run-all.ps1`'s limit detection that was not mine and is kept). The second session fixed what
the first had left failing, found and closed the SIM-PIN hazard below, wrote the tests the first had
not, and did the documents and this report. The commits are in order on the branch.

## The library, as read at 1.5.0

Every call this task makes, the AT command behind it, and whether it blocks. **All of them block
except two.** A blocking call waits on a condition variable with no timeout of its own
(`WalterDefines.h`, `_returnAfterReply`); what gives up is the library's command task, after
`CONFIG_WALTER_MODEM_CMD_TIMEOUT_MS` (30 s) per attempt.

| Call | Sends | Blocks |
|---|---|---|
| `begin(uart_port_t, 0)` | — | yes, and a long time: see below |
| `setNetworkEventHandler` | — | **no**: it stores a pointer |
| `checkComm` | `AT` | yes |
| `reset` | the module's reset pin, 10 ms low, then a 1 s wait, then waits for `+SYSSTART` | yes: 1 s + up to one command timeout |
| `getSIMState` | `AT+CPIN?` | yes |
| `unlockSIM(…, pin)` | `AT+CPIN=<pin>` | yes. **It keeps the pointer** in a static `_simPIN`, so the string must outlive the call |
| `getRAT` | `AT+SQNMODEACTIVE?`, or nothing at all when its cache is warm | yes, or not at all |
| `setRAT` | `AT+SQNMODEACTIVE=<rat+1>` | yes |
| `setOpState` | `AT+CFUN=<n>` | yes |
| `setNetworkSelectionMode` | `AT+COPS=0` | yes |
| `definePDPContext(1, apn)` | `AT+CGDCONT=…` | yes |
| `setNetworkAttachmentState(true)` | `AT+CGATT=1` | yes |
| `getNetworkRegState` | — | **no**: the buffered `+CEREG` state. This is why the wait for the network is a poll and is the one step whose deadline is exact |
| `getPDPAddress` | `AT+CGPADDR=1` | yes |
| `getClock` | `AT+CCLK?` | yes |
| `getSignalQuality` | `AT+CESQ` | yes |
| `getRSSI` | `AT+CSQ` | yes |
| `getCellInformation` | `AT+SQNMONI=0` | yes |
| `getIdentity` | `AT+CGSN=2` | yes |
| `getSIMCardID` | `AT+SQNCCID` | yes |
| `getSIMCardIMSI` | `AT+CIMI` | yes |
| `configPSM` | `AT+CPSMS=…` | yes |

**What `begin` does** (`WalterModem.cpp:4152`), because it is more than a constructor: it installs
the UART driver on the port given, with hardware flow control and the pins from its own Kconfig (RX
14, TX 48, RTS 21, CTS 47, reset 45 — the module's internal wiring per the Walter datasheet, none of
them one of our seven); it creates **three static FreeRTOS tasks** (`uart_rx_task` at priority 3,
`queueProcessingTask` at 2, `eventProcessingTask` at 4, all pinned to core 0); it sets the modem
reset pin's direction and enables the chip's deep-sleep pad hold; on a cold boot it calls `reset()`
and on a wake from deep sleep `_sleepWakeup()` instead; and it sets `AT+CMEE=1` and `AT+CEREG=5` —
the second of which is what makes the PSM timers the network grants arrive at all. It is idempotent
only on success: see defect 1.

**What it keeps in RTC memory across a deep sleep**: `_pdpCtxSetRTC` (the PDP contexts),
`_socketCtxSetRTC`, `_coapCtxSetRTC`, `_mqttTopicSetRTC` and `blueCherryRTC` — written by
`_sleepPrepare()`, which only runs inside the library's own `sleep()`.

**What its `sleep()` does to the ESP32 — for task p3-04.** `sleep(seconds, false)` calls
`_sleepPrepare()`, waits a second, and then `esp_deep_sleep()`: **it takes the whole board down, for
a timer wake-up and nothing else.** It arms no other wake source, so neither the radio's attention
line nor USB would bring the Walter back (`docs/ARCHITECTURE.md` §10 wants all three), and it gives
nothing a chance to hold a pad, write the journal or tell the radio first. `sleep(seconds, true)` is
light sleep and drops the UART's flow control while it sleeps. **Recommendation to task p3-04: sleep
the board itself and do not call this.** The consequence to handle is that the library's RTC copy
then never happens, so on the next boot `begin()` takes its `_sleepWakeup()` branch (the wake cause
is not `UNDEFINED`) and does **not** reset the modem — which is right if the modem kept running and
wrong if it was taken down, and in the second case `begin()` can return false. That is what defect 1
is about, and `WalterUplink::present()` handles it.

Nothing this task calls is marked deprecated. The `[[deprecated]]` declarations at 1.5.0 are all in
MQTT, CoAP, sockets, HTTP and the old `*SetEventHandler` spellings; the two that will matter are
`httpDidRing` and `httpGetContextStatus`, for task p3-02.

## What is wrong with the library at 1.5.0

Four defects, all read in the source rather than inferred:

1. **`begin()` cannot be called twice, and cannot be retried after a failure.** It guards on
   `_initialized`, but sets it only at the end; every failure path returns false with it still
   false. A second call would install the UART driver again and create the three static tasks again
   over the same static buffers. So `WalterUplink` calls `begin()` **once per boot** and, if it
   fails, goes on with `reset()` and `checkComm()` rather than calling it again.
2. **A refused SIM PIN is retransmitted — and three refusals block the card.** The command task
   retransmits a command that answered `ERROR` or `+CME ERROR`, not only one that timed out
   (`WalterModem.cpp:2079` and `:2093` set `RETRY_AFTER_ERROR`; `:1731-1748` sends it again), up to
   `cmd->maxAttempts`, which is `CONFIG_WALTER_MODEM_DEFAULT_CMD_ATTEMPTS` (3) for every public
   call — `_queueModemCMD` takes a per-command value but is private, and `unlockSIM` does not pass
   one. **One call to `unlockSIM` with a wrong PIN therefore sends `AT+CPIN=<pin>` three times and
   blocks the SIM**: a PUK, the operator's letter and a person at the mast. The task's rule ("at
   most once per PIN value") is not keepable over that, so `sdkconfig.defaults` sets
   `CONFIG_WALTER_MODEM_DEFAULT_CMD_ATTEMPTS=1`, with the reason beside it, and a `static_assert` in
   `modem/walter_uplink.h` holds the two Kconfig values to `core::uplink::kModemCallCeilingMs`. The
   guard was shown to fire: with the attempts put back to 2 the build stops with *the comparison
   reduces to (60000 <= 30000)*.
3. **`durationToTAU` and `durationToActiveTime` are wrong**, which is why `core/uplink/psm.h` does
   the 3GPP encoding itself. `_convertDuration` (`WalterModem.cpp:4776`) never assigns
   `smallest_modulo`, so `modulo < smallest_modulo` is true for every candidate and the **last**
   usable unit wins rather than the closest one; and it then reports
   `*actual_duration_seconds = final_base * final_mult` using the unit's **index** instead of
   `base_times[final_base]`. A wrong TAU is a modem that sleeps for 2 seconds or for 320 hours.
4. **The `+CCLK` parse ignores its own `sscanf`.** `WalterModem.cpp:2585` compares the return to 8
   and the body of the `if` is empty, so a malformed clock report is used as if it had parsed. The
   library does have a floor of its own — `WALTER_MODEM_MIN_VALID_TIMESTAMP`, 1672531200
   (2023-01-01), below which it answers `-1` — and it converts with `mktime`, which assumes the
   ESP32's local time zone is UTC (nothing here sets `TZ`, so it is). This is the reason
   `core/uplink/clock_window.h` exists and is stricter.

## Deviations from the spec or the task

- **The interface is `components/interfaces/`, not `components/hal/`.** The task says
  `components/hal/Uplink`; `hal/` was renamed in phase 0 because ESP-IDF owns a component of that
  name (`docs/ARCHITECTURE.md` §1 says so). Same place, different word.
- **`bringUp(deadline)` is on the policy, not on the interface.** The task puts it in the
  interface's list and also asks `UplinkPolicy` to own "the sequence … its deadlines as named
  constants, the backoff, and how long this wake may spend on the modem at all". Both cannot be
  true: a policy whose only lever is one `bringUp()` call owns none of the order. So
  `interfaces::Uplink` carries the *steps* the sequence is made of — each one a thing any LTE modem
  can be asked, so the port the task exists to make cheap stays cheap — and
  `UplinkPolicy::bringUp(budget_ms)` is the one call everything above sees. The phase's own README
  asks for exactly this split ("the policy is in `core/` and tested against a fake modem"). The
  interface's other five, `takeDown`, `state`, `networkTime`, `signal`, `identity` and
  `powerSaving`, are where the task puts them.
- **The failure *enum* is in `interfaces/uplink.h`'s neighbour, not in `core/uplink/`.** Precisely:
  `core::uplink::Failure` and the table are in `core/uplink/failure.h` as the task says, and the
  interface never names them — it answers in its own terms (`SimState`, `Registration`, `bool`) and
  the policy is what turns those into a failure. That keeps `interfaces/` ignorant of `core/`, as
  `interfaces/wall_clock.h` is of the link.
- **Two calls of the interface take no deadline**, where the task says "every call takes a deadline
  and returns by it". `registration()` is the modem's buffered `+CEREG` state: it sends nothing,
  costs nothing and cannot block, which is exactly why the wait for the network is a poll of it and
  is the one step whose deadline is honoured to the millisecond. `takeDown()` takes none because it
  is what happens on every way out of a wake, including the ways out that are failures, and a
  take-down that refused to start because a deadline had passed would leave a modem on. Both are
  said in `interfaces/uplink.h` beside the declarations.
- **The bench section is `docs/bench.md` §11, not §10.** §10 is the supervisor's, from task p2-05.
- **One library Kconfig value is changed** (`CONFIG_WALTER_MODEM_DEFAULT_CMD_ATTEMPTS=1`), where
  phase 0's report had concluded that every library switch keeps its default. Phase 0's finding was
  about the *protocol* switches, which do not compile when off; this is a retry count, and defect 2
  is why. Said again under *Decisions*.
- **The modem is on UART2.** The task does not say; the library's examples use UART1, which is this
  firmware's radio link (`platform/uart.cpp`). The modem's pins go through the GPIO matrix, so the
  port number is ours.
- **Out of scope, as the task says, and so left alone**: HTTP (p3-02), the APN and the PIN as real
  settings (p3-03), sleep (p3-04). The APN and the PIN are two build constants that are empty,
  behind a `Settings` struct the settings task fills, and `UplinkPolicy::pinChanged()` is the call
  task p3-03 makes when a person provisions a different PIN.
- **GNSS, MQTT, CoAP, BlueCherry and the sockets could not be switched off, and it saved nothing.**
  The task asks for it "where that is possible in the component's Kconfig"; at 1.5.0 it is not
  possible for any of them, which phase 0's task 01 had already established by trying each switch in
  the build (`tasks/phase-0/reports/01.md`, and `sdkconfig.defaults` repeats the reasons). Nothing
  of them is called. The one protocol this task does call into is none of those.

## Decisions taken without asking

- **`CONFIG_WALTER_MODEM_DEFAULT_CMD_ATTEMPTS=1`.** Defect 2. The alternative was to keep the
  library's 3 and accept that one wrong PIN blocks a card, or to refuse to send a PIN at all and
  make task p3-03's `lte.pin` setting useless. The cost of 1 is that a command lost to noise is not
  retransmitted by the library — on a UART that is a trace inside the module, with hardware flow
  control — and the retry this firmware really relies on is the next wake's. It also makes one
  blocking call's worst case 30 s instead of 90, which is what the wake's budget is sized against.
- **"At most once per PIN value" is read as "a refused PIN is never sent again".** Read literally it
  would mean a correct PIN may be sent once in the unit's life, which — with the modem switched off
  between wakes, so the card re-locks every wake — would put a PIN-locked SIM off the air after one
  wake. So: a PIN is sent only when the card asks for one, only when one is set, and **never again
  once it has been refused**; a card can lose at most one of its three tries to this firmware.
  `host_test/core/uplink/test_uplink_pin.cpp` counts the sends.
- **The refusal lives in retained storage, which a power cut clears.** So a unit that loses power
  may spend one more of the card's three tries. The other side of that trade is a unit whose SIM can
  never be unlocked again after a flat battery, which is worse. The durable place is task p3-03's
  NVS settings store, which already owns "a changed `lte.pin` clears the *this PIN was refused*
  flag"; mirroring the flag there is the one thing this decision leaves for it. A host test walks
  the power cut so that the behaviour is a decision and not a surprise.
- **No function of the PIN is stored anywhere.** Not a hash: a digest of a four-digit number is not
  a secret. What distinguishes "the same PIN" from "a new one" is a `pin_epoch` the caller gives.
- **The backoff is counted in wakes, not in seconds.** A Walter has no clock it can trust across a
  deep sleep (`interfaces/clock.h`: `esp_timer` restarts at zero) and no time of day until this very
  task gives it one, so "every fourth wake" is a thing it can count and "in four hours" is not. How
  long a wake is apart is task p3-04's, which is where the battery's answer belongs.
- **A wake is counted even when the backoff skips it**, or "every fourth wake" would mean nothing.
  `beginWake()` is therefore separate from `bringUp()`, and the wake cycle must call it once a wake.
- **`no-time` is reported beside the uplink, never as a failure of it**, as the task's table says —
  and a time that is not the network's is returned with its epoch zeroed, so that nothing downstream
  can read a 1970 out of a result that said it was a default.
- **A RAT that will not be set is not a refusal to attach.** The module's own default is LTE-M, so
  the likely outcome is an attach that works anyway; a unit off the air over a setting would be
  worse. It is recorded and the sequence goes on.
- **The RAT is read and set before the SIM**, because setting it needs a modem reset
  (`WalterModem.h`, `softReset`: "required when switching from RAT") and a reset clears `_simPIN`
  and the card's unlocked state. A PIN sent twice in one wake is one of three tries thrown away.
- **`WalterUplink::rat()` prefers the RAT this object set to the one the library reports.** The
  library's `getRAT` answers from a cache its own `setRAT` does not update, so without this a modem
  found on NB-IoT would be set to LTE-M and still *read* as NB-IoT for the rest of the boot — and
  every bring-up of that boot would set it again and spend the modem reset a RAT change needs.
- **Power saving: off between wakes is the default, PSM is a setting**, as the task asks
  (`spec/SYSTEM.md` §10 item 5 is the bench question). "Off between wakes" is the modem's radio in
  its minimum state (`AT+CFUN=0`) and the ESP32 asleep — not the library's `sleep()`, for the
  reasons under *What its `sleep()` does*.
- **`lte up` counts the wake, then says what the backoff would have done, and goes ahead anyway.** A
  person asking is not the backoff's business, but "why did it not try by itself" should have an
  answer on the same screen.
- **The network's time is not yet wired into `interfaces::WallClock`.** The policy reports it and
  `lte time` prints it; the thing that would set the radio's clock from it is step 2 of the wake
  sequence (`docs/ARCHITECTURE.md` §10), which is task p3-05's. `main/` still answers "I have no
  time to give", which is the correct answer for a firmware that has not attached. Said in §9 so
  that it is a seam and not an omission.
- **Task p0-01's `modem_anchor.cpp` is deleted.** It existed to keep the library in the link while
  nothing called it; something calls it now, and `tools/verify.sh` greps for the two real objects
  instead.

## Tested, and only compiled

**Tested on the host** (56 test cases and 2 540 assertions of this task's own files, under ASan and
UBSan, inside a suite of 547 cases and 250 363 assertions
that is green):

- the good path, and **every failure of the table reached by the script that causes it**, with the
  console line each one prints;
- the backoff over a month of wakes with no coverage — the attempts thin out 1, 1, 2, 4, 8, 16 and
  stop at the cap; coverage returns and the next allowed attempt succeeds and empties it; it
  survives a restart and not a power cut; a changed failure starts the count again;
- the PIN: refused once and never sent again, across restarts, across a month of wakes, and through
  a person's `lte up`; a changed PIN gets exactly one try; a PIN command that never answers costs
  the card nothing and is retried next wake; a card that wants a PIN this firmware does not have is
  never guessed at;
- **every call returns by its deadline against a fake that never answers**, and the wake's budget is
  never exceeded whatever it is set to; a bring-up that would overrun is abandoned cleanly with the
  modem taken down and says so;
- the time: 1970 refused, before the build date refused, absurdly after it refused, a sane one
  accepted and marked as the network's, and a modem that answers 1970 twice and then the real time;
- the 3GPP timer encoding against TS 24.008's units, both ways, and the modem's eight-character bit
  strings;
- **nothing identifying in anything the firmware prints**: a whole wake and every console line but
  `lte id` greped for the fake's IMEI, ICCID and IMSI — and `lte id` checked to print them, so that
  a grep which has stopped matching cannot pass;
- that nothing under `core/uplink/` allocates, and that it includes nothing but its own nine
  headers.

**Only compiled** — every line of `components/modem/walter_uplink.cpp`, which is the 23 library
calls above and the mapping of their results. Specifically unproven until the bench: that the modem
answers on UART2 at all; that `AT+CPIN?`'s CME codes are the ones mapped; that `AT+SQNMONI`'s
`netName` and `band` are what `lte` prints; that `+CEREG`'s PSM bit strings parse; that an attach
happens inside `kRegistrationDeadlineMs`; and the deadline arithmetic against a real library call,
which can overrun by up to `kModemCallCeilingMs` (reported as `Result::overran`, never silently).

## Not verified here (and why)

No session can flash a board, put a SIM in it or screw an antenna on. `docs/bench.md` §11, *The
modem*, is the walk, in the order the rig is brought up; these are its items.

- **`lte up` with the SIM in and the antenna on**: registered, the operator and band named, a signal
  reading, and `lte time` within a second or two of a phone's clock.
- **How long an attach takes from cold, three times.** It sets `kRegistrationDeadlineMs` and through
  it `kWakeBudgetMs`.
- **The antenna off, and no SIM**: the right failure, promptly, and `lte` saying when it will try
  again — and the interval doubling over four attempts.
- **A PIN-locked SIM**: `sim-locked`, `never automatically`, and **nothing sent to the card**. Not
  with a wrong PIN on a card anybody needs.
- **The current drawn while searching, while attached and with the modem down**, on the Walter's own
  supply with a meter in series: the three numbers task p3-04's policy table needs.
- **PSM once there is a reason to**: what the network grants as against what was asked for, and the
  same three currents again — `spec/SYSTEM.md` §10 item 5.
- **A modem that is really silent**: `modem-silent`, one reset, not two.
