# p5-02 — One door

Until this task the firmware could not name a register that erases a chip, and four checks held
that. `spec/SYSTEM.md` S-5a makes one exception — a person's typed `rak provision <radio> confirm`
— and this task builds **the door** that exception goes through, and keeps the rest of the house as
sealed as it was. The door can erase through the CTRL-AP, soft-reset through it, write UICR words
and the base's flash outside the application's region, and nothing else; it opens only with a
grant that one function makes from the typed text and that **the door checks against the chip
itself**; and every test of the tree that is not about the door still runs against a simulated chip
whose tripwire fires the moment any of it is touched. **Nothing calls the door yet**: that is task
03's sequence, and rail R3b holds that it will be the only caller.

What came of it, in one line each:

- `core/nrf52/provision_grant.h` — `ProvisionGrant`, no public constructor, made by
  `grantFromTypedCommand()` alone from S-5a's grammar (`<DEVICEID>`, `locked`, `locked:<key16>`);
  moved from is spent, and a spent grant is refused.
- `core/nrf52/provision_door.{h,cpp}` — `ProvisionDoor(Nrf52&, swd::Dp&, Clock&, ProvisionGrant&&)`
  with `open()`, `approtectStatus()`, `eraseAll()`, `softReset()`, `writeUicr()`,
  `writeApprotect(kind)`, `writeFlash()`, `blankCheck()`; every register access cites the Product
  Specification beside it; the three writes refuse without a successful erase in the same opening.
- `host_test/sim/nrf52_chip` — both kinds of APPROTECT by `INFO.VARIANT`, the three factory states,
  a real CTRL-AP `ERASEALL` and soft reset, a pin reset that the reset line now reaches, resets
  counted by kind, UICR written like flash — all behind `allowProvisioning()`; the tripwire armed
  by default with its four sentences word for word.
- `tools/check_rails.py` — R3 allows the forbidden names in exactly two files; **R3b** (new) holds
  the door to its one caller; `test_nrf52_forbidden.cpp` reads the tree for both.
- `docs/ARCHITECTURE.md` §1, §4, §5, §12 and `README.md`'s rails table say what the door is and
  who may open it.

## Deviations from the spec or the task

1. **IN-141 could not be read; the Product Specification's own chapter stands in for it.** Every
   URL for Nordic's IN-141 PDF answers 403 or 404 from this machine (as the memory of task p1-04
   records for Nordic's PDFs in general). The HTML rendition of the nRF52840 Product Specification
   *was* read — *Debug and trace > CTRL-AP* (the five registers, offsets and values), *Access port
   protection* ("Build codes Dxx and earlier" / "Fxx and later", "Disabled via ERASEALL", the
   protection "remains disabled until: Pin reset, Power or brownout reset, Watchdog reset if not
   in Debug Interface Mode, Wake from System OFF", "Program UICR.APPROTECT to HwDisabled" and
   "Firmware must write APPROTECT.DISABLE to SwDisable"), *Debug Interface mode*, NVMC's
   electrical specification (tERASEALL **169 ms** typical, nWRITE 2, tWRITE 41 µs) and *Writing to
   UICR* ("written in the same way as flash"; "will only take effect after a reset"), *UICR*
   (every register's offset; "default to 0xFFFFFFFF"), *FICR* — and the code and the simulator
   cite those. Nordic's DevZone note on the improved APPROTECT was read too; it names IN-141 as
   the source for revision 3 and says a soft reset re-enables the protection *when the firmware's
   own start-up is what disabled it* — which is the simulator's existing `protects_after_reset`
   knob, kept. The note says MDK **8.45.0** where the task says 8.40.2; the number is not used in
   code, and the simulator's `bootloader_opens_port` knob is the honest form of it.
2. **The header is where this repository keeps headers.** The task names
   `components/core/nrf52/provision_door.{h,cpp}`; the source is there and the header is at
   `components/core/include/core/nrf52/provision_door.h`, as every header of `core/` is. The grant
   has a header of its own, `provision_grant.h`, because the task lets `console.cpp` include the
   grant's header but not the door's.
3. **R3b's list for the grant's header has the door's two files on it.** The task says "the
   grant's header by `core/provision/` and `core/console/console.cpp` and nothing else"; the door
   takes a `ProvisionGrant&&`, so `provision_door.h` and `provision_door.cpp` must include it. The
   rail says so, by name, and refuses everything else.
4. **The door's timeout constants are not named `kEraseAll…`.** R3's grep is a substring match on
   `kEraseAll`, so the door's header — which may not name a forbidden register — calls them
   `kChipEraseTimeoutMs` and `kChipErasePollMs`. Said here so that nobody "fixes" the names.
5. **The simulated chip's notion of the kinds is the silicon's, not the variant table's.**
   `improvedApprotect()` is "Fxx and later" (the letter F or after, and a variant that is not text
   at all) and everything A–E is hardware-only; task 03's table is stricter (A–D, F, nothing else)
   and refuses the rest. The two are different questions.

## Decisions taken without asking

- **The grant is spent on any attempt to open, refusals included.** The typed line buys one
  opening; a `DEVICEID` that was not this chip's does not get a second look with the same grant.
  The test *one grant, one opening* holds it.
- **`locked` is the lower-case word only; `<key16>` and the `DEVICEID` are case-free.** S-5a
  writes `locked` as a keyword and says of the `DEVICEID` alone that it is read "without regard to
  case". The key is kept upper-cased, so task 03 compares it against the hex it prints.
- **`eraseAll()` and `softReset()` end by opening the session again** (`Nrf52::open()` on the held
  slot: connect, power-up, `IDR`, `APPROTECTSTATUS`, and the memory port and `identify()` when the
  port reads open), and a port that still reads closed is **not an error** for them: the result
  says `port_open = false`, and the sequence decides (S-5a: one soft reset, then stop). The
  reconnect is unconditional, and the comment says why: whether the debug power-up survives the
  part's reset is the part's business, a line reset and `DPIDR` are always allowed, and both a
  part that needs it and one that does not are tested.
- **Timeouts and waits:** `ERASEALLSTATUS` polled every 10 ms for 5 s (tERASEALL 169 ms typical,
  no maximum given; the bench tool used 5 s); CTRL-AP `RESET` held 10 ms and the part given 10 ms
  after release (the Product Specification gives no figure; the bench tool's numbers; the first
  board says — phase 6). `writeUicr` waits `READY` after each word with the nRF52 layer's existing
  50 ms bound.
- **`writeFlash`'s two regions are `[0, app.begin)` and `[bootloader_start, flash_end)`.** The
  forbidden span is the application region *and* the file system above it, as one span from the
  board profile; the MBR parameter page and the bootloader's settings page lie in the second
  region and are the base's to write if §4a's file carries them (the fixture does not).
- **`writeApprotect(kLegacy)` writes nothing but still demands an erase in this opening**, like the
  other two writes, so that the sequence cannot reach it out of order on either kind.
- **A refusal at opening carries what the port read** (`port_open`), for the console's line.
- **`DoorStatus::kNrf52` carries the nRF52 layer's own status** for anything the door does not
  name (`kBadRegion`, `kSlotBusy`…); `kProtected`, `kNotNrf52840`, `kNvmcTimeout` and `kSwd` are
  mapped one for one.
- **The simulator:** a chip erase counts as "flashed" for R4's undeclared-window check, so a door
  test must declare its windows (they declare the base's two); `FlashTally` gained `erase_alls`,
  `uicr_writes` and `provisioning_chips`; `factoryLocked()` means *by firmware* (`0xFFFFFF00`) on
  a legacy part and *by default* (the word erased) on an improved one; `ERASEALLSTATUS` is busy for
  a set number of reads (3, the bench tool's) rather than for a simulated time, as the task asked;
  a pin reset and a power-on reset the debug port (`SwdTarget::resetDap()`), so a host that does
  not reconnect afterwards fails its test; the reset line reaches the chip through
  `SwdTarget::on_pin_reset`, wired by `Nrf52Bench` — **the update bench (its own world) is not
  wired**, and task 03 wires it where its test needs the port after a reset.
- **Nothing links the door, on purpose.** The target build compiles `provision_door.cpp` with the
  rest of `core/` (warnings as errors, no ESP-IDF include), but with no caller `--gc-sections`
  drops it and the image is the size it was. An anchor in `main/` would itself break R3b, which
  names `main/` among the directories that include neither header; task 03's sequence is the
  caller, and the link is proved then.

## Not verified here (and why)

Nothing on silicon in this task, as the task says: the door is walked by task 03's command, on the
bench in phase 6 (`docs/bench.md` §4a is task 03's to write), so no line was added to `bench.md`
here. What that walk will settle about *this* task's numbers and models, for the person reading
the output then:

- **tERASEALL on a real part** against the 5 s bound (169 ms typical); the command prints the
  time.
- **The soft reset's 10 ms hold and 10 ms settle**, and whether the real part's debug port needs
  the reconnect the door does unconditionally (both are handled; the bench says which it was).
- **The port after the pin reset** on a build code Fxx module with the RAK's bootloader
  (`spec/SYSTEM.md` §10.2): the simulator has it both ways behind `bootloader_opens_port`; the
  first board picks one.
- **A legacy (A–D) part**, if one ever turns up: the simulator's conservative model (the erased
  UICR read only at the next reset, so the soft-reset path runs) is the bench tool's, not a
  measurement.
