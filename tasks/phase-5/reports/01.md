# p5-01 — The base in the store

A release of the repeater firmware now carries, per image, the board's **base**: the MBR,
SoftDevice S140 6.1.1, bootloader and UICR words a factory RAK4630 has to be given before any
image of ours can run on it, as one Intel HEX file (`spec/FIRMWARE-MANIFEST.md` §4a,
`spec/SYSTEM.md` S-5a). The Walter now reads that entry, judges the file by §4a's seven rules
against **its own** board table, and keeps it — one per radio slot, beside golden, candidate and
scanner, behind a door only task 03's command can reach. **It writes nothing to a radio.**

What came of it, in one line each:

- `core/image/base.{h,cpp}` — §4a's seven rules over a `provision` file **as a stream**, with the
  reference's refusals word for word; and `BaseWords`, the file's data as `(address, word)` in
  address order, which task p5-03 writes.
- `image/manifest` — `provision` joins `Use`; §2's five rules for such a file, each a
  `ValidateReason` with `manifestref.validate`'s words.
- `image/verdict` — **check 5p**: the region against this build's board table, then §4a against
  the build's region, yielding an **`AcceptedBase`** that no road connects to an `AcceptedImage`.
- `image/store` — `Which::kBase`, one area per slot, its own door `commitBase(const AcceptedBase&)`,
  never promoted, outside the bad list, erasable by a command, and whole-or-absent after a power
  cut anywhere.
- the console and the cable — `image list`/`verify`/`erase`/`receive` `base`, and
  `walterctl.py push --as base`.

## Decisions taken without asking

- **A base area holds 640 KB, not an image area's 796 KB.** Eight areas of `kImageBytesMax` would
  need 6 400 KB of a 6 144 KB partition. The arithmetic, which `image list` prints and
  `test_store.cpp` re-derives: the index 8 KB + six image areas (2 × 3 × 200 sectors) 4 800 KB +
  two base areas (2 × 161 sectors) 1 288 KB = **6 096 KB of 6 144 KB, 48 KB left**. 640 KB is
  ~2.75 × 232 KB of flash bytes — Intel HEX of 16 data bytes a record costs 44 characters — and a
  RAK4630's base is 192 KB of flash (MBR 4 KB, S140 6.1.1 148 KB, bootloader 40 KB), so ~528 KB.
  The base areas are laid out **after** the six, so every image area is where it was.
- **The base is not in the index.** The index maps the three promotable roles to areas; the base's
  area is the constant `kBaseArea`. That is how "a promotion never moves a pointer to or from it"
  is held — there is no pointer — and it keeps the index record byte-identical to phase 2's, so
  `kFormatVersion` did not have to change and no store already written becomes unreadable.
- **A base's record keeps §4a's summary where an image's keeps its descriptor.** Those 96 bytes are
  inside the record's CRC; adding fields after it would have moved the CRC and made every existing
  record of format 1 unreadable. The record's `use` byte says which of the two the bytes are, and
  neither is ever read as the other. The summary is a bitmap of UICR's 194 registers plus five
  words — 52 bytes of the 96.
- **`Check::kBase = 50`.** §5 calls it *5p*, not a seventh number; the enum's other values are §5's
  own numbers, so an out-of-band value keeps that true. `describe()` says "check 5p, the base".
- **An `Outcome`'s `why` is the verdict's own buffer for a 5p refusal.** §4a's sentences carry a
  line number or an address, so they cannot be static text; `core/image/` has no formatting, so
  `base.cpp` writes the decimal and the `0x%08X` itself into a 160-byte field of the result, which
  lives as long as the verdict. Both callers — the transfer's response and the console's line —
  print it at once. Said in `verdict.h` where `Outcome` is declared.
- **The bounds of the stream reader, and what each pass keeps.** Rule 1's last clause — "no address
  given two different bytes" — cannot be answered byte-exactly from a stream without remembering
  the bytes. What the reader keeps instead is `BaseRuns`: the addresses the file covers as at most
  **32 merged intervals**, 520 bytes. A record that overlaps one of them is a *candidate* repeat,
  and only then is the file walked again to see whether the byte actually **differs** (giving the
  same byte twice is allowed, as the reference allows it) — so the refusal names the line and the
  address the reference names, exactly. More than 32 disjoint runs, or more than 8 repeats, is
  `kTooManyRuns`/`kTooManyRepeats`: not a base, said in this firmware's own words. The rest of a
  pass is the six watched words (72 bytes), UICR's bitmap (25), the record being parsed (255) and a
  256-byte read buffer — **~900 bytes a pass, and never the file**. `BaseReader` is 2 016 bytes,
  `BaseResult` 736; the whole verdict is 35 520 (it was ~33 000) and the console's own reader, for
  `image verify base`, 2 016 more. A read of the fixture is capped at 256 bytes and counted by the
  test.
- **`BaseWords` fills one 4 KB window a pass.** Task 03 needs `(address, word)` in address order,
  and the file's records need not be in that order. One pass over the file per nRF52840 page: a
  192 KB base is 49 windows, so ~22 MB read from the Walter's own flash — nothing beside the
  minutes the same base takes to write over a 125 kHz debug port. 5 624 bytes, the caller's to
  place. A word the file gives none of is never handed out; one it gives part of comes out padded
  with `0xFF`, because erased flash reads `0xFF` and the NVMC can only clear bits.
- **`kMaxFilesPerImage` is seven.** §2 now lists seven `use` values and "a file is one way of
  delivering that image".
- **A base is listed under the image it goes under**, so `image receive base` asks check 3 for the
  repeater's role, the slot's board and its band — as an `swd` file does. A release carries one base
  per board, not one per role.
- **`image erase base` is allowed.** S-5 keeps the golden image because something must always be
  there to fall back to; nothing falls back to a base, and S-5a is a person's command from end to
  end.
