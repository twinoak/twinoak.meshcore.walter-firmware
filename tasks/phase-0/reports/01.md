# p0-01 — the toolchain

The repository builds, tests and verifies itself inside one Docker image, on this machine and in
CI, with one command. `tools/verify.ps1` runs `tools/verify.sh` in `espressif/idf:v5.5.5` (pinned by
digest in `tools/idf-image.txt`) with the checkout bind-mounted and the build in a volume: the spec
copy against its manifest, the spec's two self-checks, the host tests under the sanitizers, the
firmware build with `dptechnics/walter-modem` 1.5.0 resolved, compiled and linked, and the partition
table against what was built. Cold, with the image already pulled, it is green in 28 s on this
machine; warm in 5 s. The firmware prints `twinoak-walter 0.0.0-dev`, which slot it runs from, and
idles. Everything the task asked was done; four things differ from how it was described, all below
under *Deviations* — the largest being that the interfaces directory is `components/interfaces/`,
not `components/hal/`, because ESP-IDF owns a component named `hal`.

Why v5.5.5: `walter-modem` 1.5.0 declares `idf: ">=5.0.0"` and its `modem_firmware_flash` example's
`sdkconfig.defaults` was generated on 5.4.1, so the 5.4 and 5.5 lines are both candidates. 5.5.5
(2026-07-17) is the newest patch of the newest 5.x line and its branch is still being updated
(`release-v5.5`, 2026-09-21); 5.4.4 (2026-04-15) is the end of a line that has aged out. ESP-IDF
6.0 and 6.1 exist (2026-03 and 2026-08) and are a new major that the library's February 2026
release predates; nothing was tried there. The library compiled on 5.5.5 at the first attempt with
no warnings, so the fall-back to 5.4.4 that was planned was not needed. The digest pinned is the
manifest list's, so the same line resolves on an amd64 runner and an arm64 laptop.

## Deviations from the spec or the task

- **`components/hal/` is `components/interfaces/`.** ESP-IDF has a component named `hal`
  (`$IDF_PATH/components/hal`, included as `<hal/gpio_hal.h>` and friends), and a project component
  of the same name *replaces* it: the first build died in mbedtls with `hal/sha_types.h: No such
  file`. The directory is `components/interfaces/`, the include prefix `interfaces/`, and
  `docs/ARCHITECTURE.md` §1 says so; `tasks/README.md` and the task files still say `hal/` — read
  it as this directory (the reviewer may want a line in `FOLLOWUPS.md` for task 03, which writes
  the first interface). `tools/cmake/no_idf_include.cmake` forbids `hal/` as an ESP-IDF prefix.
- **The modem library's unused protocols could not be switched off.** The task: off "where its
  Kconfig allows (keep HTTP and sockets)". At 1.5.0 the Kconfig offers the switches and the code
  does not honour them, each tried in the build: MQTT or GNSS off → `WalterModem.h` fails
  (`WMMQTTEventData`/`WMGNSSEventData` name types defined only under the switch;
  `WalterModem.cpp:4011` touches `gnssHandler` outside its guard); CoAP off (which takes BlueCherry)
  → `WalterModem.cpp:615ff., 3779ff.` refer to `_blueCherry` and the MOTA handlers
  (`out/experiments/build-coap-off.log`); MOTA off → `WalterHTTP.cpp` loses `esp_log.h`, which it
  only had through MOTA's includes. So every library switch keeps its default (`y`), nothing of it
  is called, the pin stays exactly 1.5.0 as the task says, and `sdkconfig.defaults` carries the
  evidence. The library's own `add_compile_options(-Wno-error)` is also ineffective (it comes after
  `idf_component_register`, so CMake does not apply it to the already-created target); the library
  compiles under ESP-IDF's `-Werror` with its exemptions, which is enough — it had no warnings.
- **No partition for the modem library's firmware update.** ARCHITECTURE §11 asked for "whatever
  the modem library needs for a modem-firmware update". Read in the source (`WalterModem.cpp`,
  `_motaFormatAndMount`): a wear-levelled FAT partition labelled `ffat` holding `mota.dup`, which
  for the current modem firmware `LR8.2.1.0-61488` is 9.0 MB (the `modem_firmware_flash` example
  gives it 0xBE0000). 3 + 3 + 6 + 9 MB does not fit in 16 MB. Nothing is allocated; MOTA is never
  run (it is BlueCherry-driven); a modem firmware update is a bench procedure — QuickSpot's example
  flashed for the occasion, or the module's `UART1` (datasheet §"Firmware upgrade"). §11 is
  corrected accordingly and the 3.75 MB above `rakfw` is left unallocated for a decision later.
- **"Compiled into the image and called by nothing"** needed a reference: a static library that
  nothing references is compiled but dropped by the linker. `components/modem/modem_anchor.cpp`
  takes the address of `WalterModem::begin` and `main` stores it in a volatile; nothing calls it.
  Phase 3's uplink replaces the anchor.
- **The merged image is made by `idf.py merge-bin`** (ESP-IDF 5.5's own, `esptool merge_bin` under
  it), named `twinoak-walter-factory.bin`; the release (task 02) may rename it.
- **CI rounds:** filled in below after the PR ran — *none* if this line still reads so.

## Decisions taken without asking

- **ESP-IDF v5.5.5**, above. **doctest v2.5.3** as the one test framework (vendored header, MIT;
  `host_test/third_party/doctest/README.md`).
- **`cryptography` pinned to 44.0.3**, the version already in the image's Python environment
  (esptool depends on it): `tools/requirements-verify.txt` is then a check that costs no network,
  and a different pin would fight esptool's constraint.
- **PSRAM off.** The datasheet lists Walter variants with 2 MB quad and 8 MB octal PSRAM; a firmware
  configured for one kind aborts its boot on the other; nothing here needs it yet.
- **CPU at the default 160 MHz**, not QuickSpot's 240: nothing here is compute-bound and the unit
  runs from a battery.
- **`-Os` with assertions** instead of ESP-IDF's `-Og` default: a field firmware.
- **Flash auto-detect off, QIO explicit**: the datasheet says quad; auto-detect exists for unknown
  boards and costs ~900 B IRAM.
- **The table's numbers**: `nvs` 64 KB, `journal` 64 KB (subtype `0x41`), `rakfw` 6 MB (subtype
  `0x40`; 2 radios × 3 images × 1 MB, 1 MB being the whole flash of an nRF52840 so no radio image
  can be larger), `coredump` 64 KB; the 0x9000–0xDFFF gap empty as the agent firmware learned.
- **Rollback and this image.** Read in `bootloader_utility.c` (5.5.5): the bootloader marks a slot
  `PENDING_VERIFY` only if its `otadata` state was `NEW`, which only `esp_ota_set_boot_partition`
  writes; an image flashed over USB sits in a slot whose state is `UNDEFINED` (0xFFFFFFFF, "app can
  boot and work without limits"), so no rollback is ever attempted on it and it boots every time.
  This image therefore **confirms nothing** — it prints the state (`undefined (flashed over USB, not
  by an update; rollback does not apply)`) and leaves it: per S-6 an image confirms itself only
  after booting, speaking to the radio and reaching the server, none of which exists yet, and an
  image that arrives by an update and cannot do that *should* be rolled back. Task 02/04 adds the
  confirmation when there is something to confirm. The bench checks the premise (below).
- **`app_main` returns** after printing; FreeRTOS idles; the task watchdog watches the idle tasks.
- **One build volume and one cache volume per clone**, named with a hash of the clone's path, so
  two checkouts on one machine do not share a build directory. `managed_components/` and
  `dependencies.lock` land in the checkout (the component manager's choice); the lock is committed,
  the directory is git-ignored.
- **The product version is never `git describe`**: `-DPROJECT_VER=` from the release, else
  `0.0.0-dev`, so a build says what it was told and the manifest's `version` is the same string.
- **`host_test/` runs core with `-fno-exceptions -fno-rtti`** and the test binary with exceptions
  (doctest wants them); both under the sanitizers.

## Not verified here (and why)

No Walter was on a desk; a session cannot flash a board. `docs/bench.md` §1, *The Walter alone on
USB*, has the same three lines in the order the rig is brought up:

1. **Flash the factory image over the module's USB-C** with the esptool line in README.md
   (`--flash-mode dio`, `0x0 out/images/twinoak-walter-factory.bin`), open the port: the console
   prints `twinoak-walter 0.0.0-dev`, then `running from ota_0 at 0x010000 (3072 KB), ota state
   undefined (…)`, then `console on USB; nothing to do yet - idling`. The USB Serial/JTAG console
   and the QIO switch are what only a board shows.
2. **After a reset the same image runs** — three resets, three times the same banner, the state
   staying `undefined`. This is the check of the rollback premise above: if a second boot ever
   says `aborted` or the bootloader finds no bootable app, the premise is wrong and the fix is a
   `esp_ota_mark_app_valid_cancel_rollback()` at boot until task 04's real confirmation.
3. **Nothing of ours drives the radio-facing pins** (GPIO 1, 2, 4, 5, 7 read as inputs after boot);
   task 03 owns their rules, this only confirms task 01 touches none of them.
