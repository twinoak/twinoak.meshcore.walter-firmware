# p0-03 — the board

The seven pins this firmware shares with the radio now have their rules in one place and nowhere
else: `RadioPins` (`components/core/board/`), the only object that touches them, enforcing every
rule of `docs/ARCHITECTURE.md` §2 inside itself and tested against fake pins that record every
transition with its time and check the rules themselves — by name, at the transition that breaks
one. The reset line has no operation that drives it high; a reset is a 100 ms open-drain pulse and
two are a second apart, waited for rather than refused, across a deep sleep too; a kill releases
every other pin first, drives the kill line high or not at all, is bounded, and waits for the rail
to settle before anything faces the radio again; a failure part-way ends in the safe state; SWD
cannot be acquired with the rail off, nor its clock toggled with reset asserted. The pin map is
held against the table in ARCHITECTURE §2 by a test that reads the document, and `tools/verify.sh`
greps that nothing outside `components/platform/` calls the GPIO driver and nothing outside
`core/board/` names the pins. Around it: the first five interfaces and their ESP-IDF
implementations, `Health` (why the last boot happened, in RTC memory), and a console on the
module's USB — `help`, `status`, `reboots`, `pins`, `rak reset`, `rak kill <seconds>`, `reboot` —
whose parser and commands are host-tested, including **3 000 random command sequences (10 482
lines, 106 resets, 270 kills, 91 reboots) that broke no rule**. In `app_main`, the safe state is
the first thing that happens.

`tools/verify.ps1` is green on this machine: **cold 36 s** (spec 0, spec-tools 0, host-tests 8,
release-tests 1, build 26, partitions 0, release 1), **warm 11 s**. **67 host test cases, 123 729
assertions**, under ASan and UBSan. The firmware is 322 144 bytes, 10.2 % of its slot (15 200 bytes
more than task 02's). Every acceptance criterion is met; the deviations and the decisions are
below. The kill's bounds and the settle time are **placeholders** — the hardware documents give no
number for the rail — and the report says so where the task asks.

## Deviations from the spec or the task

- **`components/hal/` is `components/interfaces/`** — task 01's deviation, inherited: ESP-IDF
  owns a component named `hal`. Every "hal" in the task file is this directory; the include prefix
  is `interfaces/`.
- **TX in the safe state is pulled up, not driven high.** ARCHITECTURE §2 said "UART idle high
  while the radio is powered" and the task "TX high if the radio is believed powered"; built as:
  TX is an *input with the chip's weak pull-up* (tens of kΩ) whenever the radio is believed
  powered and the UART is not in use, a plain input when it is not, and driven only between
  `uartEnable()` and `uartRelease()`. The radio's receiver sees the same idle high; a radio that
  is unexpectedly dead sees microamps through 470 Ω + ~45 kΩ instead of the ~7 mA the series
  resistor would allow a driven pin — rule 3's "make it zero" applied to the state the firmware
  sits in most of the time — and phase 1's criterion "the UART's pins are only driven between
  `uartEnable()` and `uartRelease()`" holds by construction. The pull-up is off during a kill (the
  fake counts a pull-up as "not an input" while KILL is high). ARCHITECTURE §2's table and rule 1
  say so now. A fourth pin mode, input-with-pull-up, is the cost.
- **The spacing across deep sleep is honoured conservatively, because the clock restarts.**
  The time of the last reset is kept in retained storage as the task asks, and a new `RadioPins`
  over the same storage honours it to the millisecond (tested). But ESP-IDF's `esp_timer`, which
  the platform clock is, "restarts from zero upon wakeup from deep sleep"
  (`docs/en/api-reference/system/esp_timer.rst`, v5.5.5). So a record whose time is *ahead* of the
  clock — a new clock epoch — is read as "a reset ended just now", and the first pulse after a
  wake waits a full second (tested with a restarted fake clock). Correct, never early, at most one
  second late; the duty-cycle task (phase 3), which owns sleeping and waking, can carry the time
  slept across (an RTC-backed offset) and then the record is honoured exactly. The same rule
  covers no record and a power cut.
- **The first reset after a boot waits a second** whatever the record says, because a Walter
  power-up glitches nRESET and reboots the radio (`BENCH-BREADBOARD.md` §6 caveat 3) a few hundred
  milliseconds before `app_main` runs, and a pulse inside that window would be the second tap of
  the bootloader's double-tap (caveat 4). The task does not say this; the spacing rule implies it.
- **A kill takes the UART and SWD lines from their holders; a reset is refused while SWD is
  held.** The task: `killCycle()` "releases the UART and SWD pins and the reset pin first" —
  built literally: the kill releases them itself and the holder's `SwdLines` operations return
  false from then on (tested), so the order on the wires is what the rule wants whoever holds
  what. For the reset, the task says "nothing can toggle the SWD clock while reset is asserted";
  built as `resetPulse()` returning `kSwdHeld` while the lines are acquired (the holder releases
  first — phase 1's flasher step 7 does exactly that) plus `SwdLines::clock()` refusing while
  `reset_asserted_`, and the fake's `swdclk-while-reset` underneath both. Phase 1 task 06's
  selector gets its own operation here.
- **`rak kill` has no confirmation word.** Phase 3 task 03 says `rak kill` beyond a few seconds
  asks for one; that task owns the grammar and adds it. Here the bounds (1–30 s) are the guard.
- **The banner is printed by `main`, not by the console.** `docs/bench.md` §1 and `README.md`
  tell a person to expect the banner first, then the slot, then the descriptor; the console's
  `begin()` prints the boot's reason and the first prompt after them. The old last line
  (`console on USB; nothing to do yet - idling`) is gone; `docs/bench.md` §1 says what replaced
  it.
- **ARCHITECTURE §2's table gained a D-sub column**, so that the host test which reads it holds
  all three of the task's columns (net, D-sub pin, GPIO) and not two. The spare's net is written
  `` `spare` `` so it parses like the others. Nothing else in the table changed except the TX
  row's rule (above).
- **The grep of criterion 3 is in `tools/verify.sh`**, not only run by hand: the task says
  "`grep` finds…", and a grep that runs on every verification is the one that keeps finding
  nothing when phase 1 adds the UART and SWD.

## Decisions taken without asking

- **What the firmware believes about the rail** is derived, not set: *off* while the kill line is
  driven; *unknown* for `settle_ms` after it was released — and for `settle_ms` after boot, since
  a Walter that reset in the middle of a kill left the line to float back on just before; *on*
  otherwise. `uartEnable()`, `swdAcquire()` and `resetPulse()` wait out *unknown* (bounded by the
  settle time) and refuse *off*. `status` prints it.
- **`safe()` does not check the driver's answers**: it is the fallback after a refused operation,
  and every pin is tried regardless. Every other operation stops at the first refusal and calls
  it; the outcome is `kPinRefused`. In the fake, refusals are injected by predicate (tested for
  the kill at three points).
- **The reset pin is written low first, then made open-drain; the kill line is written high
  first, then made an output.** Level before enable, always, so that a pin never drives a level
  nobody asked for; the fake's `kill-driven-low` catches the other order.
- **The fake's `reset-driven-high` is stricter than the rule**: writing the reset pin high in
  *any* mode is a violation, not only push-pull. A pulse is accepted between 100 and 150 ms long
  (the platform's `delayMs` adds a tick, so a 100 ms request is 100–110 ms on the board).
- **The platform's `delayMs` is `vTaskDelay(ticks + 1)`**, never shorter than asked (vTaskDelay(n)
  blocks for n−1 to n ticks), and a busy wait under one tick. At `CONFIG_FREERTOS_HZ=100` the
  pulse is 100–110 ms and the spacing ≥ 1000 ms.
- **`gpio_config()` per mode change, with the `INPUT_OUTPUT` and `INPUT_OUTPUT_OD` modes for the
  driven ones.** `gpio_config` sets the direction, both pulls and the pad's GPIO function in one
  call (`esp_driver_gpio/src/gpio.c`), so a pin a peripheral once owned comes back; the input
  stays enabled on outputs so `gpio_get_level` reads the pad and `pins` shows the line nRESET
  actually sits at while it is pulled low.
- **Retained storage is two slots of up to 128 bytes** in `RTC_NOINIT_ATTR` memory, each with a
  magic (`0x54575201`, bumped if the layout changes), the record's size, the bytes and a CRC-32
  (`esp_rom_crc32_le`). A record of another size is not the same record — a firmware whose
  `Health::Record` grew does not read the old bytes as the new ones (tested on the host with a
  truncated record). The reset record is 8 bytes, the health record 44.
- **`Health` pushes an entry for every boot, the first included**, so `reboots` always shows this
  boot; the entry carries the length of the run before it (kept fresh by `tick()` once a second,
  which is one RTC-memory write a second and no flash). A planned restart's reason is stored
  before the restart and consumed by the next boot only if that boot's reset reason is "software";
  a wake cause is kept only when the reset reason is "wake from deep sleep". The mapping: CPU
  lock-up → panic; power glitch → brownout; SDIO, JTAG, eFuse → other; ext0, ext1, GPIO and the
  UART wake-ups → "pin"; codes ESP-IDF does not have → unknown / other.
- **The console's line discipline is the agent firmware's**: 200 characters, printable ASCII,
  echo, `\b \b` on backspace, one line beginning `error:` for a refusal. `rak kill` takes whole
  seconds and the parser refuses a sign, a fraction, a unit and more than nine digits; the bounds
  are `RadioPins`' and the refusal prints them. `status` puts the seven pins on one line; `pins`
  gives them a table. The console writes `\n`; the platform turns it into CR LF.
- **The USB console**: the USB Serial/JTAG driver is installed (256 B in, 1 KB out) and the VFS
  pointed at it so ESP-IDF's own log lines and `printf` share the same interrupt-driven path;
  writes wait at most 20 ms for room, so a Walter on a mast printing into nothing never stalls.
  `app_main` no longer returns: it reads a byte at a time with a 100 ms timeout, feeds the console
  and ticks `Health` once a second; the task watchdog watches the idle tasks, which run while it
  waits. If the driver cannot be installed the firmware runs on without a console.
- **The property test** feeds 3 000 sequences of one to six lines, each line one to four tokens
  from a bag of commands, fragments, numbers in and out of range and junk bytes, with random pauses
  of up to 1.5 s between lines, to the console over the fake pins in strict mode; after every line
  it also checks nothing is driven, asserted or held. Seeded (`20261011`), so a failure is
  reproducible.

## New libraries (with the one-line justification)

None. `<functional>`, `<random>` and `<map>` from the standard library are used in `host_test/`
only; `core/` adds nothing beyond `<cstring>`, `<cstdio>` and `<cstdarg>` (the console's
`vsnprintf` into a stack buffer: no heap).

## Not verified here (and why)

No Walter was on a desk and no session can wiggle a pin, so what the fake pins proved on the host
is what the rig must now show on the wires. `docs/bench.md` §2, *The pins*, has the same lines in
the order the rig is brought up (`BENCH-BREADBOARD.md` §7), and §1 gained the console's lines:

1. **The console answers** (§1): the boot line and the prompt after the banner; `help`, `status`,
   `reboots`; a reset-button boot shows `boot 2: reset pin reset` with the first run's length; a
   `reboot` shows *asked for on the console*; a replug starts the record afresh. This is the
   USB Serial/JTAG driver, `esp_reset_reason()` and RTC memory, none of which the host runs.
2. **The safe state at boot**: a meter on GPIO1, 2, 4, 5, 6, 8 (high-impedance) and GPIO7 (the
   weak pull-up); `pins` agreeing.
3. **The power-up glitch is the ESP32-S3's**: nRESET's dip at the Walter's power-up, the radio's
   restart, and nothing driven afterwards.
4. **`rak reset`**: one 100 ms low pulse, never above the pull-up level; the radio restarts once;
   two in a row are a second apart and the radio does not land in UF2.
5. **`rak kill 5`**: TX, nRESET and the SWD lines quiet before KILL rises; KILL high for 5 s then
   floating; the rail falls and returns; 0 V while down, not a diode drop.
6. **Reset the Walter during a kill**: the rail comes back by itself.
7. **The numbers that replace the placeholders**: the rail's fall and settle, at a transmit load
   and at an idle one, into `kKillTiming`.

Also only a board can show: the hold calls (`holdForSleep()`/`releaseHolds()`) keeping the pads
through a real deep sleep — phase 3 sleeps and walks that; and the clock's behaviour across a
wake, which decides whether phase 3 adds the RTC-backed offset or leaves the conservative rule.
