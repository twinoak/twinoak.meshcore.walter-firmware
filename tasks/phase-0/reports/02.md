# p0-02 — the release

Pushing a tag `vX.Y.Z` now makes a GitHub Release of this firmware: the application image a
running Walter updates itself with, the merged image for a module out of the box, a
`manifest.json` that says what each is, an Ed25519 signature over it and `SHA256SUMS`. *Run
workflow* rehearses the same three jobs and publishes nothing — and so does `tools/verify.ps1` on
every verified commit, which is the part that matters most: the tag path is never run for the
first time on a tag. And from this task on the image says inside itself what it is: 96 bytes of
`spec/FIRMWARE-MANIFEST.md` §4, built at compile time, CRC-32 and all, found exactly once in each
published file and held against the manifest entry above it.

`tools/verify.ps1` is green on this machine: **cold 33 s, warm 7 s**, 15 host test cases / 327
assertions, 37 release-tooling tests. The firmware is 306 944 bytes, 9.8 % of its 3 072 KB slot.

**A tag fails today, on purpose.** The release key does not exist — it is Thomas's to make
(`spec/SYSTEM.md` §10 item 1) — so `keys/release-keys.txt` names no key and there is no
`RELEASE_SIGNING_KEY` secret. `sign_manifest.py` stops at the missing secret and
`verify_release.py` at the empty trust table, both with the `manifestref.py keygen` instructions,
and both before `gh release create`. That is the same safe state a unit is in from the other end:
no key compiled in, no update accepted (§3).

## Deviations from the spec or the task

- **`tools/verify.sh` gained two steps, not one.** The task says *`tools/verify.sh` gains: the
  release tooling's tests, and a local dry run over the build it just made*. They are two steps,
  `release-tests` and `release`, not one: the tests need no firmware, so they run before the build
  where a mistake in them is cheapest to find, and the dry run must run after it. `verify.ps1
  -Only <step>` names each.
- **No `--no-require-descriptor`.** The task notes that *`--require-descriptor` is on from the
  start here*, which reads as a flag the repeater's tooling can turn off. `build_release.py` takes
  `--require-descriptor` and the workflow passes it, but there is no negative form: a way to
  publish a file that does not say what it is is not something this repository should own. If the
  repeater's tooling needs one, that is its decision to make.
- **The local dry run's version is `0.0.0-dev`, not `0.0.0-dryrun+<sha7>`.** The task specifies
  `0.0.0-dryrun+<sha7>` for *the workflow's* dry run, and the workflow uses exactly that. A local
  `tools/verify.ps1` builds and releases `0.0.0-dev` — the version task p0-01 made the default and
  that `README.md` and `docs/bench.md` tell a person to expect on the console. One string serves
  the build, the descriptor and the manifest, so making the local rehearsal `-dryrun` would have
  changed what a bench reads for no gain; `-Version` passes anything, and
  `-Version 0.0.0-dryrun+<sha7>` was run green. It does mean a local `manifest.json` has a
  `version` that is not §2's `X.Y.Z+<sha7>` shape — `validate()` accepts it (§2 types it as a
  string), and a file named `twinoak-walter-v0.0.0-dev.bin` signed by a public test key cannot be
  mistaken for a release.
- **A dry run does not wait for CI.** The agent firmware's `ci-green` job waits for a green `ci`
  *push* run on both paths. A rehearsal here may be run on a branch, where `ci` ran for the pull
  request and not for a push, so the wait would always time out. The wait is `if:
  github.ref_type == 'tag'`; a dry run prints what `ci` says about the commit and carries on. The
  gate is unweakened: only the tag path publishes.
- **`README.md`'s two PowerShell blocks were repaired.** They contained literal tab and
  vertical-tab bytes where `.\tools\verify.ps1` and `.\tasks\run-pile.ps1` belonged — the four
  commands in *Building it* and the two in *The task piles* were unrunnable as printed. Task 01's
  own report quotes them correctly, so this is a writing accident, not a decision; this task edits
  that block anyway. (The cause is worth knowing for the next session: writing `\t` through a shell
  heredoc here turns it into a tab. Both blocks were rewritten through PowerShell instead, and
  `README.md` now holds no tab, vertical tab or CR.)
- **`idf.py` is always given `-DPROJECT_VER`.** `CMakeLists.txt` defaults it when it is *not
  defined*, but it is a CMake cache variable: a build directory that once saw
  `-DPROJECT_VER=0.3.1+abc1234` would keep saying so when the next run passed nothing. `verify.sh`
  passes `${TWINOAK_VERSION:-0.0.0-dev}` every time, so the cache is always explicit. This is why
  the same build volume could be used for the `0.3.1+abc1234` rehearsal and then returned to
  `0.0.0-dev`.
- **`project_description.json` travels to `out/images/`.** The build directory is a Docker volume
  and the release workflow runs the tooling on the runner, over the `build` job's artifact. Copying
  that one file beside the images makes `--build-dir out/images` enough, and is what lets
  `build_release.py` catch a release made under a version the build was not given.

## Decisions taken without asking

- **The manifest entry's constants are this repository's, and the descriptor is held against
  them.** `build_release.py` carries `role=manager`, `board=walter`, `band=lte-m`, `mcu=esp32s3`,
  `link 1.0`, `slot=0xFF`, `requires.link_major=1`, `id=manager.walter.lte-m` — and compares what
  it finds inside each file with them, field by field. Deriving the entry *from* the descriptor
  would have made the check vacuous. The two files' being one build is held by their bytes, not by
  their descriptors: the factory image must carry the application image byte for byte at `ota_0`'s
  offset.
- **`esp_app_desc_t` is read as a second witness.** ESP-IDF writes that structure at `0x20` of an
  application image (`$IDF_PATH/components/esp_app_format/include/esp_app_desc.h`, v5.5.5: magic
  `0xABCD5432`, `version` at +16, `project_name` at +48, `idf_ver` at +112; `0x20` because a
  24-byte image header and an 8-byte segment header come first — each read against the header and
  confirmed on the real image). Our build writes the TWOKFWD1 descriptor; both come from
  `PROJECT_VER`. A release in which they disagree, or whose `project_name` is not
  `twinoak-walter`, is refused — and `idf_ver` is where the release notes' ESP-IDF version comes
  from, read out of the image rather than typed.
- **The signing key comes from an environment variable and from nowhere else.** No `--key`
  argument, no key file, no prompt. `--test-key` reads `manifestref.TEST_PRIVATE` — the key pair
  the specification publishes on purpose — so a rehearsal needs no secret at all. "A release
  version" is `X.Y.Z+<sha>`, or a `vX.Y.Z` tag; the test key is refused for either, and refused
  outright if it turns up in `RELEASE_SIGNING_KEY`.
- **`keys/release-keys.txt`, one key a line, `ed25519 <key id> <public hex>`**, `#` comments, at
  most three (§3: room for three). The key id is recomputed from the public key and a line where
  it is wrong is refused, so a copy-paste that mixes two keys is caught at the gate rather than at
  a unit. Phase 2 generates the firmware's compiled-in table from this file.
- **`verify_release.py` is a separate tool and runs on every verified commit.** §5 is a list of
  checks a *consumer* makes; running them over the files before publishing is the cheapest place to
  find a release that a unit would refuse. It also refuses a manifest that is not in §2's canonical
  form, and one that is not this product's.
- **The host tests read the spec's fixtures through a generated table.** `index.json` becomes
  `descriptor_fixtures.h` at build time (a ~100-line Python script) instead of the tests parsing
  JSON. A JSON reader of our own would be a thing to get right before it could prove anything, and
  it would have to live in `host_test/`, not in `core/`; the image files themselves are still read
  at run time from `TWINOAK_SPEC_FIXTURES`.
- **`find()` counts every valid descriptor, not just the first two**, so a message can say how
  many there were; `Found.count != 1` is the refusal (§4, §5 check 5). `role_name` returns
  `nullptr` for a role number this firmware does not know rather than a formatted `role-7`: `core/`
  has no heap and no `sprintf`, and a name that might be mistaken for a known one is worse than
  none.
- **`SHA256SUMS` covers the two images and `manifest.json`**, not `manifest.json.sig` (written by
  the next step, and self-verifying) and not itself. The notes say so.
- **`NOTES.md` is `build_release.py`'s output**, not the workflow's YAML: it is then testable
  locally, and five tests hold what it must say — the `esptool` line, the factory-flash promise and
  the check that holds it by name, the commit, the versions, and that a release's notes do not say
  "dry run".
- **A tag must name a commit of `main`** (`git merge-base --is-ancestor`), as in the agent
  firmware: a tag on a side branch is not a release.
- **The `build` job runs the whole `tools/verify.ps1`**, not only the build step. What is published
  is then verified at its own version, which is not the version CI verified. It costs one extra
  run of a 30-second script per release.

## New libraries (with the one-line justification)

None. The release tooling is the standard library plus the `cryptography` 44.0.3 that task p0-01
already pinned in `tools/requirements-verify.txt` for `manifestref.py`'s Ed25519; the workflow's
`publish` job installs that same file on the runner. The descriptor is plain C++17 with no
dependency, and the host tests use the doctest task p0-01 vendored.
