# p10-04 — The download that does not resume

A radio image's download resumes across wakes: the image store keeps a progress record every
64 kB, so the next wake continues the file. The Walter's **own** does not — the other application
slot is erased when a write opens on it (`SelfUpdate::beginWrite` sets `written_ = 0`, and
`abandonWrite()`, which every verdict but `kStored` calls, zeroes it again) — and until this task
both of the messages a budget-stopped download produces promised a resume for either box.

Now each of the two says which box it is about, chosen by the branch that already knew
(`FetchResult::own_image`, and `runOffer`'s `walter`). **No resume was built**: that is the task's
*Out of scope*, and the figure that would decide whether to build one is still not on the bench.

`tools/verify.ps1` is green on this machine, every step, on the final tree.

## The figure

**`docs/bench.md` §18 has no measurement.** Its item *The Walter's own release over LTE, 0.1.1 to
0.1.2* (task p9-07) is unticked and the two numbers it asks for — the download's wall-clock seconds
and the wake's own elapsed time — are not written down. This pile's README says why: at the first
update over LTE, **job 22841 failed in two seconds**, because no request to `/agent/v1` has ever
carried the `X-Agent-Version` header meshmaster.dk requires (task 05 of this pile sends it). So no
download of the Walter's own image has run to completion, or to a budget stop, on a real plan.

What can be said without the measurement, against the two constants:

| | |
|---|---|
| the image | **765 904 bytes** of `twinoak-walter.bin` (this tree's build) |
| in ranges | **12** requests of 64 kB (`kRangeBytes`), the last one 21 kB; each with its own 120 s deadline (`kRangeTotalMs`) and three attempts |
| bytes a wake | **1 048 576** (`kWakeDownloadBytes`) — the file fits with **282 672 bytes spare**, a factor of 1.37 |
| seconds a wake | **1 200** (`kBackendBoundMs` = `kUpdateBoundMs`), for the *whole* exchange: the heartbeat, the claim, the download, the results |
| what the seconds demand | **≥ 638 bytes/s** sustained over the download alone. LTE-M is *a few kilobytes a second* (`spec/proposals/02`, *Serving*), so 2 kB/s is ~380 s and 5 kB/s ~150 s |

**So: a resume is not worth building on this arithmetic**, and nothing here says otherwise. Both
budgets have headroom, and the one that would bite first is the bytes (1.37×, not 10×) rather than
the seconds. What the arithmetic does *not* cover is the only thing that would change the answer: a
range that stalls. A stalled range costs up to 120 s and three of them in a row end the download
for that wake — and a 30-second stall on a POST is a **reproducible** fault on this unit right now
(phase 10's `FOLLOWUPS.md`, and task 06 of this pile puts its trace on the console). Four stalled
ranges inside one wake would spend 480 s of the 1 200 and leave a part-downloaded file that the
next wake throws away. That is the case the measurement has to rule in or out, which is why §18
now asks for the seconds **whether the download finished or not**, and why the design question
stays open in `tasks/phase-9/FOLLOWUPS.md` rather than being closed here either way.

If it does turn out to be worth building, the shape is already written down there: `esp_ota_resume`
(ESP-IDF v5.5) to reopen the slot without an erase, and the journal to carry the bytes written.

## What was built

**`core/update/fetch.h` / `fetch.cpp`.** `describe(FetchVerdict verdict, bool own_image)` — the
second parameter has **no default**, so a new caller has to say which box it is about rather than
inherit the radio's sentence by accident; the two existing callers pass `r.own_image`
(`Console`'s `fetch` error line, `WakeCycle::runFetch`'s refusal — both radio, both now provably
so). `FetchResult::own_image` is set in `fetchInto` from `store == nullptr`, which is exactly what
distinguishes the two entry points: `run()` writes into the image store and hands it the erase,
`runInto()` writes into a target of the caller's that has no progress record of its own.
`runInto`'s one early return sets it too. The `kBudget` enumerator's comment says both halves now.

**`agent/firmware_jobs.cpp`.** The `kBudget` branch's two strings are chosen by `walter`, the flag
the branch has had since task p4-05. `line_text` grew from 160 to 200 bytes: at 160 the longer
sentence would be cut mid-word once the two byte counts are long, and at 200 the line is still well
inside the console's own 200-byte cut (task p9-04) through `LOG_I`'s prefix — the worst case is
about 151 characters.

**The documents.** `docs/flashing.md`'s *The Walter's own download does not resume across wakes*
loses *whatever the job's own message says* and names what the messages say instead;
`docs/field.md` step 1 (*offered*) no longer says a cut-off download *simply resumes* without
saying which box; `docs/cycle.md`'s *Partial progress and lease extension* and
`docs/ARCHITECTURE.md` §13's `twinoak.fw.offer` row both carry the Walter's half.
`docs/console.md` needed nothing: its `fetch` is the console's, which only ever writes a radio
image, and its *resumes there* is true.

**A test fake worth naming.** `host_test/core/update/test_fetch.cpp`'s `OwnSlotTarget` is the
Walter's other application slot in the one respect this task is about: `beginWrite` zeroes
`written()` and `abandonWrite()` zeroes it again, so there is nothing to resume from. Its three
words are `core::image::this_image()`'s, as `SelfUpdate`'s are, so the fixture release of the
Walter's product passes check 3 without a second copy of the descriptor anywhere. (The first
version read them out of a local `Fields`, which the address sanitizer caught at once: a
`SlotNeeds` only points at those bytes.)

## Deviations from the spec or the task

- **`spec/proposals/02`, *Serving*, says *downloads must resume*** — "The unit is on LTE-M at a few
  kilobytes a second with a data plan measured in megabytes: downloads must resume, and the server
  should send nothing the unit did not ask for". That is met for a radio image and **not** for the
  Walter's own. This task was told to build no resume (*Out of scope*) and did not; what it changed
  is that the firmware no longer claims otherwise. The proposal is a proposal and not a decision of
  `spec/SYSTEM.md`, so nothing in `spec/` needed correcting, but the reviewer may want the sentence
  qualified where it lives — it is the only place in `spec/` that touches this.
- **The corrected `reason` does not reach meshmaster.dk today.** The follow-up says the budget
  branch *posts* `reason: …`. It writes it into the result and hands it to the runner, but
  `FirmwareJobs` is also its own `ResultGate` and `withhold(job.id)` is true for exactly this job,
  so `ModemUplink::postJobResult` drops the body on purpose (*no result, the lease is left to
  expire*, unit-protocol.md §5). The sentence therefore reaches the job's log and `out.data` and
  not the server's job page. Both were corrected anyway — the string is what would go the moment
  the gate let it, and the page's own wording is the server's to fix. Written into phase 9's
  follow-up as well, because the follow-up's wording implies otherwise.
- **`ModemUplink::postJobResult`'s own withhold line was left alone.** It says *the lease is left
  to expire and the next wake's claim continues the job* — the **job**, which is true of both
  products; it is the download that starts again. That seam knows nothing of products and nothing
  was invented to tell it.
- **`WakeCycle::runFetch`'s own budget line was left alone** (*the download stopped on its budget
  and will resume*): that path is `fetch_->run(…, radio_.slot())` and can only ever be a radio
  image, and its comment already names the store's progress record as the reason.

## Decisions taken without asking

1. **The flag lives on `FetchResult`, not on a product enumeration.** What decides the sentence is
   not "which product" but "does this target keep a progress record", and `fetchInto` already knows
   that as `store == nullptr`. A product word would have had to be threaded from the agent through
   `core/`, which cannot name `agent/`.
2. **`describe`'s second parameter has no default.** Two call sites changed instead; a default of
   `false` would let the next caller on the Walter's path say the wrong thing silently, which is
   the bug this task exists to fix.
3. **The wording.** *this slot keeps no progress, so the download starts again from zero next wake*
   — it says what happens and why in one clause, and keeps *resumes* for the radio so that the two
   can be told apart at a glance in a log. The `reason` carries the same two clauses because a job
   page quoting it should not need `docs/` beside it.
4. **The agent test takes the result gate off to read the body.** A budget stop's result is
   withheld on purpose and that is already held by the test above it; taking the gate off
   (`setResultGate(nullptr)`, documented as *posts every result*) is the only way to read the
   sentence the extension wrote, and it changes nothing in the branch under test. The log line is
   read in the shipped configuration.
5. **The bench item is written as conditional.** A budget stop of the Walter's own download should
   not happen at 1.37× headroom, so §18's new item says so and gives the way to force it (a bench
   build with a lower `kWakeDownloadBytes`) rather than pretending the walk will reach it.

## For `FOLLOWUPS.md` (the reviewer's to place)

- [ ] **`spec/proposals/02`'s *downloads must resume* is now known to be half true.** The sentence
  is in the proposal phases 3 and 4 were built from, and one of the two boxes does not do it.
  Either the proposal says *a radio image's* where it says *downloads*, or the resume gets built.
  The decision is the phase-9 follow-up's; this is only the note that the specification side of it
  exists.
- [ ] **A budget-stopped offer's `reason` is written and never sent.** The result gate withholds the
  whole body for exactly this verdict, so both the corrected sentence and the `bytes` count go
  nowhere. If meshmaster.dk's job page should say *the next wake starts the file again from zero*,
  either the gate needs an exception for the budget verdict (a result that is not a result, which
  §5 deliberately avoids) or the server needs to say it from the outcome `timeout` and the absent
  result. A decision for both sides.
