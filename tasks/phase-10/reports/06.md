# p10-06 — A trace from the console

The stall that silences this unit is reproducible on the bench in minutes, and the only account of
it is the modem library's own `TX:` and `RX:` lines — which the release build stripped at compile
time. Reading them meant a build of its own, made and flashed by cable, and so they were never
read.

They are in the release build now, silent, and one typed line raises them until the next boot:

```
> trace modem on
trace modem on: every AT command this firmware sends and everything the modem answers goes to this port, until the next boot
  the SIM PIN and the server token are taken out of every line before it is printed; nothing of the trace is kept in 'dump'
  this is for the bench, not for a unit in service: it is slow and loud, and a unit on a mast prints it into nothing ('trace modem off' ends it)
```

**The secret the task names is not the only one.** The request that goes to the modem carries
`Authorization: Bearer <server.token>` in plaintext — TLS is inside the modem, so the UART carries
the HTTP head as it is — and **the SIM's PIN goes out on the same wire**, as `AT+CPIN=<lte.pin>`
from the library's `unlockSIM`, through the `_transmitCmd` macro's `TX:` line. Both are taken out
of every line before it reaches the port.

`tools/verify.ps1` is green on this machine, every step, on the final tree.

## What was read, and what it says

The modem library at **1.5.0**, `managed_components/dptechnics__walter-modem/src/`. Three lines
print what goes over the UART, all under the tag `WalterModem`:

| Line | Where | What it can carry |
|---|---|---|
| `TX: <command>` | `WalterDefines.h`, the `_transmitCmd` macro | every AT command, element by element, **unescaped** — `AT+SQNSRECV=<id>,<n>`, and **`AT+CPIN=<pin>`** |
| `RX: <escaped>` | `WalterModem.cpp:1783`, `_processModemRSP` | every buffer the modem answered: `+SQNSRING`, `+SQNSRECV: <id>,<n>`, `+SQNSH`, `+CME ERROR: 4`, and the bytes of a response |
| `TX: <escaped>` | `WalterModem.cpp:2054`, at the modem's data prompt | the payload of a `socketSend`, which for this firmware is **the HTTP request as it is** — the head with `Authorization: Bearer <token>` and the body |

The second and third are inside `#if CONFIG_LOG_MAXIMUM_LEVEL >= ESP_LOG_DEBUG` (with the
3 080-byte `_logEscapeBuffer` they share), the first is a plain `ESP_LOGD`. The longest line the
library can print is an escaped payload: `WALTER_MODEM_RSP_BUF_SIZE * 2` = 3 080 bytes after
`TX: ` and ESP-IDF's own prefix, which is what `kTraceLineBytes` (4 096) is sized from.

**Nothing of the library was edited** (`managed_components/` is never touched here), and the pin
stays exactly 1.5.0.

## Deviations from the spec or the task

- **The task's deliverable 3 is about the token; the SIM PIN needed the same rail and got it.**
  The task says *the request that goes to the modem carries `Authorization: Bearer <token>` in
  plaintext* and asks for that line. Reading the library for it found the other half: `unlockSIM`
  sends `AT+CPIN=<pin>` and the `_transmitCmd` macro logs its elements, so a `trace modem on`
  followed by `lte up` would have printed the PIN of a locked card on the port and into any paste
  of it. `docs/console.md`'s *Secrets* says both are printed by nothing; a trace line is a printed
  line. So the redactor holds two secrets and has two positional rails, and the bench item asks
  for both to be checked in the paste.
- **`trace` reads as well**, which the task did not ask for. `trace modem on|off` act; `trace`
  alone says whether the trace is on, how many lines it has printed and how many had something
  taken out of them, and the three things a person must know before using it. It is the shape
  `lte` and `trust` already have in this console (a word that reads, and words that act), and the
  count is what lets a bench walk see the redaction rail work rather than trust it.
- **The hook's body is in `core/`, not in `components/modem/`.** The task's deliverable 3 asks for
  *a test [that] sends a request with a known token through the hook*, and a hook that lived
  wholly in the modem component could not be tested at all: nothing of ESP-IDF compiles on the
  host. So `core::trace::formatAndRedact(redactor, buffer, capacity, format, va_list)` is the
  format-and-redact, with a host test over it, and the modem component is the lock, the counters
  and the write. What is **not** tested on the host is the three ESP-IDF calls themselves
  (`esp_log_set_vprintf`, `esp_log_level_set`, `fwrite`) — the bench item is where they are
  walked.

## Decisions taken without asking

1. **The global maximum log level, not the library's files alone.** The task offers either. It had
   to be the global one: the library's two most important lines — the `RX:` of every answer and
   the payload `TX:` — are guarded by `#if CONFIG_LOG_MAXIMUM_LEVEL >= ESP_LOG_DEBUG`, and
   `CONFIG_LOG_MAXIMUM_LEVEL` is a Kconfig macro out of `sdkconfig.h` that no per-component
   `LOG_LOCAL_LEVEL` and no `target_compile_definitions` can raise without redefining it (a
   warning, and an error in our own components). A per-file level would have compiled in the `TX:`
   of a command and left out the `RX:` of every answer — the half the stall is about. The cost is
   measured above and is 12 432 bytes of a 3 MB slot; the output is unchanged, because the default
   level is unchanged.
2. **The exact value is replaced, and the two positions as well.** The task offers *replaced
   exactly before the line is printed (a log hook)* or *the payload lines kept out altogether*,
   and asks which. It is **the hook**: keeping the payload lines out would have meant lowering the
   library's tag around every `socketSend`, which also silences the `AT+SQNSSENDEXT` of the send,
   the data prompt and any URC that arrived inside that window — and a `+SQNSRING` with its length
   is exactly what deliverable 5 asks the trace for. Both the exact value **and** the two
   positions are taken out, because the exact value alone would miss a token typed while the trace
   was on, and the positions alone would miss a value that turned up somewhere this firmware did
   not put it. Neither is a guess at what a secret looks like.
3. **The hook is installed once and never taken off.** `esp_log_set_vprintf` is a function pointer
   ESP-IDF reads and calls; taking it off (or freeing its buffer) while another task was inside it
   is a race whose losing outcome is a line of trace printed around the rail. So the first
   `trace modem on` of a boot allocates the 4 KB line buffer and a mutex and installs the hook,
   and `trace modem off` only puts the library's tag back to the default level. Three consequences,
   all of them wanted: switching off really does stop the lines; every log line of the image is
   redacted for the rest of that boot, whoever wrote it; and a `trace modem off` on a boot where
   nothing was ever switched on costs no allocation at all (it returns at once). The buffer is the
   **one** allocation of the whole feature, and `host_test/core/trace/test_no_allocation.cpp`
   holds that `core/trace/` makes none — it runs inside a log hook, on the library's own task.
4. **The `dump` ring keeps no trace line.** The ring is 4 kB and one stall's trace is longer than
   that: a `+SQNSRECV` line alone can be 3 kB escaped, so two of them would push out the boot
   lines, the supervisor's summary and the command replies that `dump` exists for, and a unit
   found quiet with a laptop would have **less** to say, not more. It also falls out of the
   architecture for free: the ring is filled by `Console::print`, the library's lines go to
   `stdout` through `esp_log`, and the two paths do not meet. Said so in `docs/console.md`, in
   `docs/ARCHITECTURE.md` §9 and in the command's own reply; the capture is the terminal's paste,
   which is why the bench item says *keep the whole paste; it is the only copy*.
5. **A held value shorter than four characters is not searched for** (`kLeastSecret`). The
   settings table allows a `server.token` of one character, and asterisking every occurrence of
   one character would leave a trace nobody could read — a silent failure of the feature. Four is
   the SIM PIN's own minimum and far below any token. Nothing is lost: the two positional rails
   are the exact ones, and the token and the PIN each have exactly one place this firmware writes
   them into.
6. **A dropped line rather than an unredacted one.** A line that cannot take the buffer's mutex
   inside a second is dropped and the hook answers 0. A second is far more than a `vsnprintf` and
   an `fwrite` need, so it should never happen; if it does, a lost line of a bench trace is the
   cheaper half.
7. **`trace modem on|off`, with `modem` as a word of its own.** The task says *or whatever name
   fits the console's grammar*. The second word is there because the lines are the modem's, and a
   later task that wanted a trace of something else should not have to change the grammar. The
   command sits in `help`'s *the uplink* group, beside `lte` and `http get`.
8. **Both secrets are read from the settings at the moment the trace is switched on**, not held by
   the hook from boot. The console is the only thing that has the store and is the only thing that
   can switch the trace on, so that is where they are read; an unset key is `""` and holds nothing,
   and a build with no settings store (a missing `nvs` partition) hands over two empty strings and
   leans on the positional rails, which is what they are for.

## Not verified here (and why)

No session opened the unit's ports: the first unit is on Thomas's bench (this pile's README), and
nothing of this task can be proved without the modem answering. The three ESP-IDF calls behind the
seam (`esp_log_set_vprintf`, `esp_log_level_set`, the `fwrite`) are the part no host test reaches.

Two items in `docs/bench.md`, in the order the rig is brought up:

1. **§13, ★ *The trace, from the console*** — the one that replaces *The trace build, if it stalls
   again*. `trace modem on`, `lte up`, `agent obs` (the backlog is what makes it stall),
   `agent wake`, `trace modem off`; **keep the whole paste**. Then the five things to read it for:
   the last `TX:` before the 30 s gap (the reading from the code is `AT+SQNSRECV=<id>,<n>`),
   whether an `RX:` came at all in those 30 s and what it was, whether a `+SQNSRECV` before the
   gap declared more bytes than followed it, the `+SQNSH:` lines against our own `AT+SQNSH`, and —
   the pattern of 8 November — **the `+SQNSRING`/`+SQNSRECV` lengths of an answer that arrived
   (876 bytes at the server) against one that was lost (877 or 878)**, side by side. And this
   task's own two rails, which only silicon can show: **no secret in the paste** (`AT+CPIN=********`
   and `Authorization: ****…` with `lte.pin` and `server.token` both set, and `trace`'s *M with a
   secret taken out* greater than zero after a wake that posted anything), and **the end at the
   next boot** (`trace modem on`, `reboot`, then `trace` saying *are off* and `status` with no
   `trace:` line).
2. **§18, ★ *The stall, with the trace on*** — the same walk run where the adverts are, because a
   wake with nothing to post does not stall. It is the item this whole pile exists for, and it
   comes back as a paste rather than a tick.

One thing to watch while the trace is on, which no item can assert: a wake prints a few hundred
lines of it, and the library's command task is what writes them, from inside its own processing of
the modem's answers (the port itself is the chip's USB, not a UART at a baud rate, so it is the
writing and not the wire that could cost time). If a wake with the trace on behaves differently from one without it — a timing that
moves, a command that times out only when the trace is on — that is worth writing down, because
then the trace is changing what it is meant to show.

## For `FOLLOWUPS.md` (the reviewer's to place)

- [ ] **The library's escape buffer is 3 080 bytes of `.bss` in every build now.** It is a static
  inside `WalterModem.cpp`, guarded by `CONFIG_LOG_MAXIMUM_LEVEL >= ESP_LOG_DEBUG`, so compiling
  the trace in brings it whether anybody switches the trace on or not. 37 037 bytes of DIRAM are
  free, so it costs nothing today; it is worth remembering on the day something else wants DRAM
  (`tasks/phase-4/FOLLOWUPS.md` has the agent's runner on the heap for the same reason).
- [ ] **Once the trace has been switched on, every log line of that boot goes through the hook.**
  A `vsnprintf` into a 4 KB buffer, a search for two secrets and an `fwrite`, under a mutex, for
  every `ESP_LOGx` of the image until the next reset — by design (*Decisions* 3). ESP-IDF's own
  lines are few and the console does not use `esp_log` at all, so the cost should be nothing; if a
  bench walk ever finds a wake slower **after** `trace modem off` than before `trace modem on`,
  this is the place to look.
- [ ] **A `+SQNSRECV` payload longer than 4 096 bytes would be cut in the trace.** The library
  cannot print one — it escapes into 3 080 bytes — but if the modem library is ever pinned higher
  and `WALTER_MODEM_RSP_BUF_SIZE` grows, `kTraceLineBytes` has to grow with it. The cut is safe
  (the positional rails end a value at the end of the buffer), and a test holds that; it would be
  a trace with lines missing their ends, which is worse than it looks when the thing being read is
  a declared length.
