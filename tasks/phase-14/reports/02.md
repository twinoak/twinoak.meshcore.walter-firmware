# p14-02 — the three counts

The heartbeat carries `flood` now: the scope this unit's floods go out in, whether the second
flood of a transaction drops it, and the three counts of a flooded transaction — as **totals kept
across a sleep, a restart and a power cut**, because the agent library's own are since boot and
this board boots at every wake. `agent state` prints the same three in one line, and the report's
`agent` section with it. A radio of link 1.2 says nothing about scope, so there is no object at
all and the heartbeat is byte for byte what it was.

**Where the addition is made, and why a wake loses at most its own counts.**
`AgentBackend::takeFloodCounts()`, called at the end of every wake where the loop's own state is
saved (`run()`, and both of `beat()`'s save points). `FloodCounters::take()` adds the
**difference** against what it has already taken in this boot, so a wake adds its counts **once**
however often it is called, and `save()` writes the value only when a total moved. The store is
the only thing that crosses a boot: a wake that dies between a transaction and the save leaves it
holding the totals as they were before that wake — its own counts are lost, which is at most one
wake's — and the next boot starts with the library's counter at 0 and with nothing taken, so no
transaction is ever counted twice.

## Deviations from the spec or the task

- **None of the specification.** `spec/LINK-PROTOCOL.md` §6.5 is task 01's and is untouched here;
  the contract this task writes against is meshmaster.dk's `AgentFlood`, read-only, and the bytes
  are the library's own serializer's.
- **One line of `agent state` the task did not ask for**, and the deliverable it serves. The
  task's own follow-up says the library files a transaction under the mode its rule *asked* for, so
  a flood that went out in another scope may be counted under the wrong of the three, and that
  `LinkMeshCounters::scope_surprises` is how often the three could be wrong. Nothing printed that
  counter anywhere, so the bench line *and the counts can be trusted* had nothing to read. It is
  now a **second** flood line of `agent state`, printed **only when it is not 0** — so a healthy
  unit's output is unchanged — and a test drives a real one (a `region default` cleared under the
  unit's feet between the `HELLO` and the job).

## Decisions taken without asking

- **A key of its own, `agent_flood`, and not a wider `agent_wakes`.** The deliverable says *kept
  where `httpFailures` is kept*, and `httpFailures` is inside the library's `mm::WakeState` under
  `agent_state` — which this task may not change (`components/agent-core` is a hash-checked copy)
  and which is already 152 of the 160 characters a value may be. The established pattern beside it
  is task p13-02's `agent_wakes`: a version byte and the totals as hex, in one value, written only
  when one moved. A fourth key of the same shape costs 27 characters of NVS and makes the sixth
  deliverable true by construction — **nothing of what v0.1.6 wrote changes shape**, so every
  counter an older release saved is read exactly as it was and the three totals simply start at 0.
  Widening `agent_wakes` to version 2 would have had to decide what to do with a version-1 blob,
  and the only right answer is *keep the four and start the three at 0*, which is what two keys do
  without a line of code.
- **The delta, rather than a reset of the library's counter.** `mm::FloodPolicy` cannot be seeded
  or cleared and is part of the copy, so `take()` keeps what it has already taken in this boot and
  adds only the growth. That is also what makes the end of a wake a safe place to call it from:
  this board runs more than one wake in a boot (a console `agent wake`, a trial's own heartbeats),
  and the second wake of a boot must add its own floods and not the first's again.
- **The heartbeat reads the totals as they stand when it is built**, which is before this wake's
  jobs have flooded. So a wake's own floods are reported by the **next** heartbeat — exactly as a
  companion exit node reports the counts it had when it built the body — and the handover is a
  pointer (`ModemUplink::countFloodsFrom`), not a copy.
- **One function builds the object, two callers use it.** `fillFlood(out, scope, unscoped_retry,
  totals)` in `identity.cpp`, beside `addRadioIdentityLost` and `addWakeCounters` and for the same
  reason: `ModemUplink::postHeartbeat` swaps the totals into **the object the library built**,
  leaving the member, its place, its order and the other two fields as the library wrote them, and
  the console's `agent heartbeat` builds the same object from the same two readers. The printed
  body and the posted one cannot disagree.
- **`agent heartbeat` now reads the flood scope as it reads the identity.** `IdentityProbe::
  heartbeat()` already refreshed the identity so that a body printed before any `agent id` would
  not be a body with no key in it; the same argument applies to the scope, because the object is
  written when the mesh has one to report. One `FLOOD_SCOPE` once a session, and not a frame
  against a radio of 1.2.
- **`agent state`'s line says *in all* where the library's says *since boot*.** Three words a
  person reads rather than a second figure to explain, and the test holds that the printed line
  does **not** carry *since boot*: 56 unanswered transactions cannot have happened in one wake.
- **The rule clause is read back out of the library's own line.** `describeFlood` is the one place
  the four readings of the rule are written and this task may not change it, so the clause after
  the **last** `; ` of its line is taken as the rule — no rule of the four carries a semicolon, and
  all four are held to it by test. A library whose line changed shape would put its whole line
  where the rule goes: nothing invented, nothing lost, and those tests would say so first.
- **The totals saturate rather than wrap.** A counter that wrapped would read on the exit node's
  page as a unit whose unscoped try had suddenly stopped earning its airtime.

## Not verified here (and why)

No session opens a port, so nothing below has been on a board. The lines are in `docs/bench.md`
beside task p14-01's four, in the order the rig is brought up; the first and the third need the
radio's own link 1.3 (the repeater firmware's pile 3.13) and read as the 1.2 line until it is
there.

1. **The three counts move, and by one.** Before p14-01's flooded login, `agent state`'s flood
   line; after it, the same line with **exactly one** of the three up by one — and the job's own
   line says which it should be: a reply to the first try (*flood in the radio's default scope*) is
   `scoped`, a reply only to the second (*flood with no transport code*) is `unscoped`, neither is
   `none`. A job whose sends went **direct** must move none of them.
2. **They outlive a sleep and a power cut.** Note the three, let the unit sleep and wake, read them
   again; then pull the power for ten seconds and read them once more. Still there. That is the
   whole reason they are in the settings store and not in RTC memory, and it is the one thing a
   host test cannot show on this board.
3. **The line on meshmaster.dk.** After the next check-in, the unit's exit node page must carry the
   companion's own sentence — *Floods scoped dk; one unscoped retry; answered N scoped, M unscoped,
   K not at all* — with the same three numbers `agent state` printed, and `agent heartbeat` must
   show the `flood` object they came out of. No flood line at all means the radio is still at 1.2,
   which is correct.
4. **And the counts can be trusted.** `agent state` after a day of flooded jobs must carry **no
   second flood line**. The one that would appear names the floods that went out in a scope this
   end had not asked for, and each of those is a count the library may have filed under the wrong
   one of the three.
5. **The heap on the board.** `heap` at the console on the first boot of this release, against
   `tools/heap_at_start.py`'s model: the main task is created with 12 376 bytes to spare and the
   tightest big allocation has 988. The model has been right to the byte for v0.1.2 and v0.1.3 in
   QEMU, and the board is the last word.
