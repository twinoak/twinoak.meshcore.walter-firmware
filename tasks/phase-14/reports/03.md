# p14-03 — the notes say what is true

Three places said that no check runs on the pull request a release leaves behind. One does.
GitHub starts a `ci` run for it and **holds it for a maintainer's approval**; the three sentences
now say that, and both ways out of it. Nothing the publish job *does* changed: outside its
comments and the pull request's body, `release.yml` is byte for byte what it was.

## What #60, #63 and the repeater's #50 actually did

Read from GitHub, not from the task file:

| | |
|---|---|
| the held run | `ci`, event `pull_request`, actor `github-actions[bot]`, **status `completed`, conclusion `action_required`**, and **zero check runs** on the head commit. So nothing reports `main`'s required `verify`, and the job's own `gh pr merge` is refused — which is what the job already expects |
| #60 (v0.1.5) | held at 18:13:47 on 13 November as run 43480569598; Thomas approved it (`triggering_actor` ThomasEg, `run_attempt` 2), it started 18:33:52 and was **green at 19:04:57**; merged |
| #63 (v0.1.6) | opened 08:23:50 on 15 November, run 43694305570 still `action_required` **more than six hours later** with the release long since out. A held run does **not** expire into red by itself inside the day |
| the repeater's #50 | merged at 18:00:57 on 13 November without the run being approved; its run 43467131534 went to **`failure` at 18:00:58** — one second later. The red run Thomas found an hour after a good release was *the merge concluding the held run*, not an expiry |
| `main`'s protection | `required_status_checks.contexts: ["verify"]`, `enforce_admins: false` — so *Merge without waiting for requirements to be met* is offered to an administrator, and both ways out are real here |

The repository already knew this elsewhere: `docs/upstream.md` (*One click before CI runs*) and
`.github/workflows/upstream.yml` describe the same hold, with **Approve and run** and the
`gh api .../actions/runs/<id>/approve` route. The release's prose had simply never been brought
to it. The new text in `docs/release.md` points at it by name.

## What the release gate does with a held or an expired run on that commit (deliverable 2)

**Nothing — it never asks about it**, twice over:

1. `tools/release/release_notes.py`'s `ci_commit` walks back along the **first parents** while a
   commit changes nothing but `VERSION` and `release-notes/`, and returns the first commit that
   changed anything else. The notes commit is walked *past*, so whatever state its own run is in
   — held, red, cancelled or absent — is never read.
2. The step that then waits asks for `gh run list --workflow ci.yml --commit "$ci_sha" --event
   push`. The held run is a **`pull_request`** run on the branch head, so it would not be a
   candidate even without the walk.

A correction the walk makes sound rather than necessary: the notes commit **can** have a run of
its own. A person merges that pull request, so the push to `main` is a person's event and `ci`
does start — v0.1.5's merge commit `70732c0` got run 43484073183, which the next push to `main`
cancelled 19 minutes later under `ci.yml`'s `concurrency`/`cancel-in-progress`. A gate that
waited for it would have waited 80 minutes for a cancelled run. The walk is why it does not.

## Deviations from the spec or the task

- **The task's third sentence is not what happened.** Deliverable 1 asks the body to say that *a
  run nobody approved is listed as failed after about an hour*. It is not. #63's has been
  `action_required` for more than six hours with nobody waiting on it. What turned the repeater's red was
  **the merge**: run 43467131534 concluded `failure` at 18:00:58, one second after pull request
  #50 merged at 18:00:57. So the body and the document attach the red run to *merge without
  waiting*, which is the choice that causes it and the only one a person can do anything about,
  and say instead that a held run left alone does not go red by itself. The task's *and that
  failure is about nothing* is kept word for word, because it is true.
- **One sentence of `release.yml` was left standing although it says the old thing** — the gate
  step's `echo "$SHA changes only VERSION and release-notes/ above $ci_sha, and has no ci run of
  its own"` (~L160). It is neither a comment nor the body, and deliverable 4 and the third
  acceptance criterion hold the rest of that file byte for byte, so it was not touched. Filed in
  `tasks/phase-14/FOLLOWUPS.md` as `[later]`, with the note that the branch barely runs: a
  release is refused with no waiting line, so `main`'s head is never a release-notes-only commit
  when one starts. The matching sentence in `tools/release/release_notes.py` — which deliverable
  4 does not cover — *was* corrected.
- **A line in `release-notes/unreleased/` was written although the standing rule says not to.**
  `release-notes/README.md` and `tasks/RUNBOOK.md` §2 both say a document, a test or a rail
  writes no file, and this task is exactly those three. Deliverable 5 asks for one anyway, so one
  is there, and it earns its place under the README's fourth heading — *anything a person must do
  by hand* — because after a release a person must now approve a held check or merge past it, and
  until today nothing told them. The line says plainly that nothing on a unit changes. Delete it
  if the release body is the wrong place for it; nothing else depends on it.

## Decisions taken without asking

- **`ci_commit`'s docstring and the `ci-commit` command's stderr line were corrected too**, though
  the task only asked me to read them. They are the authority `docs/release.md` points at for why
  the walk is sound, and leaving *that commit has no ci run of its own and never will* beside a
  corrected document would have put the retired belief back the first time somebody read the code
  instead of the prose. No behaviour changed: a docstring and one `sys.stderr.write` string. The
  test class `TheCiRun`'s docstring went with them.
- **The new tests live in `tools/release/test_release_notes.py`, not in `tools/check_rails.py`.**
  A rail is for something a person could break and nobody would notice on the board; this is
  prose about the release process, and it belongs with the release tooling's own tests, which the
  `release-tests` step already runs.
- **The body gained a two-item list.** It was a paragraph; the two ways out read better as two
  bullets, and `gh pr create --body-file` takes markdown. The heredoc was run through bash to
  check that nothing in it needed escaping that was not already escaped.
- **The document keeps the run identifiers and the clock times** (43480569598, 43467131534,
  43484073183, and the minutes). The whole trouble here was a sentence nobody could check against
  anything; the next person to doubt these can open them.
