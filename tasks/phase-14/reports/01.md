# p14-01 — the scope on the link

The box link speaks **1.3** from this end. `FLOOD_SCOPE` (`spec/LINK-PROTOCOL.md` §6.5), its
capability bit `0x100`, and the byte at the end of a send's answer; `LinkMesh` tells the agent
library the radio's default flood scope and sends the one flood without it; `rak scope` reads it at
the console. A radio of 1.2 is untouched — this end says nothing about scope and its frames are
byte for byte today's but for `HELLO`'s minor — and so is a radio of 1.3 whose Walter is older.

**Room was made first**, as phase 13's follow-up asks: `agent::kKeptScratchBytes` is 19 456 and not
20 480, and it costs nothing (below).

## Deviations from the spec or the task

- **Where the one flood without the scope is decided, for a discovery.** The task says *not when the
  job holds a path: the send goes direct, and a path has no scope*. That is right for `SEND_LOGIN`,
  `SEND_REQUEST` and `SEND_CLI`, which §6.2 sends direct when the job holds a path — but
  `SEND_DISCOVERY` is **always flooded**, path or no path, and §6.5 scopes "every
  `SEND_DISCOVERY`". The specification wins (`tasks/README.md`): the three ask *does this job hold
  a path*, and a discovery does not ask. In practice the library only sends a discovery when it
  holds no path, so the two readings differ nowhere a job reaches today.
- **Nothing else.** `spec/LINK-PROTOCOL.md` §6.5, §6.2 and §5.1 and the task's summary table agree
  on everything else: the type, the bit, the three modes, the answer's shape, the 30-byte name,
  `mode` 2 being for one send and being cleared by `JOB_BEGIN` and `JOB_END`, and `ERR_STATE` below
  1.3.

## Decisions taken without asking

- **The scratch, and what gave the room up: nothing.** The place phase 13's follow-up names is
  `agent::kKeptScratchBytes`, and 20 480 was a round figure rather than a bound. The largest image
  `agent/KeptImage.h` can write is the library's own arithmetic — the 32-byte header, eight result
  headers of 12 over 12 288 bytes of bodies, and 64 adverts of 108 — which is **19 328 bytes**, so
  **19 456** holds everything the loop may keep with 128 bytes over and drops nothing that was not
  dropped before. 19 456 and not 19 328 because the allocator rounds a block of this size up to a
  multiple of 1 024 (TLSF's `mapping_search`, 16 subdivisions of a power of two): anything from
  18 433 to 19 456 takes the same 19 456-byte block, so the largest of them is the one to ask for.
  Two `static_assert`s in `agent_backend.h` hold the figure to the library's numbers, so a copy of
  `agent-core` that grew the result buffer or the ring fails the build instead of quietly dropping
  the tail of what a sleep keeps.
- **`scoped` *absent* is a `bool` beside the byte, and not a third value.** `SendResponse` gains
  `has_scoped` and `scoped`. Nothing in that payload says which a session is (§5.1 does), so the
  decoder reports whether the byte was there and the reader decides what that means — and the one
  shape whose tail is a field this codec knows needed two of the fixture sweeps told about it (the
  truncation sweep allows a payload one byte short; the trailing-byte sweep holds a 1.2 send answer
  to *it still decodes* rather than to its fields, because the first byte appended to one **is** a
  legal `scoped`).
- **A `FLOOD_SCOPE` 2 answered `OK` with `mode` 1 is not a refusal.** §6.5 says asking 2 sets 2 and
  that the answer says what the next send will be; a radio that answered 1 to a 2 is outside the
  specification. Rather than invent a refusal, this end believes the answer: `expect_scoped_`
  follows the `mode` that came back, so the flood that follows is held against it and a surprise is
  counted and the name read again — the machinery deliverable 6 already asks for. The send is
  failed only when the request was **refused or unanswered**, which is what the task says.
- **A scope name over 30 bytes is kept truncated, not refused.** §6.5 says 1 to 30; the name is
  reported and never computed with (the radio puts the transport code on the packet), so a name
  this end cannot hold whole is still worth more to a person on meshmaster.dk than nothing.
- **The ask goes where the key goes.** `AgentBackend::handOverIdentity()` and the console's
  `IdentityProbe::identity()` — the two places `LinkMesh::setOwnKey` is called — now also call
  `askFloodScope()`. That is "once a session, where the unit's own key is asked, before the
  heartbeat is built" with no new seam and no new call site to keep in step.
- **The shim forwards `floodScope()`/`setFloodMode()` to `LinkMesh`.**
  `host_test/agent-link/shim/support/FakeMesh.h` overrode every other `IMesh` call and not these
  two, so the library's 46 runner scenarios would have run the repeater fake's idea of a scope
  instead of the road. They are forwarded now. Nothing in either copied suite calls
  `FakeMesh::setFloodScope`, and against the radio of 1.2 those scenarios use both answers are
  `nullptr`, so all 70 of them are unchanged.
- **The console's `rak scope` prints sentences and not status codes**, in two lines where one would
  pass the console's 200-byte line (`Console::printf`). The `ERR_STATE` branch says *the radio
  answers that nothing is scoped in this session … its own session is older than 1.3 until the next
  'rak hello'*, because that is the case a person will actually meet — a radio that restarted —
  rather than "a session that settled low", which the Walter's own stale session number would
  contradict.
- **The scripted radio's switch is `speakLink13(scope)` / `speakLink12()`**, and it moves three
  things together because §5.1 ties them: the bit in `caps`, the minor the body says, and a `band`
  (a body of minor 1 or more ends with one, so a 1.3 body without one would not decode). The radio
  now also answers `HELLO` with **the highest minor both ends know** rather than its own, and keeps
  the session's version per boot — which is what makes the restart case and the *a 1.3 radio for a
  1.2 Walter* case real rather than asserted.

## Not verified here (and why)

No session opens a port, so nothing below has been on a board. The lines are in `docs/bench.md`
beside task p9-06's, in the order the rig is brought up, and each is starred where it needs the
radio's own 1.3 (the repeater firmware's pile 3.13).

1. **`rak hello` and `rak scope` on a radio of 1.3.** `capabilities` carries `flood-scope` (bit
   `0x100`) and `protocol` says 1.3; `rak scope` prints the region the radio floods in — `dk` on a
   unit that follows the Danish standard, the same word `rak cli region default` answers — and *the
   next send takes the default scope (mode 1)*. `rak status` right after must show `client_tx`
   unmoved: §6.5 puts nothing on the air.
2. **And a radio of 1.2 says so, in words.** Worth doing **before** the radio is updated, which is
   the state the unit is in the moment this release lands: `rak scope` says *this radio speaks 1.2*,
   and the unit's exit node on meshmaster.dk carries **no flood line at all**.
3. **A scoped login on the air.** With both 1.3s on the unit: a job for a repeater the server knows
   no path to, or `rak mesh status <key>` of a neighbour the unit holds no path for. The line must
   say *flood in the radio's default scope*, and a second try of the same transaction *flood with no
   transport code*.
4. **A restarted radio says nothing about scope.** `rak reset`, then `rak scope` **without** a
   `rak hello` first: nothing is scoped in that session. One `rak hello` and it is `dk` again. This
   is the window in which this unit must tell the server nothing rather than a scope the radio is
   not using.
5. **The heap on the board.** `heap` at the console on the first boot of this release, against
   `tools/heap_at_start.py`'s model: the main task is created with 12 488 bytes to spare and the
   tightest big allocation has 1 084. The model has been right to the byte for v0.1.2 and v0.1.3 in
   QEMU, and the board is the last word.

## Follow-ups left

One new item in [`FOLLOWUPS.md`](../FOLLOWUPS.md), which deliverable 6 asks for: **the library
counts a flood under the scope it asked for, not the one it got.** `FloodPolicy::sent(flooded,
mode)` files the transaction under the mode the rule chose, so a flood asked `Scoped` that §6.2's
`scoped` says went out unscoped is counted as `answeredScoped`. This end notices — the name is read
again and `LinkMeshCounters::scope_surprises` counts it — and cannot correct the figure:
`components/agent-core` is a hash-checked copy of upstream and is not changed here. The cure is in
the exit-node firmware, where `sent()` would take what the mesh says the send came to. On a healthy
unit `scope_surprises` is 0, which is how a person tells whether task 02's three counts can be
trusted.
