# p11-01 — Room for the main task

v0.1.3 could not create its main task. This task measured both releases, built a model that
explains both from the builds alone, put the room back, and said what the figure to watch really
is. The short version:

| | v0.1.2 | v0.1.3 | **0.1.4 (this build)** |
|---|---|---|---|
| the DIRAM free block when the 20 480-byte scratch asks for it | 21 884 | **20 068** | 20 836 |
| so the scratch lands in | the DIRAM heap, 1 404 to spare | **the 32 kB DRAM heap, 412 short of DIRAM** | the DIRAM heap, **356** to spare |
| the largest block the main task's 16 384-byte stack can have | 29 540 | **16 220** | 28 532 |
| the boot | runs, 12 796 left over | **`assert failed: esp_startup_start_app app_startup.c:86`** | runs, 11 788 left over |

One image booted with 12 kB to spare and the next could not start, and the difference between them
was **1 728 bytes of static data**. Not because 1 728 bytes were missing — because they moved a
20 480-byte allocation out of one heap and into the heap the main task's stack was going to use.

## Both releases measured

Built at their tags in `espressif/idf:v5.5.5@sha256:a9231d06…`, the same mounts and cache
`tools/verify.sh` uses. Static memory, from the maps:

| | v0.1.2 (5aa5542) | v0.1.3 (766e061) | 0.1.4 (this build) |
|---|---|---|---|
| `_iram_end` | 0x40382B00 | 0x40382C00 | 0x40382B00 |
| `_data_start` | 0x3FC92B00 | 0x3FC92C00 | 0x3FC92B00 |
| `.dram0.data` | 44 132 | 44 220 | 44 132 |
| `.dram0.bss` | 215 368 | 216 752 | 216 416 |
| **`_heap_start`** | **0x3FCD20B0** | **0x3FCD2770** | **0x3FCD24C8** |
| DIRAM, as the linker counts it | 303 139 used, 38 621 remain | 304 747 used, **37 013** remain | 304 187 used, 37 573 remain |
| `twinoak-walter.bin` | 763 616 | 784 560 | 771 328 |

The 1 728 bytes between v0.1.2 and v0.1.3 are **256 bytes of IRAM `.text`, 88 of `.data` and
1 384 of `.bss`** — and on the ESP32-S3 the IRAM 256 count too: `.dram0.data` starts at
`ORIGIN(dram0_0_seg) + (_iram_end - _diram_i_start)`, so a byte of IRAM-resident code displaces a
byte of DRAM one for one (`esp_system/ld/esp32s3/sections.ld.in`, `.dram0.dummy`).

**The regions ESP-IDF actually registers as heaps** (identical in all three builds but for the
first one's start, which is `_heap_start`), with what they hold when `heap_caps_init` has run:

| heap | bytes | what it is |
|---|---|---|
| `_heap_start`..0x3FCE9710 | 95 840 / 94 112 / 94 792 | the DIRAM left over. The only one that can hold a 20 kB or 64 kB block |
| 0x3FCE9710..0x3FCEEE34 | 22 308 | the ROM's own stack area. **`startup_stack`: registered in `main_task`, after the main task is created** — it can never serve the main task's stack |
| 0x3FCF0000..0x3FCF8000 | 32 768 | the half of the top 64 kB the 32 kB data cache leaves |
| 0x600FE060..0x600FFFE8 | 8 072 | RTC fast memory, priority 2 only |

Where they come from: `heap/port/esp32s3/memory_layout.c` conditioned on this build's `sdkconfig`
(`DATA_CACHE_32KB`, `MEMPROT_FEATURE`, `ALLOW_RTC_FAST_MEM_AS_HEAP`, no PSRAM, no trace memory),
trimmed by the reserved ranges of `memory_layout_utils.c` — `iram_code`, `dram_data`,
`iram_code_2`, `rtcram_data`, `rtc_reserved_data` and the ROM's own, which is **not in any header**:
`ets_rom_layout` at 0x3FF1AE90 of `esp32s3_rev0_rom.elf` (the image's `esp-rom-elfs`), whose
`dram0_rtos_reserved_start` reads **0x3FCEEE34**, so 0x3FCEEE34..0x3FCF0000 is the ROM's and the
`startup_stack` region is 22 308 bytes and not 0x68F0. The capabilities and the order they are
tried in are `memory_layout.c`'s type table with the MEMPROT branch (no `MALLOC_CAP_EXEC`),
`heap_caps_init.c`'s sort by **increasing size**, and `heap_caps_base.c`'s three priority passes.
All four heaps and all their capability words match what the running image reports, read out under
gdb (below).

**The sizes that come from the build**, from the DWARF of each ELF (`DW_AT_byte_size` /
`DW_AT_const_value`, read with pyelftools; `readelf --debug-dump=info` shows the same):
`sizeof(mm::JobRunner)` = **66 000** (0x101D0), `agent::kKeptScratchBytes` = **20 480**,
`sizeof(TCB_t)` = **340**, in all three builds.

**Every allocation before the main task, in order.** There are 72 of them in 0.1.4 and 73 in
v0.1.3, and `tools/heap_at_start.programme` is the whole list; the ones that matter:

| | asks for | its block | out of a free block of | in which heap |
|---|---|---|---|---|
| `heap_caps_init`'s array of 4 heap descriptors | 144 | 144 | the whole pool | DIRAM |
| ~50 allocations of ESP-IDF's CORE stage and the constructors before `main.cpp`'s: newlib locks and `FILE`s, the VFS entries, the console's port | 3 292 all told (3 440 with the array; 3 528 in v0.1.3) | | | DIRAM |
| **`new mm::JobRunner`** | 66 000 | **69 632** | 90 472 | DIRAM |
| **`new std::uint8_t[kKeptScratchBytes]`** | 20 480 | 20 480 | **20 836** | DIRAM (v0.1.3: the 32 kB DRAM heap) |
| `ipc0`/`ipc1`: a stack and a TCB each | 1 280, 340 ×2 | 1 280, 352 | | whichever still has room |
| the SECONDARY stage: 3×44, 7×52, two 20s and five frees | | | | |
| **the main task's stack, then its TCB** | 16 384, 340 | 16 384, 352 | **28 532** | the 32 kB DRAM heap |

The runner's 69 632-byte block for a 66 000-byte object is not waste in our code: TLSF's
`mapping_search` rounds a request up to the next second-level size class before it looks for a
block (`heap/tlsf/tlsf_control_functions.h`), and 66 000 is 464 bytes past 64 kB, so it rounds to
17×4 096. **3 632 bytes of the DIRAM heap go to that rounding.**

### The model: `tools/heap_at_start.py`

`python tools/heap_at_start.py --build-dir <dir>` prints the regions, the operations in order with
where each landed, the heap block by block when the main task is created, and the verdict; exit 0
if the stack fits with `--min-spare` (8 192) to spare, 1 otherwise. There is no fudge factor in it:
the region table, the capability table, the registration order, the priority passes and the
allocator are ported from ESP-IDF v5.5.5's own sources with the file named beside each; the build
supplies `_heap_start` and the other bounds from its map, the three sizes from its DWARF and the
options from its `sdkconfig`; and the start-up's own allocations are **recorded from this firmware
running**, not guessed — `tools/heap_programme.gdb` drives the QEMU that the pinned image ships
(`/opt/esp/tools/qemu-xtensa/esp_develop_9.2.2_20260417`) with a breakpoint on
`heap_caps_aligned_alloc_base` and one on `heap_caps_free`, and
`heap_at_start.py --from-record` replays that recording over the same build to turn it into
`tools/heap_at_start.programme`. That replay is itself the check: a recorded `free` names an
address, and the conversion fails unless the model allocated that very address.

**It was checked against the running image, which is the part that makes it worth having.** The
same gdb reads the registered heaps, the two pointers of `main.cpp` and the whole TLSF block list
out of each build at `esp_startup_start_app`, and asks the real allocator for the stack:

| read in QEMU at the moment the main task is created | v0.1.2 | v0.1.3 | 0.1.4 |
|---|---|---|---|
| `g_agent_jobs` | 0x3fcd318c | 0x3fcd38a4 | 0x3fcd35a4 |
| `g_kept_scratch` | 0x3fce4190 | **0x3fcf02e4** (the DRAM heap) | 0x3fce45a8 |
| DIRAM heap free | 76 | 16 308 | 4 |
| DRAM heap free | 29 596 | 11 548 | 28 620 |
| `heap_caps_malloc(16384, 8BIT\|INTERNAL)` | 0x3fcf0c98 | **0x00000000** | 0x3fcf1088 |
| `heap_caps_malloc(sizeof(TCB_t), …)` | 0x3fcf4c9c | 0x3fce57b0 | 0x3fcf508c |
| the model's answer for all six | identical | identical | identical |

For v0.1.3 the model's block list is the chip's byte for byte — three free blocks, 28 at
0x3fce5578, 44 at 0x3fce55f8 and 16 220 at 0x3fce57b0 — and `heap_caps_malloc` returning NULL at
exactly `assert failed: esp_startup_start_app app_startup.c:86` is the panic the core dump
recorded on the mast, reproduced in a container. The same for 0.1.4: 28 at 0x3fcf0e50, 44 at
0x3fcf0ed0, 28 532 at 0x3fcf1088, and the stack at 0x3fcf1088.

(One caveat, stated because it is the only place the model is not exact: the shipped programme is
0.1.4's recording, and v0.1.3 makes **one** allocation more — an 84-byte FreeRTOS mutex, early,
which the whole-image debug level brings. Replayed over v0.1.3 the shipped programme is therefore
88 bytes optimistic: it says the largest free block is 16 308 where the chip has 16 220. Both are
below 16 384 and the verdict is the same, and with v0.1.3's own recording
(`out/work/p11-01/programme-v0.1.3.txt`, written by `--from-record`) the model is exact. The
tool's docstring and the programme file both say to re-record when the configuration changes.)

### Why v0.1.2 started and v0.1.3 did not

In both builds the runner takes 69 636 bytes of the DIRAM heap and nothing else can hold it. What
is left over then decides everything:

* **v0.1.2**: 21 884 free, the scratch wants 20 480 → it stays in DIRAM. The 32 kB DRAM heap is
  untouched, so the main task's stack has a 29 540-byte block and takes it, 12 796 left.
* **v0.1.3**: 20 068 free — **412 short**. The scratch is not refused; `heap_caps_malloc` simply
  moves down a priority and takes 20 484 of the DRAM heap's 32 032. Now DIRAM has 16 220 and DRAM
  has 11 540, the stack wants 16 384, and there is no block for it anywhere: 22 308 bytes sit in
  the `startup_stack` heap that `main_task` has not registered yet, and RTC RAM is 8 072 and
  priority 2. `xTaskCreatePinnedToCore` returns `errCOULD_NOT_ALLOCATE_REQUIRED_MEMORY` and the
  assert fires before a line of this firmware runs.

That is also why the core dump held only `ipc0` and `ipc1`, and why it is not an update's fault:
the heap at start is the same at every boot, so v0.1.3 by cable panics every boot too.

## The room back

**`CONFIG_LOG_MAXIMUM_LEVEL_DEBUG` is out of `sdkconfig.defaults`** (the paragraph there now says
why, and what a byte of `.bss` costs). Measured in this tree, that one option is worth **680 bytes**
of static DRAM — 256 of IRAM `.text`, 88 of `.data`, 336 of `.bss` — and 88 bytes more of heap,
because it also brings one 84-byte FreeRTOS mutex into the start-up. 768 bytes all told, which took
the scratch's margin from **−412** to **+356**. The image is 771 328 bytes, 13 232 fewer than v0.1.3's
784 560.

The modem trace is a build of its own again: `sdkconfig.trace` (new) is the overlay,
`docs/bench.md` §13 says how to make one and `docs/console.md` says what the release build answers
instead. The host tests of task p10-06 all stay; the two new ones are listed above.

**What a trace build costs, since §13 now has to say it.** The debug level alone is v0.1.3's
arrangement to the byte — the same `_heap_start`, and the model says *does not fit*: short by 164
bytes on v0.1.3's own recording, 76 on the shipped one — so `sdkconfig.trace` also
turns the core dump off: 2 288 bytes of `.bss`, and a board on a cable prints its panic on the
cable. With both options the model says `FITS, with 13360 bytes to spare`, the main task's stack
stays at 16 KB, and QEMU agrees (`heap_caps_malloc(16384) -> 0x3fcf094c`). bench.md tells the
walker to run the model before flashing a trace build, and to put a release image back afterwards.

**The 16 KB main stack was not touched**, and the one build where lowering it would have been the
easy answer (the trace build, 12 288 would have fitted with 3 660 to spare) is exactly the build
that prints the most, so it did not get that answer either.

## Deviations from the spec or the task

1. **The task's cause is right but its number is not: `_logEscapeBuffer` is not what
   `CONFIG_LOG_MAXIMUM_LEVEL_DEBUG` brings.** The task (and report p10-06, and this phase's
   README) say the option brought the modem library's 3 080-byte `_logEscapeBuffer` into `.bss`.
   It did not: `.bss._ZL16_logEscapeBuffer` is `0xc08` bytes in **v0.1.2's** map as well, and in
   0.1.4's — it is a file-static of `WalterModem.cpp` that nothing guards. The option's real cost
   is the 680 bytes above, spread over the debug strings and tables of every component that has
   them. It was still the difference between an image that starts and one that does not, and the
   pile's premise holds; only the 3 080 does not. Both follow-up items are ticked with this
   correction.
2. **The model needs a recording, and the task's "the allocations from the code" is met by
   recording the code rather than reading it.** ESP-IDF's start-up makes about fifty small
   allocations before our constructors — newlib's `FILE`s and locks, the VFS entries, the console
   — whose sizes are inside newlib and ESP-IDF and cannot be derived from a reading with any
   confidence. They are recorded from the firmware itself, in QEMU, with the recorder and the
   conversion both in `tools/`. Nothing is fitted: the recording is a list of sizes and
   capabilities, every free in it has to resolve to an address the model allocated, and the result
   is checkable against the chip — which it was, three times over.
3. **The margin the task asks for is met, and it is not the margin that matters.** `--min-spare`
   8 192 is satisfied with 11 788. But the figure that decides the arrangement is the scratch's
   **356 bytes**, and 357 more bytes of `.data` or `.bss` anywhere in this firmware will move it.
   The model prints that number as *the tightest is N bytes* for exactly this reason. It is not a
   cliff into a brick, though: in 0.1.4's arrangement the flip leaves the stack ~600 bytes of
   room in DIRAM, so the build would still start and would fail task p11-02's rail long before
   anybody flashed it. Said here because the 8 kB figure on its own would read as more headroom
   than there is.

## Decisions taken without asking

1. **`compiledIn()` on the seam rather than a refusal inside the firmware's implementation.** The
   decision ("are the library's `ESP_LOGD` lines bytes of this image at all") is one Kconfig macro
   and belongs where that macro is visible, but the *sentence* and "switches nothing on" belong in
   `core/` where a host test can see them. So the seam gained a one-bit question, the console asks
   it before it reads the two secrets or calls `turn()`, and `modem::WalterModemTrace::turn()`
   refuses the same way for any other caller — a build with no debug line can never take the 4 kB
   line buffer or install the log hook.
2. **The trace build drops the core dump rather than the main task's stack.** It needed ~164 bytes
   and the two candidates were measured: no core dump to flash gives 2 288 bytes of `.bss` and
   leaves everything else alone; a 12 288-byte main stack gives the room but shrinks the stack of
   the build that prints the most, and the 16 KB was raised after an overflow. A trace build is
   watched over a cable, where a panic is read as it happens.
3. **`tools/heap_at_start.py` judges a build directory and nothing else.** It does not read the
   repository, so it can be pointed at an old build (both tags were), and it has no opinion about
   which build is the release. Task p11-02 owns the rail and the margin it enforces; this task
   left `--min-spare` at the 8 192 the task names, and exit 1 when it is not met, so that the rail
   is a one-line call.
4. **The two tags were rebuilt rather than read out of `out/images/`.** The ELF kept there is
   0.1.3+a990bf3, built before the release workflow restamped it, so its SHA-256 is not the one
   the core dump names (`5c1cb8f37…`, built on the runner). The rebuilds at the tags' own versions
   reproduce the heap exactly — `_heap_start` 0x3FCD2770 matches the figure the model needs — and
   the core dump's own evidence (the `ipc0`/`ipc1` TCBs at 0x3FCE4DAC and 0x3FCE5414, `pxStack`
   0x3FCE48A8 and 0x3FCE4F10) lands inside the rebuilt image's heap to the byte, which is the
   check that the rebuild is the image that panicked.

## Not verified here (and why)

No session opens a port, so nothing below has touched silicon. The lines are in `docs/bench.md` in
the order the rig is brought up.

- **§1, new first item — *The image starts at all, and the model said it would*.** Run
  `python tools/heap_at_start.py --build-dir /build/fw` (it must end `verdict: FITS`), flash the
  image by cable and look for **the banner**. A banner means the main task exists and `app_main`
  ran. No banner, with `rst:0xc (RTC_SW_CPU_RST)` repeating and nothing else, means the model is
  wrong — which is a finding about `tools/heap_at_start.py` and `docs/ARCHITECTURE.md` §14, not
  about the board. **Write down the first boot's lines either way**; task p11-04 wants them.
- **§13 — the release build's answer.** `trace` says *the lines are not in this build…* and no
  longer offers `trace modem on`; `trace modem on` answers *error: … are not in this build;
  docs/bench.md section 13 makes one that has them* and `status` stays quiet. One minute, no SIM.
- **§13 — the trace build, end to end.** Build it with `sdkconfig.trace`, run the model over it
  (`FITS`, ~13 kB to spare), flash it by cable: it must **start** (banner), `trace` must offer the
  command, and `trace modem on` must bring the library's `TX:`/`RX:` lines. Then the stall walk,
  and a release image back on the board afterwards.
- **The heap figures on a board.** The model's numbers come from the build and from QEMU, and QEMU
  is not silicon: the ROM revision on the board decides `dram0_rtos_reserved_start`, and the model
  reads it from `esp32s3_rev0_rom.elf`. A board whose ROM differs would move the DIRAM heap's top
  (0x3FCE9710..0x3FCEEE34 is the `startup_stack` region). ESP-IDF's own `heap_init` prints the
  region table at boot — **keep those lines from the first boot** and hold them against the four
  regions in the table above; they are how this is confirmed on the real part. Task p11-02 puts
  the same figures behind a `heap` command.

## For `FOLLOWUPS.md`

- **[02] The rail should print the tightest margin, not only the spare in the stack's block.**
  `heap_at_start.py` already prints *the tightest is N bytes* (356 in 0.1.4). A rail that fails on
  `--min-spare` alone passes a build that is 357 bytes from a different arrangement; the line to
  show a person is the tightest one.
- **[02, or later] One block for the runner and the scratch buys 2 052 bytes.** TLSF rounds 66 000
  up to 69 632 and 20 480 to 20 480, 90 120 bytes with the two headers. One allocation of
  `sizeof(mm::JobRunner) + kKeptScratchBytes` = 86 480 rounds to 88 064, so 88 068 — **2 052 bytes
  back**, which would take the scratch's 356-byte margin to 2 408. It needs a placement `new` over
  a block aligned for `mm::JobRunner`, in `main.cpp`'s initialisers, and the task put that kind of
  change out of scope.
- **[later, upstream] 464 bytes off `sizeof(mm::JobRunner)` would give back 4 096.** It is 66 000,
  which is 464 past 64 kB, and TLSF rounds the block to 69 632. Anything that takes the type under
  65 536 bytes returns a whole size class. For `meshmaster-agent-firmware`, not for here.
- **[later] The `startup_stack` heap, 22 308 bytes, is unreachable at the moment that matters.**
  It is registered at the top of `main_task`. Nothing in ESP-IDF's configuration moves that, but it
  is worth knowing that the free heap `agent id` reports includes 22 kB that did not exist when the
  main task was created.
