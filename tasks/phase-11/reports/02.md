## What the board really has, read in QEMU

The model is a model, and the task asks the boot line to be *the bench's check on it*. So before
writing the figure down, this firmware was booted in the QEMU the pinned image ships (no board,
`out/work/p11-02/qemu-two.sh` and `heap_two.gdb`) and the heap was read at the three moments that
matter, with `heap_caps_*` called on the target itself:

| read on the running image | free | largest free block | the model says |
|---|---:|---:|---|
| A — `esp_startup_start_app`, the moment the main task is created (what the model judges) | 36 316 | 27 648 | **36 316** and **27 648**: exact, both |
| B — `app_main`'s first instruction | 35 964 | 20 480 | — |
| C — the instruction after `app_main`'s `heap:` printf | **33 872** | **18 432** | 41 144 / 21 504: an upper bound, 7 272 above |

Three things came out of that, and all three are in the code and the documents now:

1. **A is exact.** The model's total free at the moment it judges is the chip's to the byte, which
   is the third independent check of report 01's model (it had the block list and the
   `heap_caps_malloc` answer; this is the registered heaps' arithmetic).
2. **`heap_caps_get_largest_free_block()` is not the largest block's size.** It is "the largest
   value of `s` for which `heap_caps_malloc(s, caps)` will succeed", and TLSF rounds that *down*
   to the second-level class below the block (`tlsf_fit_size`), because a request is rounded *up*
   before a block is looked for. The 28 532-byte block answers 27 648. The model now carries
   `Tlsf.fit_size` and prints both figures — `largest free block 21564, as a request 21504` — and
   it is the rounded one that matched the chip at A.
3. **The board's own line is 7 272 bytes below the model**, because the recording stops where the
   main task is created: FreeRTOS's idle and timer tasks, the task watchdog and `app_main`'s own
   first lines (`UsbConsole::begin()`) take the rest. 5 180 of it is before `app_main` and 2 092
   inside it. So `docs/bench.md` §1 holds a board to **33 872 / 18 432 / stack 16384 with 14 776
   never used** — measured — and names the model's figure as the upper bound it is, with a row
   for each way the board can disagree and what each means.

## What this task cost the heap

§14 asks this of any task that adds static storage, and with 356 bytes of margin it is not a
formality. Measured in this tree, main's firmware sources built and then this task's, the same way
(`git checkout main -- components/ main/`, `verify.ps1 -Only build`, and back):

| | main (f7bae91) | this task | |
|---|---:|---:|---|
| `.dram0.data` | 0xAC64 | 0xAC64 | **±0** |
| `.dram0.bss` | 0x34D60 | 0x34D60 | **±0** |
| `.iram0.text` | 0xE673 | 0xE697 | +36 |
| `.flash.text` | 0x70A38 | 0x70B20 | +232 |
| `twinoak-walter.bin` | 771 328 | 772 448 | +1 120 |
| `_heap_start` | 0x3FCD24C8 | 0x3FCD24C8 | **unmoved** |
| the model: *the tightest is* | 356 | 356 | **±0** |
| the model: spare in the stack's block | 11 788 | 11 788 | ±0 |

The four bytes of `.data` the new `g_heap_report` takes (a vtable pointer, constant-initialised —
it has no initialiser that runs) and the four of `.bss` the console's new member takes both fell
inside padding that was already there, so the arrangement is byte for byte main's. **The one
figure to watch is the IRAM fill**: `.iram0.text` ends 101 bytes below `_iram_end` now, where it
ended 137 below before. `_iram_end` is aligned to 0x100 and `.dram0.data` begins at
`ORIGIN(dram0_0_seg) + (_iram_end - _diram_i_start)` (report 01), so the next 102 bytes of
IRAM-resident code cost **256 bytes of DRAM** and would take *the tightest* from 356 to 100. The
rail would still pass; the model's new last-line would be the warning.

## Deviations from the spec or the task

1. **"What the model says it should be" is not what the board says, and the bench item says the
   measured figure instead.** The task asks for the boot line to be checked against "what the
   model predicts after the main task". The model's prediction for that moment is 41 144 free and
   a 21 504-byte block; the board reads 33 872 and 18 432, because about 7 kB is taken between the
   end of the recording and the line (above). Holding a bench item to the model's figure would
   have made the first real boot look like a finding. So the model prints its figure as an
   explicit upper bound, under *what the main task leaves behind*, and `docs/bench.md` §1 holds
   the board to the QEMU measurement — with a row saying what a kilobyte either way means and a
   row that is a stop condition (a largest free block under 16 384, which would mean the part's
   arrangement is tighter than the model's).
2. **`tools/heap_at_start.py` is task p11-01's file and this task changed it.** Three changes, all
   additive: `Tlsf.fit_size`/`largest_free_request` (above), the last section, and two lines on the
   verdict naming *the tightest*. No constant of the model was touched, nothing measured was
   written into it, and its exit codes are unchanged — the rail is still `--min-spare` and
   `DOES NOT FIT`, which is what R22 greps for.
3. **The two tags were not rebuilt again.** Criterion 1 says "rebuilt at its tag"; report 01
   rebuilt both at their tags in the pinned image and kept the ELF, map, bin and sdkconfig of each
   under `out/work/p11-01/measured/`, and the rail reads exactly those four files. Their
   `_heap_start` matches report 01's table, and a rebuild at the same commit in the same image
   would be the same bytes, so a third build of v0.1.3 would have proved nothing the kept one does
   not. Said here because the artifacts are git-ignored and a reviewer on another machine has to
   rebuild them to repeat it (`out/work/p11-01/build-tags.sh` is how).
4. **Two numbers that report 01 disproved were still in the tree, and are corrected.**
   `docs/ARCHITECTURE.md` §14's closing paragraph and `core/console/modem_trace.h` both said
   `CONFIG_LOG_MAXIMUM_LEVEL_DEBUG` cost 3 080 bytes of `.bss` (the modem library's
   `_logEscapeBuffer`); report 01 showed that buffer is in v0.1.2's map as well and the option's
   real cost is 680 bytes of static DRAM. Both now say 680 and name the correction. §14's rails
   count went from twenty-four to twenty-five with R22.
5. **Report 01's own follow-up list is not in `FOLLOWUPS.md` yet** (the reviewer moves it), so
   nothing there is ticked. The item tagged `[02]` — *the rail should print the tightest margin,
   not only the spare in the stack's block* — is done: every run prints `the tightest is N bytes`
   in the table and the verdict now repeats it in two lines of its own, and the rail's failure
   message points a person at it. The item tagged `[02, or later]` — one block for the runner and
   the scratch, worth 2 052 bytes — is **not** done: it is a change to `main.cpp`'s initialisers
   (a placement `new` over one aligned block), it moves the arrangement this task's whole job is
   to measure, and it belongs in a change that can be measured on a board. It is left for the
   reviewer to re-tag.

## Decisions taken without asking

1. **A seam of its own, `core/console/heap_report.h`, rather than four methods on
   `interfaces::Heap`.** That interface is the agent's heartbeat — "the available heap size" over
   *every* capability and the least it has ever been — and two of the new figures are not of the
   same kind: the largest free block is about one heap's arrangement, and the stack's high-water
   mark is not a heap figure at all. One `read()` returning all five numbers, so that what is
   printed is one moment rather than four reads. `interfaces::Heap` is untouched, and `agent id`
   still reports what it always did.
2. **`MALLOC_CAP_INTERNAL | MALLOC_CAP_8BIT` for all four figures**, which is
   `portFREERTOS_HEAP_CAPS` — what a task stack asks for. A total over every capability would
   include memory no stack could have used, and being able to compare the board's figure with the
   model's was the point.
3. **The margin is `HEAP_MIN_SPARE=8192` in `tools/verify.sh`, and `check_rails.py` names the
   whole assignment.** One definition, as the task asks; the second mention is a grep, not a
   second source of truth, and it is there so that lowering the margin is a failed rail rather
   than a quieter build. The model keeps its own `--min-spare` default of 8 192 (p11-01's), so a
   person running it by hand gets the same answer as the rail.
4. **The rail runs after `size` and before the copy to `out/images/`.** The release workflow takes
   `out/images/` as its artifact, so an image that cannot start is now never even copied there.
5. **It fails on `--min-spare` and prints *the tightest*, rather than failing on both.** 01's
   deviation 3 is the reason: a flip of the scratch is not by itself a boot that fails — in this
   arrangement the stack would land in DIRAM with ~600 bytes to spare, and *that* is what the
   8 192 rail catches. A second threshold on a figure that is allowed to move would fail builds
   that start perfectly well. So the tightest is printed in every run, named in the failure
   message as where to look, and not enforced.
6. **The whole model output goes to the log on every run, not only on a failure.** One run instead
   of two (quiet, then loud), ~130 lines in `out/verify/build.log`, and the figures of every
   verified build are then on disk — which is what let this report compare two builds at all.
7. **The boot line prints two figures and the command four.** A boot line is read by somebody
   looking for *did it start and with how much room*; the least-free and the stack's mark are both
   zero-information at that moment (the least free is the free, and the main task has just
   started). `heap` is where they belong.
8. **The 16 KB main stack, the runner's 66 000 bytes and the scratch's 20 480 were not touched.**
   Measuring is this task; moving them is not.

## Not verified here (and why)

No session opens a port. Both items are in `docs/bench.md`, in the order the rig is brought up,
and they are the two the task asks for.

- **§1, new item — *The `heap:` line, against what the model said*.** Flash the image, read the
  second line of the boot, and hold it against **free 33 872, largest free block 18 432**, which
  is what this build read in the image's QEMU. Then `heap` on the prompt: the same two, the least
  free (the free, at a fresh boot) and **16384 bytes, N never used** — QEMU's N at that point is
  14 776. The item has a row for each way the board can disagree: a few hundred bytes is agreement,
  a kilobyte either way is a finding about `tools/heap_at_start.py` and §14, and a largest free
  block **under 16 384** is a stop — the image started, so a block was found, but the part's
  arrangement is then tighter than the model's and the next release's margin is not what it says.
  Keep ESP-IDF's own `heap_init` region table from that boot either way.
- **§16, new item — *`heap` after a day on the cable*.** Both watermarks are this boot's (a deep
  sleep is a boot and the heap is built from nothing), so the day on the battery leaves nothing to
  read: this is a day with the cable in, which is what keeps the unit awake, and then `heap` with
  all four figures written down. The stack's *never used* is the figure that could one day let the
  16 KB come down; the least-free is the one that would show the copied library's parsers leaking.
- **QEMU is not silicon.** The three readings above are the same firmware on the same chip model
  in an emulator, and the one thing an emulator can get wrong here is exactly the thing report 01
  flagged: the ROM revision decides `dram0_rtos_reserved_start`, which the model reads from
  `esp32s3_rev0_rom.elf` and which moves the DIRAM heap's top. A board whose figures are far from
  the table above is that, and §1's third row is what to do about it.
- **The `heap:` line itself has no host test**, because `app_main` is platform code that
  `host_test/` does not compile (`docs/ARCHITECTURE.md` §12). What is held on the host is the
  console's `heap`, which prints the same two figures through the same seam; what holds the boot
  line is R22's grep (`main/main.cpp` must contain `g_heap_report` and `std::printf("heap: `) and
  the QEMU reading above.
