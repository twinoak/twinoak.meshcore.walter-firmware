# p11-04 — A release starts before it is published

`v0.1.3` was built in the pinned image, passed every host test, fitted its slot, carried its
descriptor, was signed with the release key and verified against all of
`spec/FIRMWARE-MANIFEST.md` §5 — and it could not start. Nothing in this repository had ever
asked an image to *start*. Now two things do, and this task is the second:

| | |
|---|---|
| **the gate** | `tools/release/boot_gate.py` boots the release's `-factory.bin` in the QEMU the pinned image ships and refuses it unless it reached `app_main`, printed the banner **with the version being released in it**, and printed `app_main`'s `heap:` line with the main task's stack taken |
| **where it runs** | `tools/verify.sh`'s `release` step (so: a laptop, and ci) and `.github/workflows/release.yml`'s publish job, **between `build_release.py` and `sign_manifest.py`** — the file it boots is the file that would be published, and nothing is signed before it has started |
| **how it reads the boot** | **gdb, not a serial port.** QEMU's `esp32s3` has no USB Serial/JTAG peripheral, that peripheral is this firmware's console, and ESP-IDF drops every console byte while no USB host is connected — measured, below. The gate breaks where the bytes are handed over and reads them there, and breaks on `esp_system_abort` as well, so a refusal can name the panic |
| **what it costs** | **about a second** (the window closes at the `heap:` line itself), 90 s at the outside. No firmware source changed: `git diff main -- components/ main/ sdkconfig.defaults` is empty, so `_heap_start`, *the tightest* (332 bytes) and R22 are untouched by this task |
| **what it is held by** | rail **R23**, `python tools/check_rails.py`: *all 26 hold*. Four ways of losing the gate were tried and each fails the rail |

And the one that matters most: **the `v0.1.4` that is published on github.com right now,
downloaded and checked against its own `SHA256SUMS`, starts** — `twinoak-walter 0.1.4+62538fa`
and its `heap:` line, in 1 s.

## How the boot is read, and why not the console

The task leaves the choice open — "its console, if it carries this firmware's USB output, or
`gdb` breakpoints the way 01 and 02 did. Say which, and why." It is **gdb**, and the reason was
measured rather than assumed:

1. **UART0 carries the ROM and nothing else.** A boot of this firmware in this QEMU writes nine
   lines to `-serial`: `ESP-ROM:esp32s3-20210327` … `entry 0x403c8948`, and then silence
   (`out/work/p11-04/gate1/uart0.log`). The console is not UART0 — the module's USB-C is the
   ESP32-S3's own USB and `sdkconfig.defaults` says `CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG=y`.
2. **QEMU's `esp32s3` has no USB Serial/JTAG peripheral.** `-device help` lists none, and four
   `-serial` chardevs give: port 0 the ROM's lines, port 1 the binary frames this firmware sends
   the *radio* over UART1, ports 2 and 3 nothing.
3. **ESP-IDF throws the console away before a wire.**
   `$IDF_PATH/components/esp_driver_usb_serial_jtag/src/usb_serial_jtag_vfs.c`'s
   `usb_serial_jtag_write()` is `if (!usb_serial_jtag_is_connected()) return -1;` at its first
   line, and in an emulator no USB host is ever connected. So *nothing a release prints can reach
   any port of this QEMU* — not the banner, not the `heap:` line, not a panic.

So the gate breaks at **`usb_serial_jtag_write + 3`** and reads the buffer it was handed
(`$a3`, `$a4`) with gdb's `append binary memory`: the exact bytes the firmware printed, one call
per line, before ESP-IDF drops them — which is what a cable would have shown, minus the CR LF the
layer below adds. Three hooks all told, and the ESP32-S3 has **two** instruction breakpoints, so
each one's place was chosen:

| hook | where | why there |
|---|---|---|
| `app_main` + 3 | flash → one hardware breakpoint, deleted the moment it is hit | criterion 1, and it gives the slot back |
| `usb_serial_jtag_write` + 3 | flash → the slot `app_main` gave back | the console's own bytes |
| `esp_system_abort` + 3 | **IRAM** → a *software* breakpoint, which gdb can write, so it costs no hardware slot and stays armed for the whole run | `$a2` is the panic's own sentence |

The `+ 3` is the Xtensa windowed ABI's `entry` (three bytes, no narrow form): at the function's
first instruction the arguments are still in the *caller's* window and gdb reads nonsense off
`$a2` — which it did, until the hooks were moved past it. Every run disassembles the three
prologues into its `gdb.log` as the evidence for that (`entry a1, 0x150`, `entry a1, 32`,
`entry a1, 32`). The addresses come from the image's own `nm` over the ELF the gate is given, and
a name that two symbols answer to is a refusal rather than a guess.

## Deviations from the spec or the task

1. **The `heap:` line is asked of an image that has one, and `v0.1.2` has none.** The task asks
   the gate to refuse unless the `heap:` line was printed, *and* that it pass `v0.1.2` — and
   `v0.1.2` cannot print that line, because task p11-02 added it in `0.1.4`. So the gate looks for
   the line's **format string in the image's own bytes** (`heap: %lu bytes free`) and asks only an
   image that carries it; one that does not is judged on `app_main` and the banner, and says so in
   its output. Every build this repository makes now carries it and R22 holds `main/main.cpp` to
   printing it, so the criterion is not softened for anything that could be released today. The
   alternative — refusing `v0.1.2` — would have made the gate's one *passing* reference image fail
   for a reason that has nothing to do with starting.
2. **The gate is a step of the publish job, not a job of its own.** The task says "`release.yml`
   boots the release's factory image … before the manifest is signed". A job of its own would have
   had to boot `out/images/twinoak-walter-factory.bin` (the build's artifact); as a step of the
   publish job it boots `out/release/twinoak-walter-<tag>-factory.bin`, **the file that would be
   published**, with `build_release.py` above it and `sign_manifest.py` below it, where the
   ordering is one screen of one file and R23 can hold it. It costs that job a `docker pull` of
   the pinned image (~1 minute on the runner) and the boot is one second.
3. **`tools/verify.sh`'s gate runs in the `release` step, not the `build` step.** R22's model runs
   in the build step, before the images are copied; this one needs the release's own factory file,
   which `build_release.py` writes in the release step. The consequence is worth stating: a build
   that cannot start is still *built* and copied to `out/images/` locally — R22 is what stops that
   one, from the map, in the build step — and what the gate stops is a *release*.
4. **The gate's window is wall-clock-bounded and the bound is not reached in the good case.** 90 s,
   stated in `verify.sh` (`BOOT_GATE_SECONDS`) and in the gate's own `--seconds`; in practice the
   window closes at the write that begins `heap:`, about a second in. An image with no `heap:`
   line in it (`v0.1.2`) runs to the bound, so the two old releases were measured with
   `--seconds 20` and `90`; nothing in their transcripts arrives after the first second.
5. **`docs/ARCHITECTURE.md` §14 gained a subsection** ("And the release is started"), which the
   task does not list among the words. §14 is where the rails count lives (twenty-five → **twenty-
   six**) and where the v0.1.3 account is; leaving the gate out of it would have left the one
   document that explains the fault silent about half the answer.
6. **`docs/bench.md`'s intro and three items outside §1 were touched** — the release the walk is
   walked with is `v0.1.4` now, and two items name the published `-factory.bin` by version. §18's
   item *The Walter's own release over LTE, 0.1.2 to 0.1.3* is **not** rewritten: that walk
   happened on 9 November and ended in a rollback, so the item needs more than a version bump and
   it is left for the reviewer (below).

## Decisions taken without asking

1. **The transcript is the firmware's own bytes, captured at the VFS, rather than a list of
   values read out of memory at breakpoints.** The gate could have asked the target for the same
   facts (call `heap_caps_get_free_size`, read `core::banner()`); reading the **bytes the
   firmware printed** means the gate judges what a person at a cable would judge, the whole early
   boot is in the log as evidence, and the reading of it is a pure function two transcripts can
   test. It also made the three criteria one mechanism instead of three.
2. **A panic is a hook of its own, and its backtrace is in the refusal.** Without it, v0.1.3 would
   have been refused as "never reached `app_main`, and did not panic either", after the full 90 s.
   With it the refusal is one second long and names `esp_startup_start_app app_startup.c:86`.
3. **The gate takes a factory image and an ELF, and knows nothing about the repository.** No
   `--build-dir`, no reading of `out/`: it is pointed at two files, so it can be pointed at a tag's
   rebuild or at a file downloaded from github.com — which is how three of the four runs above
   were done. `tools/verify.sh` and the workflow are the two places that know which files.
4. **A free port, asked of the kernel, rather than 3333.** Two gates on one machine (a `verify`
   run and a release run, or two clones) would otherwise take each other's gdb server. The flash
   image is written fresh for every run, because QEMU writes to it (otadata) and a reused one
   would not be the released bytes.
5. **The eFuse block is 1 024 zero bytes**, which is a module out of the factory: no secure boot,
   no flash encryption, nothing burned. It is written by the gate rather than taken from a build
   directory's `qemu_efuse.bin`, so the gate needs nothing but its two files.
6. **The gate's own output is printed in full in every run**, passing or failing (the transcript,
   the gdb markers, the three verdicts), and the workflow puts it in the run's summary either way.
   A gate whose output is only interesting when it fails is one nobody reads until it fails.

## New libraries (with the one-line justification)

None. The gate is one Python file with no import but the standard library, and the two programs it
runs — `qemu-system-xtensa` (`esp_develop_9.2.2_20260417`) and `xtensa-esp32s3-elf-gdb` — are

## Not verified here (and why)

No session opens a port (`tasks/phase-11/README.md`). The gate is an emulator, and the two things
it cannot be are in `docs/bench.md`:

- **§1, *A released factory image says on the console what its manifest says about it*** — now
  marked as *no longer a gate on a release, and still the only thing that reads these lines off
  silicon*. The dry run's `-factory.bin`, flashed by cable, for the banner, the descriptor line
  and the `heap:` figures on the real part: the ROM revision decides `dram0_rtos_reserved_start`
  and QEMU's is `esp32s3_rev0_rom.elf`'s, so a board that disagrees by a kilobyte is a finding
  about the model and not about the build (§1's table says what each case means).
- **§1, *The image starts at all*** — the item now says that every release has already shown that
  much in the pinned image's QEMU, so a board that does not print a banner is a disagreement
  between the part and the emulator rather than a surprise about the build. That is the sentence a
  bench walk is for.
- **The first unit over LTE**, which is this release's own next step and nothing a session can do:
  the radio, the modem, the three conditions of the trial and the switch from the release before.
  `release.md`'s *What it does not prove* says it in those words.
- **A unit that took `v0.1.4`.** Not known when this task ran; README and `flashing.md` say so
  rather than guessing.

  `begin()` would be caught by *the panic hook* rather than by the window. Worth doing when there
  is a second criterion worth reading off a line.
- **[later] `stdout` is not line-buffered on this board, and nobody has checked what a cable sees
  when no host is attached.** The console lines of `UsbConsole::write` go through the driver's
  ring buffer; `printf`'s go through the VFS, which **drops everything while the USB host is not
  connected** (the finding that shaped this gate). A Walter booting on a mast therefore prints its
  banner and `heap:` line to nobody — which is right — but a person who plugs a cable in *after* a
  boot sees neither, and `reboot` on the console is how they are seen at all today. Worth a line
  in `docs/console.md` at least.
