# p18-01 — The watchdog ends with the scanner

The first NoiseScope session on a unit (21 November, Bellevue, meshmaster.dk job 39506) measured
all six of its steps and ended `stuck`, and the radio was healthy an hour later saying
`booted: 3 (watchdog)`. The scanner starts the nRF52840's hardware watchdog at 60 s and feeds it
from its own loop; the repeater that comes back feeds nothing; and the flasher left every flash by
`AIRCR.SYSRESETREQ`, which is **not** one of the resets that clears a watchdog. So the watchdog
reset the repeater 59 s into the golden image's three-minute proving period, and a restart there is
a failure by rule.

**What this task did.** Every flash of a radio now ends the same way: the debug power-up withdrawn
(which is what ends debug interface mode), the lines released, and **the image started by a pulse
on `nRESET`** through `RadioPins::resetPulse()` — which waits out the spacing of `ARCHITECTURE` §2
rule 2 and records the pulse. The `SYSRESETREQ` is gone, not kept in front of it: a flash leaves
**one** reset and **one** boot, so the boot the proving period reads is the boot the pulse started,
and nothing has to tell two boots apart. The proof itself is untouched — a restart inside the
proving period is still a failure, and nothing forgives a watchdog.

The simulated chip has that watchdog now, from the Product Specification: started by the image in
its flash, paused while the debugger holds the core, surviving `SYSRESETREQ`, cleared by a pin
reset and a power-on. A session against it with the old exit ends `stuck` at 60 s of the golden
image's first boot — the test of 21 November, reproduced to the second — and with this task's exit
it ends `restored`.

`tools\verify.ps1` **green in 570 s**; `core_tests` 1 424 cases and 806 230 assertions, all
passing; the image is **848 336 bytes against `main`'s 848 864** (p15-04's report), 528 bytes
smaller, the soft-reset path and the finding it carried being the difference.

## What the Product Specification says

Read from Nordic's own PDF, **nRF52840 Product Specification v1.11** (`4413_417 v1.11 /
2024-10-01`). Nordic's download URLs answer 403 to anything headless (the memory of task p1-04),
so the file came from a GitHub mirror of Nordic's PDF and its own title page is what names the
version; the HTML rendition's *Debug and trace > Debug Interface mode* page was read through
WebFetch beside it and agrees word for word. Extracted text is in `out/docs/nrf52840_ps.txt`
(git-ignored).

**5.3.6.8 Reset behavior** — "The various reset sources and their targets are summarized in the
table below", the columns being CPU, Peripherals, GPIO, Debug⁶, SWJ-DP, RAM, WDT, Retained
registers, RESETREAS:

| Reset source | what it resets |
|---|---|
| CPU lockup⁷ | CPU, Peripherals, GPIO |
| **Soft reset** | **CPU, Peripherals, GPIO** — and nothing else |
| Wakeup from System OFF mode reset | CPU, Peripherals, Debug⁸, RAM⁹, WDT |
| Watchdog reset¹⁰ | CPU, Peripherals, GPIO, Debug, RAM, WDT, Retained registers |
| **Pin reset** | **CPU, Peripherals, GPIO, Debug, RAM, WDT, Retained registers** |
| Brownout reset | all nine |
| Power-on reset | all nine |

with footnote 6 "All debug components excluding SWJ-DP", 7 "Reset from CPU lockup is disabled if
the device is in Debug Interface mode", 8 "The debug components will not be reset if the device is
in Debug Interface mode", 10 "Watchdog reset is not available in System OFF", and the note "The RAM
is never reset, but depending on a reset source the content of RAM may be corrupted."

So, the three things the task asks for:

1. **The watchdog under a soft reset: not reset.** The WDT column is blank for *Soft reset* — a
   soft reset is "generated when the SYSRESETREQ bit of the application interrupt and reset control
   register (AIRCR) in the ARM core is set … A soft reset can also be generated via the register
   RESET in the CTRL-AP" (5.3.6.4), and the watchdog's own chapter says it in the other direction:
   "After it is started, the watchdog's configuration registers, which comprise registers CRV,
   RREN, and CONFIG, will be blocked for further configuration. **The watchdog can be reset from
   several reset sources, see Reset behavior**" (6.36.3). It keeps counting, with the same timeout,
   into the boot the soft reset begins — which is exactly what the repeater firmware says of it
   (`src/roles/scanner/config.h`: *the nRF52840's WDT, which cannot be stopped and which survives
   the soft reset into the bootloader with the same timeout*).
2. **The watchdog under a pin reset: reset.** The WDT column is marked for *Pin reset*, which "is
   generated when the physical reset pin on the device is asserted" and "is configured via both
   registers PSELRESET[n]" (5.3.6.2). A pin reset also resets the debug components (all but the
   SWJ-DP) and the retained registers, and does **not** clear `RESETREAS`, which "will be
   cumulative" unless written (5.3.7.11); `RESETREAS.RESETPIN` is the bit it sets, `DOG` the
   watchdog's and `SREQ` a soft reset's.
3. **A pin reset while the debugger still asks for power.** The device "is in the Debug Interface
   mode as long as the debugger is requesting power via CxxxPWRUPREQ. Once the debugger stops
   requesting power via CxxxPWRUPREQ, the device is back in normal mode" (*Debug Interface mode*).
   Only two rows of the table are qualified for that mode — CPU lockup (footnote 7, the reset is
   *disabled*) and Wakeup from System OFF (footnote 8, the debug components are *not* reset) — and
   the *Pin reset* row carries neither, so by the table a pin reset resets the debug components and
   the WDT whether or not the debugger is holding power; what it never resets is the SWJ-DP, so the
   device would **stay** in debug interface mode across the pulse. The Product Specification does
   not say that in so many words for the WDT, and **this firmware does not rest on it**: `finish()`
   withdraws the power-up first (`Nrf52::close()` → `Dp::powerDown()`), so the pulse lands on a
   device that is back in normal mode and the question does not arise. That is the one reason the
   order in `finish()` is the order it is.

And why the pause mattered through fifteen minutes of flashing: CONFIG.HALT "Pause watchdog while
the CPU is halted by the debugger" (6.36.2), which is what `wdtBegin()` sets — so the watchdog
stood still for the whole flash and spent its 60 s on the *new* image's first minute.

## Deviations from the spec or the task

- **The task left the choice of *which* flashes get the pulse open (deliverable 2), and the answer
  is every flash, in one place.** `Flasher::finish()` is the only exit of `flash()` and
  `flashTest()` and of every failure after the halt, so that is where the pulse is and no caller
  knows anything about it. The alternative the task named — only the flashes that follow a scanner
  — would need the four callers it lists (a session's switch back, the way back when the scanner
  did not show itself, a session taken up again after a restart, the supervisor's own flash of the
  golden image over a radio whose last word was a scanner's) to agree about what the radio was
  running, and a Walter that has just restarted cannot always know. Every flash is the simpler rule
  and — because the pulse *replaces* the soft reset rather than following it — it costs nothing: no
  extra second, no extra boot. What it does cost is three things worth saying out loud:
  1. **No confirmation.** `SYSRESETREQ` could be read back in `DHCSR.S_RESET_ST`; a pin cannot. The
     boot window's `HELLO` is the confirmation now, and a pulse that does not reach the chip reads
     as `kNoBoot`. **The reset line has never been scoped on a unit** (`docs/bench.md` has no
     ticked item), so this is the task's largest untested assumption: if that line were dead, a
     radio flash would end `stuck` and the repeater would come back at the supervisor's power
     cycle (rung 3) — which is where the watchdog bug left it anyway, so the floor is today's
     behaviour, not worse.
  2. **A refused pulse leaves the radio halted**, where the old exit always left it running. It is
     a `kFailed` at `kReset` with the pin layer's word in `why`, and the only way `resetPulse()`
     can refuse inside `finish()` is a pin driver that refused — the same driver that had just
     carried the whole flash. The supervisor's power cycle is the way out.
  3. **On a build code Fxx module whose firmware does not write `APPROTECT.DISABLE`, the exit's
     pulse closes the access port** (PS *Access port protection*: an improved part is open "until"
     a pin, power or brownout reset), where a soft reset left it open. Such a module is one that
     any power cycle — the supervisor's rung 3, a mast losing power — closes as well, so nothing
     this firmware can do keeps it usable; the closed port is now reported where it belongs, at the
     next flash's `open()` (`kProtected`). A new test says so: *a build code Fxx module whose
     firmware does not open its port: the flash completes, the pulse closes the port, the next
     flash says so*. `spec/SYSTEM.md` §10.2 is still open and `rak provision` still answers it: its
     own sequence is unchanged and it reports the port after its reset.
- **`Result::port_closed_after_reset` is gone, with the console line that printed it.** It was set
  from the `kProtected` answer to the `AIRCR` write; with no write there is nothing to read, and
  the port is closed only *after* the lines have been let go. `docs/console.md` and `docs/bench.md`
  carried the old sentence and now carry the new one: `the radio was started by a pulse on the
  reset line; the next reset pulse waits out the spacing`.
- **`RadioPins::noteRadioReset()` is gone** (header and body). Its comment named one caller — "the
  flasher's system reset through the debug port" — and that caller is gone; `resetPulse()` records
  the pulse itself, which is what the spacing rule reads. No test used it.
- **`Nrf52::systemReset()` now has no caller in the firmware.** It is left where it is, documented
  and tested (`test_nrf52_core.cpp`, `test_nrf52_chip_approtect.cpp`, the forbidden-register rail's
  sweep of the whole API): it is the nRF52 layer's operation, not the flasher's policy, and the
  door's own `softReset()` (S-5a's one allowed reset) is a different function on the CTRL-AP.
- **The simulated world drops the radio's pending output at a chip reset**
  (`radio.forgetPending()` in `UpdateWorld::settle()` and `ChipRadio::settle()`). The pulse's
  extra second exposed something the old timing hid: in a *resumed* flash — the Walter died after
  the first flash's reset and re-flashes — a boot the previous flash began could fall due while
  this flash's exit waits out the spacing, and the scripted radio's queued `EV_BOOT` then outlived
  the chip reset and was read after the window opened as the boot being proved, with the real one
  arriving later as a restart. `forgetPending()`'s own comment is this case ("a module whose
  firmware was replaced has no EV_BOOT of the old one's still in flight"), and on a board the
  Walter's own reset clears its UART with it. It is the bench that was generous, not the firmware
  that is fragile; said here because it is a behaviour of the simulators, not of the code under
  test. Two of `test_radio_update_power_loss.cpp`'s 12 interruption points found it.
- **Five test files edited, none of them in what it asserts about an outcome:**
  `test_flasher.cpp` (three reset counts read as `resets().pin` instead of `counters().aircr_resets`,
  the removed field, and the Fxx case rewritten as above), `test_flasher_refusals.cpp` (a target
  that goes silent **after** the halt now gets its pulse and runs again — the old exit skipped the
  reset as undeliverable and left the radio halted, so this is a change for the better and the test
  says why), `test_console_flasher.cpp` (the rig wires the reset line to the chip; the printed
  line; the counters), `test_supervisor.cpp` (rung 4's cure now counts **two** pulses, rung 2's and
  the flash's; and the *chip is protected* subcase also says `bootloader_opens_port = false`, so
  that the module stays shut across rung 2's pulse, which now reaches the chip), and
  `test_firmware_jobs.cpp` (*nothing was flashed* counted in the world's chip resets rather than in
  one wake's pin counters, which a wake throws away).
- **Four benches wire the reset line to the simulated chip** (`update_bench.h`, `chip_radio.h`,
  `supervisor_bench.h`, `wake_bench.h`): `target.on_pin_reset = chip.pinReset()`, as
  `sim/nrf52_bench.h` and the provisioning bench already did. Without it the flasher's pulse would
  be a pulse on a wire nothing is listening to.

## Decisions taken without asking

- **The pulse replaces the soft reset; it does not follow it.** The task's deliverable 3 allows for
  a soft reset still being there ("the boot the soft reset began, where there still is one"). Both
  were weighed. Keeping it would leave the radio running whatever happened to the pulse, which is
  the safer-looking half; but it also means two resets 1.1 s apart, two boots, and a first boot
  whose `EV_BOOT` can arrive inside the second boot's window — a race to be closed by draining the
  UART in the link client, which is machinery this task should not be adding and which task p18-03
  is about to work in. One reset and one boot has no race to close, and the deviation above says
  what it costs instead.
- **The watchdog is a knob of the simulated chip and of the bench, not of this firmware.** Nothing
  under `components/` reads or writes a WDT register: the watchdog belongs to the radio's firmware,
  and what this firmware owes it is a reset of the right kind. So `sim::Nrf52Chip` grew
  `startWatchdog()`, `feedWatchdog()`, `serviceWatchdog()` and `watchdog_fed`, and the update
  bench's scanner starts and feeds one (`bench::kScannerWatchdogMs`, 60 000, with the repeater
  firmware's `WDT_TIMEOUT_S` cited beside it).
- **`watchdog_fed` rather than a feed per loop turn.** A bench that jumps the clock by five minutes
  in one `advance()` would otherwise look like five minutes of nobody feeding. The flag says which
  of the two things the running image is — a scanner that feeds from its loop, or a repeater and a
  bootloader that feed nothing — and the countdown only runs for the second. `feedWatchdog()` is
  still there as the one reload request, which is what the chip's own test uses.
- **`pointless` is gone from `finish()`.** The old exit skipped the reset when the port was
  unusable (no target, lines lost, protected), because an `AIRCR` write could not be delivered. The
  pulse needs no port, and a core that was halted when the lines went is exactly the radio that
  most needs starting, so the pulse is issued whenever the core was halted — and `kPins` and
  `kSelect`, where nothing was touched, still get nothing.

## Not verified here (and why)

No session opens a port; nothing of this was on a board. The two lines are in `docs/bench.md`
beside the session's own walk, where the rig's order puts them:

1. **A session on a desk radio ends *restored*, where 21 November's ended `stuck`.** `rak session
   30 sweep` on a radio that can be spared for forty minutes, then `journal`: the same four stages
   — `flashing-golden`, `booting`, `proving` — with **`restored`** last and about three minutes
   between `proving` and it, not the 59 s the watchdog allowed, and no second outage at the next
   wake. A `stuck` with *the radio restarted inside the proving period* about a minute into the
   proof means the pulse did not reach the chip.
2. **`rak status` after a flash: the reset reason the pulse leaves.** Expected `booted: 2 (reset
   pin)` where the old exit left a software reset. The repeater's reading is the one to trust — it
   said `3 (watchdog)` after the watchdog's own reset on 21 November, so it does read `RESETREAS` —
   and `1 (power-on)` would mean the bootloader clears that register before the application sees
   it, which is what the scanner's own `reset: por` hinted at (`tasks/phase-17/FOLLOWUPS.md`). The
   word goes in the item either way: it is the one reading that says the reset line, and not the
   debug port, started the image.

And the thing neither of them is: **the reset line itself has never been scoped on a unit**
(`docs/bench.md` §2's `rak reset` item is unticked, as every item of that file is). Every flash now
depends on it. §2's item is the one to walk first, and it is cheap: one pulse of 100 ms, never above
the pull-up level, and the radio restarting once.
