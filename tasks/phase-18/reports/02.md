one of them, and a wake says in its own words how many it made and why the last one was the last.

## What was built, and where each piece is

**The number** (`walter_agent/identity.h`, `identity.cpp`). Five constants beside the transaction
caps, under the same *PLACEHOLDER / TO BE SET ON THE BENCH* warning, and `intent::claimsFor(band)`
beside `intent::forBand(band)`. They are **not** written in anybody's arithmetic, unlike the caps:
nothing prices a claim, so they are plain numbers and only a bench reading can move them. Five rows
in `docs/bench.md`'s *What to bring back* (rail B holds that).

**The room** (`core/cycle/wake_room.h`, `.cpp`). `couldHold(want_ms)`: where this wake stands
against the most one may ever be raised to. What a claim needs of it is `kLeastCallMs` for the
claim itself plus `roomForCallsAfter(mm::kClaimMax)` — a result for each job it may hand over and
the observations, each at the modem's command timeout. The **jobs' own time is not in it**, because
a lease the ceiling cannot cover is cut and the library ends that job `timeout` with the room still
there to post the result (task p16-06's rule, unchanged).

**The two gates** (`modem_uplink.cpp`). The library claims again on one bit — whether the answer to
the last result said more work waits — and **this firmware writes that bit**. So the one place a
board can end a wake's claiming without failing a call is where that answer is read, and the same
is true of the heartbeat's reply for the first claim. Both clear `jobsWaiting` when there is no
room, and a latch (`ModemUplink::stopClaiming`, three bytes of padding in `WakesRoom`) carries the
reason to whoever prints it. The first reason wins; `forgetTheWakesRoom()` clears it at the top of
a wake, as it already cleared the room's three bytes.

**What ends the claiming, and who says so:**

| who | when | the word |
|---|---|---|
| the result gate | a job left to its lease for want of budget — a download the wake could not pay for, a session the bound cut, an apply about to restart the board | *no room* |
| the firmware jobs | an apply, a session or a power cycle whose radio did not come back | *the radio is away* |
| the uplink | the bound cannot be raised to cover another claim | *no room* |
| the library | its own six words, translated: *nothing waits* and *an empty claim* → *nothing waiting*; *the wake's claims* → *the band's number*; *a result kept*; *no transactions*; *no time* → *no room*; *the claim did not come back* → *a claim failed* | |

**`holding`** (`ResultGate`, `FirmwareJobs::holdsOutsideTheBuffer`, `ModemUplink::claimJobs`). The
reviewer's reading of the server was the find this deliverable rests on: meshmaster.dk hands a
claim that states `holding` **every** job it has leased to this exit node whose lease is running,
that has no result and whose id the claim did not name — it keeps no record of an answer that did
not arrive, so *whose answer was lost* is not a question it can ask. With one claim a wake that
cost nothing, because those leases had lapsed by the next wake; with several it would hand this
unit its own work back mid-flight. Two ids at most go in: the one the gate is leaving to its lease,
and the one the journal holds as owed. The member is still written by the library's own writer out
of one array — a claim this firmware composed a member of itself would be a second dialect — and
`mm::kMaxClaimRequestLen` was already the longest body that writer can write, so the request buffer
needed no change.

**Between two claims nothing of the first is left**, which is deliverable 3 and was already true:
`keepPayloads` zeroes all `mm::kClaimMax` kept payloads before it reads a claim's bytes;
`claimJobs` calls `wipeReply()` whether the parse took or not; the token is wiped before every call
returns; and the library's `JobRunner::endClaim()` wipes every credential of a claim before the
loop rounds again (`AgentLoop.cpp:864`). The case *between two claims of a wake nothing of the
first is left* reads it back off the object: the first claim's payloads are gone, its job ids are
in no byte of the uplink, and no password is either.

**What the unit says.** Three readers, one vocabulary:

```
agent wake: config done, heartbeat done, results skipped, claim done, jobs done, observations done
  5 job(s) claimed, 5 run, 0 not run; 0 result(s) flushed, 0 kept; 1 batch(es), 16 advert(s) posted, 0 left
  3 claim(s), 5 job(s) run; the last claim was the last: nothing waiting
```

```
> agent jobs
claims    3 last wake, 5 job(s) run; the last was the last: nothing waiting
```

```
> journal
   1. seq 12 at 1791936012: wake 1, the timer: radio healthy, band plenty, steps …
       3 claim(s), 5 job(s) run; the last was the last: nothing waiting
```

The journal's wake payload is **44 bytes** (41 before), and `decode` reads the three older lengths
— 32, 37 and 41 — answering 0 claims and *it did not say* for what they never held. A wake that
claimed **more than once** is news, so such a wake gets an entry; one claim is what every wake made
before this task and is not news by itself.

**The bytes** (deliverable 6). `kWakePostBytes` is untouched at 32 kB. Measured by the new cases:
sixteen one-section `twinoak.report` results are **19 469 bytes**, so an ordinary result is about
1 220 bytes and **some twenty-seven of them fit** a wake; six whole-console reports are **32 684**,
about 5 450 each, so **six** of those fit and the seventh is kept. A result that does not fit is
kept with the timestamps it was made with and ends the claiming (*a result kept*), which is the
library's own rule.

## Deviations from the spec or the task

1. **The room before a claim is read at the heartbeat's reply and at each result's, not inside
   `claimJobs`.** The task says *a claim is not made … and that is `no room`, not a failure*. A
   refusal inside `claimJobs` can only be `false`, which the library counts as a failed claim: a
   `claimFailures`, a `noteFailure()` and the backoff that comes with it — and, since the bump, a
   second ask, because a call this firmware never began leaves the shape `mm::answerWasLost`
   reads as lost (`tasks/phase-18/FOLLOWUPS.md`'s *A claim the wake's own room refuses is asked
   twice*). So the claim is ended one step earlier, where this firmware writes the bit the library
   claims on. Nothing goes on the wire, nothing backs off, and the work stays the server's.
2. **The result-post gate is proved at the call level and by the arithmetic, not inside a whole
   wake.** `a wake with no room for another claim is told nothing waits` drives a real
   `ModemUplink` with a guard armed to within a minute of the ceiling; `couldHold`'s own five
   subcases are the arithmetic. A **whole** wake can only come within 95 s of the one-hour ceiling
   by having a session run into its own 58 min 40 s bound, and that latches *no room* for the other
   reason (the gate withholds the result) before the bound's gate is reached. The bench's §29 is
   where the real shape is walked.
3. **`theRadioAfterAJob` reads the machine's own ending as well as the supervisor's word.** The
   task says *healthy by the supervisor's own word*. The supervisor classifies at step 3 of a wake
   and `Supervisor::health()` is written nowhere else, so its word alone cannot have seen a radio
   this job lost — it would have said *healthy* about a radio that had just failed its proof. Both
   must now say the radio is there: the machine's own ending (the apply's outcome, the session's
   `restored`, the HELLO inside the power cycle's boot window) **and** `radioHealth() == kHealthy`.
   It is conservative the other way — a radio whose first install has just succeeded is classified
   `kAwaitingFirstInstall` until the next wake, so that wake claims no more — which is the right
   way round for a wake with a radio in hand.
4. **After an apply of the Walter's own image the word is *no room*.** There is no wake left to
   claim in: the switch restarts the board, and the result gate withholds the result, which latches
   *no room*. On the host the wake returns and the word can be read; on a board nobody ever reads
   it. A word of its own would be a seventh value nothing ever prints.
5. **Two of the library's seven words are not held by a test of ours.** Five are — a case of this
   task reaches *nothing waits*, *an empty claim*, *the wake's claims*, *a result kept*, *no
   transactions* and *the claim did not come back*, so a bump that rewords any of those fails here.
   *No time* (the wake's seconds at the server spent) is not reachable on these benches without a
   claim being refused for want of room first, so a bump that reworded it would quietly leave
   *it did not say* in the journal. A follow-up, not a fault: the library gives no enum for these,
   and this firmware must not write a second dialect of them.
6. **The scripted meshmaster.dk learned two halves of the server it did not have.** `jobsWaiting`
   in a **result's** reply (meshmaster.dk's task p4.47-253), without which no wake can claim again
   at all; and *work waits* now counts a lease this server holds with no result, not only something
   queued — because that is what it hands back, and with one claim a wake nothing could be handed
   back inside one. `leasedWithNoResult(job)` puts it in that state by hand, which is what a
   session the bound cut and an apply awaiting its trial leave behind.

## Decisions taken without asking

- **`interfaces::Claims` lives in the seam** (`interfaces/backend.h`), beside `Reached` and `Ask`
  and for the same reason: the journal, `agent wake` and a report must have one vocabulary for
  *why it stopped asking* and not three, and `core/` cannot name `components/agent/`.
- **The claims and the jobs run are asked for, not carried**: `interfaces::WakesRoom` grew three
  fields and it is a value the wake cycle asks for after the exchange, so it costs no byte of any
  object that lives for the boot. The latch is the fourth byte of the uplink's own `WakesRoom`,
  which is padding; the eight bytes of .bss above are its alignment.
- **The journal payload grew to 44 bytes**, with `kWakePayloadBytesV3` (41) added to the two older
  lengths the decoder accepts. A slot is 64 bytes whatever the payload holds, so the three bytes
  cost nothing; what they could have cost is the entries already on a unit's flash, and those read
  back as 0 claims and *it did not say*.
- **A wake that claimed more than once is news** for the journal. It is the new thing this pile
  does and the figure a person reading a week of the log will look for; it costs at most one entry
  a wake, and a wake of one claim writes nothing, so a quiet unit's log is unchanged.
- **`ResultGate::holdsOutsideTheBuffer` has a default of none**, so a gate that only withholds —
  every one in the host tests but the firmware jobs — is unchanged. The one production
  implementation overrides it.
- **A gate that does not state `holding` is left alone.** `holdingCount` below 0 is the library
  saying *this agent does not say*, and the member's absence is what stops the server handing
  anything back at all; turning it into a statement would ask for exactly what deliverable 11
  exists to prevent. The library states it in every claim, so that branch is the shape of the API
  and not a case this unit meets.
- **`agent id`'s intent line gained the claims number.** The band's five numbers are placeholders
  a person reads on a bench, and that line is where the other five are already read.
- **A new `docs/bench.md` §29** rather than items hung on §17: this is a wake's whole shape
  changing, and §17's items are the agent's first calls. The five new placeholders are rows in
  *What to bring back* under the existing identity.h block, which rail B holds.

## Not verified here (and why)

A session can build and run the host tests; it cannot flash a board, reach a network or talk to
meshmaster.dk. Everything above is tested against simulators only — a scripted meshmaster.dk behind
this firmware's own HTTP/1.1, a simulated nRF52840 behind a simulated RAK, a scripted NoiseScope on
the UART — and the same items are in `docs/bench.md` §29, in the order the rig is brought up.
**meshmaster.dk's pile 4.47 has to be deployed first**: `jobsWaiting` in a result's reply is what a
wake claims again on, and a server without it leaves this unit making exactly the one claim it made
before.
