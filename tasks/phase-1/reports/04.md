# p1-04 — The nRF52 target

Through task 03's debug port the Walter now reads and writes the nRF52840's memory
(`components/core/swd/mem_ap`), says exactly which chip it is talking to, tells whether the chip
will let it in, stops and restarts the core, and erases and writes flash pages
(`components/core/nrf52`) — and it is **unable to erase the whole chip or its UICR by any path a
program can take on its own**: no function writes `NVMC.ERASEALL`, `NVMC.ERASEUICR`, the control
port's `ERASEALL` or an address in UICR; a host test reads every source under `components/` and
fails if one of their names appears anywhere but the header that defines them, and the simulated
chip fails the running test the moment one of them is written. `erasePage` and `writeWords` take a
`FlashRegion` and refuse anything outside it before the flash controller is touched; there is no
overload without one.

The other half is **`host_test/sim/nrf52_chip`**, a simulated nRF52840 behind task 03's
wire-level target: an AHB-AP whose auto-increment wraps exactly as the strict reading of ADIv5 has
it, a control access port, 1 MB of flash that only clears bits and needs `CONFIG` right, FICR,
UICR, an NVMC whose `READY` takes simulated time and stalls the bus, and the core's three debug
registers with a core that is running or halted and a Local reset's exact effect on each. It
records every erase and write, and it can be told to be protected, to be another part, to report
`READY` late or never, to lose power at the Nth flash operation, and which region alone may be
touched. Every register in it and in the firmware carries the chapter it came from — Nordic's
nRF52840 Product Specification, Arm's Armv7-M Architecture Reference Manual (DDI 0403E.e), Arm's
ADIv5 (IHI 0031G) and Arm's Cortex-M4 Technical Reference Manual (DDI 0439B), all read for this
task (`out/docs/`, git-ignored) — and where the task's starting facts and the documents disagreed,
the document won (below).

**62 new test cases** of the host suite's **244 test cases, 2 084 389 assertions**, under
AddressSanitizer and UndefinedBehaviorSanitizer; **`tools/verify.ps1` green in 45 s** with the
firmware rebuilt. `rak swd id` and `rak swd mem <addr> [words]` are on the console. One session.

  chosen.** The HTML rendition of the nRF52840 Product Specification ("NVMC > Electrical
  specification > Flash programming", read 2026-10-11) gives: tWRITE **41 µs typical**, tERASEPAGE

  used", and no maximum. Chosen (`nrf52.h`): **`kErasePageTimeoutMs = 300`**, 3.5 times the

  the 300 ms bound is reached after 301. The simulator uses the typical values and the knobs
  `ready_extra_us` (late: 235 ms passes) and `ready_never` (the bound) to exercise both edges.

## Deviations from the spec or the task

- **The console commands are `rak swd id` and `rak swd mem <addr> [words]`, not `rak id` and
  `rak mem`.** Task p1-02 gave `rak id` to the link's `IDENTITY` request (the node's public key
  and name), and `docs/console.md` documents it so; the SWD commands already live under `rak swd`
  (task 03's `rak swd connect`). The phase README's exit criterion says `rak id` reads the chip
  over SWD; `docs/bench.md` §4 and this report say `rak swd id`. The reviewer may want to rename
  one or the other in the README.
- **The auto-increment block.** The task says `TAR` advances "only within a 1 KB block"; that is
  ADIv5's *guarantee* (C2.2.2), and the Cortex-M4's AHB-AP actually wraps at 4 KB (DDI 0439B
  Table 8-6). The host rewrites at every 1 KB, correct for both; the simulator wraps at 1 KB by
  default — stricter than the chip, which is the right side — and a test runs the same host
  against the 4 KB wrap. `docs/ARCHITECTURE.md` §4 says both numbers.
- **The datasheet gives typical flash timings, not maxima** (above, fifth criterion). The bounds
  carry a margin instead of a datasheet maximum, and say so.
- **Two identification numbers are not Nordic's.** The AHB-AP's `IDR` (`0x24770011`) comes from
  Arm's Cortex-M4 TRM, the control port's (`0x02880000`) from Nordic's register table; the firmware
  insists only on *class MEM-AP* and *designer Nordic* respectively and prints the numbers, and
  `docs/bench.md` asks for them.
- **`Dp::connect()` changed** (task 03's code): when the `SELECT` write after `DPIDR` FAULTs, it
  is written once more. Found by the lines-lost test: a transfer cut off by a lost line leaves
  `WDATAERR` set, a line reset does not clear it (B4.3.3), and the first write of the next session
  FAULTed. `transfer()` had already cleared the flag through `ABORT`; the retry costs nothing on
  the happy path, and task 03's counts are unchanged.
- **The simulator's `AccessPort` interface changed** (task 03's): `read` and `write` return
  `kOk` or `kError` (an error sets `STICKYERR` and the next request gets FAULT, as B2.2.2 and
  B4.2.4 have it), and `stalls()` lets a port ask for WAIT. `StubAp` and its one test adapted;
  every task 03 test still passes.
- **A reset may close the port on a build code Fxx module** (above, the table's APPROTECT row).
  Not in the task; found by reading Nordic's note for the citation. `resetAndHalt()` and
  `systemReset()` re-read the protection afterwards and return `kProtected` rather than a timeout;
  the simulator models it (`protects_after_reset`); `docs/ARCHITECTURE.md` §4 tells task 05 to halt
  a running core. The design holds: identification, protection, flash and core control all work on
  an open chip; only the order of operations in the flasher is constrained.
- **The Product Specification was read in its HTML rendition**, which "corresponds to the latest
  version only"; its PDFs returned 403 to every download attempted from this machine. The
  citations say so (`regs.h`). Nordic's own MDK header (`nrf52840.h`, nrfx, 2018 — on this
  machine in the PlatformIO Adafruit framework) was read beside it and agrees on every offset.
- **What the bus does on a flash write with `CONFIG` wrong is not in the document**, so the
  simulator does the strict thing: nothing is written, and the test fails with the sentence
  (`PS NVMC "Writing to flash"`). The firmware never gets there (`CONFIG` is set in the same
  function, and restored in it).
- **CI rounds: none** — see the end of this report, written after the pull request's run.

## Decisions taken without asking

- **Protection is read from `CTRL-AP.APPROTECTSTATUS` and nothing else** — not `UICR.APPROTECT`,
  which is a wish; the status register is what the hardware is doing, on every revision.
- **The control port's `IDR` must say Nordic** (JEP106 `0x44`, continuation 2) and the memory
  port's must say *class MEM-AP*; anything else is `kNoControlPort` / `kNoMemoryPort`, before
  memory is touched. A protected chip is reported *after* the control port is known to be Nordic's.
- **`identify()` sanity-bounds `CODESIZE`** to 4096 pages (16 MB): an "Unspecified" `0xFFFFFFFF`
  would otherwise make a flash size of nothing. Anything but part `0x52840` with 4096-byte pages
  and a sane count is `kNotNrf52840`; the identity is still filled in and printed.
- **`read()` is refused on a non-nRF52840 too**, the task's "refused by everything below" read
  literally; `rak swd id` still prints what FICR said about the stranger.
- **`halt()` leaves halting debug on; `run()` turns it off** (`C_HALT` 0 to leave Debug state,
  C1.5.4, then `C_DEBUGEN` 0) and clears the reset vector catch, so a radio that was looked at
  runs as if no debugger had been there. `resetAndHalt()` halts the core first so nothing runs
  between the vector-catch write and the reset, and clears the catch after. `systemReset()` turns
  debug off before the reset so the core runs free, and confirms the reset by `S_RESET_ST`.
- **The core polls tolerate FAULT during a reset** (the bus is in reset; the debug port has
  cleared the flag) and are bounded: 10 ms for a halt, 100 ms for a reset, one read a millisecond.
- **`writeWords` writes the block, then waits for `READY` once**; the words themselves are paced
  by the bus (a stall is a WAIT, retried). A word write is one transfer; a block read is two
  (DRW then RDBUFF — the posted read is not pipelined across words). At 125 kHz that is about
  0.43 ms a word written and 0.86 ms a word read: a 400 KB image is some 45 s to write and 90 s to
  read back, plus a 1 KB `TAR` rewrite every 256 words. Task 05 may want a pipelined block read
  in `Dp` if the verify is too slow; nothing here prevents it.
- **The `FlashRegion` rules**: `begin < end`, both multiples of the page size the chip reported,
  `end` inside the chip's flash. Which region is the flasher's; the type exists here so that an
  erase or write without one is a compile error.
- **The `TAR` cache** forgets after the word at offset `0x3FC` of a block (what the AP did there is
  IMPLEMENTATION DEFINED) and after any error (C2.2.2: not incremented on an error response; and
  after a timed-out WAIT nothing is known).
- **`rak swd mem` prints at most 32 words**, four a line, and both commands are read-only: the
  console halts nothing and writes nothing until task 05's `rak flash`.
- **The simulated chip's defaults** are a provisioned RAK4630 as the bench expects to find it:
  variant `AAF0`, 1 MB, `UICR.APPROTECT` HwDisabled (`0x5A`), `NRFFW[0]` `0xF4000`, nRESET on
  P0.18, `REGOUT0` 3.3 V; the port open. Power loss is deterministic (the first half of a page
  erased and the next word half, or a word's low half not programmed) so that a test can say
  exactly what it finds.
- **The simulator also holds a host to** the debug keys (`DHCSR` without `0xA05F`, `AIRCR` without
  `0x05FA`: ignored and reported), the Cortex-M4's `MasterType` rule, `VECTRESET`, a flash write
  with `CONFIG` wrong, `ERASEPAGE` with `CONFIG` wrong or a non-page address or while busy, a
  write to FICR, banked-data and non-word accesses (not modelled: reported). A read or write of
  nothing is an error response (FAULT to the host), recorded but not a failed test.
- **The test-only knobs are public fields of `Nrf52Chip`**, as task 03's target has them; the
  firmware never sees the type.

## New libraries (with the one-line justification)

None. `components/core/swd/mem_ap` and `components/core/nrf52` include `<cstdint>`, `<cstddef>`
and this repository's own headers. The host tests use `<filesystem>` (C++17, for the grep over

## Not verified here (and why)

No board was on a desk. What the simulator proved against the documents, the chip must now
confirm — above all the numbers the documents did not give and the behaviour they describe in
words. `docs/bench.md` §4 has four new items, in the order the rig is brought up:

1. **`rak swd id`**: `DPIDR 0x2ba01477`; `control access port: IDR 0x02880000 (Nordic);
   protection: open`; `memory access port: IDR 0x24770011 (Arm, class MEM-AP; the Cortex-M4's
   AHB-AP)`; `chip: nRF52840, variant AAF0, flash 1024 KB = 256 pages of 4096 bytes (INFO.FLASH
   1024 KB)`; the device id; `core: running`. **Write the variant down** — it decides whether
   production modules arrive protected; and note whether the two `IDR` values are as predicted.
   The RAK's own console keeps answering: the command halts nothing.
2. **If `protection: PROTECTED`: stop.** Opening a module is `BENCH-BREADBOARD.md` caveat 6, by a
   person, once per module; this firmware will not. And the rev-3 question the simulator can only
   assume: whether `rak swd id` right after `rak reset` says *protected* on a module whose firmware
   opens the port at run time — the flasher halts a running core because of it.
3. **`rak swd mem 0x10000100 2` prints `00052840 41414630`**; `rak swd mem 0x00026000 4` prints
   the application's vector table (or `ffffffff`, which tells task 05 its region table is wrong);
   `rak swd mem 0xE000EDF0` prints `DHCSR` with `S_RETIRE_ST` set and `S_HALT` clear;
   `rak swd mem 0x50000000` says `FAULT ... at 0x50000000` and the next command works.
4. **The radio's current after `rak swd id`** is what it was before (task 03's item, now for this
   command too).

Also only a board can show: that a protected chip's AHB-AP answers memory accesses with an error
response (the simulator's reading of "blocks the debugger"; it might instead return zeros or
WAIT, and the firmware never gets that far on a protected chip, so either way it refuses); the
real tWRITE and tERASEPAGE on this silicon with the HFINT running, and whether a word write ever
stalls the access port long enough to be seen as WAIT at 125 kHz (the simulator says never at the
typical 41 µs); that `S_RESET_ST` and `S_HALT` both read 1 after `resetAndHalt()` and that the
access port FAULTs, or does not, during the system's reset sequence; and the Cortex-M4's 4 KB
auto-increment wrap, which the host never relies on. None of these is reachable from the console
yet — they are task 05's `rak flash`, which is where the bench exercises erase, write and the
core's halt for the first time, with the region table and the bootloader's settings page decided.
