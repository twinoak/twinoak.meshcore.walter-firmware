## The calls that gained a slot

`core::board::Slot` is a small value type (`index`, 0 or 1; `kSlotCount` 2, `isSlot()`); a unit has
one position (`TargetSelect::slots()` is 1) and slot 0 is the default everywhere.

| Where | Before | Now |
|---|---|---|
| `core/board/slot.h` | — | `Slot`, `SelectResult`, `TargetSelect` (`slots()`, `select()`, `selected()`), `SingleTarget`, `SlotLock`, `SlotHold` |
| `core/board/dual_target.h/.cpp` | — | `DualTarget` over `RadioPins`, the feasibility document's §3 protocol |
| `core/board/radio_pins.h` | — | `selectorProgram(uart_sel, debug_sel)`, `selectorPrograms()`; `kSelectorHalfUs`, `kSelectorBits`, `kSelectorWindowUs`, `kSelectorWindow{Min,Max}Us` |
| `link::client::Client` | one `Session`, one `Mode` | `slot()`, `useSlot(slot)`, `sessionOf(slot)`, `modeOf(slot)`; `Session`, `Mode`, `boot_id_known` and `time_pending` are **one per slot**; ctor takes `board::SlotLock&`; `Fault::kSlotBusy` |
| `link::client::Client::exchange()`, `hello()`, `poll()` | — | each takes a `SlotHold` on the client's slot for its whole duration |
| `flasher::Flasher` | `(pins, clock)` | `(pins, clock, slots)`; `flash(image, profile, progress, slot = {})`, `verify(image, profile, slot = {})`, `flashTest(profile, progress, slot = {})`; new first step `Step::kSelect`; `Plan::slot` |
| `flasher::findProfile` | `findProfile(name)` | `findProfile(slot, name)`, plus `profileForSlot(slot)` and `kSlotsPresent` |
| `nrf52::Nrf52` | `(dp, clock)`, `open()` | `(dp, clock, slots = nullptr)`, `open(slot = {})`, `slot()`; `Status::kSlotBusy` |
| `console::Command` | — | `slot`, from an optional `@N` directly after the word `rak` |
| `console::Console` | — | ctor takes `board::SlotLock&`; `slotOk()`; `rak reset`, `rak kill`, `rak swd connect|id|mem` each take a `SlotHold`; `rak flash-test` passes the slot to the flasher and reads its profile from `profileForSlot` |
| `main/app_main` | — | constructs `SingleTarget` + `SlotLock` and hands them to the client, the console and (through the console) the flasher |

**One selection at a time.** `SlotLock::take(slot)` selects the slot and holds it; `release()` gives
it back; `SlotHold` is the RAII form. Takes of the *same* slot nest and do **not** re-program the
selector (an operation calls others: the flasher identifies the chip inside its own hold). Another
slot while one is held is `kBusy` and nothing is steered — a request on the wire is never left
half-way. `Client::useSlot()` refuses while a hold stands, so the client cannot even be *pointed* at
the other radio mid-exchange.

**What is not per slot:** the client's event queue and the scanner's text ring. §3's events carry no
slot, the Walter steers the UART to one radio at a time, and what arrives arrives from the radio the
wires reach. Said so in `client.h`.

## Deviations from the spec or the task

- **`DualTarget::select()` programs both flip-flops to the same radio.** §3 gives two independent
  bits on purpose — "the Walter can keep the live console on module A *while* it flashes module B
  over SWD" — and this does not use that. The slot seam the task asks for is *one selection at a
  time* (`SlotLock`), and two independent selections would be two guards and two sessions of
  liveness; splitting them is work for the task that has a board. `RadioPins::selectorProgram()`
  takes the two bits separately, so the split is a line in `DualTarget` when it is wanted, and a
  host test drives the asymmetric case (UART to B, debug to A) to show the bit order is right.
- **No board profile for slot 1.** `profileForSlot(kSlot1)` is `nullptr` and `kSlotsPresent` is 1.
  What a dual position's manifest `board` is called is not decided anywhere — not in S-11, not in
  `FIRMWARE-MANIFEST.md`, not in the feasibility document — and inventing a name would put it in the
  firmware before the hardware. The dual tests pass `kRak4630Single` to the flasher directly, which
  is what a dual adapter carrying two RAK4630s would use either way.
- **`Client::radioWasReset()` is about the current slot**, not both. On a dual adapter nRESET is
  *routed* like the debug lines (§2.2), so one slot's reset is not the other's news. A kill is the
  exception — it cuts the whole rail (§5: "You cannot power-cycle one module alone") — and the
  caller tells each slot in turn; with one slot there is nothing to tell. Noted in the code.
- **The console's slot goes in front: `rak @1 hello`, not `rak hello @1`.** The task says "an
  optional `@1`" without saying where. In front is the only place that works for every subcommand:
  `rak cli <line>` takes the rest of the line verbatim (§5.7), so `rak cli get radio @1` must send
  `get radio @1` — and it does, to slot 0. A test holds both halves of that.
- **`tools/verify.sh` gained a check** (`check_selector_off`) beside task p0-03's pin-ownership
  grep. The acceptance criterion asks the report to *show where* the firmware constructs
  `SingleTarget`; a grep is how that stays true after this session.
- **`components/core/CMakeLists.txt` lists sources one by one and the host build globs them.** The
  host tests were green with `board/slot.cpp` and `board/dual_target.cpp` missing from the firmware
  component, and the firmware would not link. Added, in its own commit; this is the kind of gap the
  runbook's "green locally is the bar" catches only if the local run is the *whole* script, which
  is why this one was.

## Decisions taken without asking

- **`Slot` is a struct with a `uint8_t index`**, not an `enum class` and not a bare integer: an
  enum could not express "slot 7" for a refusal test, and a bare integer would pass where a count
  or an address is wanted. `kSlotCount` is 2 — the width of the seam, the dual adapter's two
  positions — and is *not* how many a unit has, which is `TargetSelect::slots()`.
- **The programming window is 120 µs: a 20 µs half-period, two bits, a setup and a trailing edge.**
  §3 asks for 100–500 µs ("the sweet spot"), above the bulkhead's ~1 µs RC and below the adapter's
  own ~2–5 ms filter. 20 µs is 25 kHz — twenty times the bulkhead's time constant and a tenth of
  the ~300 kHz the same lines carry SWD at — and a `static_assert` in `radio_pins.h` fails the
  build if the arithmetic ever leaves the document's range.
- **The reset the window implies is spaced like a real reset** (ARCHITECTURE §2 rule 2), as the task
  asks. The adapter's RC and Schmitt buffer mean no radio sees it, and the simulated selector models
  exactly that — but nothing in this firmware can measure a filter on a board that does not exist,
  and a bootloader left in UF2 mode is how a radio is lost. The cost is a second before each
  selection on a dual adapter, which falls on nobody today; the dual board's task has the standing
  to decide otherwise, and `selectorProgram()` is the one line to change. **This is the one place
  where the design pays for its caution**, and it is worth saying plainly: with the document's
  "program the register before every SWD or UART operation", a dual unit would wait a second before
  every poll of the link. That is a real finding for whoever builds the board — the answer is
  probably to let the selector's window skip the spacing once a scope has confirmed the filter, or
  to make the Walter trust `selected()` between operations.
- **`poll()` takes a hold and does nothing when another slot holds it.** Listening is radio-facing
  too: the bytes that arrive are the selected radio's. It still never *opens* the port (task p1-02's
  decision) and never waits.
- **The window forwards its stray clocks to the module selected at that instant**, as §3 says the
  hardware does ("the 2–3 SWDCLK pulses do reach the previously-selected module's SWD pins, but a
  valid SWD transaction needs a full 8-bit header"). The simulated debug ports see those edges and
  resynchronise on the next line reset, which is the document's claim, tested: two flashes of
  different slots in a row both succeed.
- **The fake pins learned the window rather than losing the rule.** `swdclk-while-reset` still fires
  on every bench that has not declared a selector — every bench of a unit as built. Where one *is*
  declared (`FakePins::selector_allowed`, set by `sim::Selector`'s constructor), an assertion of
  nRESET during which SWDCLK moved is a *programming window*: counted, held against §3's 100–500 µs
  in microseconds by a new rule `selector-window`, and not treated as a reset pulse the next one
  must be spaced from — because no radio saw it. `RadioPins` is stricter and waits anyway.
- **The selector's filter threshold is 2 ms**, the low end of §3's "~2–5 ms". The shortest filter is
  the one most likely to pass something on, which is the strict reading for a simulator.
- **`Nrf52` takes an optional `SlotLock*`.** Given one, `open(slot)` holds the slot until `close()`.
  The flasher passes none: it holds the slot around everything it then asks of the chip, and a
  second hold would be the same selection twice. The console passes none either — it holds the slot
  itself for the whole command — but it does pass the slot to `open()`, which is where `identify()`
  gets the slot the task asks it to take.
- **`host_test/sim/dual_bench.h` is the only place `DualTarget` is ever constructed**, plus the two
  cases that construct one deliberately to watch a rule fire. Two chips, two debug ports, two
  scripted radios, one set of wires.

## Not verified here (and why)

**The dual adapter does not exist** — `DUAL-RAK4630-FEASIBILITY.md` is an investigation with the
verdict "feasible", not a board. Nothing below can be walked today; it is written down so that the
board's bring-up has a list. `docs/bench.md` §6 carries it.

Nothing on the single adapter changes, and the bench lines of tasks 02 to 05 are unaffected. Two
lines are worth typing once while the rig is up, and they are in `docs/bench.md` §6:

- `rak @0 hello` prints what `rak hello` prints, to the byte; `rak @1 hello` answers *error: slot 1:
  this adapter has 1 radio, so slot 0 is the only one* with no frame on the UART and nothing on the
  seven pins; `rak @2 hello` is refused by the parser instead.
- Every other item of `docs/bench.md` §§1–5 behaves as it reads. The one output that changed is
  `rak flash-test`'s first line, which now begins `flash-test: slot 0, rak4630-single, …`.

When a dual adapter is built, these are its own (`docs/bench.md` §6):

- the selector programmed with a scope on SWDCLK and nRESET: a window of 100–500 µs, two rising
  edges on the gated shift clock, and **no** reset at either module's own reset pin;
- the power-on default read back as module A, with no selection programmed at all;
- `rak @1 hello` answering from the second radio while `rak @0 hello` answers from the first;
- a flash of slot 1 that leaves slot 0 running — the simulation's claim, on silicon;
- whether the programming window really needs the reset spacing this firmware applies to it (see
  *Decisions*), measured with a scope on the module side of the RC.
