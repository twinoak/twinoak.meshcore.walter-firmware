# p1-01 — The link codec

Protocol 1.0 as bytes, from the Walter's end, under `components/core/link/codec/`: CRC-16/CCITT-FALSE,
COBS, the packet, a frame receiver and a frame writer, a `Reader` and a `Writer` over a byte span,
one struct per payload with an encoder for every request and a decoder for every response and every
event, and one header that is `spec/LINK-PROTOCOL.md`'s tables of numbers. No heap, no ESP-IDF
include, nothing that touches a UART — task 02 puts it on the wire.

It is held against `spec/fixtures/link/link-v1.json`, read at run time: every CRC and COBS vector
both ways, all **69 cases** (30 requests, 32 responses, 7 events — 24 request types, 24 response
types, 3 event types), every invalid frame, the stream, and three properties the fixtures imply
rather than list. **19 test cases, 6 295 assertions** of the host suite's 86 and 130 024, under
AddressSanitizer and UndefinedBehaviorSanitizer. `tools/verify.ps1` is green in 18 s warm, 47 s
after a build from cold.

Nothing in the task was left out. Four things differ from how the task or the specification
describes them and are under *Deviations*; the largest is that a decoded message's
variable-length fields are **views into the payload** rather than copies, which is what "no heap"
costs.

## What was built, and what each piece is held to

| File | What | Held to |
|---|---|---|
| `codec/wire.h` | the numbers of §2–§8: the sizes, the type table with each type's capability and section, statuses, roles, peer kinds, capability bits, reset reasons, `STATUS` flags, time states and sources, reboot modes, LPP permissions, path modes, send results, reply states, attention reasons, the timings of §10 | a test reads the ranges, the response bit, §7's encoded path length and §6.2's legal trace hash sizes |
| `codec/crc16.h` | CRC-16/CCITT-FALSE, `constexpr`, bitwise (no table in the image) | §2's check value over `123456789` is a `static_assert`; all 4 fixture vectors |
| `codec/cobs.h/.cpp` | COBS both ways, for buffers up to a packet | all 8 fixture vectors both ways, and that no encoding holds a zero; a decoder refuses a zero, a block past the end, the `0xFF` code, an empty input, and a decoding that does not fit |
| `codec/packet.h/.cpp` | build and parse a packet, build a frame | every case's `packet` and `frame`; the length and CRC refusals; that a failed parse leaves the caller's `Packet` untouched (§2's "never interpret bytes before the CRC has passed") |
| `codec/frame.h/.cpp` | `FrameReceiver` (246-byte buffer, drops counted by reason, empty frames not errors, a `feed()` for any chunking) and `FrameWriter` (the idle `0x00`) | the `stream` fixture fed in chunks of all, 1, 3 and 7 bytes; all 6 `invalid` frames, with our reason held against the fixture's word; noise between frames is one drop; an overflowing frame is one drop at its terminator and the next frame is read; the writer's 100 ms rule, a restarted clock, and a 247-byte longest write read back |
| `codec/reader.h`, `codec/writer.h` | the little-endian scalars, `str8`, *rest*; sticky failure | a read past the end fails and changes nothing; two's complement; a `str8` longer than what is left; a `str8` over 255 bytes |
| `codec/messages.h/.cpp` | a struct per payload; `encode()` for all 24 request types, `decode()` for all 24 response types and 3 event types; the shared `Path`, `HelloBody`, `ReplyRecord` and `Observation` | every case; every response and event payload truncated to **every** shorter length (919 truncations); trailing bytes ignored; the refusals of both directions |

**Three properties the fixtures imply but do not list.**

1. **Truncation.** For each of the 39 response and event payloads, the payload is decoded at every
   length from 0 to its own — 919 decodings — and the outcome must be *monotone*: there is one
   length at which it starts decoding, every shorter prefix is refused, and nothing reads out of
   bounds (ASan and UBSan with `-fno-sanitize-recover=all` are the proof). For a shape whose last
   field is not a *rest*, that length must be the whole payload: a byte short is malformed, never
   a field read past the end. The shapes that do end in a *rest* — §5.7's CLI reply, §5.8's LPP
   bytes, and a reply record in state 3 or 4 — are named in the test with their sections, because
   for them a shorter payload is a shorter field and not a malformed one.
2. **Trailing bytes are ignored** (§5.1: a minor adds fields at the end): two bytes appended to
   every non-*rest* payload still decode to the same fields.
3. **Directions** (§3): every `request` case is `w2r` and every `response` and `event` case is
   `r2w`, and a response's `wire_type` is its type with bit 7 set.

## Deviations from the spec or the task

- **A decoded message's variable-length fields are views, not copies.** `core/` has no heap, so a
  `str8`, a *rest*, a path's hashes, a pubkey, an observation's `app_data` are a pointer and a
  length (`codec/view.h`) into the payload they were decoded from — which is the `FrameReceiver`'s
  own buffer, valid until the next frame is read. Whoever keeps one copies it; task 02's client is
  the first to need to, and `docs/ARCHITECTURE.md` §3 now says so. The alternative inside "no
  heap" was a fixed array of the largest legal size in every struct — 238 bytes for a `str8` ×
  three in the `HELLO` body — which would also have made a *legal* message refusable the day a
  radio's version string grew. The task's words were "a plain struct per payload"; these are
  plain structs, but they do not own their bytes.
- **A decoder is strict about a value that selects a layout and lenient about one that is only
  data.** The task says "decoders check every length and legal value". Taken literally that would
  refuse a `status`, `role`, `reset_reason`, `time_state`, `send`, `attention` or capability bit
  this firmware does not know — but §5.1 says a minor version adds exactly those and that a
  receiver ignores what it does not know, and a Walter that refused the whole response would learn
  less than one that passed the number on. So: `path_mode` and a reply record's `state` are
  checked (the rest of the payload cannot be read without them), as are every declared length and
  §7's `app_len` ≤ 32, §6.1's 1–3 bytes per hop, 1–63 hops and 64 bytes of hashes, and §7's
  implied path length; the data values are handed over as they arrived. A test holds both halves.
- **Length limits are enforced on what this end sends, not on what it reads.** An encoder refuses
  §5.7's console line outside 1–160 bytes, §6.2's mesh CLI line outside 1–148, a password over 15
  bytes, a three-byte trace hash size, a pubkey that is not 32 bytes and a path that does not add
  up — this end is the one that could put them on the wire. A decoder does not refuse, say, a CLI
  reply longer than §5.7's 160 bytes: it is a *rest*, the bytes are all there, and dropping the
  response would lose more than it protects. The limits are in `codec/wire.h` either way.
- **`hash_size` is checked for `SEND_TRACE`, the length of `hashes` is not.** §6.2 gives the legal
  sizes (1, 2, 4, 8 — three-byte hashes are `ERR_RANGE`) and says `hashes` is *rest*; it does not
  say the rest must be a whole number of hops, and `linkref.py` does not check it either. The
  encoder therefore checks the size and leaves the length to the caller rather than inventing a
  rule.
- **`spec/` was changed twice and reverted**, to prove the coverage test (above). Both times with
  `git checkout -- spec/fixtures/link/link-v1.json` straight after, and `verify.ps1`'s `spec` step
  and `linkref.py check` are green on the committed tree. `CLAUDE.md` says never to edit a file
  under `spec/`; an experiment that puts it back is how task p0-01 proved the same step, and
  nothing of it is committed.
- **CI rounds: none.** The first run on the pull request was green (see *CI* below); the local
  script and the runner agreed.

## Decisions taken without asking

- **`FrameWriter` takes an `interfaces::Clock&`** and measures the idle time from the last frame
  *it built*. §2 says a frame goes out in one piece with nothing interleaved, so whoever owns the
  UART sends what `write()` returns before asking for another; `forgetIdle()` is there for the
  cases where that stops being true (the radio was reset, the UART was released), and a clock that
  went backwards — `esp_timer` restarts at zero at every wake from deep sleep — counts as idle,
  which costs one byte and is never wrong.
- **The first frame after a `FrameWriter` is made is always prefixed.** Nothing has gone out, so
  the line has been idle for as long as this object has existed.
- **`FrameReceiver` counts by reason** (`kOverflow`, `kCobs`, `kLength`, `kCrc`) and keeps the last
  one, saturating rather than wrapping. §2 only asks for "dropped and counted"; the breakdown is
  what a console line and the supervisor will want, and `STATUS`'s `link_errors` is the radio's
  same number from the other end. The words are this firmware's: §11 says a receiver has to drop
  and count a frame, not agree on the word. The test maps the two vocabularies anyway — the
  fixtures' `crc` → `kCrc`, `cobs` → `kCobs`, `short`/`oversize` → `kLength` or `kOverflow` — and
  the mapping holds for all six invalid frames.
- **The decoded packet has its own buffer** (244 bytes beside the 246 of the receive buffer, 490
  per receiver). COBS can be decoded in place — each block consumes exactly as many bytes as it
  produces — but a reader would have to prove that to believe the code, and 244 bytes of a 16 MB
  part is not where this firmware saves memory.
- **`OBS_PULL` decodes into a fixed array of five records**, which is what a 240-byte payload can
  hold (the smallest record is 45 bytes and the response's head is 5); a `count` larger than that
  is malformed. The array, and not a view per record, because the records are the one field a
  caller walks.
- **The empty requests are one template** (`NoPayload<Type>`, aliased to `StatusRequest`,
  `TimeGetRequest`, …) and the five status-only responses are one struct (`StatusOnly`, aliased to
  `RebootResponse`, …) — which also decodes §3's answer to a request of a type the radio does not
  know, the one response whose type has no struct of its own. Distinct types, so a caller cannot
  send one where another was meant, and `kType` is always where the frame writer looks for it.
- **The codec is in the image but not in the link.** Nothing calls it yet, so the linker drops it.
  Task p0-01 added `components/modem/modem_anchor.cpp` to force the modem library in because its
  task asked for "compiled into the image"; this task does not, task 02 makes the question
  disappear, and an anchor for our own code would be a line somebody has to remember to delete.
  The build still proves it compiles and the archive still contains it.
- **`cobsEncode` refuses an input longer than a packet** (244 bytes), which is the only input that
  could need general COBS' `0xFF` code; §2 says an encoder need not implement it. The `0xFF` path
  is a `return 0` with a comment saying it cannot be reached from a packet of this link.
- **A `str8` is not checked for valid UTF-8.** §2 says a `str8` is UTF-8; a response is not
  malformed because a stranger's advert name has a bad byte in it, and `core/` has no business
  decoding characters. `Text` is documented as a run of bytes that happens to be text.
- **The test-side JSON reader is new code** (`host_test/fixtures/json.h`, 333 lines, header-only,
  heap and exceptions allowed because it is a test): the task says the tests read the fixture *at
  run time*, and nothing in the container's Python-free C++ environment reads JSON. Two things in
  it are not ordinary JSON handling and are why it is not a vendored library: it remembers every
  key that was read, which is what makes the coverage test a property of the tests instead of of
  someone's attention, and it refuses a number that is not an integer rather than rounding a
  32-bit `boot_id` through a `double`.
- **A doctest message carries a `std::string`, never a `const char*` variable.** doctest
  stringifies a pointer as a pointer (`filldata<T*>` in `doctest.h`), so a message built from a
  `const char* key` printed an address where the field's name should have been. Found by seeding
  the allocation above and reading what the test said; fixed in a commit of its own.

## New libraries (with the one-line justification)

None. The codec uses `<cstddef>` and `<cstdint>` and nothing else; the tests use the doctest
already vendored (task p0-01) and the JSON reader written here, which is 333 lines of test support
rather than a dependency.

## Not verified here (and why)

**Nothing.** Bytes in, bytes out: the codec touches no pin, no UART and no clock but a fake one,
and every line of it runs on the host under the sanitizers. `docs/bench.md` gains nothing — the
first bench line for the link is task 02's `rak hello`, which is the first thing that needs a
radio on the other end.

Two things are worth knowing when the rig exists, neither of them this task's to check:

- the codec agrees with `linkref.py`, which is the specification as code. It agrees with the
  **radio firmware's** codec only in that both pass the same fixtures; the first time the two
  speak is task 02 on the bench.
- `FrameWriter`'s idle measurement is of the moment a frame was *built*, not of the last bit that
  left the UART. At 115200 baud a 246-byte frame takes 21 ms to clock out, so a frame built 100 ms
  after the last one may follow it on the wire by 80 ms and still be prefixed. That costs one byte
  and never an error (§2: an empty frame is not an error). Task 02 owns the UART and may stamp the
  send instead.
