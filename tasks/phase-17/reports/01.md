# p17-01 — A manifest of six images

The three bounds of `core/image/manifest.h` were sized for a manifest filled to every `use`
`spec/FIRMWARE-MANIFEST.md` §2 names at once — eight images of seven files, 957 tokens — which no
board can have: `swd`, `usb-dfu`, `usb-uf2` and `provision` are the radio's, `ota` and `factory`
are the Walter's. The token table alone was 20 480 bytes of `.bss` in an image whose scarce
resource is static DRAM at boot.

They are now **six images, five files an image and 640 tokens**, and the one `ImageVerdict` the
firmware keeps as a static of `app_main` is **11 608 bytes smaller**: 35 472 bytes of `.bss` before,
23 864 after. The figure task p16-04 named as the one to watch — the room the kept-image scratch has
left in the heap it lands in — went from **644 bytes to 12 252**, which is 4 596 bytes more than the
5 256 pile 16's task 05 said would pay for the PSRAM.

Nothing of what a manifest is, what is read of it or what it is refused with changed.

## Deviations from the spec or the task

- **The specification and the task do not disagree.** §2 names seven `use` values and says nothing
  about how many a board may have, so nothing in `spec/` is contradicted by bounding an image at
  five files: a manifest with six files in one image is well-formed by §2 and is refused here by a
  firmware bound, at check 2, with the bound it broke — which is what §5's check 2 and this
  firmware's `describe()` already said about eight images. `python spec/tools/specsync.py verify
  spec` passes; nothing under `spec/` was touched.
- **`kMaxManifestBytes` (8 192) is the bound that bites first, and it is not this task's.** A
  manifest filled to the new bounds is **10 302 bytes** of canonical JSON, so a release of more than
  about four images of four files is refused by `core/image/receive.h`'s byte bound before the
  parser ever sees it — not at check 2 with the bound it broke. That was already true of eight
  images of seven files (and much more so), and `receive.h`'s comment claimed the opposite: *a
  manifest filled to the parser's bounds (eight images of six files) is about 7 KB of JSON … so 8 KB
  is "anything this firmware could accept"*. The constant is out of scope (`FOLLOWUPS.md` holds it,
  together with the 19 KB the two manifest buffers take), so only the comment was corrected, to say
  which of the two bounds refuses what and to point at that follow-up. **An item was added to
  `tasks/phase-17/FOLLOWUPS.md`**, tagged `[later, found by 01]` and put beside the item about the
  two 8 KB buffers, which is the same constant: today's releases are nowhere near either bound, but a
  six-image release would be refused for its size rather than with the bound it broke. Nothing in
  that file was ticked.
- **`ManifestParser::tokenCount()` is an addition, not a change.** The task says nothing else of a
  manifest changes; this reads out what the last parse took and nothing acts on it in the firmware.
  It costs two bytes of the verdict and makes the central claim of the task — that 640 tokens is
  enough for the releases there are — a measured figure in six tests instead of a sentence in a
  comment. Under *Decisions taken without asking* as well.
- **`docs/update.md` names no bound of the manifest**, so it was not edited; `docs/ARCHITECTURE.md`
  §6 did (*eight images, six files an image, 1024 tokens* — itself wrong about the second) and now
  gives the three new ones and why they are what they are.

## Decisions taken without asking

- **Which six images, and which five files.** The phase README chose the numbers; the reasoning
  beside each constant had to be written. Six is §2's three radio roles (`repeater`, `bridge`,
  `scanner`) in its two bands (868, 433); the Walter's own manifest is one image, and a dual
  adapter's second radio is another *position* for the same six images, not a seventh image. Five is
  the most uses one image can have: `swd`, `usb-dfu`, `usb-uf2`, `provision` and `debug` on the
  radio, `ota`, `factory` and `debug` on the Walter. Both are written down where the constants are,
  so the next task that wants a seventh image reads why there were six.
- **The two new fixtures are generated, not hand-written.** `repeater-release-shape` and
  `repeater-bounds-full` (and `repeater-bounds-plus-file`) are built by
  `host_test/fixtures/gen_manifest_fixtures.py` from the specification's own
  `manifest-repeater-base.json`, validated by `manifestref.validate` and signed with the
  specification's test key, like every other variant there. The generator also emits the two bounds
  it shaped them for (`kMaxImagesHere`, `kMaxFilesPerImageHere`), which the test holds against the
  C++ constants — so a bound changed in one place and not the other fails loudly rather than quietly
  testing nothing.
- **`tokenCount()` rather than a second token counter in the test.** The alternative was a recursive
  counter over the fixture's JSON in the test or in the generator, which would be a second
  implementation of jsmn's counting rule and could agree with itself while disagreeing with the
  parser.
- **A release-note line was written.** The change is not invisible: a unit starts with about twelve
  kilobytes more of its memory free, and a release beyond either bound is refused with the bound it
  broke. `release-notes/unreleased/p17-01-a-manifest-of-six-images.md`, 375 characters,
  `tools/release/test_release_notes.py` green.
- **The stale figures in `docs/ARCHITECTURE.md` §14 were brought up to date** where they are about
  the number this task moves (*the tightest is N bytes*: 356 → the measured 644 on `main` and 12 252
  here) and a paragraph was added on what a bound of the manifest costs in static memory, which is
  deliverable 5. The historical figures of v0.1.2, v0.1.3 and 0.1.4 in that section were left as
  they are; so was the section's mention of a 20 480-byte kept scratch, which is pile 16's drift and
  not this task's to correct.

## Not verified here (and why)

A session cannot flash a board, so the whole of this is the host suite, the heap model and the
linker map. The model is checkable against silicon and has been (report p11-01), and this task
changes nothing about how it is run — but the two things a board would add are:

- **⚠ Nothing.** This task adds no bench line of its own: there is no new behaviour to walk, and the
  memory it frees is only visible as the boot's `heap:` line being higher. `docs/bench.md` was
  therefore not touched. The next release's boot line should be **about 11.6 kB higher** than the
  one before it, and if it is not, this measurement is wrong — that is the one thing a board can
  say about this task, and pile 17's task 02 is the task that needs a board anyway.
- **A real release at either bound has never existed**, here or anywhere: today's biggest is two
  images of four files, and the fixtures of six images of five files are this repository's own. If
  the repeater's release tooling ever writes a fifth image, the byte bound above refuses it before
  these bounds do.
