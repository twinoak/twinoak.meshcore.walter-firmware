# p13-01 — What the unit says about itself

On 13 November a wake request reached the unit's radio, the radio answered *ok*, and the unit did
not check in. `wake` says whether it woke and by what, `agent state` says what wait was owed, `lte`
says how far the uplink got — and all three are behind a USB port on a unit meant to sit on a mast.

This task adds one job type, `twinoak.report`, that returns those lines.

| | |
|---|---|
| **the lines are the console's own** | a section *is* a console command. `Console::writeSection(name, out)` points the console's one way out (`print`/`printf`) at the report's buffer instead of at the port and runs the printer. There is no second rendering of anything, so a line added to a command is a line the report gains with it |
| **the seam** | [`core/console/report_source.h`](../../../components/core/include/core/console/report_source.h) — three methods, implemented by `Console`, held by `agent::FirmwareJobs`. The direction is the opposite of the console's other probes (the agent asks core/ here), so a seam rather than an `#include "console.h"` in `components/agent/` |
| **it changes nothing** | the sections are the read-only commands: `agent obs` without its pull, the *counts* of `rak events` without taking the events out of the queue, the band this wake decided rather than a new reading and a new decision. `radio` asks this unit's own radio over the box link; nothing goes on the air |
| **it fits** | the whole data object is at most **8 000 bytes**. Sections are written in the order asked; one that does not fit whole is cut **at a line end** and marked `cut`; the ones not started are named in `left`; a name this firmware has no section for is in `unknown` |
| **what it cost in RAM** | **nothing that matters**: 32 bytes of `.bss` (rail R22's tightest margin 332 → 300) and 3 056 bytes of flash. The result buffer is the one `twinoak.fw.*` already had — see *Decisions* |

## What it costs

From the code, and from the tests' own `MESSAGE` lines (run by hand in the image):

| | |
|---|---|
| **all eleven sections, a fresh unit** | **6 968 bytes** of `data`. By section: `wakes` 441, `agent` 598, `uplink` 750, `observations` 950, `jobs` 1 036, `journal` 152, `radio` 848, `power` 460, `restarts` 209, `settings` 222, `log` 709 |
| **a full result** | **7 748 bytes**, inside the contract's 8 000 and the library's own `kDataCap` of 8 192 |
| **two of them against one wake's 32 kB** | `kWakePostBytes` is 32 768 (`walter_agent/agent_backend.h`). Two full reports are ~15.5 kB of body with their envelopes — under half the wake's bytes, and the heartbeat and an observation batch still fit |
| **what happens to the second when the budget is spent** | nothing is lost and nothing is posted past the bound. The library's `JobRunner::post` checks `mayPost(len)` against the wake's ledger; a result that would pass it is **kept behind the queue in the order it was made** (`resultsKeptForBudget_`), nothing backs off for it, and the next wake posts it with the timestamps it was made with. `agent jobs` shows it as `pending`, and `agent state`'s `result(s) posted late` counts it |
| **how long it holds a wake open** | the time of the console printers plus, for `radio` only, **three link exchanges** — one `STATUS` for `rak status`, and `rak watch` and the event counts, which ask the radio nothing new. Everything else is RAM and flash reads. It asks for no lease extension and does not raise the wake's bound: it is not an update |
| **a wake claims once, two jobs at most** | `kClaimMax` is 2 and `AgentLoop::wakeJobs` claims once a wake, so a report takes one of the two. That was already a phase-13 follow-up and is unchanged by this task |

## The new lines (deliverable 6)

Four sections did not answer their question, and the answer went **into the console command**, so
that the cable and the report gained it together:

| command | the line |
|---|---|
| `wake` | `the clock: 1794595200, from the cellular network` — or that it is not set in this boot. The question is *did it wake at that time*, and the wake record keeps no time of day: it is eight bytes a wake in RTC memory (`core/cycle/wake_reason.h`) and `Record` is 100 of the 128 a retained slot has. Growing it would reset the wake log, the band's hysteresis, the spurious count and the faults in a row for one wake, as task p10-01's growth did — too much for a timestamp that `journal` already has |
| `journal` | a wake entry now reads `seq <n> at <epoch>`. `cycle::WakePayload` has carried `at_epoch` since p3-05 and nothing printed it; this is where **the last twelve wakes are dated**, and it is what lines a wake up with a wake request a server sent |
| `agent state` | `the clock: <epoch>, from <source>` — or that it is not set in this boot. Every epoch above it (`lastHeartbeatAtEpoch`, a result's timestamps) is that clock's, and on a unit that never attached `lastHeartbeatAtEpoch 0` means *no clock*, not *never* |
| `rak events` | the link's own counters line, the one `status` has printed since p3-03 — mode, retries, timeouts, drops, events — extracted into `Console::printLinkCounts()` and called by both. The `radio` section's question asks for the retries and timeouts, and `rak status` carries the radio's `link_errors` and not this end's |

What was **not** added, and why: how many attentions the radio raised, and how many its hourly
limit refused. §5.7's `STATUS` carries neither and nothing else does, so the firmware says nothing
rather than guessing; the link protocol is the design repository's and there is a follow-up.

## Deviations from the spec or the task

- **An advert's name is not in the secrets test as an advert.** The criterion asks for *an advert
  heard from a stranger with a name*. The bench's path for one needs a simulated RAK with a
  repeater behind it (`sim::SimRak`, `meshBehind`), which the firmware-jobs bench does not build;
  and `agent obs` prints **no name by construction** — the printer has no field for one, which is
  held by `test_identity_console.cpp`'s *never an advert's name*, and the report is that same
  printer. What the test does instead is the other half of S-12: a line the radio sent **as text**
  (a scanner's NDJSON with a stranger's words in it), printed by `rak text`, which the ring is
  held shut for — so the `log` section cannot carry it either. Both halves of S-12 are covered;
  the one that is covered by construction is covered somewhere else.
- **`agent jobs` cannot say how long a job took.** The section's question asks for it. The copied
  library's `JobRunner::Record` keeps the epoch and the transaction count and no start or finish,
  and `components/agent-core/` is a copy of a private upstream that this repository does not edit
  (`docs/upstream.md`). Follow-up left; the type, the outcome, *when* it ran and whether a result
  still waits are all answered today.
- **The fixtures are not where the other contract fixtures are.** The task says *where the copied
  ones are*. `host_test/agent-core/tests/fixtures/contracts/` is held byte for byte to its
  `MANIFEST.txt` before anything is built, so a shape meshmaster.dk does not have yet cannot be
  put there without breaking the copy. They are in
  [`host_test/fixtures/contracts-ahead/`](../../../host_test/fixtures/contracts-ahead/) with a
  README that says exactly what they are and what must happen to them, and a follow-up to compare
  them byte for byte with the server's own and move them across once task 216 is deployed.
- **`sayRadio`'s line became two.** `agent: <why>: only this unit's own job types are claimed
  (<the types>); a mesh job this end cannot tell is its own is not claimed` is 246 characters with
  five types in it, and the library's line buffer is 239 — it was cut off exactly where it said
  why, which is the thing that line's own tests guard. The reason is one line now and the types
  are the next, so a sixth type costs the list and nothing else.

## Decisions taken without asking

- **The result buffer is the one that was already there.** The contract's 8 000 bytes do not fit
  `FirmwareJobs`'s 4 kB `data_`, and 4 kB more of `.bss` would have moved the agent's 20 kB
  scratch into another heap and broken rail R22 — which is exactly how v0.1.3 came not to start
  (phase 11's task 01; main's tightest margin today is 332 bytes). `data_` and `body_` are now one
  array of 8 704 bytes with two named halves: a result's `data` in the first 4 096 and an owed
  result's envelope in the rest, as before — and a report, **which is never owed**, takes the whole
  of it. `postOwedResult` runs after the heartbeat and outside any job; a report is written, posted
  and done inside the one call that runs it. The header says so where the constant is, and the
  measured cost of the whole task is 32 bytes of `.bss`.
- **The report's own lines are not kept in the ring `dump` prints.** A section did not print to the
  port, and a ring filled with the last report is a `log` section that says nothing about the port.
  `agentLine()` — the copied library's own log lines — goes straight to the port and the ring for
  the same reason, whatever is being written.
- **The document is assembled by hand; only a section's text goes through `mm::JsonWriter`.** A
  report is cut at a line end and a forward-only writer cannot be rewound. The punctuation is this
  firmware's own and the section names are held to `a-z` by the payload reader, so nothing in the
  document needs escaping; a section's lines are **a stranger's bytes** and go through the one JSON
  writer this firmware sends anything with, escaped **in place** — the writer is given the room
  that is left, writes the line as a JSON string into it, and the two quotes are taken off. No
  second buffer.
- **`pump()` is held to polling the radio while a section is written.** `rak status` waits, and the
  library's waits call the console's pump; a transfer or a trial stepped from inside a section
  would print its lines into the section's buffer and never into the port. The flag is saved and
  put back rather than taken with a `LineInProgress`, because a report can be asked for by a wake
  that a typed `agent wake` started.
- **A name that is not 1 to 16 characters of `a-z` is answered in neither list.** The contract says
  names are `a-z`; echoing anything else back would be the one place in the document that needed
  escaping. It is counted and named in the job's log line instead.
- **Both `left` and `unknown` are always written, empty or not.** The contract's block shows both;
  a server that always finds the two arrays is simpler than one that must test for them.
- **A payload with no `sections` array at all is `failed`**, as a `twinoak.fw.*` payload this
  firmware cannot read is. The outcome is `ok` whenever the job *ran*, which is every other case —
  including one where nothing fitted.

## Not verified here (and why)

No session opens a port. Everything below needs the rig, and the same lines are in
[`docs/bench.md`](../../../docs/bench.md) §21 in the order the rig is brought up.

- **A report asked for from meshmaster.dk.** It needs meshmaster.dk's task 216 deployed. Queue a
  `twinoak.report` for `wakes, agent, uplink, jobs`, then `agent wake` on the cable: the job page
  shows the four sections, and each is what the same four commands print on the port in that same
  wake. **The point of the whole task** is that the two are the same bytes, and that can only be
  seen with a unit and a server.
- **The 13 November question itself.** With a unit on a mast and a wake request sent: ask for
  `wakes` and `agent` afterwards and read whether the unit woke at that time, by what, and what
  wait it still owed. That is the first open follow-up of this phase, and this report is what it
  is to be decided from.
- **A full report over LTE.** A 7–8 kB result is a bigger body than this unit has posted; watch
  the wake's byte ledger (`agent jobs`' `buffer` line and `agent state`'s `result(s) posted
  late`), and that a second report in the same hour is kept and posted at the next wake rather
  than dropped.
- **The `radio` section against a silent radio.** With the jumper pulled: the section must say so
  in `rak status`'s refusal line and still come back, rather than holding the wake open.
- **The four new console lines on the port**: `wake`'s clock line, `journal`'s dated wake entry,
  `agent state`'s clock line, and `rak events`' link counters — all four seen in the simulator,
  none on a board.
