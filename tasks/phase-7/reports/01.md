## Deviations from the spec or the task

- **The release workflow could not have published anything before this task, and the task's own
  deliverable 3 would have been the first to find out.** `release.yml`'s build job runs
  `tools/verify.ps1 -Version X.Y.Z+<sha7>`; `verify.sh`'s `release` step then built the files at
  that version and signed them with the specification's **test key**, which
  `sign_manifest.py` refuses for a release-shaped version — a rail, deliberately, since a public
  key's signature proves nothing. The step would have returned 1, the build job would have gone
  red, and the publish job would never have run. Nothing had caught it because every green run
  until now was at `0.0.0-dev` (CI) or `0.0.0-dryrun+<sha7>` (the workflow's own dry run), and the
  one documented command that is release-shaped — `.\tools\verify.ps1 -Version 0.3.1+1a2b3c4`, in
  `README.md` and `docs/release.md` — had apparently never been run. The fix is in `verify.sh`: at
  a release's own version the step makes the files and runs **every** refusal over them (the
  factory image's reach, both descriptors, the manifest, the hand-written notes, the version
  agreement) and then *asserts that the test key is refused*, saying in its log that the signature
  and the `verify_release.py` gate are the publish job's, with the secret, immediately before
  `gh release create`. Nothing is skipped quietly: a `manifest.json.sig` that is not there is said
  to be not there. `docs/release.md`'s *Rehearsing* and the workflow's comment say the same.
- **The repeater firmware has no release and no `docs/flashing.md`.** The task's deliverable 1
  points at *the repeater firmware's own guide (its `docs/flashing.md`)* and deliverable 2 at
  *which repeater-firmware release it goes with*; read at `main`, that repository has neither —
  `docs/` holds `ARCHITECTURE.md`, `bench.md`, `link.md`, `noisescope.md`, `provisioning.md`,
  `release.md` and `upstream.md`, and `gh release list` and its tag list are both empty (its pile
  3.7 is what makes the first one). So: the guide names the two cable paths that repository does
  document — the bootloader's drive with `firmware.uf2` after a double-tap, or
  `adafruit-nrfutil dfu serial -pkg firmware.zip` (its `README.md`, *Building it*, and its
  `docs/bench.md` §1) — and says its own guide is the page to follow once it exists; and
  `release-notes/v0.1.0.md` says plainly that there is no release of it yet and that this one will
  name the pairing when there is. No link is made to a file that is not there.
- **This report is finished in two commits, and the second is a second pull request.** Two
  criteria can only be shown after the tag, and the tag goes on a `main` that already carries this
  report (`RUNBOOK.md` §4: merge, then the release). The second pull request touches
  `tasks/phase-7/reports/01.md` and nothing else — the same deviation, for the same reason, as
  `p1.8-35` in the exit-node firmware.
- **Four documents and three code comments were corrected that the task did not name.** Deliverable
  4 names README, `keys/README.md` and `keys/release-keys.txt`'s comment block. The same claim was

## Decisions taken without asking

- **The notes file is required by `build_release.py`, not by the workflow.** The task says *have
  the workflow put it in front of `NOTES.md`*; the workflow does, by running the tool that writes
  `NOTES.md`. Putting the rule there rather than in a YAML step means one definition, a test for
  it, and the same refusal whether a tag, a dry run or a laptop asks — and the local rehearsal at a
  release's own version now exercises it before CI ever sees the tag.
- **Required for a release-shaped version only** (`X.Y.Z+<sha7>`), by the same regular expression
  `sign_manifest.py` uses to decide what the test key may sign. A dry run (`0.0.0-dryrun+<sha7>`)
  and a plain build (`0.0.0-dev`) need no file and get the generated part alone, which already says
  in its own first paragraph that nothing is published.
- **A `---` rule between the two parts**, and no heading above either: GitHub puts *TwinOak Walter
  firmware v0.1.0* above the body already, and a second title would be the third place the version
  is written.
- **`--latest` is passed explicitly.** The exit-node firmware left it to GitHub's ordering
  (`p1.8-35`); here the rule itself — *Latest, not a pre-release, while Thomas is his firmware's
  only user* — is said out loud in the workflow, where a later release will inherit it, rather than
  depending on version ordering staying what it is today.
- **`release-notes/README.md` was written**, although the task only named `vX.Y.Z.md`: a directory
  whose contents are refused when missing needs to say what belongs in one, and the file is what
  stops the next release's notes from becoming a hand-written copy of the generated table.
- **The bench lines went into `docs/bench.md` §1 and §18**, where the rig's own order puts them,
  rather than into a new section of their own (§1 is the Walter alone on USB, which is where a
  released image is first flashed; §18 is where the server shows a version).
- **The guide names the public key's hex in the bench item**, not only the key id: `sha256sum -c`
  and `manifestref.py verify` are what a person can run on a laptop with nothing of this repository
  checked out, and the public half is public by definition (`keys/README.md`).
